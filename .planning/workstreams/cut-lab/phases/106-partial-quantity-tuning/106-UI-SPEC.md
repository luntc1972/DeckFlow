# Phase 106 — UI Design Contract: Partial-Quantity Tuning & Add Basics

> Visual and interaction contract for the inline copy-tuner in the Cut Lab Decide workspace. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. **Retroactive spec**: 106-DESIGN.md and 106-01…106-05-PLAN.md are
> already committed and Codex-converged. This document does not reopen any locked decision (inline placement, no
> new step tab, +/- steppers, add-basic control, progressive enhancement, `WorkingListRows`/`AddableBasics` field
> names, `CutLabAdjustApiResponse { CutLabStateJson, CardsRemaining }` contract). It pins the remaining visual,
> state, copy, a11y, and responsive details the plans left to "reuse existing cutlab visual language" so 106-04's
> executor has one unambiguous source, styled consistently with Phases 101–105.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — no shadcn/component library. Server-rendered Razor + hand-authored CSS custom-property theme system. |
| Preset | not applicable |
| Component library | none (no Radix/Base UI). Native HTML controls (`<button>`, `<select>`, `<form>`, `<table>`) with token-driven custom chrome. |
| Icon library | none. Text glyphs only (`▲`/`▼` for deltas, `−`/`+` for steppers), always paired with an `aria-label`. |
| Font | inherited site-wide stack (no phase-specific font). |

This phase adds **zero new CSS custom properties**. Every visual below reuses tokens already defined in every
guild theme's `:root` (`--line`, `--ink`, `--muted`, `--panel`, `--panel-soft-bg`, `--accent`, `--accent-strong`,
`--on-accent`, `--focus`). See **Tokens** below for the full reuse map and why no new token is needed.

## Color

DeckFlow is a multi-theme (per-guild CSS fork) app, not a single 60/30/10 palette — dominant/secondary/accent
below describe the **role**, not one hex, because each of the ~19 guild themes supplies its own values for the
same token names.

| Role | Token | Usage |
|------|-------|-------|
| Dominant (60%) | `--panel` / `--bg` | Page background, table background |
| Secondary (30%) | `--panel-soft-bg` (falls back to `--panel`) | Stepper button fill, quantity-input analog fill (matches `input[data-cut-lab-floor]`) |
| Accent (10%) | `--accent` / `--accent-strong` | **Reserved for:** the "Add basic land" submit button (`.run-button`, matches "Recalculate analysis"); the added-basic row's left rail (matches `.cutlab-floor-badge--adjusted`'s accent rail); focus rings (`--focus, var(--accent)`); the existing Export/Decide step-tab active state (unchanged, inherited chrome) |
| Destructive | `--danger` | **Not used by this phase.** Cutting a copy via `−` is a routine, reversible tuning action, not a destructive one (no confirmation, no red framing) — consistent with the existing Cut Lab principle that the tool never frames a card/action as objectively bad. `−` uses the same neutral chrome as `+`. |

Accent is explicitly **not** used on the `−`/`+` stepper buttons themselves (neutral bordered chrome, matching

## Component Contract

### 1. Stepper control (per tunable working-list row)

**Data source (locked, from 106-04-PLAN):** rows come from `Model.WorkingListRows`
(`CutLabWorkingList.Derive(pool, decisions, QuantityAdjustments)` projection) — **never** `Model.Pool`. The Razor
`@foreach` iterates the full `WorkingListRows` collection but must **skip rendering a `<tr>` for any row where
`IsLegalMultiple` is `false`** (e.g. `@if (!row.IsLegalMultiple) { continue; }` at the top of the loop body). The
rendered table therefore contains **only** the basics and any-number cards currently in the working list — never
the ~90+ ordinary singleton rows. This is what keeps the section a compact "tuning" tool rather than a second
100-row pool table.

**Markup shape** (mirrors the existing `conflicts-table` / `data-prompt-cedh-reference-table` pattern used by the
pool table, floor table, and compare table — so it inherits the existing mobile card-stack transform for free):

```html
<div class="history-timeline__wrap">
  <table class="conflicts-table" data-prompt-cedh-reference-table role="table">
    <thead>
      <tr><th scope="col">Card</th><th scope="col">Role</th><th scope="col">Quantity</th></tr>
    </thead>
    <tbody>
      <!-- one <tr> per WorkingListRows entry where IsLegalMultiple -->
      <tr data-cut-lab-tuner-row="@row.Name" data-cut-lab-quantity="@row.CurrentQuantity"
          data-cut-lab-legal-max="@row.LegalMax">
        <td data-label="Card">
          <strong>@row.Name</strong>
          @if (row.IsAddedBasic) { <span class="kb-chip cutlab-tuner-badge--added">Added</span> }
        </td>
        <td data-label="Role">@row.RoleLabel</td>
        <td data-label="Quantity">
          <div class="cutlab-stepper">
            <!-- each button is its OWN <form>, mirroring RenderDecisionForm / the accept-reject-defer pattern -->
            <form method="post" action="~/cut-lab/adjust" data-cut-lab-adjust-form>
              @Html.AntiForgeryToken()
              <input type="hidden" name="CutLabStateJson" value="@Model.CutLabStateJson" />
              <input type="hidden" name="CardName" value="@row.Name" />
              <input type="hidden" name="Delta" value="-1" />
              <input type="hidden" name="IsAddedBasic" value="false" />
              <button type="submit" class="cutlab-stepper-btn" aria-label="Remove one @row.Name"
                      data-cut-lab-adjust data-cut-lab-card="@row.Name" data-cut-lab-delta="-1"
                      disabled="@(row.CurrentQuantity <= 0 ? "disabled" : null)"
                      aria-disabled="@(row.CurrentQuantity <= 0 ? "true" : "false")">−</button>
            </form>
            <span class="cutlab-stepper__count tabular" data-cut-lab-quantity-value>@row.CurrentQuantity</span>
            <form method="post" action="~/cut-lab/adjust" data-cut-lab-adjust-form>
              @Html.AntiForgeryToken()
              <input type="hidden" name="CutLabStateJson" value="@Model.CutLabStateJson" />
              <input type="hidden" name="CardName" value="@row.Name" />
              <input type="hidden" name="Delta" value="1" />
              <input type="hidden" name="IsAddedBasic" value="false" />
              <button type="submit" class="cutlab-stepper-btn" aria-label="Add one @row.Name"
                      data-cut-lab-adjust data-cut-lab-card="@row.Name" data-cut-lab-delta="1"
                      disabled="@(row.CurrentQuantity >= row.LegalMax ? "disabled" : null)"
                      aria-disabled="@(row.CurrentQuantity >= row.LegalMax ? "true" : "false")">+</button>
            </form>
          </div>
        </td>
      </tr>
    </tbody>
  </table>
</div>
```

**Sizing / states (CSS, `site-common.css` only — never `site.css`):**

```css
.cutlab-stepper {
  display: inline-flex;
  align-items: center;
  gap: 0.5rem;               /* sm */
  flex-wrap: nowrap;         /* never wrap on narrow widths — 2 buttons + count always fits the 1fr mobile column */
}

.cutlab-stepper form { display: contents; }  /* matches .cutlab-proposal__actions form pattern */

.cutlab-stepper-btn {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  min-width: 44px;
  min-height: 44px;
  border: 1px solid var(--line);
  border-radius: 10px;
  background: var(--panel-soft-bg, var(--panel));
  color: var(--ink, inherit);
  font: inherit;
  font-weight: 600;
  line-height: 1;
  cursor: pointer;
}

.cutlab-stepper-btn:hover:not(:disabled) {
  border-color: var(--accent-strong, var(--accent));
}

.cutlab-stepper-btn:disabled {
  cursor: not-allowed;
  opacity: 0.45;             /* distinct from the .cutlab-decision-btn:disabled busy state (opacity .72, cursor:progress) */
}

.cutlab-stepper__count {
  min-width: 1.75rem;
  text-align: center;
  font-weight: 600;
}

.cutlab-tuner-badge--added {
  margin-left: 0.5rem;
}

tr:has(> td .cutlab-tuner-badge--added) {
  border-left: 3px solid var(--accent);   /* reuses the exact .cutlab-floor-badge--adjusted accent-rail idiom */
}
```

**States:**
- **Default (enabled):** neutral bordered chrome, `--panel-soft-bg` fill, `--ink` glyph — identical visual weight
  to the reject/defer decision buttons, deliberately quieter than the green Accept button.
- **Hover:** border brightens to `--accent-strong` (matches `.run-button:hover`/`.copy-button:hover` idiom); no
  background change (steppers are clicked repeatedly — a background flash on every hover would be noisy).
- **Focus-visible:** inherits the universal `outline: 2px solid var(--focus, var(--accent)); outline-offset: 2px;`
  rule already in `site-common.css` (no new rule needed).
- **Active/in-flight (server round-trip pending):** apply the exact same busy-state technique as
  `setSubmitterBusyState` (swap button content for the existing `.cutlab-busy-spinner` + `Recalculating…` text,
  disable all four adjust-form buttons on the row while in flight) — reuse, do not invent a second spinner style.
- **Disabled — legal bound (`−` at 0, `+` at `LegalMax`):** native `disabled` attribute **and** `aria-disabled="true"`
  on the button (belt-and-suspenders since some AT ignores native `disabled` semantics inconsistently across
  browsers), `opacity: 0.45`, `cursor: not-allowed`. This is a **persistent, non-error** state — do not use
  `--danger`/red.
- **Server is authoritative:** the server (`CutLabAdjustmentApplier`, 106-03) independently re-validates
  `CutLabLegality.IsLegalMultiple`/`LegalMax` on every POST regardless of the client-rendered `disabled` attribute
  — the client-side disable is a UX convenience, never the security boundary (matches the CLAUDE.md/threat-model
  posture already locked in 106-03).

### 2. Add-basic control

Placed as its own `.toolbar` row directly below the tuner table (matches the "Recalculate analysis" button
placement pattern under the Role-floors table):

```html
@if (Model.AddableBasics.Count > 0)
{
  <form method="post" action="~/cut-lab/adjust" data-cut-lab-adjust-form class="toolbar cutlab-tuner__add-basic">
    @Html.AntiForgeryToken()
    <input type="hidden" name="CutLabStateJson" value="@Model.CutLabStateJson" />
    <input type="hidden" name="Delta" value="1" />
    <input type="hidden" name="IsAddedBasic" value="true" />
    <label for="cut-lab-add-basic-select">Add a basic land</label>
    <select id="cut-lab-add-basic-select" name="CardName" data-df-select data-cut-lab-add-basic-select required>
      <option value="" selected disabled>Choose a basic…</option>
      @foreach (var basic in Model.AddableBasics)
      {
        <option value="@basic">@basic</option>
      }
    </select>
    <button type="submit" class="run-button" data-cut-lab-add-basic>Add basic land</button>
  </form>
}
else
{
  <p class="cutlab-floor-source-default">All basic land types are already in your working list. Use the steppers above to add more copies.</p>
}
```

- `Model.AddableBasics` order is **canonical, locked by 106-04-PLAN**: Plains, Island, Swamp, Mountain, Forest,
  then the five Snow-Covered variants, then Wastes — filtered to exclude any basic already present in
  `WorkingListRows`. Do not re-sort.
- The submit button reuses `.run-button` (accent-filled, matches "Recalculate analysis") — this is the one accent
  usage on this control, per the Color contract.
- `required` + a disabled placeholder option on the `<select>` prevents a same-origin no-JS submit with an empty
  `CardName` (defense-in-depth; the server independently rejects a blank/invalid name per 106-03).

### 3. Live count + validation feedback

**JS success path (extends 106-04-PLAN Task 3's committed handler with the minimal same-scope client update
needed for the control to be legible — no new endpoint field, no contradiction of the committed
`CutLabAdjustApiResponse { CutLabStateJson, CardsRemaining }` shape):**

1. POST to `/api/cut-lab/adjust` (locked).
2. On `200`: write `CutLabStateJson` to every hidden state input (locked); update
   `[data-cut-lab-sticky-remaining]` to `` `${cardsRemaining} to cut` `` (locked); call the Export-tab enablement
   updater (locked).
3. **Additive, same handler:** for a stepper click on an **existing** row, optimistically update that row's own
   `[data-cut-lab-quantity-value]` text to `currentQuantity + delta` (both values are already known client-side
   — the posted `delta` and the row's prior displayed count) and re-evaluate that row's own two button `disabled`/
   `aria-disabled` states against `data-cut-lab-legal-max` and the new quantity. This uses only data already on
   the page; it requires no new server field.
4. **Add-basic path (new row, no existing `[data-cut-lab-tuner-row]` to patch):** on success, clone the tuner-row
   template client-side (same technique already used in `cut-lab.ts` for package-row insertion —
   `data-cut-lab-package-id` templating) to insert a new row for the added basic at quantity 1, then remove that
   basic from the add-basic `<select>` options. If this insertion is judged out of scope for the Task-3 time-box,
   the **documented fallback** is acceptable: the add-basic form submits as a normal (non-intercepted) POST for
   this one action, causing a full-page re-render exactly like the no-JS path — do not silently leave the new row
   invisible with no feedback. Pick one of these two behaviors explicitly; do not ship neither.
5. On non-`200`: reuse `readErrorMessage`/`renderDecisionError` verbatim (no new error-rendering path).

**No-JS path (locked, unchanged):** `POST /cut-lab/adjust` full-page re-render — this already correctly reflects
every row, the sticky bar, and the Export tab because it re-runs `CutLabViewModel.From` from scratch. No
Phase-106-specific no-JS work is needed beyond what 106-04-PLAN Task 2 already specifies.

**Known, accepted limitation (document, do not silently ship as a mystery):** `CardsRemaining` in the adjust
response is `Math.Max(currentCount − 100, 0)` (the same clamp `CutLabCutRoundEngine.BuildQueue` has always used) —
it **floors at 0** and therefore cannot distinguish "exactly 100" from "under 100" via the JS response alone.
This is an existing, already-committed 106-01/106-03 contract and is **not reopened** by this spec. Practical
impact: after a JS-only adjust that drives the true count under 100, the sticky bar (which hides once
`cardsRemaining` reaches 0) will disappear as if the target were met. This is safe because the actual export gate
is independently re-validated server-side by `CutLabExportComposer` (`countOk = countTotal == 100`, Phase 105,
unchanged) — a user cannot copy an off-target export even if the tab briefly looks enabled. Log this exact
wording as a Phase 107 backlog candidate: *"Adjust endpoint's CardsRemaining floors at 0 — cannot distinguish
exactly-100 from under-100 in the JS-only path; low severity, server export gate is unaffected."* Do not attempt
to fix the endpoint contract inside 106-04 — that would reopen a locked 106-03 decision.

### 4. Legality reflection

- **Server-side is authoritative, always.** `CutLabAdjustmentApplier.Apply` re-checks `CutLabLegality
  .IsLegalMultiple`/`LegalMax` and the `CutLabBasicLands` whitelist on every POST regardless of what the client
  rendered or sent (106-03, locked). The UI must never imply the client's `disabled` attribute is the enforcement
  mechanism — it is a legibility aid only.
- **Legal-multiple rows** (5 basics + Snow-Covered variants + Wastes + the 9 any-number cards: Persistent
  Petitioners, Dragon's Approach, Relentless Rats, Rat Colony, Shadowborn Apostle, Slime Against Humanity, Templar
  Knights, Nazgûl, Seven Dwarves): steppers render, `+` disabled only at `LegalMax`.
- **Singleton rows:** never appear in the tuner table at all (filtered out per Component 1 above) — there is no
  "disabled stepper" state for a singleton to avoid implying quantity editing is possible-but-blocked; it's simply
  not offered.
- **Added-basic vs. ordinary legal-multiple row:** visually identical except the `Added` `kb-chip` badge + accent
  left-rail (Component 1) — both get the same stepper behavior once materialized; there is no second-class
  treatment after creation.
- **Count-gate correctness fix (required, in-scope for 106-04 Task 2, additive-only — does not touch
  `CutLabViewModel` or any 106-01/103 contract):** the `WorkflowStepTab(4, "Export", …)` `IsEnabled` condition at
  `CutLab.cshtml:22` currently reads `cardsRemainingToTarget == 0`. Because 106 introduces the ability to tune
  **under** 100 (impossible before 106, since the Option-A engine only ever proposed cuts that kept the count
  ≥ 100), this condition must change to `currentCount == 100` (the `currentCount` local var, `Model.CurrentCount`,
  already exists at line 11 and is the true derived-list total) so the Export tab does not enable prematurely
  when the working list has been tuned below target. This is a one-line, additive, non-contradicting fix to a
  Razor-only file already in 106-04's `files_modified` list.
- **New proposal-panel branch (required, additive-only, Razor-only):** insert an `else if (currentCount < 100)`
  branch **before** the existing `else if (Model.Proposal.IsAtTarget)` check in the `Model.Proposal.HasProposal`
  chain (lines 971–984), using the copy from the Copywriting Contract ("You're under 100 cards" / "Add copies or
  a basic land…"). `Model.Proposal.IsAtTarget`/`IsNothingToCut` are computed from the same clamped round-plan
  value as `cardsRemainingToTarget`, so without this branch a user who over-tunes below 100 would incorrectly see
  "You're at 100 cards" or "your working list is already at 100 cards." Ordering this branch first resolves the
  ambiguity without touching the `IsAtTarget`/`IsNothingToCut` view-model booleans themselves.

## Accessibility Contract

- **`aria-label` on every stepper button**, not just visual glyph: `Remove one {CardName}` / `Add one {CardName}`
  — the `−`/`+` glyphs alone are not sufficient labels (matches the existing pattern where every
  `RenderDecisionForm` button carries an explicit `ariaLabel` parameter).
- **`aria-disabled="true"` alongside the native `disabled` attribute** on legal-bound buttons (belt-and-suspenders
  for AT that surfaces one but not the other).
- **`aria-live="polite"` on `[data-cut-lab-sticky-remaining]`.** This element is not currently marked as a live
  region even though the Decide-tab decision flow already patches it via JS; Phase 106 adds a second write path
  (adjust) to the same element, making this the first phase where the region updates from two different
  interaction types. Add `aria-live="polite" aria-atomic="true"` to the sticky-bar count span so screen-reader
  users hear the updated remaining count after either a decide or an adjust action, without re-announcing the
  whole sticky bar.
- **Keyboard operability:** every stepper button and the add-basic submit button are native `<button
  type="submit">` inside a `<form>` — full keyboard operability (Tab, Enter/Space) is free; no custom key
  handling is required or should be added.
- **Focus management after a JS-intercepted submit:** per the existing `setDecisionButtonsBusy`/restore pattern,
  focus must remain on the clicked stepper button after its request completes (do not move focus away) so a
  keyboard user can immediately click it again to continue tuning — do not steal focus to the sticky bar or any
  patched region.
- **The add-basic `<select>` has a real, visible, associated `<label for>`** (`Add a basic land`), not a
  placeholder-only or `aria-label`-only pattern, matching form-labeling conventions used elsewhere in the page
  (`Turn target` goal inputs, floor inputs use header-cell association via the table's `<th>`).
- **Color is never the only signal.** The legal-bound disabled state is communicated via `disabled` +
  `aria-disabled` + reduced opacity + `cursor: not-allowed`, not via a color change alone. The "Added" badge is
  communicated via visible text (`kb-chip` "Added"), with the accent rail as a secondary, non-load-bearing visual
  reinforcement.

## Responsive Contract

- **Table shell:** the tuner table reuses `class="conflicts-table" data-prompt-cedh-reference-table role="table"`
  — this is the *exact* markup convention already driving the app's existing mobile card-stack transform at
  `max-width: 600px` (`site-common.css:1158-1253`): headers become visually hidden, each `<tr>` becomes a
  bordered card, and every `<td>` not special-cased (`Select`/`#`/`Player`) renders as a full-width `{label}:
  {value}` row via `td::before { content: attr(data-label); }`. **No new mobile CSS is required for the table
  shell** — only for the stepper-group internals below, because the generic transform doesn't know how to lay out
  a compound `−`/count/`+` cluster inside its value column.
- **Stepper group at mobile widths:** `.cutlab-stepper` keeps `flex-wrap: nowrap` intentionally — two 44×44px
  buttons plus a ~28px count (≈120px total with gaps) always fits inside the mobile card-stack's value column
  (`1fr` of a `6.5rem 1fr` grid, i.e. ~calc(100vw − 6.5rem − card padding), comfortably >120px down to a 320px
  viewport). Do not let it wrap to two lines — a wrapped stepper (count on its own line, buttons split) is the
  same defect class as the tracked "pool-row Package-assignment label truncation" mobile bug in the Phase 107
  backlog; this phase must not add a new instance of it.
- **Tap targets:** both stepper buttons and the add-basic submit button stay at the established `min-height:
  44px` (and `min-width: 44px` for the compact stepper buttons specifically, since they are square glyph buttons,
  not full-width text buttons) at every viewport — no mobile-specific shrink.
- **Add-basic control at mobile widths:** the `.toolbar` class already stacks its children `flex-direction:
