# Phase 999.3: Packet Download Session Cache - Context

**Gathered:** 2026-05-20
**Status:** Ready for planning
**Mode:** interactive `discuss` (4 gray areas selected, all answered)

<domain>
## Phase Boundary

Eliminate full Scryfall pipeline replay on packet download. Today the three workflow services each expose a preview+download endpoint pair where both endpoints call `BuildAsync(request, ...)` from scratch — a large Commander deck pays the multi-minute Scryfall round-trip cost twice. Phase 999.3 adds an in-memory result cache keyed off the BuildAsync-relevant input fields so the download endpoint reuses the artifact built during preview when the same inputs are resubmitted.

**Affected call sites (today's "build twice" defect):**

- `DeckController.cs:465` — `_deckAnalysisPacketService.BuildAsync` (preview `POST /deck-analysis`)
- `DeckController.cs:512` — `_deckAnalysisPacketService.BuildAsync` (download `POST /deck-analysis/download`) — **no short-circuit today**
- `DeckController.cs:584` — `_deckAnalysisPacketService.BuildAsync` (upload `POST /deck-analysis/upload` zip import)
- `DeckController.cs:643` — `_deckComparisonService.BuildAsync` (preview `POST /deck-comparison`)
- `DeckController.cs:727` — `_deckComparisonService.BuildAsync` (download `POST /deck-comparison/download`) — short-circuits today when `ComparisonResponseJson` set AND both deck sources empty (lines 705-725)
- `DeckController.cs:894` — `_metaGapService.BuildAsync` (preview `POST /cedh-meta-gap`)
- `DeckController.cs:971` — `_metaGapService.BuildAsync` (download `POST /cedh-meta-gap/download`) — short-circuits today when `MetaGapResponseJson` set AND `DeckSource` empty (lines 956-969)

**What this phase does:**

1. Introduce a `PacketSessionCache` (or per-service equivalent) that stores `Task<DeckAnalysisPacketResult>` / `Task<DeckComparisonResult>` / `Task<MetaGapResult>` keyed by a SHA-256 hex hash of the BuildAsync-relevant input fields. Cache TTL = 5 minutes absolute. Eviction governed by `MemoryCacheEntryOptions.Size` capped at ~10 MB.
2. Compute the cache key as `SHA256( System.Text.Json.Serialize( { commander, normalizedDeckSource, includeCardVersions, includeSideboardInAnalysis, includeMaybeboardInAnalysis, targetAiPlatformKey, selectedQuestionIds[] }, deterministicOptions ) )`. DeckSource normalization runs URL→canonical-text resolution (reusing existing importer cache) so URL-mode and paste-mode of the same deck collapse to one key. Fields excluded from the key: `WorkflowStep`, `*ResponseJson`, parsed-response objects (`AnalysisResponse`, `SetUpgradeResponse`, `ComparisonResponse`, `MetaGapResponse`), `ImportWarning`. Per-service field bags differ (deck-comparison has DeckA + DeckB; cedh-meta-gap has tournament filters); each service supplies its own keyed input bag.
3. On preview endpoint (and `/deck-analysis/upload`): run BuildAsync, compute the key, write the result into the cache, return as today.
4. On download endpoint: order is (1) existing response-json-only short-circuit for deck-comparison and cedh-meta-gap (no Scryfall pipeline); (2) compute key, `TryGetValue` cache; (3) cache hit → build zip from cached result without re-running BuildAsync; (4) cache miss → fall through to today's full `BuildAsync` call. Cache is pure optimization, never a correctness contract.
5. Log every cache lookup with `_logger.LogInformation("Packet cache {Outcome} for {KeyPrefix} ({SizeBytes} bytes)", outcome, key.Substring(0,8), sizeEstimate)` so the hit ratio is observable via `grep 'Packet cache hit' /data/logs/web-*.log`.
6. Test gate matches Phase 999.1/999.2: manual UAT measuring preview→download click timing on a large Commander deck (expect <2s download click vs today's 2+ min), `dotnet.exe build DeckFlow.sln -c Release` exits 0 with 0 warnings, and grep gate confirming `TryGetValue` + `Set` symmetry in all three services.

**What this phase does NOT do:**

- Touch the BuildAsync pipeline itself or the Scryfall service layer — speed comes purely from skipping the redundant call.
- Replace or remove the existing response-json-only short-circuit on deck-comparison/cedh-meta-gap downloads (D-08 precedence). Phase 999.3 layers cache BETWEEN that short-circuit and BuildAsync.
- Add a persistent (disk/Redis) cache. In-memory only. Process restart = cold cache. Acceptable per D-10.
- Add per-IP or per-session salting to the key (D-04 — global scope).
- Add stampede protection (per-key SemaphoreSlim, Lazy<Task<T>> singleflight) — D-11 accepts duplicate work, matches existing cache patterns (`CardLookupCache`, `CommanderSpellbookService`, etc., none have stampede locks).
- Add a "session expired, regenerate preview first" error UX on cache miss — D-10 falls through silently to BuildAsync; cache miss is invisible to user except for the wait time they would have had without 999.3.
- Add a `DECKFLOW_PACKET_CACHE_*` env-var feature flag. CLAUDE.md prefers structural fixes over flags. TTL + SizeLimit constants tunable in code if needed.
- Add automated xUnit tests asserting BuildAsync-skip behavior — VSTest unreliable in WSL per CLAUDE.md. Manual UAT + grep gate is the empirical gate. (Test surface for the cache wrapper alone — pure value-object key normalization — is a separate decision left to the planner if it lands risk-free.)
- Migrate the existing limitless shared `IMemoryCache` singleton to use `SizeLimit` — too broad a blast radius. Packet cache uses a DEDICATED `MemoryCache` instance with its own SizeLimit (D-06).
- Address the Phase 999.4 truncated-JSON UX problem — separate phase, separate scope.
- Touch the edhtop16 filter-defaults backlog item — that was the OLD 999.3 (now an unnumbered backlog entry after the collision was resolved 2026-05-20).

<decisions>
## Implementation Decisions

### Cache key composition

- **D-01:** **Hash only Scryfall-pipeline-relevant input fields.** Keyed fields: `commander`, `normalizedDeckSource`, `includeCardVersions`, `includeSideboardInAnalysis`, `includeMaybeboardInAnalysis`, `targetAiPlatformKey`, `selectedQuestionIds[]` (deck-analysis); analogous per-service bags for deck-comparison (DeckA + DeckB versions of the above) and cedh-meta-gap (commander + filter window + minEventSize + maxStanding). Excluded: `WorkflowStep`, `*ResponseJson`, parsed-response objects, `ImportWarning`. Rationale: the user pasting an AI response into Step 3 and clicking Submit MUST hit the cache so download doesn't re-fetch. Hashing the whole request would 100%-false-miss preview→download.

  Rejected alternatives:
  - Hash entire DeckAnalysisRequest after JSON-serialize — WorkflowStep + ResponseJson fields change between preview and download/Step 3 paste, defeats the purpose.
  - Hash inputs gathered DURING BuildAsync (post-importer deck text) — must enter BuildAsync first to compute the key; only saves the Scryfall pipeline cost, not the deck-fetch cost (which today is already cached separately by importer-level cache). Insufficient win for the layering complexity.

- **D-02:** **Normalize DeckSource (URL → canonical text) before hashing.** Run the same URL-resolution path BuildAsync uses (importer cache already handles dedupe), then hash the normalized text. Same deck via URL vs via paste = one cache entry. Rejected: raw DeckSource + DeckInputSource mode in the key (cheaper compute but lower hit rate; user clicking download immediately after preview would still hit since the same DeckSource is on the form, so the false-miss is only across mode switches — acceptable but not optimal).

- **D-03:** **SHA-256 hex of canonical-JSON-serialized field bag.** Build an ordered dictionary of the keyed fields, serialize via `System.Text.Json.JsonSerializer.SerializeToUtf8Bytes` with a deterministic options instance, compute `SHA256.HashData`, format as lowercase hex. ~64-char string keys. Matches existing `IMemoryCache` string-key pattern (CardLookupCache, Spellbook, etc.). Rejected: MD5/FNV-1a (algo inconsistency for negligible perf gain), pipe-delimited concat (long keys + escaping bugs).

- **D-04:** **Global key scope — no per-IP / per-session salt.** User A's preview write can serve User B's download read for the same deck. Matches existing global caches (CardLookupCache, CommanderSpellbookService, MechanicLookupService — all keyed only by the upstream identifier with no user salt). No PII in the key — deck contents are already public via Archidekt/Moxfield URLs. Rejected: per-IP-hash salt (rare concurrent-same-deck scenario doesn't justify the hit-rate loss), per-session salt (lowest hit rate).

### TTL + eviction

- **D-05:** **5-minute absolute TTL.** Matches typical preview→read→download user flow (look at the preview pane, read the prompt text, click download), and aligns with the existing 5-minute `ScryfallTaggerHttpClient.SetHandlerLifetime` invariant in `Program.cs` so neither bound is the surprising one. Long enough that a slow reader doesn't expire mid-flow, short enough that a stale deck re-import isn't served days later. Rejected: 2-minute sliding (hot-key memory creep risk on 512MB Render Starter), 10-minute absolute (unnecessary memory pressure), 60-second absolute (too tight for actually-reading-the-preview workflow).

- **D-06:** **Dedicated `MemoryCache` instance with `SizeLimit`, NOT the shared singleton.** Construct `new MemoryCache(new MemoryCacheOptions { SizeLimit = 10_000_000 })` registered as a singleton (or per-service equivalent — planner picks abstraction shape). Packet results don't share LRU pressure with card lookups / spellbook combos. Comment at `DeckFlow.Web/Services/CardLookupCache.cs:10` confirms the shared `IMemoryCache` carries no `SizeLimit` — packet results would silently grow memory on the 512MB Render tier otherwise. Rejected: share existing IMemoryCache with parallel insertion-order ConcurrentDictionary (bookkeeping complexity), share existing IMemoryCache trusting TTL alone (unbounded under spam).

- **D-07:** **Entry `Size` = estimated payload bytes via character-count sum.** Compute `Size = (result.ReferenceText?.Length ?? 0) + (result.AnalysisPromptText?.Length ?? 0) + (result.DeckProfileSchemaJson?.Length ?? 0) + (result.SetUpgradePromptText?.Length ?? 0)` (analogous per service). UTF-16 char count is close enough to byte cost for capacity bookkeeping. `SizeLimit = 10_000_000` ≈ 20 large entries or 200 tiny ones. Rejected: fixed Size=1 with count-cap (capacity unpredictable across deck sizes).

### Scope across endpoints

- **D-08:** **All 3 services in Phase 999.3: deck-analysis, deck-comparison, cedh-meta-gap.** Symmetric scope, matches Phase 15 D-04 / 999.2 D-02 family pattern. Same defect shape would reappear on the other two endpoints within weeks. Per-service key field bags differ (deck-comparison has DeckA + DeckB; cedh-meta-gap has tournament filters) but the wrap shape and cache abstraction are uniform. Rejected: deck-analysis only (would invite repeat bug reports on the other two), deck-analysis + cedh-meta-gap (carves out deck-comparison for no real reason — its 2-deck-source normalization is mechanical).

- **D-09:** **`/deck-analysis/upload` also writes to the cache.** Zip-import path calls `BuildAsync` (DeckController.cs:584); after BuildAsync completes the upload handler writes to cache identically to the preview handler. User flow: upload zip → view fills in → download → cache hit. Symmetric. (deck-comparison and cedh-meta-gap have no `/upload` endpoint — out of scope.)

- **D-10:** **Download endpoint precedence: (1) existing response-json-only short-circuit FIRST, (2) cache lookup SECOND, (3) BuildAsync fallthrough THIRD.** The deck-comparison (line 705) and cedh-meta-gap (line 956) downloads have a fast path that builds the zip from `request` + ResponseJson alone when no deck source was sent (Step 3 round-trip-edit case, zero network calls). Phase 999.3 layers BENEATH that — only when the request still carries the original Scryfall-pipeline inputs does the cache lookup happen. Preserves existing fast paths; rejected: cache-first (wasted lookup on response-json-only requests since they don't write to cache).

### Cache miss fallback

- **D-11:** **Silent fall-through to full `BuildAsync` on cache miss.** No "session expired, regenerate preview first" UX. Cache miss can happen via TTL expiry, process restart, browser bookmark of the download URL, or first-ever submit. In every case the legacy behavior (BuildAsync runs, user waits, zip downloads correctly) is the right thing. Cache is pure optimization, never a correctness contract. Logged for observability but invisible to user. Rejected: return 4xx with regenerate instruction (terrible UX for bookmarked download URLs + would invalidate AI response paste in Step 3).

- **D-12:** **Accept duplicate work on stampede.** Two concurrent same-key previews (multi-tab / double-click) both miss, both run BuildAsync, both Set the cache. Last writer wins. No per-key SemaphoreSlim, no Lazy<Task<T>> singleflight. Matches existing cache patterns in the codebase — CardLookupCache, CommanderSpellbookService, MechanicLookupService all accept duplicate work on stampede. Rationale: rare event, second caller sees no perceptible slowdown vs serial, abstraction complexity not justified at the user volumes this app sees.

- **D-13:** **Structured Serilog log line per cache lookup.** `_logger.LogInformation("Packet cache {Outcome} for {KeyPrefix} ({SizeBytes} bytes)", outcome, key.Substring(0,8), sizeEstimate)` where Outcome ∈ {hit, miss, write, evicted}. Greppable in `/data/logs/web-*.log` for hit-ratio tuning. Default `ILogger<T>` DI pattern, no new infrastructure. Rejected: counter exposed on admin endpoint (overkill), no observability (silent regression risk).

- **D-14:** **Test gate: manual UAT + `dotnet build` clean + grep gate.** Matches Phase 999.1 / 999.2 model. UAT script: submit a large Commander deck preview, time the download click — should be <2s vs today's 2+ min. Grep gate confirms `TryGetValue` + `Set` symmetry across all 3 services + the cache wrapper file is present. xUnit unit tests on the cache wrapper itself (pure-value key normalization) are a planner-discretion add IF they can be written without VSTest WSL flakiness (i.e., assertion logic is build-time deterministic, no integration scaffolding). Default position: skip xUnit, manual UAT only, same as 999.1 and 999.2.

### Claude's Discretion

- Cache abstraction shape — single shared generic `IPacketSessionCache<TKey, TResult>` interface in `Services/Http/` style vs three per-service private caches keyed off a shared dedicated `MemoryCache` instance. Both satisfy D-06. Planner picks the one with the smaller blast radius given the actual `*Service.BuildAsync` signatures. The user did not select this gray area for discussion; planner has full latitude.
- Cache-key field-bag struct naming convention (`DeckAnalysisCacheKeyInputs`? `PacketCacheKey<DeckAnalysisRequest>`?) — pure naming, follows project's existing `*Request` / `*Result` pattern.
- Whether to emit a single `CacheService.cs` central registration extension method (cf. `AddDeckFlowResiliencePipelines()`) or wire the cache directly in `Program.cs` per-service. Either works; cf. CardLookupCache pattern.

### Reusable Assets
- `IMemoryCache` DI registration (`Program.cs:70`) — already wired; the dedicated packet MemoryCache instance per D-06 is a separate construction registered as a singleton alongside it.
- `MemoryCacheEntryOptions` + `SizeLimit` pattern — used inside `CardLookupCache.cs` (which itself opts NOT to participate in SizeLimit; comment at line 10 documents the rationale). Phase 999.3 inverts that choice for packet results.
- `System.Text.Json.JsonSerializer.SerializeToUtf8Bytes` + `System.Security.Cryptography.SHA256.HashData` — both BCL, no new NuGet refs needed for D-03.
- Existing download short-circuit logic at `DeckController.cs:705-725` (deck-comparison) and `:956-969` (cedh-meta-gap) — keep verbatim per D-10; cache layers below.
- Serilog structured logging (`Program.cs:34-47`) — Logger<T> already DI'd into all 3 services; D-13 reuses the existing pattern.

### Established Patterns
- **Cache lifetime:** `IMemoryCache` registered as singleton; consumers inject via constructor. Packet cache mirrors this (singleton dedicated instance).
- **Cache key shape:** string keys, no compound objects. SHA-256 hex satisfies that.
- **Test seam pattern:** services accept `Func<...> executeAsyncOverride` via internal test ctor + `[InternalsVisibleTo("DeckFlow.Web.Tests")]`. If planner DOES add xUnit cache-wrapper tests, this seam pattern applies.
- **No keyed services / no Strategy interfaces:** Phase 15 D-01 forbids it. Per-service cache field bags via dedicated input-bag types per D-01, not via a polymorphic strategy.
- **Plain default-author commits, one logical change per commit:** Phase 999.2 family pattern — likely one commit per service (3) + one commit for shared cache wrapper if one is added + one commit for README/STATE update.

### Integration Points
- `DeckController` constructor already injects all 3 services + `IMemoryCache` (transitively via dependent services). Adding the new packet cache to `DeckController` ctor is the only controller-side surface change needed.
- `DeckAnalysisPacketService` / `DeckComparisonService` / `MetaGapService` constructors get the new dedicated packet `MemoryCache` injected (or the wrapper interface per Claude's-discretion abstraction choice).
- Cache write happens AFTER `BuildAsync` returns (inside the service or inside the controller — planner picks); cache read happens BEFORE `BuildAsync` is called on the download path (controller-side for clarity, but service-side would also work).

<deferred>
## Deferred Ideas

- **Multi-instance horizontal scaling:** Render Starter is single-instance today. If DeckFlow ever moves to multiple web replicas, the in-memory cache is per-replica — preview hits instance A, download hits instance B → miss. Out of scope for 999.3 (premature; would need Redis or sticky sessions and neither is justified today).
- **Persistent disk cache under `MTG_DATA_DIR`:** Process restart cold-cache could be solved by writing results to `/data` with a TTL sweep. Adds disk I/O + serialization surface; not justified at current usage. Note for future.
- **Cache-aware ETag on download response:** Could emit `ETag` based on the same hash so browser-side caching kicks in for repeated downloads of the same artifact. Out of scope; download is a POST today, browser caching doesn't apply.
- **edhtop16 filter-defaults backlog item:** Formerly numbered 999.3, now unnumbered backlog entry (collision resolved 2026-05-20 — see ROADMAP.md line 301). Independent investigation; promote via `/gsd:review-backlog` when ready.
