## STEP 3 — Latency delta: the corrected formula

**Formula (per `<interfaces>`, round-1 review W-4):**

```
added wall-clock = (throttled calls in the flow - 1) x max(0, 500ms - s)
```

where `s` is the measured per-call service time. The upper bound (`s = 0`, i.e. Scryfall responds
instantly) is `(calls - 1) x 300ms`, reported alongside.

**Measured `s`:** the production anchor (`.planning/debug/cutlab-import-scryfall-429.md`, log
window 2026-07-31T02:56:16Z-02:56:26Z) states: *"a single import emits 21 HTTP requests in ~10s,
alternating `POST /cards/collection` and `GET /cards/search`, spaced 200-300ms."* This is a
directly-stated inter-request-start spacing, not a separately-isolated service time — the log
alone cannot cleanly separate "time spent waiting on the throttle" from "time spent waiting on
Scryfall's own response" because at today's 200ms floor the two overlap. Treated honestly: **`s`
is somewhere in `[~0ms, 300ms]`, and the observed 200-300ms spacing implies `s` is very likely AT
OR ABOVE today's 200ms floor for a meaningful fraction of calls** (if `s` were reliably below
200ms, the floor alone would produce a flat 200ms spacing, not the observed 200-300ms range).
**`s` is reported as the bracket `[200ms, 300ms]`, sourced from this log line — not a single
point estimate — because a tighter number cannot honestly be extracted from a spacing
observation alone.**

**The delta function, worked out algebraically** (not assumed): let `wait_today(s) = max(0, 200-s)`
and `wait_new(s) = max(0, 500-s)`. `delta(s) = wait_new(s) - wait_today(s)`.
- For `s` in `[0, 200]`: `delta(s) = (500-s) - (200-s) = 300` — **flat 300ms regardless of `s`**,
  as long as `s` does not exceed today's floor. This is exactly the "upper bound" formula, and it
  turns out to be exact (not just a bound) for any `s <= 200ms`.
- For `s` in `[200, 500]`: `delta(s) = (500-s) - 0 = 500-s` — shrinks linearly from 300ms (at
  `s=200`) to 0 (at `s=500`).

Applying the measured bracket `s ∈ [200, 300]`: **`delta` per throttled gap ranges from 200ms
(at `s=300`) to 300ms (at `s=200`)** — i.e., the service-adjusted delta and the zero-service-time
upper bound coincide at the low end of the bracket and diverge by up to 100ms/gap at the high end.
This is reported as a range, not a single number, because the log does not resolve `s` more
tightly than that.

## STEP 5 — Concurrency effect and timeout census

### Concurrency

`ScryfallThrottle.Gate` is a single process-wide `static SemaphoreSlim(1, 1)`
(`ScryfallThrottle.cs:35`) — every flow in STEP 1's table serializes through the SAME gate,
regardless of which controller or user triggered it. At 200ms this process can sustain roughly
5 Scryfall req/s in aggregate, across ALL concurrent users and ALL flows combined; at 500ms this
drops to roughly 2 req/s in aggregate.

**Concrete effect of 2-3 concurrent users:** if User A starts a Cut Lab import with 25 misses
(27 calls) and User B starts a Deck Analysis with 10 misses (13 calls typical) at nearly the same
moment, their calls interleave through the one gate — the combined 40 calls (39 gaps) take
roughly `39 x 500ms = 19.5s` of aggregate serialized throttle time at the new interval (vs
`39 x 200ms = 7.8s` today), and each user's OWN wall-clock time is inflated by however many of the
other's calls land in between theirs, not just their own call count. In the worst case (the two
requests' calls land fully interleaved 1:1), each user could see roughly double their own
solo-case wall time. This is a real, load-dependent risk that gets strictly worse at 500ms.
Render's Starter plan is a single web instance (512MB) per `.planning/PROJECT.md`'s stated
constraints — there is no horizontal scale-out here that would give each request its own gate;
this static gate genuinely serializes all production Scryfall traffic for the whole app.

flagged as measurably closer to its ceiling, and it is flagged with the actual number (7.8s of

## STEP 6 — Recommendation

**Recommendation: adopt with a named mitigation option disclosed, but do NOT implement it here —
that is the user's call at the checkpoint, and plan 111.1-05 is scoped to the global, unmitigated
form only.**

What this report supports:
- The redundant-call fix (111.1-01) plus the punctuation second pass (111.1-03) have already cut
  the worst-case burst roughly in half for the flows that share `ResolveBatchAsync` (confirmed by
  the production-anchor reconciliation in STEP 3: the exact scenario that produced 21 requests
  pre-fix now produces 11-12).
- Raising `MinInterval` to 500ms is a genuine, documented-limit-driven correctness fix (Scryfall's
  own docs: 2/sec hard limit for the four endpoints in play, with a stated ban-risk penalty for
  ignoring it) — but it is a global, unconditional slowdown of every flow in STEP 1's table, not
  a Cut-Lab-scoped change, because the gate is process-wide static state.
- The added cost at the modeled worst case (25 misses) ranges from ~5-8s (single-call-fallback
  flows) to ~15-23s (`SearchPrintingFallbackCardAsync` flows), which is meaningful wall-clock time
  on flows that mostly have NO timeout budget to absorb it against — meaning users will feel it as
  "slower," not see it fail, EXCEPT for Manabase, where it measurably narrows an existing 20s
  margin.
- **Named mitigation, NOT implemented:** Scryfall's rate-limit table is per-ENDPOINT, not global —
  `/cards/collection`, `/cards/search`, `/cards/named`, `/cards/random` are the four capped at
  2/sec; "all other methods" stay at 10/sec (100ms). A per-endpoint interval (keyed by request
  path rather than one shared `MinInterval`) would let the throttle pace exactly to the documented
  limit per endpoint instead of applying the strictest limit to every caller uniformly — this is a
  real design option worth naming, but it is a materially different, larger change (new keying
  scheme, more state, more tests) than the one-constant edit plan 111.1-05 is scoped to build, and
