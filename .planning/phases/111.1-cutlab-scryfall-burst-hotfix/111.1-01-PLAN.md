<objective>
Ship the user-facing production hotfix. This plan is the complete, safe, standalone unit: after it
lands the banner cause is removed and no regression is introduced. The ADR/match-key work (plan 03)
and the throttle pacing change (plans 04/05) are deliberately NOT in this plan and must not gate it.

Three defects are fixed together because shipping any subset regresses something:

1. **SC-1** — `CutLabAnalysisContextBuilder.cs:410` passes `_cardResolver.ResolveSingleAsync` as the
   post-batch-miss fallback delegate. `ResolveSingleAsync` re-POSTs `cards/collection` for an
   identifier that already failed on that exact endpoint moments earlier in the 75-card batch call,
   then falls through to `cards/search` anyway. This roughly doubles live Scryfall call volume per
   miss and is what turns a ~2-call import into a ~21-request burst. The live probe recorded in
   `111.1-REVIEWS.md` §0 PROVES the removed POST rescues nothing that `SearchFallbackCardAsync`
   does not also resolve — this is measured, not assumed.

2. **SC-2** — `CutLabAnalysisContextBuilder.cs:434` rethrows *every* exception when
   `failOpenOnLookupErrors: false`, including a transient HTTP 429. That rethrow is what aborts the
   whole import and produces the banner.

3. **B-1 (round-1 review blocker)** — fixing (2) alone introduces a NEW defect. Names in a swallowed
   chunk land in neither `resolvedByName` nor `knownMissingNamesSet`, yet `ResolveCardsAsync` still
   writes the partial pool to a 30-minute cache (`CutLabResolvedCardCache.cs:16`), and
   `CutLabPageService.ProcessAsync:275-282` then primes every `Card is null` name — 429 casualties
   included — as `unresolvedCardNames`, i.e. as *known-missing*. `ResolveEntriesAsync`'s blind
   `TryGetCachedResolvedCards` short-circuit (`CutLabPageService.cs:491-495`) then returns the
   degraded pool for 30 minutes. Pre-fix, the fail-closed throw happened BEFORE the cache write, so
   partials were never cached and "Try again shortly" actually worked. Task 3 keeps that true.
