<objective>
Cut the page down: collapse the intake, unify the progress reporting, and flip
the collapse defaults.

Purpose: 07-CONTEXT E-3/E-4. Even after the reorder and the wizard, step 1 alone
is a very tall page, and the intake form still owns the first viewport on every
step.

Output: two new components in `site-common.css`, an intake summary in the view,
one progress strip, and collapse defaults that no longer differ by viewport.

**D-1 resolved 2026-08-03: Option 3, wizard + pinned proposal (~1,107px desktop).**
07-03's runtime panel-hiding and G-2's exactly-one-visible assertion remain in
force; this plan supplies the density work that supports the pinned proposal in
07-05. There is no soft-fix branch to execute.
</objective>

<environment>
- Layout CSS goes in `site-common.css`, NOT `site.css`. Token additions go in each theme's `:root`.
- Do not use `--theme-surface` for panel backgrounds; it renders light in dark themes. Use `--panel`.
- Reference implementation of both new components: `.planning/ui-design/cut-lab/proposed/mock-shared.css`. It is a mockup, not production CSS — port the rules, review them against the theme tokens, do not paste blind.
</environment>

<tasks>

<task type="auto">
  <name>Task 1: Intake summary component</name>

  When `Model.HasResult`, render the intake form inside a closed
  `<details>` whose `<summary>` is the new `.cutlab-intake-summary` row:
  commander, card count, bracket label, play experience, and the board breakdown
  already available as `Model.BoardCounts.ToBreakdown()`.

  The form itself must stay in the DOM and stay submittable — collapsing it must
  not drop `CutLabStateJson`, the antiforgery token, or any intent field. Users
  re-import from here.

  Expose the summary text from `CutLabViewModel` rather than assembling it in
  Razor, so it is unit-testable. Add a `CutLabViewModelWordingTests` case.
</task>

<task type="auto">
  <name>Task 2: Unified progress strip</name>

  Add `.cutlab-progress` carrying: `{baseline} → 100`, a progress bar, `{n} to
  cut`, `{n} cut`, `{n} locked`, and the round label.

  Today this information is spread across the sticky bar (`:1196-1205`), the
  round banner (`:1236-1239`), the pool sticky bar (`:357-360`), the lock count
  (`:329`) and the export count (`:900-909`). Fold the first four into the strip.
  Leave the export count where it is — it gates a form and is not progress.

  **No DTO or patch-builder change is required — verified 2026-08-02.** Every
  value the strip needs already reaches the client:

  | Strip value | Source | Where |
  |---|---|---|
  | current count | `patch.currentCount` | `CutLabUiPatchDto.CurrentCount` |
  | to cut | `patch.cardsRemaining` | `CutLabUiPatchDto.CardsRemaining` |
  | cut so far | derived from `patch.cutsMade.length` | `cut-lab.ts:3071` |
  | round label | `patch.nextProposal.roundLabel` | `cut-lab.ts:3067` |
  | locked | derived client-side from checked lock boxes | `updateLockedCountChip`, `cut-lab.ts:991-1014` |

  `locked` in particular is NOT server-patched — it is counted in the DOM. Do
  not add a `LockedCount` field to the DTO; it would be a second source of truth
  for a number the client already owns.

  What this plan MUST preserve is the attribute names. Keep
  `data-cut-lab-sticky-current`, `-remaining`, `-round`, `-accepted` and
  `-locked`, plus `data-cut-lab-lock-count`, `data-cut-lab-pool-sticky-count`,
  and `data-cut-lab-pool-sticky-breakdown`, on the unified component, spelled
  exactly as today. `DeckFlow.Web/wwwroot/ts/cut-lab.ts:999-1000,3046-3071`,
  `DeckFlow.Web/Views/Deck/CutLab.cshtml`,
  `DeckFlow.Web.Tests/CutLabViewRenderTests.cs`,
  `DeckFlow.Web/ts-tests/cut-lab-pool-filter.test.ts`,
  `DeckFlow.Web/ts-tests/cut-lab-lock-interactions.test.ts`, and
  `DeckFlow.Web/e2e/cut-lab-smoke.spec.ts` consume this complete selector
  contract; preserve it rather than migrating consumers.
  and `updateLockedCountChip` locate them by those selectors; renaming any of
  them silently stops the strip updating after a decide, with no error.
</task>
