```typescript
((): void => {
  'use strict';

  let initialized = false;

  const attachFeedbackBusyState = (): void => {
    if (initialized) {
      return;
    }
    initialized = true;

    const form = document.querySelector<HTMLFormElement>('form.feedback-form');
    if (!form) {
      return;
    }

    const button = form.querySelector<HTMLButtonElement>('button.feedback-submit');
    if (!button) {
      return;
    }

    form.addEventListener('submit', () => {
      // D-08: do NOT preventDefault — let the browser POST normally.
      // D-11: disabled flag prevents double-submit.
      button.disabled = true;
      button.classList.add('feedback-submit--busy');
      // D-09: text swap for the duration of the request.
      button.textContent = 'Sending…';
    });
  };

  document.addEventListener('DOMContentLoaded', attachFeedbackBusyState);
  if (document.readyState !== 'loading') {
    attachFeedbackBusyState();
  }
})();
```

Notes:
- IIFE wrapper + `'use strict'` + module-less compilation matches every other file in `wwwroot/ts/`.
- The form lookup is cheap (single querySelector); on every non-feedback page the early return after `!form` makes this a no-op even though the script is currently scoped to the Feedback view only via @section Scripts (defence in depth).
- `submit` event listens on the form, not the button — Enter-key submit from a text input still triggers the busy state.
- Listener does NOT call `event.preventDefault()` (D-08). The button.disabled flip happens synchronously inside the submit handler, but browsers serialize and queue the form's POST before processing further DOM mutations, so the POST is fully in flight before disabled takes effect. (Verified pattern; same approach as site.ts's existing button-disabling listeners on cache-clear UI.)
- Use the literal Unicode ellipsis character `…` in `'Sending…'` (matches UI-SPEC §"Copywriting Contract"). Save as UTF-8.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-06 | T (Tampering) | feedback.ts submit handler | accept | The handler is purely visual — it disables the button and swaps text after the submit event fires; it cannot modify the request body or headers. A malicious local script could disable the handler entirely, but that only loses the spinner — it does NOT bypass server-side validation or rate limiting. |
| T-02-07 | D (DoS) | Double-submit prevention | mitigate | `button.disabled = true` blocks the second click in the browser. Server-side rate limit (5/hr per IP, existing) is the actual brute-force defense; this client-side measure is UX, not security. UI-SPEC and CONTEXT.md (D-11) explicitly mark server-side anti-double-submit token as Phase 4 candidate, not this phase. |
| T-02-08 | I (Information Disclosure) | wwwroot/js/feedback.js public asset | accept | Compiled JS is a public asset by design. Source has no secrets; every conditional and selector is feedback-specific and reveals no internal architecture. |
</threat_model>
