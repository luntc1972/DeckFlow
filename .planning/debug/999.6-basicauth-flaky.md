## Hypotheses Tested

### H1 — Cross-class env-var race between `BasicAuthMiddlewareTests` and `AdminBruteForceTrackerStoreTests` — **PASS**

**Premise:** xUnit v2 runs test classes in parallel collections by default (one collection per test class unless explicitly assigned). Both test classes mutate the same process-wide environment variables (`FEEDBACK_ADMIN_USER`, `FEEDBACK_ADMIN_PASSWORD`) via independent disposable helpers. When xUnit interleaves a fact from class A with a fact from class B, the env-var state observed by `BasicAuthMiddleware.InvokeAsync` is non-deterministic.

**Specific race window for `CorrectCredentials_InvokesNext`:**

1. `BasicAuthMiddlewareTests.CorrectCredentials_InvokesNext` enters its arrange block.
2. `EnvScope.Set(EnvUser, "admin", EnvPass, "secret")` runs at line 86 — captures previous values, sets new.
3. Concurrent on another xUnit thread, `AdminBruteForceTrackerStoreTests.SuccessfulAuthDoesNotCountTowardThrottle` (or sibling fact `ElevenFailedAuthsFromSameIp_TenthReturns401_EleventhReturns429`) finishes — its `_envPass.Dispose()` (line 169 of `AdminBruteForceTrackerStoreTests.cs`) fires `Environment.SetEnvironmentVariable("FEEDBACK_ADMIN_PASSWORD", _previous)`. If `_previous` was null when that fact's EnvScope captured it, the password env var is now NULL process-wide.
4. `CorrectCredentials_InvokesNext.middleware.InvokeAsync(context)` runs (line 94 of BasicAuth tests). Inside `InvokeAsync` at production lines 53-54, `Environment.GetEnvironmentVariable("FEEDBACK_ADMIN_PASSWORD")` returns null.
5. Line 56-63 of `BasicAuthMiddleware`: `if (string.IsNullOrWhiteSpace(user) || string.IsNullOrWhiteSpace(password))` → returns **503 Service Unavailable** ("Admin not configured.") without invoking `_next`.
6. Back in the test: `Assert.True(nextCalled)` fails because the 503 short-circuit never called `next`.

**Evidence:**

1. **Static facts** (grep, not runtime):
   - Two distinct `EnvScope` implementations confirmed: `BasicAuthMiddlewareTests.cs:101-135` and `AdminBruteForceTrackerStoreTests.cs:158-170`.
   - Both write process-global `FEEDBACK_ADMIN_USER` / `FEEDBACK_ADMIN_PASSWORD` via `Environment.SetEnvironmentVariable`.
   - 5 + 2 = 7 facts across the two classes touch these vars; xUnit's default collection-per-class with `parallelizeTestCollections: true` runs them concurrently.

2. **xUnit parallelism default:** Per xUnit v2 documentation, `parallelizeTestCollections` defaults to `true`. Each test class is its own collection unless `[Collection("name")]` is applied. No `xunit.runner.json` in this project overrides the default — confirmed by `find DeckFlow.Web.Tests/ -name "xunit.runner.json"` returning empty (verified via `grep` of test project tree during this investigation — file absent, default applies).

3. **Failure mode prediction matches observed assertion:**
   - Predicted: `next` never called because middleware short-circuits with 503 when `password` is null after the dispose race.
   - Observed: `Assert.True(nextCalled)` at `BasicAuthMiddlewareTests.cs:96` is the failing assertion. Lines 97-98 (`Assert.NotEqual(401)`, `Assert.NotEqual(503)`) would also fail with status 503 — but `Assert.True` fires first.

4. **Filter-isolation confirms parallel-only failure mode:**
   - `--filter "FullyQualifiedName~BasicAuthMiddlewareTests"` excludes the `Security.AdminBruteForceTrackerStoreTests` class entirely — no cross-class race possible — passes 5/5.
   - Full-suite includes both classes — fails reproducibly.
   - This is the textbook fingerprint of a cross-class shared-state race, not an intra-class fact-order bug (which would fail in filter-isolation too if `[Theory]` row ordering or fact ordering inside the class were the cause).

5. **Middleware read pattern (production code, lines 53-54):** `Environment.GetEnvironmentVariable` is called fresh on every `InvokeAsync` — no construction-time cache. This means the middleware sees the env var state AT THE INSTANT of the InvokeAsync call, which is exactly the window where a concurrent `EnvScope.Dispose()` from the other test class can race.

**Verdict on H1:** **PASS.** Cross-class env-var race confirmed. The orchestrator pre-confirmed hypothesis (Codex HIGH #4) holds; the symptom (`Assert.True(nextCalled)` failing) precisely matches the predicted failure mode (middleware sees null password, returns 503, `next` never invoked).

### H2 — `BasicAuthMiddleware` caches env vars at construction — **FAIL (falsified)**

**Premise:** If `BasicAuthMiddleware` snapshotted env vars in its constructor (or read them once and cached in a static), a concurrent mutator could leave the cache stale.

**Evidence:**
- `DeckFlow.Web/Infrastructure/BasicAuthMiddleware.cs` constructor (lines 17-31): captures only `_next`, `_logger`, `_realm`, `_store`. No env-var read.
- `InvokeAsync` (lines 33-102): calls `Environment.GetEnvironmentVariable("FEEDBACK_ADMIN_USER")` (line 53) and `Environment.GetEnvironmentVariable("FEEDBACK_ADMIN_PASSWORD")` (line 54) on EVERY invocation.
- No static field, no `Lazy<>`, no construction-time snapshot.

**Verdict on H2:** **FALSIFIED.** Middleware reads env vars fresh on every InvokeAsync. The race is in the test infrastructure, not the middleware. (This means Branch F-MIDDLEWARE-IDEMPOTENT is NOT applicable — there is no production state-management bug to fix.)

### H3 — `IMemoryCache` / `AdminBruteForceTrackerStore` retention across facts — **FAIL (falsified)**

**Premise:** `AdminBruteForceTrackerStore` is created per-fact via `CreateStore(out var dbPath)` at `BasicAuthMiddlewareTests.cs:18-22`. If the temp DB path were reused across facts, brute-force state could leak.

**Evidence:**
- `CreateStore` uses `Guid.NewGuid():N` to generate a unique temp DB path per fact (`BasicAuthMiddlewareTests.cs:20`).
- Each fact constructs a NEW `AdminBruteForceTrackerStore` instance bound to that unique path.
- No `IMemoryCache` involvement in this middleware path; the store is SQLite-backed and instance-scoped.
- Even if the store leaked state, the failing assertion is `Assert.True(nextCalled)` — a missing `next` call corresponds to 503/401 short-circuit, not a 429 throttle. Throttling would surface as `Assert.NotEqual(Status401Unauthorized)` at line 97 failing with status 429, not as `nextCalled == false`.

**Verdict on H3:** **FALSIFIED.** Store is per-fact-fresh; failure-mode shape doesn't match throttle-leak.

### H4 — Intra-class fact-order state bleed (e.g., `WrongCredentials_Returns401` leaves lockout state) — **FAIL (falsified)**

**Premise:** xUnit runs facts within a class in undefined order. If `WrongCredentials_Returns401` (line 69) ran before `CorrectCredentials_InvokesNext` (line 84) and left throttle state in a shared store, the correct-credentials fact would 429 instead of 200.

**Evidence:**
- Each fact in `BasicAuthMiddlewareTests` creates its OWN store via `CreateStore(out _)` (lines 31, 44, 60, 75, 91). No store reuse across facts.
- If H4 were the cause, the filter-isolated `--filter "FullyQualifiedName~BasicAuthMiddlewareTests"` runs would ALSO fail intermittently (5/5 facts all run, ordering still undefined). But filter-isolation passes 5/5 reproducibly.

**Verdict on H4:** **FALSIFIED.** Intra-class state isolation is intact; failure only manifests in cross-class scheduling.

## Root Cause

`BasicAuthMiddlewareTests` (5 env-mutating facts) and `DeckFlow.Web.Tests.Security.AdminBruteForceTrackerStoreTests` (2 env-mutating facts) are in DIFFERENT xUnit test classes, hence DIFFERENT default xUnit collections, hence eligible for PARALLEL execution by the xUnit v2 runner (the project does not override `parallelizeTestCollections`).

Both classes mutate the SAME process-wide environment variables (`FEEDBACK_ADMIN_USER`, `FEEDBACK_ADMIN_PASSWORD`) via independent `EnvScope` disposables. Because the env vars are process-wide global state, any temporal interleaving where one class's `Dispose()` (restoring null/previous) fires AFTER another class's `Set()` but BEFORE that other class's `InvokeAsync()` reads the var causes the reader to observe stale/null state.

For `CorrectCredentials_InvokesNext` specifically: when the password env var is null at `BasicAuthMiddleware.InvokeAsync` line 54, the middleware returns 503 ("Admin not configured.") at line 60-62 without calling `_next` — which manifests as `Assert.True(nextCalled)` failing at line 96.

The race is wholly in the test layer. The production middleware is correct (idempotent fresh-read on every invocation). The fix is to serialize the two env-mutating test classes via the project's existing-and-codified xUnit collection-serialization pattern (TESTING.md §"Process-wide environment isolation via xUnit collections", currently used by `CategoryKnowledgeStoreTests` and `DeckFlowDatabaseConnectionFactoryTests` for `MTG_DATA_DIR` and DB-provider env vars).

## Verdict

**`FLAKY_DUE_TO_CROSS_CLASS_ENV_VAR_RACE`**

Not a stale test. Not a real production bug. The middleware is correct; the test infrastructure has a global-state coupling between two test classes that the default xUnit parallelism exposes.

## Recommended Fix Shape

**Branch: `F-ENV-COLLECTION`** (D-14 default; the only deterministic option under Codex R2 MEDIUM #2 for the empirically-confirmed cross-class race).

Rationale for choosing F-ENV-COLLECTION over F-ENV-CLEAR-EAGER:
- F-ENV-CLEAR-EAGER (eager `Environment.SetEnvironmentVariable(..., null)` before each fact's `EnvScope.Set`) does NOT serialize concurrent mutators. Two facts in different classes can still interleave their Set/Dispose around any other class's InvokeAsync. The race window stays open; the fix is non-deterministic.
- F-ENV-COLLECTION serializes facts from BOTH env-mutating classes into a single xUnit collection with `DisableParallelization = true`, eliminating the race window entirely.
- The pattern is ALREADY a codified convention in this codebase: see `DeckFlow.Web.Tests/CategoryKnowledgeStoreTests.cs:13-21` and `DeckFlow.Web.Tests/DeckFlowDatabaseConnectionFactoryTests.cs:15-24`. TESTING.md §"Process-wide environment isolation via xUnit collections" documents it as the project's standard approach.

Rationale for NOT choosing F-MIDDLEWARE-IDEMPOTENT:
- H2 falsified the construction-time cache hypothesis. The middleware already reads env vars fresh on every InvokeAsync — it is already idempotent under env-var mutation. There is no production bug to fix.
- D-15 escalation path does not fire.

### Concrete Diff Sketch

**New file 1:** `DeckFlow.Web.Tests/Infrastructure/EnvScope.cs`

```csharp
using System;
using System.Collections.Generic;

namespace DeckFlow.Web.Tests.Infrastructure;

/// <summary>
/// Disposable helper that captures and restores process-wide environment variables.
/// Subsumes the two prior inline EnvScope helpers in BasicAuthMiddlewareTests and
/// AdminBruteForceTrackerStoreTests. Combine with <c>[Collection("AdminEnvSerial")]</c>
/// on env-mutating test classes to serialize their parallel execution and eliminate
/// the cross-class race on FEEDBACK_ADMIN_USER / FEEDBACK_ADMIN_PASSWORD.
/// </summary>
internal sealed class EnvScope : IDisposable
{
    private readonly Dictionary<string, string?> _previous = new();

    private EnvScope(params string[] keys)
    {
        foreach (var key in keys)
        {
            _previous[key] = Environment.GetEnvironmentVariable(key);
        }
    }

    public static EnvScope Clear(params string[] keys)
    {
        var scope = new EnvScope(keys);
        foreach (var key in keys) Environment.SetEnvironmentVariable(key, null);
        return scope;
    }

    public static EnvScope Set(string name, string value)
    {
        var scope = new EnvScope(name);
        Environment.SetEnvironmentVariable(name, value);
        return scope;
    }

    public static EnvScope Set(string k1, string v1, string k2, string v2)
    {
        var scope = new EnvScope(k1, k2);
        Environment.SetEnvironmentVariable(k1, v1);
        Environment.SetEnvironmentVariable(k2, v2);
        return scope;
    }

    public void Dispose()
    {
        foreach (var (key, value) in _previous)
        {
            Environment.SetEnvironmentVariable(key, value);
        }
    }
}
```

## Forbidden Fix Shapes

- **`[Fact(Skip="...")]` on any BasicAuth or AdminBruteForce fact.** Violates D-03 ("no new `[Skip]` directives"). Phase closes with the same Skipped count it opened with.
- **`[Collection("AnyName")]` decoration WITHOUT a corresponding `[CollectionDefinition(..., DisableParallelization = true)]`.** Grouping facts into a named collection without disabling parallelization is a paper-over per D-10: it silences the test-runner-reported flakiness only because of incidental xUnit scheduling, not because the underlying race is fixed. Two collection members can still race against another collection's members.
- **Branch F-ENV-CLEAR-EAGER alone (eager `Environment.SetEnvironmentVariable(..., null)` before each `EnvScope.Set`).** Allowed by the plan ONLY IF the debug session falsifies cross-class racing (Codex R2 MEDIUM #2). This session CONFIRMS cross-class racing → F-ENV-CLEAR-EAGER is ruled out for this fix. The clear-then-set is not atomic with respect to concurrent mutators; two mutators on different threads can still interleave.

**D-14 nuance — legitimate vs. paper-over Collection decoration:** A `[CollectionDefinition(DisableParallelization = true)]` covering ONLY the env-mutating test classes (`BasicAuthMiddlewareTests` + `AdminBruteForceTrackerStoreTests`), with the root cause named in this debug doc and the commit body, IS the legitimate xUnit serialization pattern. The project ALREADY uses this exact pattern for `CategoryKnowledgeStoreTests` (`MTG_DATA_DIR` mutation) and `DeckFlowDatabaseConnectionFactoryTests` (DB-provider env vars). It is documented in `.planning/codebase/TESTING.md` lines 106-115 as the canonical approach. Distinct from a paper-over because (a) root cause is identified and recorded, (b) only the env-mutating classes are serialized (no broader test-suite parallelism degradation), and (c) the pattern matches an existing project convention.
