- DECISION D-OPEN (resolves Codex HIGH #3 — sidebar default state): render
  `<details class="admin-sidebar__disclosure">` WITHOUT the `open` attribute. Rationale: SC2 /
  AMOB-01 require the sidebar to COLLAPSE to a disclosure below 768px — rendering `open` would
  start it expanded at 320-768px, contradicting "collapses to disclosure." Without `open` the
  `<details>` starts CLOSED, so at mobile width only the `<summary>` ("hamburger Menu") shows
  and the nav is hidden until the user activates it (the Plan 01
  `.admin-sidebar__disclosure:not([open]) .admin-sidebar__nav { display: none }` rule provides
  the collapse). On DESKTOP (>=769px) the Plan 01 `@media (min-width: 769px)` guard forces the
  nav + brand visible with `display: block !important` and CLIPS (not hides) the `<summary>`
  toggle, so the closed `<details>` is irrelevant above the breakpoint — the nav is always shown
  on desktop regardless of the disclosure's open/closed state. Net: collapsed-by-default on mobile,
  always-visible on desktop, no JS. This is the explicit decision; all checkpoint steps below
  align to it.

- DECISION D-DESKTOP-NAV (resolves cycle-2 NEW HIGH + cycle-3 PARTIAL HIGH-3 — closed <details>
  forced visible on desktop, fallback contradiction): the D-OPEN pattern relies on the Plan 01
  `@media (min-width: 769px)` `display: block !important` rule to paint the nav + brand inside a
  CLOSED `<details>` at >=769px. RISK: the `<details>` semantic state stays "collapsed" even
  though the content is visually present, and browser / screen-reader behavior CAN diverge — some
  assistive tech may treat content inside a closed `<details>` as hidden from the a11y tree
  regardless of CSS `display`.

  CONTRADICTION FIXED THIS REVISION (cycle-3): the prior revision hid the desktop `<summary>` with
  `display: none` while ALSO claiming the `<summary>` was the "operable fallback" — but a
  `display:none` summary is removed from the a11y tree and cannot be operated, so the fallback was
  self-contradictory. RESOLUTION — ONE coherent no-JS pattern (Plan 01 admin-mobile.css implements
  it; this decision documents the contract and the checkpoint asserts it):
    (a) At >=769px the nav + brand are FORCED visible (`display: block !important`).
    (b) The `<summary>` is NOT `display: none`. It is CLIPPED with the `.sr-only` pattern
        (`position: absolute; width: 1px; height: 1px; overflow: hidden; clip: rect(0 0 0 0);
        white-space: nowrap;`). A CLIPPED element (unlike `display:none`) STAYS in the
        accessibility tree and remains keyboard-focusable — so it is visually removed (the
        always-visible nav is the desktop chrome) WHILE remaining a real, operable disclosure
        control if any AT treats the closed `<details>` as collapsed and skips the forced-visible
        nav. There is no contradiction: the summary is operable precisely because it is clipped,
        not hidden.
  VERIFICATION (kept no-JS): the human-verify checkpoint adds an EXPLICIT 769px desktop step that
  confirms (1) the nav is keyboard-reachable (Tab lands on all four nav links in order) AND
  announced + operable by a screen reader, and (2) the `<summary>` is reachable by keyboard and
  announced as an expandable control (i.e. it is clipped-but-operable, NOT removed) — proving the
  fallback is real. The checkpoint resume-signal requires the verifier to state which branch held
  (nav directly SR-reachable, OR summary-fallback exercised) AND to confirm the summary is
  focusable (consistent with the clipped-not-hidden decision). This keeps the implementation no-JS
  while making the semantic tradeoff explicit, coherent, and verified rather than assumed.
