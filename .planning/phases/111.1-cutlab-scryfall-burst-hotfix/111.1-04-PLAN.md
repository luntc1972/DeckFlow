`DeckFlow.Web/Services/Scryfall/ScryfallThrottle.cs`:
```csharp
private static readonly TimeSpan MinInterval = TimeSpan.FromMilliseconds(200);   // :17
private static readonly SemaphoreSlim Gate = new(1, 1);                          // :35  PROCESS-WIDE
private static DateTime _lastCallUtc = DateTime.MinValue;                        // :36
```
The gate serializes ALL Scryfall traffic in the process and spaces consecutive calls by
`MinInterval`. Therefore: added latency for a flow = (throttled calls in that flow - 1) x 300ms,
and under concurrency the queueing delay is additive across all in-flight flows, not per-flow.

Every `ScryfallThrottle.ExecuteAsync` call site (complete list, from grep):
```

DeckFlow.Web/Services/Scryfall/ScryfallCommanderSearchService.cs:48
DeckFlow.Web/Services/Scryfall/CardSearchService.cs:51

DeckFlow.Web/Services/Scryfall/ScryfallSetService.cs:68, :74
DeckFlow.Web/Services/Scryfall/ScryfallTaggerLookupService.cs:157
```
CRITICAL MEASUREMENT FACT: the throttle wraps at the PRODUCTION constructor (e.g.
`ScryfallCardResolver.cs:76-88` build the default `_executeCollectionAsync` / `_executeSearchAsync`
delegates by wrapping them in `ScryfallThrottle.ExecuteAsync`). The `internal` test constructors
inject override delegates that BYPASS the throttle entirely. Consequence: you cannot measure this by
timing a test run — a test-seam run has no pacing in it at all. What a test seam CAN give you,
exactly and deterministically, is the **count** of delegate invocations, and each invocation is
exactly one throttle pass in production. Count, then multiply. Do not attempt to time it.

`ScryfallReferenceResolver.ScryfallBatchSize = 75` (`ScryfallReferenceResolver.cs:75`), so a 100-card
pool is 2 collection chunks, plus one fallback call per miss.

REAL OBSERVED PRODUCTION ANCHOR (`.planning/debug/cutlab-import-scryfall-429.md`, log evidence
2026-07-31T02:56:16Z-02:56:26Z): a single Cut Lab import emitted **21 HTTP requests in ~10s**,
alternating `POST /cards/collection` and `GET /cards/search`, spaced 200-300ms. This is a measured
data point for the pre-plan-01 Cut Lab flow and must anchor the report. Note that plan 111.1-01
removes the redundant POST, so the post-fix Cut Lab count for the same pool is roughly halved —
recompute it rather than reusing 21.

Scryfall's documented per-endpoint hard limits (fetched 2026-07-31, cited in RESEARCH.md):
`/cards/search`, `/cards/named`, `/cards/random`, `/cards/collection` = **2/second (500ms)**;
`/cards/manifest` = 10/minute; all other methods = 10/second. The comment at `ScryfallThrottle.cs:13`
cites the "all other methods" 10/sec ceiling as if it applied here — it does not.
