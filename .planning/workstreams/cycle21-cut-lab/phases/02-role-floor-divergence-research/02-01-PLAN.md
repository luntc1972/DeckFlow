### 3. `boardFilter` sits after `CancellationToken`

`CardCategoryRepository.GetCategoryDeckMembershipForCommanderAsync` (`:204-207`) declares
`(string commanderName, CancellationToken cancellationToken = default, string? boardFilter = null)`.
The project convention, stated in CLAUDE.md's Function Design section, is that
`CancellationToken cancellationToken = default` is the **last** parameter. ROADMAP success criterion
6 requires the reorder with no production runtime behavior change.

## Correction to a stated assumption — the reorder is NOT compile-safe at the call sites

The phase brief asserted the runner "uses a named arg, so reorder is compile-safe there."
**That is wrong**, and getting it wrong produces a confusing build failure. Verified call shapes:

| Call site | Current shape | Breaks under reorder? |
|---|---|---|
| `RoleFloorResearchCommandRunner.cs:113-116` | `(commanderName, token, boardFilter: "mainboard")` | **YES** — only `boardFilter` is named; `token` is **positional** and would bind to the new slot-2 `string? boardFilter`. |
| `CategoryKnowledgeRepository.cs:101` | `(commanderName, cancellationToken, boardFilter)` | **YES** — fully positional passthrough body. |
| `CategoryKnowledgeStore.cs:282` | `(commanderName, cancellationToken)` | **YES** — positional 2-arg; the token would bind to `string? boardFilter`. |
| `CategoryCacheSchemaParityTests.cs:305-308` | `(name, CancellationToken.None, boardFilter: "mainboard")` | **YES** — same shape as the runner. |
| `CategoryCacheSchemaParityTests.cs:273`, `:309` | `(name)` only | No — both remaining parameters stay optional. |

`CategoryKnowledgeStore.cs` was listed in the phase brief as an *unaffected* caller because it
implements the shorter `ICategoryKnowledgeStore` signature. Its own **signature** is indeed
unaffected; its **body** at `:282` calls the reordered repository method positionally and must be
fixed. All other `ICategoryKnowledgeStore` implementors and test doubles
(`FakeCategoryKnowledgeStore.cs:155`, `HarvestStatsAggregatorTests.cs:82,148`,
`CategorySuggestionServiceTests.cs:224`, `CutLabPageServiceTests.cs:2945`,
`CutLabAnalysisContextBuilderTests.cs:670`, `CommanderCategoryService.cs:55`) are genuinely
untouched — they only ever see the two-parameter interface method.

## Design Decisions

### D-01 — name the token at every remaining call site

Rather than relying on positional order surviving a future edit, every updated call site passes
`cancellationToken: <token>` **by name**. The reorder exists precisely because positional order was
wrong once; naming the token makes the next reorder harmless.

### D-02 — wave 1 is SERIALIZED: 02-01 → 02-03, with 02-02 the only safe concurrent plan

The plan set originally listed `02-01`, `02-02` and `02-03` all as `wave: 1`, implying all three could
run at once. **They cannot.** `02-01` Task 3 and `02-03` Task 2 each run `dotnet build DeckFlow.sln`
plus both test projects and then commit. Concurrently they contend on three shared resources:

| Resource | Failure under concurrency |
|---|---|
| `obj/` and `bin/` for `DeckFlow.Core`, `DeckFlow.CLI`, both test projects | Interleaved MSBuild writes produce spurious build failures and stale `project.assets.json` |
| `.git/index.lock` | The second plan's `git add` / `git commit` fails outright |
| Pinned test counts (~1630 Core / ~2095 Web) | Non-deterministic while the sibling plan is adding test members |

Ordering, binding on the executor:

| Order | Plan | Concurrency |
|---|---|---|
| 1 | `02-01` | Runs first, alone among the dotnet-touching plans. Baseline counts: Core ~1630, Web ~2095. |
| 2 | `02-03` | Starts only after `02-01`'s second commit exists. Expected counts at its GREEN gate: Core ~1630 **plus** the test members `02-03` Task 1 adds, Web ~2095 unchanged. `02-01` adds no test member, so the Core baseline it inherits is unchanged from `HEAD`. |
| any | `02-02` | Python-and-docs only, no `dotnet`, disjoint files (`scripts/edhrec-brackets/**`). It commits the already-written fetcher and records the completed acquisition; it runs no fetch and makes no network call. **The only plan safe to run concurrently with either of the above.** |

Waves 2 through 7 each contain exactly one plan, so no further serialization is needed. `02-03`'s
frontmatter carries `depends_on: [02-01]` to make this machine-visible rather than prose-only.

**The phase is 9 plans across 7 waves**, not the 8 across 6 an earlier draft assumed: plan `02-09`
(the `edhrec.csv` expected-role-count grid) was added on 2026-07-27 at wave 6, pushing the live-run
plan `02-08` to wave 7.

### D-03 — scope gates are tracked-and-task-scoped, never a bare `git status` count

A bare `git status --porcelain` assertion ("lists only two files") is **unsatisfiable in this
worktree** and is dangerous: it either halts a correct task or provokes an agent into "cleaning"
untracked files that later plans depend on. See the Scope Fence's scope-gate block for the binding
form and the permanent-untracked set.
