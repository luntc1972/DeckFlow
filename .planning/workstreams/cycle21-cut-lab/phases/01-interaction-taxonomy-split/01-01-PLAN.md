# Phase 1 Plan 01 — Interaction Taxonomy Split

## Why This Phase Exists

`CutLabRoleAssigner.cs:141-143` already calls two distinct classifier predicates and then merges
both results into a single `interaction` role key:

```csharp
if (interactionMeritPreGate
    || DeckStatClassifier.IsBoardWipeCard(oracle)
    || DeckStatClassifier.IsTargetedRemovalCard(typeLine, oracle))
{
    assigned.Add(InteractionRole);
}
```

The merge is the only thing this plan undoes. Two reasons it matters:

1. **Template alignment.** The 2025 Command Zone template splits targeted disruption (~12) from
   mass disruption (~6). Cut Lab's single interaction floor tops out at 12, which under-counts the
   combined guardrail and cannot express the very different ratios different decks want.
2. **It unblocks Phase 2.** Targeted removal and board wipes have materially different
   per-commander distributions. Averaging them into one bucket inflates within-role variance,
   which deflates the z-scores and Cohen's d that Phase 2's statistical bar reads. Measuring a
   role that is about to be redefined also wastes the run outright.

## Design Decisions

### D-01 — Targeted and mass are MUTUALLY EXCLUSIVE by construction

**Corrected after plan review round 2.** An earlier draft required both-predicate cards to join
both roles. That case is unreachable: `DeckStatClassifier.IsTargetedRemovalCard` opens with
`!IsBoardWipeCard(oracleText)` (`DeckFlow.Core/Analysis/DeckStatClassifier.cs:185`), so the two
predicates can never both be true for the same oracle text. Combined with D-02's wipe subtraction
on the merit path, **no card can hold both `interaction-targeted` and `interaction-mass`**.

Consequences that matter downstream:

- Do **not** write a "card in both interaction roles" test — it cannot be constructed from the
  real classifiers, and a test that fabricates it would be asserting fiction.
- There is **no double-counting** between these two roles. A single card contributes to exactly
  one of the two interaction floors. This is why D-03 does not claim a double-count effect.
- Cut Lab's general multi-role model is unchanged — a card can still hold e.g. `ramp` and `draw`
  simultaneously. The exclusivity is specific to this predicate pair.

If a future change removes the `!IsBoardWipeCard` guard from `IsTargetedRemovalCard`, this
decision must be revisited; add a `// Why:` comment at the assignment site recording the
dependency so the coupling is discoverable.

### D-02 — `interactionMeritPreGate` is a SUPERSET signal and must have wipes subtracted

**Corrected after plan review — the original form of this decision was wrong and would have
broken the phase's own acceptance criteria.**

`interactionMeritPreGate` is NOT a counterspell-only or targeted-only signal. At
`PlanRoleClassifier.cs:70` it is set as `roles.HasFlag(PlanRole.Interaction)`, and
`PlanRole.Interaction` is set from two paths that both include sweepers:

- `GrantsInteraction` (`:190`) returns `interactionMerit || IsBoardWipeCard(oracle) || IsTargetedRemovalCard(...)`
- `IsInteractionCategory` (`:242`) matches the tags `removal`, `interaction`, `protect`, **`wipe`**, `answer`

So `targeted = interactionMeritPreGate || IsTargetedRemovalCard` would assign every wipe-only card
to `interaction-targeted`, directly contradicting must-have truth 2 and required test 1.

**Correct assignment.** Note `isMass` is computed FIRST and then subtracted from targeted, and that
mass must consider the **category path** as well as the oracle heuristic — corrected after review
round 2, where the heuristic-only form still leaked category-tagged wipes into targeted:

```
isMass   = DeckStatClassifier.IsBoardWipeCard(oracle) || HasWipeCategoryTag(categories)
isTargeted = !isMass
             && (DeckStatClassifier.IsTargetedRemovalCard(typeLine, oracle)
                 || interactionMeritPreGate)
```

`HasWipeCategoryTag` is a local private helper in `CutLabRoleAssigner` matching the token `wipe`
in any supplied category, mirroring `PlanRoleClassifier.IsInteractionCategory`'s `"wipe"` arm
(`:242`). It is defined locally rather than by modifying `PlanRoleClassifier`, which the Scope
Fence forbids; `CutLabRoleAssigner` already sets local-gating precedent for the engines role
(`:154-162`). Add a `// Why:` comment naming the mirrored vocabulary so drift is discoverable.

Expressing targeted as `!isMass && (...)` rather than `... && !isWipe` is deliberate: it makes the
exclusivity from D-01 structural and readable at the call site instead of an emergent property of
two separate conditions.

Truth table this produces:

| Card | mass | targeted |
|---|---|---|
| Wipe by oracle heuristic | yes | no |
| Tagged `wipe`, oracle misses the heuristic | yes | no |
| Targeted removal only | no | yes |
| cEDH counterspell (merit, neither predicate) | no | yes |
| Generic `interaction`/`answer` tag, no predicate match | no | yes |
| Both predicates | unreachable — see D-01 | unreachable |

The generic-tag row is deliberate: an answer classifiable as interaction but not as a sweeper
defaults to targeted, the larger and more common bucket. The explicit `wipe` tag is NOT treated
that way, which is the round-2 correction.

The wipe subtraction is done **inside `CutLabRoleAssigner`**. `PlanRoleClassifier` is not modified
— narrowing the upstream out-parameter would change the Manabase interaction lens, which is out of
scope per the Scope Fence.

### D-03 — Floor bands split 2:1; the aggregate DEFAULT BUDGET is preserved, the guardrail BEHAVIOR changes

Today: `"interaction" => normalizedBracket switch { 2 => 6, 3 => 8, 4 => 10, _ => 12 }`.

| Bracket | targeted | mass | sum | shipped merged floor |
|---|--:|--:|--:|--:|
| B2 | 4 | 2 | 6 | 6 |
| B3 | 5 | 3 | 8 | 8 |
| B4 | 7 | 3 | 10 | 10 |
| B5 | 9 | 3 | 12 | 12 |

Mass flattens at 3 from B3 up because higher-bracket decks answer specific threats rather than
sweeping; targeted absorbs the growth. This mirrors the Command Zone 2025 revision, where targeted
removal nearly doubled while board wipes dropped.

**What is and is not preserved — corrected after plan review.** The sums match, so the aggregate
default budget is unchanged. Behavior is **not** unchanged, in two specific ways:

1. **Per-role pressure is new.** Counts accumulate per role
   (`CutLabAnalysisContextBuilder.cs:219`), weak-floor findings fire per role
   (`CutLabStructuralFindings.cs:261`), and cut warnings fire per broken role
   (`CutLabFloorRules.cs:112`). A deck holding 10 targeted answers and 0 wipes satisfied the old
   merged floor of 10 and now breaches `interaction-mass`.
2. **There is NO double-counting between the two roles.** An earlier draft claimed a both-role
   card could satisfy both floors with one unique card. That is void: the roles are mutually
   exclusive by construction (D-01), so every card contributes to exactly one of the two
   interaction counts and the two counts sum to the old merged count exactly. The split
   redistributes the same cards; it does not inflate them.

**This is the intended behavior, not an accepted regression.** The entire point of splitting the
role is to surface "you have twelve removal spells and no sweeper" — a composition gap the merged
floor structurally could not express. ISPL-03 is therefore worded as a budget claim, and the
regression test asserts the budget identity, not behavioral equivalence.

### D-04 — Legacy floor migration splits proportionally

`CutLabFloorRules.ClampFloors` currently drops any role key that fails `TryGetCanonicalRole`
(`:44-48`: `changed = true; continue`). A persisted user-set `interaction` floor would therefore be
**silently discarded** — the user's override lost with no warning. That is the ISPL-02 failure this
plan must prevent.

Migration rule, applied only when the legacy key is present AND `IsUserSet`:

```
targeted = round(legacyFloor * targetedDefault / (targetedDefault + massDefault))
mass     = legacyFloor - targeted
```

Subtracting for `mass` guarantees the split sums exactly to the legacy value regardless of
rounding. Both migrated entries carry `IsUserSet = true`. A legacy entry that is NOT user-set is
dropped (it was a stale default; fresh defaults supersede it).

**Mixed-payload precedence — added after plan review.** `CutLabStateSerializer.Deserialize`
(`:46`) always funnels through `ClampFloors`, and `ClampFloors` keeps the FIRST canonical entry it
sees for a role (`:40-48`, via `seenRoles.Add`). An untrusted payload can therefore contain the
legacy `interaction` key AND one or both new keys, and without an explicit rule the winner would
depend on array insertion order rather than intent. Required rule:

> If the payload contains any **user-set** floor for `interaction-targeted` or `interaction-mass`,
> those explicit new-key entries win and the legacy `interaction` entry is discarded without
> migrating. Otherwise the legacy key is migrated, **and any non-user-set entry for either new key
> is removed first so the migrated values cannot lose the dedupe race.**

The second clause was added in review round 2. Without it, a payload holding legacy `interaction`
plus a *stale non-user-set* `interaction-targeted` still resolves by array order: `ClampFloors`
keeps the first canonical entry it sees per role (`:40`, `:48` via `seenRoles.Add`), so a
stale entry appearing before the migrated one would win. Deleting non-user-set new-key entries
before inserting migrated ones removes the race entirely.

With both clauses the migration is idempotent by construction: after one pass the new keys exist
and are user-set, so a second pass takes the discard branch. An "already-migrated state is a
no-op" test does not prove this on its own — the two mixed-payload cases (user-set and
non-user-set new keys, each in both array orders) must be tested directly.

## Regression Risks

| Risk | Why it could bite | Mitigation |
|---|---|---|
| Wipes leak into the targeted role | `interactionMeritPreGate` is a superset containing wipes via BOTH the heuristic and category paths — the original plan missed the first, the round-1 revision still missed the second | D-02 mass-first subtraction incl. `HasWipeCategoryTag` + tests 1 and 2 |
| Persisted floors silently lost | `ClampFloors` drops unknown keys by design | D-04 migration + tests 9-13 |
| Mixed legacy/new payload resolves by array order | `ClampFloors` keeps the first canonical entry per role (`:40`, `:48`) | D-04 two-clause precedence rule + tests 11-12, each run in both array orders |
| Aggregate budget drifts | Split bands could stop summing to the merged floor | Test 8 asserts equality per bracket |
| Manabase taxonomy collaterally split | Same string, different concept, 10+ call sites | Scope Fence; verification step 4 |
| Per-role breaches read as a regression | Decks that passed one merged floor of 10 can now breach `interaction-mass` | Intended per D-03. The phase summary must state this plainly so UAT does not file it as a bug |
| A "both interaction roles" test gets written anyway | It is the natural thing to write for a multi-role model | D-01 forbids it explicitly; test 6 asserts the exclusivity property instead |
| Numeric count assertions missed | `toHaveCount(9)` / `Equal(8, …)` contain no searchable role keyword | Third discovery grep in Task 5 is mandatory |
| Suite fails outside the listed files | `files_modified` proved incomplete twice — vitest missed on pass 1, count assertions on pass 2 | Task 5 discovery greps run BEFORE editing; gate is whole-suite green, not "listed files updated" |
| e2e coverage quietly reduced | Easiest fix is deleting the broken tests | Task 5 requires retarget, not deletion |
