# Phase 2 Plan 11 — make the criterion-3 smoke run cheap

## Why this plan exists

Plan `02-08`'s D-06 smoke run must prove ROADMAP criterion 3: zero qualifying commanders exits 2 and
writes NO artifact. The proof is about the **placement** of the guard inside `RunAsync` — that it
precedes `BuildGoNoGo`/`WriteFindingsFiles` — which no unit test can pin, because
`RoleFloorGuards.HasNoQualifyingCommanders` is already unit-tested in Core while its CALL SITE is not.

Today that proof is extortionate. The ordering in `RoleFloorResearchCommandRunner.RunAsync` is:

```
:326  ResolveCardsAsync            <- full Scryfall pass over the whole corpus
:429  qualifyingCommanders built
:493  HasNoQualifyingCommanders -> :509 return 2
:561  BuildGoNoGo / WriteFindingsFiles
```

`--min-decks 999999` does not help: qualification is evaluated at `:429`, long after the expensive
work at `:326`. So the smoke run pays the **full 26-minute Postgres membership load and a full
Scryfall pass** before it can return 2. The 2026-07-28 attempt died at exit 1 inside a Scryfall
rate-limit window having proven nothing.

A commander cap makes the same proof cost seconds, and — with `cards_full.json` already at 20.29 MB —
likely zero Scryfall calls, which removes the rate limit from the critical path entirely.

## Design Decisions

### D-01 — cap commanders, not decks

`LoadCommanderRowsAsync` pages `GetPagedProcessedCommanderRowsAsync(page, 200, ...)` until a short
page ends it. Capping there shrinks every downstream cost at once: fewer membership queries, fewer
raw decks, fewer distinct card names, so fewer Scryfall lookups. Capping decks or cards instead would
leave the dominant per-commander membership cost untouched.

### D-02 — default unlimited; omitting the option changes nothing

The option is `int?` defaulting to `null`. When absent, the paging loop is byte-for-byte the behavior
it has today. This plan must not alter any real run.

### D-03 — a limited run MUST be labelled in provenance

This is the important one. A truncated corpus that exits 0 would write a findings artifact indistinguishable
from a full run — the same repudiation risk plan `02-08` D-07 guards against for a Postgres-only run,
and the same class of failure this whole phase exists to kill.

So when a limit is in effect, the run provenance records it explicitly, and the markdown carries a
warning line. A limited run is a diagnostic, never evidence.

### D-04 — the stop decision lives in Core

Per the standing convention that CLI logic belongs in `DeckFlow.Core` with tests in
`DeckFlow.Core.Tests`, the "should paging stop, and how many rows survive" decision goes in Core
beside the existing `RoleFloorGuards`, not inline in the paging loop. `DeckFlow.Core.Tests` already
references `DeckFlow.CLI` and `InternalsVisibleTo("DeckFlow.Core.Tests")` exists, so this is testable
either way — put it in Core because that is where the convention says it goes.
