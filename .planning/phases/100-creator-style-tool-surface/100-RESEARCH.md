### Locked Decisions

- **D-100-01:** Profiles reach Render via a **git-shipped seed artifact** — no Postgres migration, no DirectPush this cycle. Deploy = update.
- **D-100-02:** Seed contains **fused profiles AND creator deck-cache rows** (exemplars/whitelist inputs) — full engine read-path parity between local and prod. Live APIs (Scryfall guard, Spellbook) and prod-crawled `category-knowledge.db` are NOT part of the seed.
- **D-100-03:** Seed format is **JSON files in repo** (diffable, no binary churn — public repo), hydrated into the prod-local store at startup, mirroring the `ContentKbSeedLoader` pattern in `Program.cs`.
- **D-100-04:** Seed generated by a **new DeckFlow.CLI export command**, run manually after crawl/fusion; user commits the output. No Studio UI work, no build-time export.
- **D-100-05:** **Single flag `tool.creator-style.enabled`** (ToolRegistry convention) gates everything — tool visibility AND cache-bypass registration. The roadmap name `creator.style-artifact` is retired as an alias; requirements/roadmap references map to this one key. Seeded OFF on both dialects; operator flips in /Admin/Flags.
- **D-100-06:** Creator-style packet **uses `PacketSessionCache`** and registers its flag in the service's own prompt-mutating cache-bypass list, following the `DeckAnalysisPacketService.PromptMutatingAnalysisFlags` pattern (satisfies roadmap success criterion 3; saves repeat throttled Scryfall/Spellbook calls).
- **D-100-07:** OFF state = tile/nav hidden + route 404 + **SeoPaths/sitemap gated on the flag** — the sitemap must NOT advertise `/creator-style` while it 404s (fixes the deck-history quirk).
- **D-100-08:** Phase-99 review backlog: **fold the cheap user-facing correctness items** — IN-01 (epsilon verdict compare), IN-03 (degraded-notice wording branches on excludedCount), IN-04 (unavailable ≠ degraded status), IN-08 (exemplar dedup) — into Phase 100. - **D-100-09:** Creator picker = **dropdown listing only creators present in the store**, each labeled with evidence depth (e.g. "34 decks · 12 videos"). Picker is the source of truth — no free-text creator entry.
- **D-100-10:** Deck input **reuses the standardized import component** (site dropdown + URL/paste toggle) used by meta-gap/comparison. Known backlog caveat: deck-input-store restore desync applies to all split-input tools — do not fix here, just inherit.
- **D-100-11:** **Single form → result** page structure (meta-gap/manabase shape). No `_WorkflowStepTabs` multi-step strip.
- **D-100-12:** Tile in **Analyze section**, craft-first copy: lead with measured build style + real exemplars ("critique your deck against a creator's measured build style"); AI mention limited to "ChatGPT-ready packet". **No creator-crawl/KB-sourcing claims in copy** (standing legal/messaging rule).

- **D-100-14:** **ChatGPT-only arm at ship.** No Claude/Gemini prompt variants this cycle (ADR-0001 makes each arm hand-maintained; add arms after the tool proves value).
- **D-100-15:** Grounding degradation → **deliver packet + visible warning banner** above it. Notice wording branches per IN-03: cards-withheld text only when exclusions actually occurred; upstream-outage text otherwise.
- **D-100-16:** Profile-unavailable is a **distinct state, never dressed as grounding degradation** (IN-04). Empty store in prod → page shows a clear "no creator profiles loaded" state instead of the form.

## Project Constraints (from CLAUDE.md)

- **Tech stack pinned**: ASP.NET 10 + Razor, no framework migration.
- **512MB Render web-tier RAM cap** — the new seed loader adds one more startup hydration pass (mirroring `ContentKbSeedLoader`); keep it a single streaming JSON deserialize, not an in-memory multi-copy.
- **RestSharp + Polly v8 pattern only** — do not introduce a new HTTP client shape; Phase 99 code already uses the existing Scryfall/Spellbook services, Phase 100 adds no new HTTP egress.
- **Guild theme CSS**: layout CSS → `site-common.css` only; any new custom property goes in `:root` of **all 15** theme files (per UI-SPEC).
- **No secrets in commits** — the JSON seed files (D-100-03) contain creator deck data (public Archidekt decklists) and fused profile numbers, not secrets; safe for the public repo, but must not accidentally include `category-knowledge.db` or transcript-derived local-only content per D-100-02.
- **Testing**: WSL VSTest unreliable; xUnit + `dotnet build` clean is the gate; UI testing must never open a Windows browser — `scripts/run-web-test.sh` + `npx --no-install playwright test`.
- **LF line endings** enforced by `.gitattributes`; new `.cs`/`.ts`/`.cshtml`/`.json` files must be LF.
- **Commits**: plain default-author, no Co-Authored-By trailer; README updated when behavior changes; commit per logical change.
- **Formatting**: `.editorconfig` changed-lines gate; five carve-outs apply (`{ get; init; }` never collapsed to `{ get; }` — directly relevant, since `CreatorDeckCacheEntry`/`CreatorStyleProfile`/`FusedTarget` all use `{ get; init; }` and will round-trip through the new JSON seed loader exactly like `ContentKbSeedLoader`'s `ContentSiteIndexRow`).
- **No new packages without approval** — this phase needs none; everything (System.Text.Json, System.CommandLine, xUnit, Playwright) is already a project dependency.
- **GSD workflow enforcement** — this phase must be executed via `/gsd:execute-phase`, not ad-hoc edits.

## Summary

Phase 100 is a pure **wiring phase**: every piece of business logic it needs (rubric scoring, whitelist/grounding, exemplar selection, artifact text assembly) already exists and is fully tested from Phase 99 (`DeckFlow.Web/Services/CreatorStyle/CreatorStylePacketService.cs`, confirmed already fixed for the two CR-01/CR-02 correctness defects flagged in `99-REVIEW.md` — superseded/conditional target filtering and zeroed-Karsten-metric fabrication are both resolved in the current `BuildAsync`). What Phase 100 must build is: (1) a `CreatorStyleController` + `CreatorStyle.cshtml` view following the `ManabaseController`/`Manabase.cshtml` pattern almost exactly (not `DeckComparison.cshtml` — see Pitfall 1 below); (2) a new flag `tool.creator-style.enabled` seeded OFF in `FeatureFlagStore.cs` on both Postgres and SQLite seed blocks, cataloged in `FeatureFlagCatalog.cs`, registered in `ToolRegistry.cs`, and applied via `[FeatureFlagGate("tool.creator-style.enabled")]`; (3) net-new `PacketSessionCache` wiring inside `CreatorStylePacketService` (it currently has none) mirroring `DeckAnalysisPacketService`'s read-side/write-side latched-local bypass pattern; (4) a net-new seed-hydration mechanism for `ICreatorStyleProfileStore` (local-only `content-kb.db`) and `ICreatorDeckCacheStore` (provider-aware `creator-deck-cache.db`) that mirrors `ContentKbSeedLoader` but targets two different stores/files; (5) a new `DeckFlow.CLI` export command mirroring `content-index-export` exactly; (6) sitemap gating — but the codebase does **not** have the `SeoPaths` class CONTEXT.md's canonical_refs assume (see Pitfall 2); and (7) the full xUnit+Playwright+README bundle following `tool-toggles.spec.ts`/`manabase.spec.ts`/README `## Highlights` conventions.

A critical branch-state finding: this working tree (`plan/cycle-17-creator-style`) diverged from `main` long before the SEO-structured-data work (`SeoPaths`, `StructuredDataBuilder`), the Deck-History phase, and the Cut-Lab cycle-18 work landed on `main`. `SitemapController` on this branch still uses a hardcoded static `IndexablePaths` string array that does not even include `/manabase` or `/bracket` (both already-shipped tools) — it predates those tools and was never kept in sync. The planner must NOT plan around a `SeoPaths` class that does not exist in this tree; the correct, self-contained fix is to make `SitemapController.IndexablePaths` (or a small flag-gated addition to it) consult `IFeatureFlagCache` directly for the one new entry.

**Primary recommendation:** Build `CreatorStyleController : DeckToolControllerBase` (single action pair: GET `/creator-style` empty form, POST `/creator-style` build+render) plus `Views/Deck/CreatorStyle.cshtml` cloned from `Manabase.cshtml`'s structure (hero → `_DeckToolTabs` → single `<form>` with the `DeckInputSource`/`data-sync-panel` toggle already matching `CreatorStyleRequest`'s existing shape → creator `<select data-df-select>` populated server-side from `ICreatorStyleProfileStore` → result panel with warning/info/error banners → `<textarea readonly>` + `.copy-button`). Wire the flag through all four required touch points (`ToolRegistry`, `FeatureFlagStore` seed ×2 dialects, `FeatureFlagCatalog`, `[FeatureFlagGate]`) in the same commit so no touch point is missed (a common miss pattern verified against `FeatureFlagCatalogTests` which fails the build if any seeded key lacks a catalog description).

### Pattern 3: Prompt-mutating flag → PacketSessionCache bypass (net-new for CreatorStylePacketService)

**What:** `DeckAnalysisPacketService` maintains a static `PromptMutatingAnalysisFlags` array and two coordinated methods: `ShouldBypassPacketCache()` (read-side, used in `TryComputeCacheKeyAsync` to skip cache lookups) and a build-time **latched local** (read once at the top of `BuildAsync`, reused at the write site) so a mid-request flag flip cannot desync the enrichment decision from the cache-write decision. `CreatorStylePacketService` currently has **no** `PacketSessionCache` reference at all — this is 100% new code, not a copy of existing wiring.
**When to use:** Adding cache-bypass to `CreatorStylePacketService.BuildAsync`.
**Example:**
```csharp
// Source: DeckFlow.Web/Services/DeckAnalysisPacketService.cs:159-166, 344-364 — pattern to replicate
internal static readonly IReadOnlyList<string> PromptMutatingCreatorStyleFlags = new[]
{
    "tool.creator-style.enabled",
};

private bool IsCreatorStyleFlagOn(string flagKey)
    => _flagCache is not null && _flagCache.Snapshot().TryGetValue(flagKey, out var on) && on;

private bool ShouldBypassPacketCache()
    => PromptMutatingCreatorStyleFlags.Any(IsCreatorStyleFlagOn);
```

### Anti-Patterns to Avoid

- **Building a second multi-step wizard:** D-100-11 explicitly forbids `_WorkflowStepTabs`. `_DeckToolTabs` (the persistent cross-tool nav strip) is a *different* partial and MUST still be included — every sibling tool page renders it. Do not confuse the two.
- **Assuming `SeoPaths` exists:** It does not on this branch (see Pitfall 2). Do not write a plan step that edits a nonexistent file.
- **Re-deriving the URL/paste toggle from `DeckComparison.cshtml`:** that view has no toggle at all (two static textareas). Use `Manabase.cshtml` as the toggle template (Pattern 2).
- **Seeding the flag in only one dialect's SQL block:** `FeatureFlagStore.cs` has two independent string constants (`PostgresSeedSql`, `SqliteSeedSql`); CS-30 explicitly requires both.
- **Forgetting `FeatureFlagCatalog.Descriptions`:** `FeatureFlagCatalogTests` asserts every seeded key has a non-empty description — the build's test suite fails, not just a lint warning.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |

## Common Pitfalls

### Pitfall 1: UI-SPEC's "closest sibling" for deck-input columns is imprecise

**What goes wrong:** `100-UI-SPEC.md` names `DeckComparison.cshtml` as the template for the `.sync-columns`/`data-sync-panel` toggle. Direct inspection shows `DeckComparison.cshtml` has **no** `data-sync-panel` toggle at all — it has two static textareas (Deck A / Deck B) inside a `.sync-columns` two-column CSS layout, with no URL/paste mode switch. The actual `data-sync-panel` + `<select data-df-select>` URL/paste toggle pattern lives in `Manabase.cshtml` (and `DeckAnalysis.cshtml`, `DeckPrimer.cshtml`, `Bracket.cshtml`, `DeckSync.cshtml`, `DeckConvert.cshtml`, `SuggestCategories.cshtml`).
**Why it happens:** `DeckComparison.cshtml` does use `.sync-columns`/`.sync-column` CSS classes, but for a *different* purpose (laying out two decks side by side), which is a surface-level name match to what the UI-SPEC was looking for.
**How to avoid:** Use `Manabase.cshtml` as the deck-input toggle template (single deck, matches `CreatorStyleRequest`'s existing `DeckInputSource`/`DeckUrl`/`DeckText` shape exactly). This does not violate the UI-SPEC's *intent* (reuse the standardized `data-sync-panel` toggle) — it corrects which existing file actually contains that toggle.
**Warning signs:** If a plan step says "copy the sync-columns block from DeckComparison.cshtml for the toggle," it will produce two static textareas with no mode switch, contradicting D-100-10's "URL/paste toggle" requirement.

### Pitfall 2: `SeoPaths` does not exist on this branch — CONTEXT.md/UI-SPEC reference code that isn't here

**What goes wrong:** CONTEXT.md's canonical_refs and the UI-SPEC assume a `SeoPaths` class exists for sitemap gating (`SeoPaths (DeckFlow.Web) — SEO/sitemap path registry; must become flag-aware`). A repo-wide grep confirms `SeoPaths` does not exist anywhere in this working tree. `git log --all` shows `SeoPaths` was introduced in commits (`ca1c9176`, `1ba66b8d`, etc.) that live on `main` but are **not ancestors of the current `plan/cycle-17-creator-style` branch** — this branch diverged from `main` before that SEO work (and before the Deck-History phase and Cut-Lab cycle-18) landed. `git log --oneline main..HEAD` / `HEAD..main` shows hundreds of commits of divergence in each direction.
**Why it happens:** The `100-CONTEXT.md` and `100-UI-SPEC.md` documents were likely written with awareness of the intended target state of the codebase (possibly cross-referencing `main` or memory of other work), not this specific branch's actual file tree.
**How to avoid:** Do not plan a step that edits `SeoPaths.cs`. Instead, directly modify `DeckFlow.Web/Controllers/SitemapController.cs`: inject `IFeatureFlagCache`, and gate the `/creator-style` entry (add it to a small flag-checked addendum rather than the static array, or filter the whole array through a small per-path flag-key lookup). Note also that the *existing* `IndexablePaths` array does not include `/manabase` or `/bracket` (both shipped, and `/manabase` is default-ON) — the sitemap is already stale/hand-maintained and not synchronized with `ToolRegistry`. The safest, most scoped fix satisfying CS-30/D-100-07's actual acceptance bar ("must NOT advertise `/creator-style` while it 404s") is: only add `/creator-style` to the sitemap output when `tool.creator-style.enabled` is true; do not attempt a full `ToolRegistry`-driven sitemap refactor as part of this phase (out of scope, larger blast radius).
**Warning signs:** Any plan step referencing `SeoPaths.cs`, `SeoPaths.Tools`, `SeoPaths.Normalize`, or `IsShareablePage` will fail — none of these exist in this tree yet. If the user wants the full `main`-branch SEO infrastructure available, that requires an explicit rebase/merge decision outside this phase's scope — flag to the user before planning assumes it.

### Pitfall 3: ROADMAP.md/STATE.md phase-tracking metadata is stale relative to actual code

README.md even has a `### Creator measured-style extractor (substrate)` Highlights bullet already documenting Phase 95's crawler.
**Why it happens:** STATE.md's Roadmap Summary table appears to not have been updated as phases were executed via a different session/branch flow, even though the phase-completion commits and code are present.
**How to avoid:** Ground all "does X exist" questions in code (`grep`/`find`), never in STATE.md's summary table alone, for this milestone. The planner should treat Phases 94-99 as **fully implemented and available** substrate, not as risk/blocked items.
**Warning signs:** A plan step that says "first verify Phase 95's crawler exists" or treats the measured-extractor/distiller/fusion pipeline as unbuilt would be redundant — it is built, tested, and DI-registered already.

### Pitfall 4: `ICreatorStyleProfileStore` has no "list all creators" query — needed for the picker (D-100-09)

**What goes wrong:** The interface only exposes `GetBySlugAsync(slug, ct)` and `UpsertAsync(profile, ct)` — there is no method to enumerate all stored creator slugs (with `MinDecks`/evidence-depth data) for the dropdown. D-100-09 requires the picker to be populated *only* from creators actually present in the store, each labeled "N decks · M videos."
**Why it happens:** Phase 94's store was designed around single-slug lookup for the packet-building read path; a listing query was never a Phase 94-99 requirement (those phases only ever read one profile at a time).
**How to avoid:** Plan a small, additive interface change: `Task<IReadOnlyList<CreatorStyleProfileSummary>> GetAllAsync(ct)` (or similar) on `ICreatorStyleProfileStore`, implemented in `CreatorStyleProfileStore` (Core). Note the video-count half of "N decks · M videos" is NOT on `CreatorStyleProfile` at all (it has `MinDecks` but no video count) — that data lives in `ContentVideoStore`/`ContentSiteIndexStore` keyed by source, so the picker's evidence-depth label needs a join across two stores, or a deliberately simpler label using only `MinDecks` (deck count) if video count is judged not worth the extra query. Flag this precisely for `discuss-phase`/planning — it's a genuine open design point, not just an implementation detail.
**Warning signs:** A plan step that calls `GetAllAsync` on `ICreatorStyleProfileStore` today will not compile — the method does not exist.

### Pitfall 5: The `tool.creator-style.enabled` cache-bypass wiring (D-100-06) has an unusual self-referential shape — verify intent before implementing literally

**What goes wrong:** In every existing precedent (`PromptMutatingAnalysisFlags` on `DeckAnalysisPacketService`), the bypassed flags are *content-mutating tuning flags* distinct from the tool's own visibility flag — e.g. `analysis.multi-axis-score` changes what's IN the packet while `tool.deck-analysis.enabled` controls whether the page is reachable at all. D-100-06 asks for the SAME flag (`tool.creator-style.enabled`) to be both the visibility gate AND the sole entry in the packet's cache-bypass list. Since the route 404s entirely while the flag is OFF, no request can ever reach `BuildAsync` in the OFF state — so the practical effect of the bypass-while-ON rule is that Creator-Style packets are simply **never cached** for the lifetime of this phase (cache bypass is unconditionally true whenever the tool is reachable at all).
**Why it happens:** The single-flag topology (D-100-05) collapses what would normally be two independent flags (visibility + content-tuning) into one, and the cache-bypass wiring pattern was specified by analogy to `DeckAnalysisPacketService` without an intermediate content-mutating flag to actually bypass on.
**How to avoid:** This is very likely *intentional and correct* — D-100-06's stated rationale ("saves repeat throttled Scryfall/Spellbook calls") is still served by `PacketSessionCache`'s *primary* purpose within a single browser session's re-navigation/resubmission (e.g., the same deck+creator combo posted twice in one session), and the explicit non-goal is caching *across* a flag flip (flip OFF then back ON should never replay a stale pre-flip packet). Implement it as specified: register `tool.creator-style.enabled` as the sole `PromptMutatingCreatorStyleFlags` entry, effectively meaning caching is a no-op today. This keeps the architecture consistent with `DeckAnalysisPacketService` and trivially extensible if a future content-mutating creator-style flag is added later (e.g. rubric-weighting tuning). Do not "optimize" by skipping the bypass-list wiring on the theory that it's currently a no-op — CS-30 requires it explicitly and it is cheap.
**Warning signs:** None functionally — this is a documentation/understanding risk for the planner, not a code risk. Worth one line in the plan's rationale so a future reviewer doesn't "fix" the apparent redundancy.

### Pitfall 6: `LookupTimeout` (20s) may be too tight for the creator-style pipeline's heavier upstream fan-out

**What goes wrong:** `DeckToolControllerBase.LookupTimeout` = 20 seconds is used verbatim by `ManabaseController`. Creator-style's `BuildAsync` does strictly more upstream work per request than Manabase: deck load + Scryfall resolve (same as Manabase) **plus** a Commander Spellbook combo lookup, **plus** a whitelist-pool grounding batch, **plus** a second additional-candidates grounding batch (exemplar cards + combo cards) — all funneled through the shared `ScryfallThrottle` (~5 req/s global gate shared across the whole process, per `Program.cs` comments), which serializes with any other concurrent Scryfall-using request site-wide.
**Why it happens:** The 20s constant was sized for Manabase's single Scryfall-resolve pass; Creator-Style's pipeline (documented in the Architecture Diagram above) issues multiple additional network round-trips in sequence.
**How to avoid:** Either reuse `LookupTimeout` as a starting point and verify empirically during implementation/UAT that it's sufficient (Salubrious Snail's ~39-deck sample keeps `GetByCreatorAsync` cheap since it's a local read, so the bottleneck is Scryfall/Spellbook calls, not deck-cache size), or size a slightly larger dedicated timeout constant for this controller. Flag as a build-time/UAT check rather than a blocking research unknown.
**Warning signs:** e2e or manual UAT sees frequent `OperationCanceledException` → "took too long to load" error banner on the creator-style form under real network conditions.
