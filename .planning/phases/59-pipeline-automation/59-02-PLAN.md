## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator UI → settings file | operator-entered on/off + cutoff persisted to local disk |
| settings file → app at startup | a file an attacker with local FS access could edit is read back |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-59-03 | Tampering | auto-approve-settings.json | mitigate | Load() validates/falls back to safe defaults (Enabled=true, Cutoff=5) on corrupt/unparseable input AND semantically clamps a parsed-but-invalid cutoff (negative→DefaultCutoff, >MaxCutoff→MaxCutoff) — never throws to the UI; the two stored values are non-sensitive scalars only |
| T-59-04 | Information Disclosure | auto-approve-settings.json | mitigate | Acceptance gate confirms only the two scalar settings are written — no secrets/connection strings in the file (public-repo + secrets-in-dashboard rule). File lives under the operator-local studio data dir, not the repo. |
| T-59-05 | Elevation of Privilege | cutoff = 0 path | accept | A cutoff of 0 auto-approves every distill, but auto-approve only sets approval_status — publish is a separate, operator-confirmed gate (Plan 03 / existing Publish flow). Operator-chosen risk on a single-operator local tool. A NEGATIVE cutoff can no longer reach the signal (clamped to DefaultCutoff on load/save). |
| T-59-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages (System.Text.Json already present); in-solution only. Format/CarveOut gates on changed lines. |
</threat_model>
