# Phase 01.1 Plan 02 — Bug 2: protection is invisible to the oracle-text heuristic

## Why This Plan Exists

`PlanRoleClassifier.FromHeuristic` (`:171-205`) consults four signals:
`IsClosingPowerCard` → Payoff, `IsTutorCard` → TutorCombo, `GrantsInteraction` → Interaction, and
`IsDrawCard` (permanent-gated) → Engine. `GrantsInteraction` (`:214-227`) is built from
`IsInteractionCard`, `IsBoardWipeCard` and `IsTargetedRemovalCard` — **removal, wipes and counters
only**.

`DeckStatClassifier.IsProtectionCard` is never called from this file at all. Cut Lab calls it
directly for its own `protection` role (`CutLabRoleAssigner.cs:165`), and
`InteractionAuditAggregator.cs:58` calls it — but the shared plan-role classifier does not. The
consequence: a protection effect earns `PlanRole.None` from the heuristic tier and registers as
Interaction only when the deck happens to carry a crowd `protection` tag, because
`IsInteractionCategory` (`:242`) matches the needle `"protect"`.

That is a real asymmetry: **the category path already treats protection as interaction; the oracle
path does not.** This plan closes it.

Phase 2 measures interaction floors per commander through `CutLabRoleAssigner`, which consumes this
classifier's `interactionMeritPreGate`. Leaving protection invisible to the oracle tier makes a
commander's measured interaction floor a function of how diligently its playerbase tags cards, which
is exactly the corpus artifact Phase 2 is trying to avoid.

## Design Decisions

### D-01 — Wire it into `GrantsInteraction`, not alongside it in `FromHeuristic`

`GrantsInteraction`'s xmldoc already claims to answer "whether a card earns `PlanRole.Interaction`
from the oracle-text heuristic". Adding a second, parallel Interaction disjunct in `FromHeuristic`
would make that doc a lie and split one decision across two places.

`IsProtectionCard(string name, string oracleText)` needs the card NAME (its first arm is
`StaxProtectionCatalog.IsProtection(name)`), which `GrantsInteraction` does not currently receive.
Extend its signature to `GrantsInteraction(string name, string typeLine, string oracle, ManabaseMode mode)`.
The method is `private static` with exactly one call site, so the signature change is contained.

### D-02 — NOT mode-gated

The counterspell carve-out exists because a casual counter is reactive insurance. Protection has a
similar shape, so mode-gating it is a fair question. It is rejected for one concrete reason:
`IsInteractionCategory` maps the `"protect"` tag to `PlanRole.Interaction` **unconditionally in both
modes** today (`FromCategories`, `:140-143`). Mode-gating the oracle arm would create a new
inconsistency in the act of fixing an old one — the same card would be Interaction in Casual when
tagged and not when untagged.

Protection is therefore an unconditional disjunct, placed AFTER the mode-sensitive
`interactionMerit` term so the existing short-circuit ordering comment stays accurate.

### D-03 — NO extra type gate inside `FromHeuristic`

`IsProtectionCard` does **not** assume a permanent — it is a pure name+oracle predicate, and every
one of the seven names in `StaxProtectionCatalog.ProtectionCards` (Boros Charm, Clever Concealment,
Deflecting Swat, Flawless Maneuver, Heroic Intervention, Teferi's Protection, Veil of Summer) is an
**Instant**.

Adding a type gate here would violate the architecture the file already documents at `:78-80`:

> the lower-level FromCategories/FromHeuristic detectors stay type-agnostic; the type rule lives
> here, at the single service entry.

The existing `PermanentOnlyRoles` gate in `Classify` (`:81-84`) strips Interaction from a
non-permanent front face, which handles all seven curated instants correctly with no new code. Both
mechanisms this signal flows through are covered by that one gate:

| Mechanism | Handled by the existing gate? |
|---|---|
| `Classify` → returned `PlanRole` | Yes — Interaction stripped for non-permanent fronts (`:81-84`) |
| `Classify` → `out interactionMeritPreGate` | Deliberately PRE-gate by contract (`:70`), and its consumers apply their own rules — see D-04 |

### D-04 — The pre-gate out-parameter is where the real blast radius lives

`interactionMeritPreGate` is set at `:70` from the ungated roles and flows to three consumers:

| Consumer | Effect of a protection permanent now setting the flag |
|---|---|
| `CutLabRoleAssigner.cs:153-158` | The card gains `interaction-targeted` **in addition to** `protection` (`:165`). |
| `ManabaseAnalysisService.cs:889-897` | `SpellRequirement.IsInteractionSpell = true`, consumed by `CastabilitySimulator` (keep-shape gate, `:557`, `:692`, `:700`) and `ManabaseAnalyzer.cs:364`. |
| `CutLabSimulationService.cs:456` | Same as above, with an empty category list, so this path is heuristic-only and sees the full delta. |

**This is not a new class of behavior.** A card tagged `Protection` already produces exactly this
double assignment today via the category path. The fix makes untagged protection permanents behave
like tagged ones. It is still a measurable output change and D-05 governs how it is accepted.

### D-05 — Measured delta: which cards actually flip

The delta is much narrower than "all protection cards", and knowing why prevents over-fitting the
tests.

`IsProtectionCard` fires on: the 7 curated names, or oracle text containing `gains hexproof`,
`gains indestructible`, `gain protection from`, or `phases out`.

- All 7 curated names are Instants. An Instant already satisfies `IsInteractionCard`
  (`DeckStatClassifier.cs:89`, `typeLine.Contains("Instant")`), so it is ALREADY Interaction
  pre-gate in both modes. **The curated-name arm contributes zero delta today.**
- The text arm only produces a delta on cards that are (a) not Instants, and (b) not already caught
  by removal/wipe detection. In practice: permanents that grant protection.

Cards in the committed test fixtures that flip, found by scanning
`DeckFlow.Web.Tests/Manabase/fixtures/*.json` for those four phrases:

| Fixture | Card | Type | Flips? |
|---|---|---|---|
| `.manabase-arch-7084567-facts.json` | Kytheon, Hero of Akros // Gideon, Battle-Forged | Legendary Creature | **Yes** — permanent front, gains indestructible |
| `.manabase-arch-7084567-facts.json` | The One Ring | Legendary Artifact | **Yes** — "you gain protection from everything" |
| `.manabase-arch-7084567-facts.json` | Plaza of Heroes | Land | Verify — lands are not in `deck.Spells`, so expected NO effect |
| `.manabase-arch-7084567-facts.json` | Brave the Elements, Flawless Maneuver, Teferi's Protection | Instant | No — already Interaction pre-gate |
| `.manabase-arch-23753514-facts.json` | Heroic Intervention, Deflecting Swat | Instant | No |
| `.manabase-arch-8066726-facts.json` | Heroic Intervention, Revitalizing Repast // Old-Growth Grove | Instant | No |
| `.manabase-brago-facts.json`, `.manabase-brago-promote-facts.json` | Loran's Escape | Instant | No |

`.manabase-arch-7084567-facts.json` is consumed by
`DeckFlow.Web.Tests/Manabase/ManabaseHealthBandRegressionTests.cs:84`, which asserts the health bands
`("Solid", "Solid")`. **That assertion is the most likely thing in the repo to break.** If it does,
the band change is a genuine product change and goes to the Task 3 checkpoint — it is not to be
edited into agreement.

### D-06 — Known limitation the wiring does NOT fix (must be reported, must NOT be fixed here)

The spike named Swiftfoot Boots, Lightning Greaves, Hexing Squelcher and Goblin Chirurgeon as
protection cards scoring `None`. Wiring `IsProtectionCard` **does not rescue those specific cards**,
because `IsProtectionCard`'s own vocabulary requires the verb form `gains hexproof` /
`gains indestructible` / `gain protection from` (plural-subject "gain", not singular "gains"):

- Swiftfoot Boots — "Equipped creature **has** hexproof and haste." No match.
- Lightning Greaves — "Equipped creature **has** haste and shroud." No match (and shroud is not in
  the vocabulary at all).
- Goblin Chirurgeon — regeneration. Not in the vocabulary.
- **Mother of Runes** (found during Codex plan review of this phase; real card in
  `.manabase-arch-7084567-facts.json`) — "{T}: Target creature you control **gains** protection from
  the color of your choice until end of turn." The vocabulary matches `"gain protection from"`
  (plural-subject verb) but NOT `"gains protection from"` (singular-subject verb, used when the
  ability targets one creature rather than "creatures you control"). Same root cause as the
  hexproof/indestructible gap above, on the `protection from` phrase specifically.

Widening `IsProtectionCard` is a `DeckFlow.Core` change that would simultaneously move
`InteractionAuditAggregator.cs:58` and Cut Lab's `protection` role (`CutLabRoleAssigner.cs:165`) — a
materially larger blast radius than this phase's stated scope, and one that deserves its own
corpus-backed vocabulary decision.

**Required of this plan:** measure it and report it at the Task 3 checkpoint. **Forbidden of this
plan:** editing `DeckStatClassifier.IsProtectionCard` or `StaxProtectionCatalog`.
