## Cache key composition

### Q1: Which fields go INTO the cache key for `DeckAnalysisRequest`?

| Option | Description | Selected |
|--------|-------------|----------|
| Only Scryfall-pipeline inputs | Hash {DeckSource normalized + IncludeCardVersions + side/maybe flags + Commander + TargetAiPlatform.Key + SelectedQuestionIds}. Exclude WorkflowStep, *ResponseJson, parsed-response objects, ImportWarning. | ✓ |
| Entire request serialized | Hash whole DeckAnalysisRequest after JSON-serialize. Zero risk of missing a field, but WorkflowStep + ResponseJson change between preview and download = 100% false-miss. | |
| Hash BuildAsync outputs (post-resolution inputs) | Most accurate but only saves Scryfall pipeline cost, not deck-fetch cost. | |

**User's choice:** Only Scryfall-pipeline inputs
**Notes:** Drives D-01. Round-trip paste of AI response in Step 3 still hits cache because WorkflowStep + *ResponseJson are excluded.

### Q2: URL vs paste of same deck — same cache entry or different?

| Option | Description | Selected |
|--------|-------------|----------|
| Normalize DeckSource before hashing | URL→canonical-text resolution before hash. Same deck = same key regardless of input mode. | ✓ |
| Hash raw DeckSource + DeckInputSource | Cheaper compute. URL vs paste = two entries. Acceptable false-miss. | |
| You decide | Planner picks based on importer cache layering. | |

**User's choice:** Normalize DeckSource before hashing
**Notes:** Drives D-02.

### Q3: Hash algorithm + format?

| Option | Description | Selected |
|--------|-------------|----------|
| SHA-256 hex of canonical-JSON | System.Text.Json deterministic + SHA256.HashData. ~64-char keys. | ✓ |
| MD5 / FNV-1a | Faster, smaller. Algo inconsistency with rest of codebase. | |
| String-concat pipe-delimited | Zero hash compute; pipe-in-deckname escaping bugs. | |

**User's choice:** SHA-256 hex of canonical-JSON
**Notes:** Drives D-03.

### Q4: Key scope — global or per-user/session?

| Option | Description | Selected |
|--------|-------------|----------|
| Global | User A's preview can serve User B's download for same deck. Matches existing global caches. | ✓ |
| Per-IP-hash | Salt with request IP. Defeats most cache value. | |
| Per-session | Salt with ASP.NET session. Cleanest privacy, lowest hit rate. | |

**User's choice:** Global
**Notes:** Drives D-04.

## TTL + eviction policy

### Q1: How long does a cached BuildAsync result live?

| Option | Description | Selected |
|--------|-------------|----------|
| 5 min absolute | Matches typical preview→download flow + 5-min handler-lifetime invariant. | ✓ |
| 2 min sliding | Hot-key memory creep risk. | |
| 10 min absolute | More forgiving but more memory pressure. | |
| 60s absolute | Too tight for actually reading the preview. | |

**User's choice:** 5 min absolute
**Notes:** Drives D-05. Aligns with `ScryfallTaggerHttpClient.SetHandlerLifetime` (5 min) per `Program.cs:83-95`.

### Q2: Memory ceiling — dedicated cache or share existing IMemoryCache?

| Option | Description | Selected |
|--------|-------------|----------|
| Dedicated MemoryCache instance with SizeLimit | Separate `new MemoryCache(SizeLimit=N)` for packet results. ~10MB ceiling. | ✓ |

| Share existing IMemoryCache, rely on TTL only | Unbounded under spam load. | |

**User's choice:** Dedicated MemoryCache instance with SizeLimit
**Notes:** Drives D-06. Comment at `CardLookupCache.cs:10` confirmed the shared singleton has no SizeLimit.

## Cache miss fallback on download

### Q1: Download cache miss — what happens?

| Option | Description | Selected |
|--------|-------------|----------|
| Silently run BuildAsync | Today's behavior on fall-through. Cache is pure optimization. | ✓ |
| Return 'session expired' error, force re-preview | Terrible UX for bookmarked download URLs. | |
| Try cache, fall through, flag in X-DeckFlow-Cache header | Observability via header instead of log. | |

### Q2: Stampede on concurrent same-key submits?
