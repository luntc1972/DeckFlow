## 1. System Classification

**System Type:** Extraction (bounded, stateless structured extraction — not agent/RAG/multi-step orchestration)

**Description:**
A local CLI `distill` step that turns each harvested YouTube transcript into structured outputs via three isolated OpenAI `gpt-4o-mini` strict-`json_schema` calls (summary ≤200 words, 3–8 timestamped clips, controlled-vocab tags). Output is written as a markdown AI-prompt artifact file (`ContentArtifactSpec` format) plus a slim site-index row. Used by the site operator (admin) to build the Content KB the ChatGPT deck-analysis workflow draws on. "Good" = artifacts whose summary/clips/tags faithfully reflect the video, parse reliably (<0.1% failure), and carry only allowlisted tags.

**Critical Failure Modes:**
1. **Structured-output parse failure** — model returns malformed/non-schema JSON, breaking persistence. Mitigated by strict `json_schema` (PITFALLS P4, <0.1% target).
2. **Out-of-vocabulary tags persisted** — LLM invents tags outside `ContentTagVocabulary`; must be rejected with WARN, never stored or indexed.
3. **Hallucinated summary/clips** — content not grounded in the transcript (fabricated claims, wrong timestamps) that then feeds the ChatGPT workflow.
4. **Uncapped spend** — runaway LLM cost; must respect the separate LLM spend cap and abort with a recorded reason.
5. **Non-idempotent re-runs** — re-distilling already-completed videos, wasting spend and double-writing rows/artifacts.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Tabletop gaming content / Magic: The Gathering (Commander & cEDH strategy media)

**User Population:** Serious Commander/cEDH deck-builders — the DeckFlow audience (CLAUDE.md Project). They consume the distilled artifact indirectly: it seeds a ChatGPT deck-analysis prompt, so the reader is a strategy-literate player who already knows what voltron, stax, or a bracket-4 list looks like and will notice when a tag is wrong.

**Stakes Level:** Low-to-Medium — hobby/strategy content. A wrong tag or fabricated summary degrades trust in the KB and can misdirect deck advice, but there is no safety, financial, legal, or privacy harm. The downside is "the tool looks like it doesn't understand the game," which is reputationally costly for a tool whose audience is expert players.

**Output Consequence:** Each artifact (≤200-word summary + 3–8 timestamped clips + archetype/bracket/card_category tags) becomes a row in the Content KB and feeds a ChatGPT deck-analysis prompt. A mislabeled archetype, an inflated bracket, or a hallucinated combo claim flows straight into the advice ChatGPT gives the deck-builder — the artifact is treated as ground truth downstream, not re-verified.

### What Domain Experts Evaluate Against

```
Dimension: Archetype fidelity
Good: The archetype tag(s) match the deck's actual primary game plan as described in the video (e.g. a sacrifice-payoff list tagged `aristocrats`; a commander-damage suit-up list tagged `voltron`). When the video discusses a hybrid (aristocrats+tokens, lands+ramp), the dominant plan is tagged, secondary plan optional.
Bad: Tagging by surface keyword rather than game plan — e.g. tagging `ramp` because the host says "ramp" once, or calling a midrange goodstuff list `combo` because a combo is name-dropped. Inventing an archetype the video never frames the deck as.
Stakes: High
Source: Practitioner archetype taxonomy (Spellweave/Draftsim EDH archetype guides); decks anchor on one primary archetype with optional secondary — keyword presence is not classification.
```

```
Dimension: Bracket accuracy (Wizards Feb 2025 5-bracket system)
Good: Bracket tag reflects the power tier the video actually situates the deck in — Exhibition (theme-first, no Game Changers/2-card combos/MLD), Core (precon-level), Upgraded (stronger, ≤3 Game Changers), Optimized (no restrictions but not metagame-tuned), cEDH (built to win fast in the cEDH meta from existing lists). Only tag a bracket when the video gives a defensible signal.
Bad: Bracket inflation — tagging a casual/precon-level discussion as `Optimized` or `cEDH` because the host name-drops powerful cards; or flattening every competitive-sounding video to `cEDH`. Tagging a bracket with no basis in the video.
Stakes: High
Source: Wizards of the Coast Commander Brackets Beta (Feb 2025); the allowlist in ContentTagVocabulary mirrors the five official brackets exactly.
```

```
Dimension: Card-category framing
Good: `card_category` tags describe functional roles the video genuinely emphasizes (ramp/removal/draw/finishers/win-cons/counter/protection/board-wipe/tutor/recursion/utility) and don't conflate distinct roles.
Bad: Conflating categories — tagging a single-target spot-removal discussion as `board-wipe`, or merging `win-cons`/`finishers` indiscriminately; emitting a category the video never discusses.
Stakes: Medium
Source: Functional card-role vocabulary locked in ContentTagVocabulary (11 categories); experienced players distinguish removal vs. board-wipe and tutor vs. draw.
```

```
Dimension: Summary thesis fidelity
Good: The ≤200-word summary captures the video's actual strategic thesis — what the deck/topic is, why it works, the key takeaway a deck-builder would act on — grounded entirely in the transcript.
Bad: A generic recap that misses the point, OR fabricated strategic claims (interactions, win lines, meta positioning) not present in the transcript. Padding to length with filler.
Stakes: High
Source: DeckFlow core value (CLAUDE.md) — the artifact must produce a useful ChatGPT round-trip; a summary that misses the thesis poisons the downstream prompt.
```

```
Dimension: Clip usefulness & timestamp honesty
Good: 3–8 clips point to genuinely useful moments (a combo line being explained, a deckbuilding decision, a key card eval). Timestamps are real when the transcript carries timing, and `null`/approximate when it does not (best-effort, D-08) — never confidently wrong.
Bad: Clips that point to filler/intro/sponsor reads; excerpts misquoting the transcript; fabricated precise timestamps presented as exact when the transcript had no timing.
Stakes: Medium
Source: D-08 best-effort timestamps; practitioner expectation that a "key clip" earns its place.
```

### Known Failure Modes in This Domain

- **Archetype misclassification by keyword.** Tagging on a name-dropped word rather than the deck's actual game plan (a midrange list tagged `combo`; a control shell tagged `stax` because it runs a tax effect). The most likely and most expert-noticeable error.
- **Bracket inflation.** Pushing decks up the Feb-2025 ladder — casual content tagged `Optimized`/`cEDH` because powerful cards are mentioned. Mirror risk: flattening genuinely-cEDH content down to `Upgraded`.
- **Card-category conflation.** Collapsing distinct functional roles (`removal` vs `board-wipe`, `tutor` vs `draw`, `finishers` vs `win-cons`) that the controlled vocabulary deliberately separates.
- **Fabricated MTG facts.** Hallucinated combos/interactions not in the video, or citing cards/rules that don't exist or behave as stated — the highest-trust-damage failure because it flows into deck advice as if verified.
- **Stale meta claims.** Asserting current-metagame positioning the transcript didn't support (the cEDH/bracket meta shifts fast; an old video's claims may be presented as present-tense truth).

### Regulatory / Compliance Context

None identified. This is hobby strategy content with no safety, financial, legal, privacy, or PII surface. The only adjacent concern — that transcripts are third-party YouTube content (MTGGoldfish, The Command Zone, EDHRECast, Tolarian Community College, Playing With Power) and need attribution/fair-use handling — is a Phase 22 display/serving concern, not a distillation-quality eval concern.

| Role | Responsibility |
|------|---------------|
| Experienced Commander/cEDH player | Rubric calibration (what counts as a correct archetype/bracket call) + production sampling of distilled artifacts to catch misclassification and fabricated claims |
| Site operator (practitioner labeler) | Reference-dataset labeling — hand-label the gold archetype/bracket/card_category tags + acceptable summary/clips for the 10–20 seed videos; adjudicate LLM-vs-human disagreements |

## 2. Framework Decision

**Selected Framework:** Official OpenAI .NET SDK — `ChatClient` with `response_format` json_schema (`strict: true`)

**Version:** `OpenAI` 2.10.0 (already a `DeckFlow.Core` dependency — zero new NuGet packages)

**Rationale:**
Phase 21 distillation is bounded, stateless structured extraction (three isolated summary/clips/tags calls per video), not agent/RAG/multi-step orchestration — so a direct SDK call is the correct lowest-abstraction tool. The OpenAI 2.10 SDK already powers Whisper via `AudioClient`, so adding `ChatClient` introduces no new dependency (honors CLAUDE.md) and reuses the proven `HttpClientPipelineTransport` + `ApiKeyCredential` construction seam in `WhisperTranscriptionService`. Strict `json_schema` Structured Outputs directly meets the <0.1% parse-failure target (PITFALLS P4).

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| Microsoft.Extensions.AI (`IChatClient`) over OpenAI SDK | Adds a new dependency requiring approval; on the v1.4 reject list for transitive baggage; provider-swappability not needed for a single-provider extraction task |
| Python frameworks (LangChain / LlamaIndex / OpenAI Agents SDK / CrewAI) | Hard constraint: .NET/C# CLI only — no Python runtime; also wrong system type (orchestration, not bounded extraction) |
| Microsoft Agent Framework (.NET) | Preview-stage multi-agent orchestration; wrong system type + banned new dependency |

**Vendor Lock-In Accepted:** Yes — OpenAI is the committed single provider for admin-side ingestion (already used for Whisper). Local admin-only tool; swappability is not a requirement.

### Entry Point Pattern
```csharp
// EXTRACTION pattern: one isolated strict-json_schema call. DeckFlow runs THREE of these
// per video (summary / clips / tags) — never combined (CONTEXT D-02). Construction MIRRORS
// WhisperTranscriptionService.CreateAudioClient (§179-189): same transport seam, same
// ApiKeyCredential, same OPENAI_API_KEY env var, retries disabled at the SDK layer because
// Polly owns resilience.
static ChatClient CreateChatClient(HttpClient httpClient, string apiKey)
{
    var options = new OpenAIClientOptions
    {
        Transport = new HttpClientPipelineTransport(httpClient),
        RetryPolicy = new ClientRetryPolicy(maxRetries: 0), // Polly pipeline owns retry, not the SDK
        NetworkTimeout = Timeout.InfiniteTimeSpan,           // CancellationToken governs timeout
    };
    return new ChatClient("gpt-4o-mini", new ApiKeyCredential(apiKey), options);
}

// A single strict-schema extraction call.
static async Task<string> ExtractJsonAsync(
    ChatClient client, string systemPrompt, string userPrompt,
    string schemaName, BinaryData jsonSchema, int maxOutputTokens, CancellationToken ct)
{
    var options = new ChatCompletionOptions
    {
        Temperature = 0f,                 // deterministic extraction, not creative writing
        MaxOutputTokenCount = maxOutputTokens,
        ResponseFormat = ChatResponseFormat.CreateJsonSchemaFormat(
            jsonSchemaFormatName: schemaName,           // e.g. "summary"; ^[a-zA-Z0-9_-]+$, <=64 chars
            jsonSchema: jsonSchema,                     // BinaryData of the strict JSON schema
            jsonSchemaIsStrict: true),                  // enforce the schema server-side
    };

    ChatMessage[] messages = [new SystemChatMessage(systemPrompt), new UserChatMessage(userPrompt)];
    ClientResult<ChatCompletion> result = await client.CompleteChatAsync(messages, options, ct)
        .ConfigureAwait(false);
    ChatCompletion completion = result.Value;

    // Guard refusals and truncation BEFORE treating output as success (CONTEXT D-12).
    if (!string.IsNullOrEmpty(completion.Refusal))
    {
        throw new InvalidOperationException($"Model refused: {completion.Refusal}");
    }
    if (completion.FinishReason == ChatFinishReason.Length)
    {
        throw new InvalidOperationException("Output truncated (MaxOutputTokenCount hit) — JSON incomplete.");
    }
    if (completion.FinishReason != ChatFinishReason.Stop || completion.Content.Count == 0)
    {
        throw new InvalidOperationException($"Unexpected finish reason: {completion.FinishReason}.");
    }

    return completion.Content[0].Text; // the strict-schema JSON document
}
```

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `ChatClient` | Per-model client (`new ChatClient("gpt-4o-mini", ApiKeyCredential, OpenAIClientOptions)`). Stateless, thread-safe, cheap to construct. | One instance per distill run, reused across all three calls and all videos. Build it inside a production-delegate factory exactly like `CreateAudioClient`. |
| `ChatCompletionOptions` | Per-call request settings: `Temperature`, `MaxOutputTokenCount`, `ResponseFormat`. | Build a fresh one per schema (summary/clips/tags) — each has a different schema and token cap. |
| `ChatResponseFormat.CreateJsonSchemaFormat(name, BinaryData schema, jsonSchemaIsStrict: true)` | Binds a strict JSON Schema to the response; the API rejects the request at submit time if the schema is illegal, and constrains generation to valid JSON. | Every distillation call. `jsonSchemaIsStrict: true` is what buys the <0.1% parse-failure target (P4). |
| `ChatCompletion` (`Content[0].Text`, `.Refusal`, `.FinishReason`, `.Usage`) | The response. `Content[0].Text` holds the JSON string; `Refusal` is non-empty on safety refusals; `FinishReason` distinguishes `Stop`/`Length`; `Usage.InputTokenCount`/`OutputTokenCount` feed the spend ledger. | After every call — read `Refusal`/`FinishReason` first, THEN deserialize `Content[0].Text`. |
| `SystemChatMessage` / `UserChatMessage` | Role-separated prompt parts. | System = role + rules + "tags MUST come from this allowlist"; User = the transcript + task. |

### Common Pitfalls
1. **Strict-schema rejection at request time.** With `jsonSchemaIsStrict: true` the API enforces that EVERY property is listed in `required`, every object sets `"additionalProperties": false`, and only a limited type set is allowed. Validation keywords like `format`, `minLength`, `maxLength`, `minimum`, `maximum`, `pattern`, `minItems`/`maxItems`, `default`, and numeric `enum` are NOT honored / may be rejected. Forgetting `additionalProperties: false` on any nested object makes the call throw *before* a completion is returned. Enforce "3–8 clips" and "≤200 words" in the prompt and in post-validation code, NOT in the schema.
2. **Optional fields must be modeled as nullable + required, never omitted.** Strict mode has no concept of "optional." A best-effort `timestamp_seconds` (D-08) must be declared `"type": ["integer", "null"]` AND listed in `required`. Leaving it out of `required` → request rejected. The model emits `null` when it can't determine a timestamp.
3. **`completion.Refusal` and `FinishReason.Length` masquerade as empty/partial JSON.** If you deserialize `Content[0].Text` without first checking `Refusal` (safety refusal → JSON absent) and `FinishReason == Length` (token cap → truncated, invalid JSON), a refusal/truncation gets recorded as a parse "success" of `null`/garbage. Per D-12, both are FAILURES: mark the video distill-failed, log, continue — do NOT retry, do NOT persist.
4. **Letting the OpenAI SDK retry on top of Polly.** The SDK default `RetryPolicy` retries internally; combined with a Polly pipeline this multiplies calls and spend, and a hidden SDK retry that eventually "succeeds" can mask the single-attempt intent of D-12. Set `RetryPolicy = new ClientRetryPolicy(maxRetries: 0)` (same as `CreateAudioClient`) and keep retry policy explicit in Polly — and per D-12 do NOT add retry that converts a transient failure into a recorded success.
5. **Long transcripts overflow the context window before you cap output.** `gpt-4o-mini` has a 128K-token input window but a 16,384-token max OUTPUT. A 90-minute transcript can approach the input limit. Pre-measure/truncate the transcript (chars/4 ≈ tokens) before the call; if it cannot fit, mark the video failed with a clear reason rather than letting the API reject it opaquely. Always set `MaxOutputTokenCount` explicitly per call (summary ~400, clips ~1200, tags ~200) — never leave output unbounded.

## 4. Implementation Guidance

**Model Configuration:**
- **Model:** `gpt-4o-mini` for all three calls (D-01). Supports strict Structured Outputs; cheapest model that handles ≤200-word summaries adequately.
- **Temperature:** `0f` — extraction must be deterministic and grounded, not creative.
- **MaxOutputTokenCount (explicit, per call — never unbounded):** summary ≈ 400, clips ≈ 1200, tags ≈ 200. These are output caps; `FinishReason == Length` means the cap was hit → treat as failure (D-12).
- **Top-level retry policy:** SDK `maxRetries: 0`; resilience lives in a Polly pipeline that must NOT convert a transient error into a recorded success (D-12, single attempt).

**Core Pattern:**
Three isolated strict-`json_schema` calls per video. Each `DistillationSchemas` entry is a `BinaryData` strict JSON schema; the matching C# `record` is what you deserialize into. Keep the service PURE (no DB writes) — the `distill` orchestrator owns persistence + artifact emit.

```csharp
// ---- 1) SUMMARY ----  schema: { summary: string }
public sealed record SummaryResult(string Summary);   // ≤200 words enforced in prompt + post-check, NOT schema
internal const string SummarySchema = """
    {"type":"object","additionalProperties":false,
     "properties":{"summary":{"type":"string"}},
     "required":["summary"]}
    """;

// ---- 2) CLIPS ----  schema: array of {timestamp_seconds:int|null, excerpt:string}
public sealed record ClipItem(int? TimestampSeconds, string Excerpt);
public sealed record ClipsResult(IReadOnlyList<ClipItem> Clips);   // 3-8 enforced in prompt + post-check
internal const string ClipsSchema = """
    {"type":"object","additionalProperties":false,
     "properties":{"clips":{"type":"array","items":{
        "type":"object","additionalProperties":false,
        "properties":{
            "timestamp_seconds":{"type":["integer","null"]},
            "excerpt":{"type":"string"}},
        "required":["timestamp_seconds","excerpt"]}}},
     "required":["clips"]}
    """;   // best-effort timestamps (D-08): null when transcript has no timing

// ---- 3) TAGS ----  schema: three string arrays (one per dimension)
public sealed record TagsResult(
    IReadOnlyList<string> Archetype,
    IReadOnlyList<string> Bracket,
    IReadOnlyList<string> CardCategory);
internal const string TagsSchema = """
    {"type":"object","additionalProperties":false,
     "properties":{
        "archetype":{"type":"array","items":{"type":"string"}},
        "bracket":{"type":"array","items":{"type":"string"}},
        "card_category":{"type":"array","items":{"type":"string"}}},
     "required":["archetype","bracket","card_category"]}
    """;

// Deserialize with snake_case mapping; tolerate model casing drift.
private static readonly JsonSerializerOptions JsonOpts = new()
{
    PropertyNamingPolicy = JsonNamingPolicy.SnakeCaseLower,
    PropertyNameCaseInsensitive = true,
};

var json = await ExtractJsonAsync(client, sys, user, "tags",
    BinaryData.FromString(TagsSchema), maxOutputTokens: 200, ct);
var tags = JsonSerializer.Deserialize<TagsResult>(json, JsonOpts)
           ?? throw new InvalidOperationException("Tags JSON deserialized to null.");

// EVERY tag filtered through the locked allowlist — out-of-vocab dropped with WARN (D-04).
var validArchetypes = tags.Archetype
    .Where(t => ContentTagVocabulary.IsValid(ContentTagDimension.Archetype, t))
    .ToArray();
// (repeat for Bracket / CardCategory; log each dropped tag at WARN, never persist it)
```

**Tool Use:**
None. This is bounded extraction — no function calling, no tools, no MCP. The only "tool" is the strict `response_format` schema constraining generation. Do not add tool definitions; they would invite the model to call functions instead of returning the schema.

**State Management:**
Stateless per call — no conversation memory, no message history accumulation (each of the three calls is a fresh 2-message exchange). Durable state is owned by the orchestrator, not the LLM service:
- **Spend:** NEW `LlmSpendLedger` (D-05), mirroring `WhisperSpendLedger` (`WouldExceedCapAsync` BEFORE the call, `RecordCallAsync` AFTER with cost from `completion.Usage`). Separate from the Whisper ledger.
- **Idempotency / resume (D-10):** per-video distill-completion status (artifact emitted + slim-index row present + summary/clip/tag rows written). A re-run skips already-distilled videos — never re-calls the LLM.
- **Run record:** `ContentHarvestRunStore.StartRunAsync` → `CompleteRunAsync` with videos distilled, LLM calls, LLM spend USD, and `aborted_reason` on cap-hit (D-11).

**Context Window Strategy:**
`gpt-4o-mini` = 128K input / 16,384 output. Each of the three calls sends the SAME transcript as user content (three passes over one transcript). For long videos, estimate tokens (`text.Length / 4`), and if the transcript + prompt overhead would exceed a safe budget (~120K), either (a) truncate the transcript with a logged note, or (b) mark the video failed with reason `transcript too long for context window` (D-12) rather than letting the API reject it. Because all three calls reuse the transcript, measure once and reuse the decision across them.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Pydantic

This is a C#/.NET system — the .NET equivalent of "Pydantic model + validate-or-retry" is **a `sealed record` schema + the API's strict `json_schema` enforcement + `System.Text.Json` deserialization + an explicit allowlist post-validation pass**. There is no Pydantic; do not introduce it.

Pattern per call:
1. Define a `sealed record` matching the schema (`SummaryResult`, `ClipsResult`/`ClipItem`, `TagsResult` — see Section 4).
2. Constrain generation with `ChatResponseFormat.CreateJsonSchemaFormat(name, BinaryData schema, jsonSchemaIsStrict: true)`. Strict mode guarantees the JSON shape, so deserialization rarely fails on structure.
3. `JsonSerializer.Deserialize<T>(completion.Content[0].Text, JsonOpts)`; treat a `null` result as a failure.
4. **Semantic validation beyond the schema** (the schema cannot express these): tag membership via `ContentTagVocabulary.IsValid` (drop out-of-vocab with WARN, D-04); clip count in 3–8; summary ≤200 words. These are code checks, not schema rules.

```csharp
public sealed record ClipItem(int? TimestampSeconds, string Excerpt);
public sealed record ClipsResult(IReadOnlyList<ClipItem> Clips);
// strict json_schema (see Section 4) guarantees shape; code enforces 3-8 count + best-effort timestamps.
```

**Retry logic:** Per CONTEXT D-12 the project deliberately chose **NO retry** — single attempt, mark-failed-and-continue. On API error, refusal (`completion.Refusal`), truncation (`FinishReason.Length`), deserialize-to-null, or empty semantic result: log the reason at WARN/ERROR, mark the video distill-failed (re-runnable on a later `distill` invocation), and proceed to the next video. The batch never aborts on one video. Surface the failure in the run record's counts. Do NOT add a retry that masks a transient failure as a recorded success — that is the specific anti-pattern D-12 forbids.

### Async-First Design

- The SDK is async-native: use `CompleteChatAsync` everywhere; flow `CancellationToken` as the LAST parameter (project convention) and `.ConfigureAwait(false)` in `DeckFlow.Core` (matches `WhisperTranscriptionService`).
- The CLI host is the async boundary: `await RunDistillAsync(...)` from the `System.CommandLine` handler. **The one common mistake: calling `.Result` / `.Wait()` / `GetAwaiter().GetResult()` on the completion task** — under the CLI's sync context this can deadlock and it swallows the real exception type, which then defeats the D-12 failure classification. Keep the whole chain `async`/`await` from the verb handler down.
- **Stream vs. await:** AWAIT, do not stream. Streaming (`CompleteChatStreamingAsync`) is for incremental UX; this is a batch CLI that must validate a COMPLETE JSON document against a strict schema before persisting. Streaming would force you to reassemble and re-validate fragments for no benefit. Await the full completion, then validate.
- Process videos sequentially (or with a small bounded `SemaphoreSlim`) so the spend cap-check stays accurate — unbounded `Task.WhenAll` can blow past the LLM cap before any `RecordCallAsync` lands.

### Prompt Engineering Discipline

- **System vs. user separation:** System message = role + hard rules ("You extract structured data from an MTG video transcript. Output ONLY the requested JSON. For tags, choose ONLY from this allowlist: <archetypes/brackets/card-categories>. Summary ≤200 words."). User message = the transcript + the specific task. Never concatenate rules into the user turn.
- **Inject the allowlist into the tags prompt.** Render `ContentTagVocabulary.Archetypes/Brackets/CardCategories` directly into the system prompt so the model is biased toward valid tags — but STILL filter every returned tag through `IsValid` (the prompt reduces, the code guarantees). The schema cannot enforce enum-of-strings reliably under strict mode, so the allowlist lives in the prompt + post-validation, not the schema.
- **Few-shot:** inline, minimal. One short worked example in the system prompt for the clips format (showing a `null` timestamp case per D-08) is worth more than retrieval; there is no dynamic example store here.
- **`MaxOutputTokenCount` is always set explicitly** (summary ~400, clips ~1200, tags ~200). Never leave output unbounded in this batch tool — an unbounded run can silently 10x spend on a pathological transcript.

### Context Window Management

Extraction-specific (not RAG chunking, not conversation summarisation): the transcript is the entire context and is sent THREE times (once per call). `gpt-4o-mini` = 128K input / 16,384 output.
- Estimate tokens before calling (`chars / 4`). If transcript + system prompt + allowlist would exceed a safe ceiling (~120K), either truncate the transcript (log the truncation) or mark the video failed (`transcript too long`, D-12) — never let the request fail opaquely at the API.
- Measure ONCE per video and reuse the decision across all three calls (they share the same transcript).
- The summary call is the largest input risk; clips/tags can optionally run against the same transcript text. Do not summarise-then-feed-the-summary into clips/tags — that loses grounding (D-02 mandates three INDEPENDENT passes over the source).

### Cost and Latency Budget

- **`gpt-4o-mini` pricing (verify current rates at platform.openai.com/docs/models):** ≈ $0.15 / 1M input tokens, ≈ $0.60 / 1M output tokens.
- **Per-video estimate (three calls sharing a ~10K-token transcript):** input ≈ 3 × 10K = 30K tokens ≈ $0.0045; output ≈ (400 + 1200 + 200) ≈ 1.8K tokens ≈ $0.0011. **≈ $0.0056 per video.** A 200-video harvest ≈ **$1.10**. Compute the EXACT cost per call from `completion.Usage.InputTokenCount`/`OutputTokenCount` and record it via `LlmSpendLedger.RecordCallAsync` — do not estimate at ledger time.
- **Cap enforcement:** `LlmSpendLedger.WouldExceedCapAsync` BEFORE each paid call (mirror Whisper ordering, Phase 20 CR-01); over-cap → skip the video's distillation and record `aborted_reason` (SC5). Separate ledger from Whisper (D-05).
- **Caching:** the durable cache IS the idempotent resume (D-10) — already-distilled videos are skipped, so the LLM is never re-called for the same video. No additional semantic cache is warranted for a one-pass batch.
- **Sub-task model routing:** `gpt-4o-mini` is already the cheap sub-task model; all three calls are classification/summarisation-grade work, so no further downgrade is sensible. Latency is non-interactive (batch CLI) — sequential calls keep the spend cap accurate and are acceptable; do not parallelise at the cost of cap accuracy.

## 5. Evaluation Strategy

> Proportionality note: this is a LOCAL, admin-only C#/.NET batch CLI tool with no Python runtime and a hard "no new NuGet packages without approval" rule (CLAUDE.md). The eval strategy is therefore **deterministic xUnit checks + a small human-labeled reference set + an optional, manually-run offline LLM-as-judge pass** — NOT a hosted eval platform. Hosted tracing (Arize Phoenix / Langfuse / RAGAS / Promptfoo) is explicitly **rejected as over-kill** for this surface; see Section 7.

### Dimensions

Mapped directly from the Section 1b domain rubric ingredients. Six dimensions: four deterministic (the structural/contract guarantees), two judgment-based (the MTG-correctness guarantees the strict schema cannot express).

| # | Dimension | Rubric (Pass/Fail) | Measurement | Pass Threshold | Gates Phase? | Priority |
|---|-----------|--------------------|-------------|----------------|--------------|----------|
| E1 | **Schema / parse compliance** (FM1) | PASS: every distilled video yields valid strict-`json_schema` JSON for all three calls; refusals and `FinishReason.Length` are classified as failures (not parsed as null). FAIL: malformed/non-schema JSON deserialized as success, or a refusal/truncation recorded as a parse "success". | **Code** (xUnit): inject the test delegate, feed canned good/refusal/truncated/garbage payloads, assert deserialize-or-mark-failed behavior. Production: per-run parse-failure count. | < 0.1% parse failure across a run (PITFALLS P4 / FM1) | **Yes** | Critical |
| E2 | **Tag allowlist validity** (FM2) | PASS: 100% of persisted/indexed tags pass `ContentTagVocabulary.IsValid(dimension, value)`; out-of-vocab candidates dropped with a WARN and never written. FAIL: any tag outside the 15 archetypes / 5 brackets / 11 card-categories reaches `content_tags` or the slim-index row. | **Code** (xUnit): feed a `TagsResult` containing in- and out-of-vocab tags; assert only valid tags persist and each drop logs WARN (D-04). | 100% of persisted tags in-vocab; 0 out-of-vocab persisted | **Yes** | Critical |
| E3 | **Summary length** (D-03) | PASS: summary ≤ 200 words. FAIL: summary > 200 words persisted. | **Code** (xUnit): word-count the `SummaryResult.Summary`; assert ≤ 200. (Enforced in prompt + post-check, never in schema — strict mode ignores `maxLength`.) | 100% ≤ 200 words | **Yes** | High |

**Rejected (over-kill for a local admin tool):** Arize Phoenix, Langfuse, RAGAS, Promptfoo. These assume a Python runtime, hosted tracing, or new package budget — none of which this phase has or wants. Lightweight local Serilog/console logging (Section 7) covers observability.

### Reference Dataset

**Size:** 10–20 videos. Start with the **10 already-harvested videos in the UAT db** from the 5 seeded channels (The Command Zone, EDHRECast, MTGGoldfish, Tolarian Community College, Playing With Power); grow toward 20 as more are harvested.

**Composition:**
- **Critical paths:** clean single-archetype videos with clear bracket signal (the common case).

- **Timeline:** build the gold labels *during* implementation against the 10 UAT videos — not after — so E5/E6 can run the moment the `distill` verb produces its first artifacts.

## 6. Guardrails

> "Real-time" here = per-video, inside the `distill` batch loop. Every guardrail ties to a CONTEXT decision and is deliberately minimal — this is a cost-bounded local batch, not a user-facing request path.

### Online (Real-Time — per video, in the distill loop)

| Guardrail | Trigger | Intervention | Source |
|-----------|---------|--------------|--------|
| **Strict `json_schema` enforcement** | Every distillation call (summary/clips/tags) | Server-side constrain generation to the schema; on refusal (`completion.Refusal`) or `FinishReason.Length` → mark video distill-failed, log, continue. Never deserialize a refusal/truncation as success. | D-12, FM1, PITFALLS P3/P4 |
| **Tag allowlist post-filter** | After the tags call deserializes | Filter every candidate tag through `ContentTagVocabulary.IsValid`; **reject + WARN** out-of-vocab tags; persist only valid ones. | D-04, FM2 |
| **LLM spend cap (separate ledger)** | Before each paid call — `LlmSpendLedger.WouldExceedCapAsync` | Over-cap → **skip the video's distillation** and record `aborted_reason` on the run record; do not make the call. Cap is independent of the Whisper ledger. | D-05, FM4, SC5 |
| **Per-video failure isolation** | Any per-video distill failure (API error, deserialize-null, refusal, truncation, transcript-too-long) | **Mark the video distill-failed, log, continue the batch.** Single attempt — **NO retry** (no retry that masks a transient failure as a recorded success). Re-runnable on a later `distill`. | D-12, FM3 |
| **Idempotent resume / skip-completed** | Start of each video's processing | If the video is already distilled (artifact emitted + slim-index row + summary/clip/tag rows present) → **skip; never re-call the LLM**. | D-10, FM5 |

### Offline (Flywheel — run manually against the reference set, not in the hot path)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| **Archetype/bracket exact-match vs. gold (E5)** | Full reference set after any prompt/schema change; production: operator spot-samples a handful of fresh artifacts per run. | If exact-match < 80% (or operator catches keyword-driven/inflated tags): revise the tags system prompt (allowlist injection, anti-keyword instruction) and re-run E5; do NOT extend the vocabulary (locked Phase 19). |
| **Summary fabrication / thesis-fidelity (E6)** | Operator reads a sample of summaries against the transcript each run; optional offline LLM-judge pre-screens for ungrounded claims. | Any fabricated fact → tighten the summary system prompt's "grounded entirely in the transcript" rule and re-judge. Recurring fabrication is the trigger to reconsider the no-retry / model choice. |
| **Out-of-vocab-tag WARN rate** | Aggregate the WARN count per run from logs / run record. | A rising WARN rate means the model is drifting off-allowlist → strengthen allowlist injection in the prompt. (Tags still never persist out-of-vocab — E2 holds regardless.) |
| **Parse-failure / distill-failed rate** | Per-run counts on the `content_harvest_runs` row. | If parse failures exceed the <0.1% target or distill-failed climbs: investigate transcript-length truncation and schema shape; this is the deferred-idea trigger to revisit bounded retry (D-12). |

## 7. Production Monitoring

> "Production" for this phase = **local admin `distill` harvest runs** on the operator's machine. There is no hosted serving surface in Phase 21 (serving is Phase 22). Monitoring is therefore **local: the `content_harvest_runs` row + structured Serilog/console logs** — not a hosted tracing platform.

**Tracing Tool:** **Local structured logging only** — Serilog/console (existing `DeckFlow.CLI` Serilog file sink) for per-video events (distill-started/completed/failed, dropped-tag WARN, spend recorded, cap-abort), plus the durable `content_harvest_runs` run record as the per-run scoreboard. **Hosted tracing (Arize Phoenix / Langfuse / OpenTelemetry collector) is NOT required and is explicitly out of scope** for a single-operator local CLI — it would add infra and (for Phoenix) a Python dependency the project rejects.

**Key Metrics to Track** (recorded on each `content_harvest_runs` row per D-11, surfaced in run-complete log):
- **Videos distilled** (success count) and **distill-failed count** (FM3/FM5 health).
- **LLM calls** made this run (three per successful video) — sanity vs. videos distilled.
- **LLM spend USD** this run (exact, from `completion.Usage`, via `LlmSpendLedger.RecordCallAsync`) + monthly total vs. cap (FM4).
- **Parse-failure count** (FM1; target < 0.1% of calls).
- **Out-of-vocab-tag WARN count** (FM2; allowlist-drift signal).
- **`aborted_reason`** when the LLM spend cap is hit (SC5).

**Alert Thresholds** (operator-facing, surfaced at run completion — no paging on a local tool):
- LLM spend cap reached → run records `aborted_reason` and stops distilling further videos (hard stop, D-05/SC5).
- Parse-failure rate ≥ 0.1% of calls in a run → investigate schema/truncation before the next run.
- Distill-failed count > 0 → the run-complete log lists failed video ids for re-run on the next `distill` (D-10/D-12).
- Any out-of-vocab-tag WARN → review the tags prompt (does not block; E2 still guarantees no out-of-vocab persistence).

**Smart Sampling Strategy:**
- **Signal-based human review:** the operator reviews artifacts for videos flagged by the offline signals — any distill-failed id, any video that produced an out-of-vocab WARN, and a random handful of freshly-distilled artifacts each run.
- **Disagreement-driven:** when the optional offline LLM-judge (E6) and the operator's spot-check disagree on summary fidelity, that video is escalated to the experienced-player calibrator for adjudication and may become a new reference-set entry.
- Because the batch is small and local, full review is feasible early; sampling matters only as the harvested corpus grows.
