# Phase 2 Plan 09 — The `edhrec.csv` expected-role-count grid (third corpus arm)

## Release Posture

**This phase ships NO user-visible change and is NOT a release.** This command lives in
`DeckFlow.CLI` and is not referenced by any controller, view or web service. No CalVer bump, no tag.

## Why This Plan Exists

A third EDHREC corpus exists, was sanctioned for community use, and was missing from the phase's
planning survey entirely:

**`/mnt/c/users/chrislunt/source/personal/deckflow/artifacts/edhrec/data-jul26-uigloqve/edhrec.csv`**
— `commander,card,count`, **14,150,220 lines including the header**, **3,378 commanders**, **31,788
distinct cards**, 618 MB. `count` is the number of that commander's decks containing that card. Its
`LICENSE.txt` reads *"EDHREC and Space Cow Media encourage community developers to use this data in
their own projects"*, with commercial use not permitted; this research is non-commercial.

What it offers that neither other corpus does: **inclusion frequency for every card, for 3,378
commanders — an order of magnitude more commanders than the bracket grid's 305 and more than four
times the Postgres corpus's 847 commanders at >=40 decks.**

What it cannot offer: **no bracket column, and no per-deck rows.** There is no distribution to take a
percentile of, and no way to condition on power level. It is a breadth instrument, not a depth one.

## The estimator, stated exactly — and what it is NOT

For commander `C` and role `R`:

```
expected[C, R] = SUM over cards ( count[C, card] / denominator[C] ) x isRole(card, R)
```

where `count[C, card]` comes from `edhrec.csv` and `denominator[C]` is `number_decks` from
`averages.csv` for commander `C`.

Each term `count[C, card] / denominator[C]` is the **inclusion rate** of that card in that commander's
decks — a number in `[0, 1]`. Summing the inclusion rates of every card that earns role `R` gives the
**expected number of role-`R` cards in a randomly drawn deck for that commander**, by linearity of
expectation.

**This is a MEAN. It is not a percentile, and it cannot be made into one.**

The intuition is worth stating because it is the exact trap decision D-B exists to close: an expected
count looks like a per-commander number derived from many decks — which it is — and therefore looks
like it should support a floor. It does not. A floor is a threshold most decks should clear, which
requires knowing the **shape** of the distribution. `edhrec.csv` gives one moment of that distribution
and discards the rest. Two commanders with identical expected interaction counts can have wildly
different 25th percentiles, and this arm cannot tell them apart.

**Binding consequence:** every figure this plan emits is tagged `RoleFloorSource.EdhrecBulk`, sits in
a record type with no percentile property, and appears only in a table whose column set contains no
percentile column. It is context for the findings, never an input to a floor.

## Design Decisions

### D-01 — a THIRD source tag, not a reuse of `Edhrec`

Plan `02-05` defined `RoleFloorSource { Postgres = 1, Edhrec = 2 }` and
`EdhrecRolePointEstimate`. Reusing `Edhrec` for this arm would be wrong on both halves of criterion 8:

| | EDHREC bracket grid (`02-06`) | EDHREC bulk archive (this plan) |
|---|---|---|
| Unit | one synthesized average deck per (commander, bracket) cell | inclusion rates aggregated over all of a commander's decks |
| Bracket | yes, B1-B5 | **none** |
| Backing count | `n_decks` per cell, >=400 to qualify | `number_decks` per commander |
| Commanders | 305 | up to 3,378 |
| Estimator | a decklist, counted | a sum of inclusion rates |

They are different measurements of different populations. Collapsing them into one source tag would
make "which EDHREC figure is this?" unanswerable from the artifact — exactly what criterion 8 forbids.

So this plan adds `RoleFloorSource.EdhrecBulk = 3` and a third record,
`EdhrecBulkRoleExpectation`, alongside plan `02-05`'s two.

### D-02 — this plan DOES edit plan 02-05's files, and the enum-count assertion change is AUTHORIZED

This must be called out rather than discovered mid-execution.

`RoleFloorFigureTests` as written by plan `02-05` asserts **"`RoleFloorSource` has exactly two
members"**. Adding a third member fails that assertion by design. Changing it is therefore required,
and it is **not** an instance of "editing an expectation to make a failure pass" — the assertion's
purpose was to prevent an accidental zero-valued default, not to freeze the enum forever.

Authorization, narrow and explicit:

  `RoleFloorFigureTests` may be modified or deleted.**
- `IRoleFloorFigure`'s three-member assertion **stays at 3** — the new record implements the same
  interface and adds nothing to it (plan `02-05` D-02's reasoning is unchanged).
- The reflection assertion proving `EdhrecRolePointEstimate` exposes no distribution property stays
  exactly as it is, and **an equivalent assertion is added for `EdhrecBulkRoleExpectation`**. The
  guarantee extends to the new type; it does not weaken for the old one.
- `RoleFloorFigureTable` gains `EdhrecBulkColumns`. Plan `02-05` D-06's reflection test discovers
  column declarations automatically, so the new list is covered the moment it exists and **must carry
  a `Source` column** or the build's test gate fails. That is the design working, not an obstacle.

Wave placement makes this safe: plan `02-05` is wave 3 and this plan is wave 6, so the two never write
concurrently. `RoleFloorResearchCommandRunner.cs` is **not** in this plan's write set at all.

### D-03 — the denominator, the partner caveat, and a self-validating gate

`averages.csv` has 6,585 data rows: **3,372 solo-commander rows** (`commander2` empty) and **3,213
partner-pair rows**. `edhrec.csv` aggregates by a **single commander name** and has 3,378 commanders.

The two do not obviously line up, and the mismatch is not cosmetic — it is the denominator.

Rule: **use the SOLO row's `number_decks`.** A commander with no solo row is skipped and recorded, not
guessed at.

**State the caveat in the artifact, do not assume it away:** it is not established whether
`edhrec.csv`'s per-commander `count` values include decks in which that commander was played as one
half of a partner pair. If they do and the solo `number_decks` does not, the ratio is inflated for
partner-capable commanders.

**So make the data prove it.** For every commander, compute `maxRatio = max over cards of
(count[C, card] / denominator[C])`. Under a correct denominator this is **structurally bounded by
1.0** — no card can appear in more of a commander's decks than the commander has decks. Therefore:

- `maxRatio <= 1.0` — the denominator is consistent for that commander.
- `maxRatio > 1.0` — **impossible**, so the denominator is wrong for that commander. Record it in a
  `DenominatorMismatches` collection with the commander, the offending card, the count, the
  denominator and the ratio. **Do NOT clamp the ratio to 1.0, do NOT drop the commander silently, and
  do NOT fall back to a different denominator to make the number look sane.** Exclude that
  commander's figures from the grid and report the exclusion with its count.

Report the mismatch count and the worst five ratios in the artifact. A large mismatch count is a
finding about the join, and it is worth more than the grid itself would have been.

Also report, per commander, how many `edhrec.csv` rows were consumed and the resulting
`sum of all inclusion rates`, which should land near a deck's card count for a well-formed commander.
A commander whose total lands far from that is worth flagging.

### D-04 — reuse the harness's card resolution path, and say exactly which parts

The requirement is to reuse the existing card-resolution and caching path rather than invent one. What
is reused, precisely:

| Component | Reused? | Where it lives |
|---|---|---|
| `IScryfallCardResolver` — the actual HTTP path, throttling and 429 handling | **YES, unchanged** | `DeckFlow.Web/Services/Scryfall/ScryfallCardResolver.cs`, registered in `DeckFlow.CLI/Program.cs:302` |
| `_role-floor-research/cards_full.json` — the on-disk cache FILE and its `name -> ScryfallCardData` shape | **YES, same file, same format** | already populated with **14,167 entries** |
| `ScryfallCardFactMapper.ToCardFact` | **YES** | shared |
| `CutLabRoleAssigner.AssignRoles` | **YES**, identical call shape | `DeckFlow.Web/Services/CutLab/CutLabRoleAssigner.cs` |
| `RoleFloorResearchCommandRunner.ResolveCardsAsync` — the batching loop around the resolver | **NO — not callable** | it is a `private static` method inside a file four other plans own across four waves |

**The batching loop is the one duplicated part, and the duplication is deliberate.** Extracting
`ResolveCardsAsync` into a shared component would mean editing
`RoleFloorResearchCommandRunner.cs` — which plans `02-04`, `02-05`, `02-06` and `02-07` all write to,
across waves 2, 3, 4 and 5. A refactor landing in wave 6 on top of four other plans' edits is a merge
hazard for a research harness that must stay reviewable.

So this plan writes its own batching loop over the SAME resolver and the SAME cache file, and records
a follow-up: **`RoleFloorResearchCommandRunner.ResolveCardsAsync` and this command's loop should be
unified into one `DeckFlow.Core` component in a later phase.** Flag it in the SUMMARY; do not do it
here.

**Cost, stated honestly.** `edhrec.csv` has 31,788 distinct cards; the cache holds 14,167 entries. So
roughly **17,600 names will miss** on the first run — about 235 `cards/collection` batches of 75, plus
a per-miss fallback search at the existing pace. That is a real third-party API cost measured in
minutes-to-hours, not seconds, and it is why this command is **implemented here but RUN at plan
`02-08`, behind the operator checkpoint**, alongside every other live call in this phase. Every card
it resolves warms the shared cache for the role-floor run.

### D-05 — two streaming passes, nothing materialised

The archive is 618 MB and 14.15 million rows. Read it with a streaming line reader; **never
`File.ReadAllLines`, never `ReadAllText`, never a `List<>` of rows.**

- **Pass 1** collects the distinct card names into a `HashSet<string>` — 31,788 entries, trivial.
  Resolution and classification happen between the passes, producing a
  `Dictionary<string, IReadOnlyList<string>>` of card name to role keys.
- **Pass 2** accumulates, per commander, the summed inclusion rate per role, plus the row count and
  the running `maxRatio`.

Peak memory is the card-to-roles map plus the per-commander accumulator, both bounded by the distinct
counts, not by the row count. Add a `// Why:` comment recording that a single pass would require
holding either all rows or all counts, and that 14.15 million rows is where "just load it" stops
working.

Parse CSV defensively: card names contain commas (`"Adrix and Nev, Twincasters"` is a commander name;
card names have the same property) and may be quoted. **Use a real CSV split that honours quoting**,
matching whatever the existing `EdhrecAveragesConverter` does for `averages.csv` — read it first and
follow it. A naive `Split(',')` will silently corrupt names, which would then silently fail to resolve
and silently undercount roles. Add a test with a quoted, comma-bearing card name.

### D-06 — the taxonomy comes from the shipped classifier, via plan 02-04's tested predicate

Do NOT retype the nine role keys. Read `CutLabRoleAssigner.RoleKeys` by reflection — the same approach
and the same failure discipline plan `02-04` D-02 established (**if the field cannot be read, that is
an ERROR and the command returns non-zero; it never degrades to "no check"**) — and validate with
`RoleFloorGuards.FindTaxonomyDrift`, the predicate plan `02-04` already put in `DeckFlow.Core` and
unit-tested.

This is genuine reuse and it is the whole point: a third arm that measured a taxonomy the shipped
classifier no longer emits would reproduce the exact `interaction`-key silent-zero bug this phase was
convened to kill.

`other` is excluded from the grid for plan `02-04` D-01's reason — it is a residual bucket measuring
classifier coverage, not deck construction. Record the exclusion in the emitted methodology.

### D-07 — this arm does not touch the go/no-go, and does not touch the harness

`BuildGoNoGo` reads Postgres distributions only. This plan adds a **separate command** with **separate
artifacts**; it does not modify `RoleFloorResearchCommandRunner.cs`, does not write to
`RESEARCH-FINDINGS.md`, and does not feed a verdict.

Its artifacts are `EDHREC-ROLE-GRID.md` and `EDHREC-ROLE-GRID.json` in the phase folder. Plan `02-07`'s
findings may cite them; nothing computes a floor from them.
