## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → controller | User-submitted DeckSource / CommanderName / SelectedQuestionIds flow into the cache key via the field-bag records. Untrusted input crosses here but does NOT escape — it is one-way hashed before any cache lookup. |
| in-process | PacketSessionCache is a singleton sharing state across all concurrent requests. No persistence boundary (in-memory only; process restart = cold cache). |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-999.3-01 | Spoofing | Cache key collision via crafted DeckSource | accept | SHA-256 collision resistance + key space is per-process / 5-min TTL / 10MB capacity → practical collision count = 0. No auth tokens or PII flow into the hashed bag. |
| T-999.3-02 | Tampering | Cache poisoning by user A serving user B's download (D-04 global scope) | accept | Deck contents are public via Archidekt/Moxfield URLs; field bag is hash-deterministic so user A's cache write CAN only serve user B's request if the field bag is byte-identical (i.e., same deck, same flags, same AI platform). The "poisoning" surface is functionally identical to two users requesting the same deck independently — there is no escalation path. Documented in CONTEXT D-04 rejection rationale. |
| T-999.3-03 | Repudiation | n/a | accept | No audit trail required for cache lookups. Serilog log lines satisfy D-13's observability requirement. |

No user input survives the SHA-256 boundary. Slicing the first 8 hex chars cannot inject control characters, ANSI escapes, or log-format directives. Verified by inspection of `Convert.ToHexString` output domain. |
