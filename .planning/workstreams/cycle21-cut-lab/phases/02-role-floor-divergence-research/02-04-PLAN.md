# Phase 2 Plan 04 — Delete the fixture writer, widen the taxonomy, stamp provenance, fail honestly

## Release Posture

**This phase ships NO user-visible change and is NOT a release.** The harness lives in
`DeckFlow.CLI` and is not referenced by any controller, view or web service. No CalVer bump, no tag.

## Why This Plan Exists

This plan closes four of the ROADMAP's ten success criteria — 1, 2, 3, and the taxonomy half of 4
and 9 — plus known defects 5 and 6 that plan `02-01` adds to the ROADMAP list.

### 1. The fixture writer must be deleted, not left uncalled (criterion 1, RFLR-09)

Four methods form the deletion set, all in `RoleFloorResearchCommandRunner.cs`:

| Method | Lines | Callers |
|---|---|---|
| `WriteSyntheticVerificationOutputs` | 818-822 | **none** |
| `BuildSyntheticVerificationComputation` | 824-865 | only `WriteSyntheticVerificationOutputs` |
| `BuildSyntheticCommander` | 867-891 | only `BuildSyntheticVerificationComputation` |
| `BuildSyntheticRoleStat` | 893-908 | only `BuildSyntheticCommander` |

Verified 2026-07-27: a case-insensitive grep for `synthetic` across `DeckFlow.CLI` hits **only** these
13 source lines, plus one unrelated string inside the generated
`DeckFlow.CLI/bin/Debug/net10.0/DeckFlow.Core.xml`, which is build output rather than source.
Criterion 1 — "grep for `Synthetic` in `DeckFlow.CLI` returns nothing" — is therefore achievable by
deleting exactly these four methods and nothing else.

**Note the criterion/gate mismatch, and who fixes it.** As written, criterion 1 says the grep returns
nothing full stop; the gate this plan runs is `grep -rni "synthetic" DeckFlow.CLI --include=*.cs`,
which excludes the generated `bin/` XML. That narrowing is correct but is a **relaxation of the
stated criterion**, so it must not be left implicit. Plan `02-01` Task 1 item 8a rewords criterion 1
to name `.cs` sources explicitly. This plan does not touch `ROADMAP.md`; it depends on `02-01`
(wave 1) having already landed that wording.

**Why deletion rather than orphaning matters.** `BuildSyntheticRoleStat` (`:893-908`) takes
`clearsBar` as an **independently hardcoded `bool` parameter**, decoupled from the also-hardcoded
ratio/z/d literals beside it at `:884-888`. That is precisely why the deleted `RESEARCH-FINDINGS.md`
showed identical statistics yielding different verdicts — an outcome impossible via the real
computation path, where `ClearsBar` is derived from the same inputs it prints. An orphaned method
that can manufacture a self-contradicting artifact is one accidental call away from doing it again.

### 2. The role taxonomy is badly stale — and this is bigger than the ROADMAP implies

`RoleFloorResearchCommandRunner.TargetRoles` (`:36-43`) is:

```
interaction, protection, engines, payoffs, wincons
```

Five roles. That is the **pre-Phase-1** taxonomy: no `lands`, no `ramp`, no `draw`, and the merged
`interaction` key that Phase 1 already split and removed.

The shipped taxonomy is `CutLabRoleAssigner.RoleKeys` (`:29-40`) — **nine** keys:

```
lands, ramp, draw, interaction-targeted, interaction-mass, protection, engines, payoffs, wincons
```

plus an `other` fallback assigned at `:191-194` only when nothing else matched.

**Consequence: the harness as it stands would measure a role key (`interaction`) that
`CutLabRoleAssigner.AssignRoles` can no longer emit.** The tally loop at `:202-208` only increments
`roleCounts` for keys already present in the dictionary, so `interaction` would silently record
**zero for every deck, for every commander** — a corpus-wide null result masquerading as a
measurement. This is the single most dangerous defect in the starting state, and the ROADMAP does not
mention it at all.

Satisfying criteria 4 and 9 therefore requires widening `TargetRoles` from 5 to 9, which cascades
into `BuildCorpusBaseline` (`:530-565`), the markdown emitter (`:672-713`), the JSON emitter
(`:736-775`), and `BuildGoNoGo` (`:567-613`). Sized honestly, this is the largest single edit in the
phase.

Lands/ramp disjointness is guaranteed by construction and needs no harness-side handling:
`CutLabRoleAssigner.cs:123` gates lands on `CutLabLockRules.IsLand(typeLine) || fact.HasLandFace`
**before** the ramp check, and `:136`'s `!isLand &&` excludes lands from ramp. The existing `// Why:`
comment there records that without the gate every land would double-count as ramp.

## Design Decisions

### D-01 — include `draw`, exclude `other`

D-C mandates `lands` and `ramp`. `draw` and `other` are the planner's call. Decision, with reasons:

**`draw` is IN.** It is a first-class shipped role with its own floor key, its own display label, and
its own `WeakFloorCase` participation. Excluding it would leave a gap for no reason other than that
D-C did not name it. `REQUIREMENTS.md`'s Out-of-Scope table lists "Land/ramp/draw floor logic
changes" as out of scope — that is about *changing floor logic*, which is Phase 3's territory;
**measuring** draw costs nothing extra and informs Phase 3's scope.

**`other` is OUT.** `other` is not a role; it is `CutLabRoleAssigner`'s residual bucket, assigned at
`:191-194` only when `assigned.Count == 0`. Its count is a function of classifier coverage, not of
deck construction. A commander-specific `other` "floor" would be meaningless, and reporting a go on
it would be actively misleading. Record the exclusion and its reason in the emitted methodology text
so a reader does not assume it was forgotten.

Final `TargetRoles`, in `CutLabRoleAssigner.RoleKeys` order so the findings tables read in the same
order as the shipped UI:

```
lands, ramp, draw, interaction-targeted, interaction-mass, protection, engines, payoffs, wincons
```

### D-02 — assert the taxonomy against the shipped classifier, over ALL NINE keys, not a five-key subset

Retyping nine strings creates a silent drift risk: a future role rename would leave the harness
measuring a key that returns zero for every deck — exactly today's `interaction` bug, recurring.

**The guard must cover every shipped key, or it does not close the hole it exists for.** An earlier
draft of this plan probed only `lands`, `ramp`, `draw`, `interaction-targeted` and
`interaction-mass`, leaving `protection`, `engines`, `payoffs` and `wincons` unprobed — so the exact
silent-zero failure this guard prevents could still occur for four of the nine roles while the guard
reported success. The authoritative list is `CutLabRoleAssigner.RoleKeys`
(`DeckFlow.Web/Services/CutLab/CutLabRoleAssigner.cs:29-40`):

```
lands, ramp, draw, interaction-targeted, interaction-mass, protection, engines, payoffs, wincons
```

`other` is a **separate** `private const` at `:27`, is not a member of `RoleKeys`, and is
deliberately OUT of scope per D-01 — the guard must tolerate it, never require it, and the emitted
methodology must say why it is excluded.

The guard has **two halves**, and both must pass:

**Half 1 — authoritative-list check (preferred over a hand-copied literal).**
`RoleKeys` is `private static readonly`, so it cannot be referenced directly. Read it by reflection
from `DeckFlow.CLI` — `typeof(CutLabRoleAssigner).GetField("RoleKeys", BindingFlags.NonPublic | BindingFlags.Static)`
— and assert `TargetRoles` is set-equal to it. This consumes the real shipped list rather than
trusting a copy. **If reflection cannot find or read the field, that is an ERROR, not a pass**: emit
a message naming the field and return non-zero. A guard that silently degrades to "no check" is worse
than no guard, because it reports success.

Reflection was chosen over the alternatives deliberately:

| Option | Verdict |
|---|---|
| Make `RoleKeys` `public` or `internal` + `InternalsVisibleTo` | **Rejected.** Widens a shipped web service's public surface for a research harness's benefit, and edits a file this plan's scope fence forbids. |
| Hand-copy the nine strings with no cross-check | **Rejected.** This is the failure the guard exists to prevent. |
| **Reflect the private field, fail loudly if absent** | **Chosen.** Zero edits to shipped code, consumes the real list, and a rename surfaces as a startup abort rather than a silent zero. |

**Half 2 — emission probes, one per shipped key.** Classify hand-built `CardFact` probes through
`CutLabRoleAssigner.AssignRoles(probe, [], isComboPiece: false, mode)` and assert (a) every key a
probe emits is in `TargetRoles` or is the literal `other`, and (b) **every one of the nine shipped
keys is emitted by at least one probe**. Half 1 proves the lists agree; half 2 proves the assigner
can actually still produce each key, which is what makes a corpus-wide zero suspicious rather than
expected.

Probes must cover all nine: a basic land (→ `lands`), a mana rock (→ `ramp`), a repeatable-draw
permanent (→ `draw`), a targeted removal spell (→ `interaction-targeted`), a board wipe
(→ `interaction-mass`), a protection permanent (→ `protection`), a repeatable-draw permanent that
`PlanRoleClassifier` also scores as `PlanRole.Engine` (→ `engines`), a `PlanRole.Payoff` card
(→ `payoffs`), and a closing-power card (→ `wincons`). Build every probe from oracle text that
existing passing tests already prove is classified as intended — read those tests, do not invent
oracle text and hope. Note the `engines` gate at `CutLabRoleAssigner.cs:157-163` additionally
requires a permanent front face plus `IsDrawCard`, and `wincons` at `:170` is
`IsClosingPowerCard(typeLine, oracle) || isComboPiece` — with `isComboPiece: false` the probe must
earn it through `IsClosingPowerCard`.

**If a shipped key cannot be provoked by any probe sourced from a passing test, STOP and report.** Do
not weaken the guard to nine-minus-one, and do not set `isComboPiece: true` to manufacture a
`wincons` hit — that would prove the flag works, not that the classifier emits the key.

### D-06 — the guard predicates live in `DeckFlow.Core` so they are testable

There is **no `DeckFlow.CLI` test project** — the solution has `DeckFlow.Core.Tests`,
`DeckFlow.Web.Tests` and `DeckFlow.Studio.Tests` only. Everything added by this plan inside
`RoleFloorResearchCommandRunner.cs` is therefore covered by grep and code-reading alone. A misplaced
exit-2 guard would produce exactly the failure this phase exists to kill — an empty artifact with
exit 0 — and would still satisfy every static acceptance criterion in this plan.

So the **pure predicates** move into `DeckFlow.Core/Research/RoleFloorGuards.cs`, where
`DeckFlow.Core.Tests` can cover them:

- `RoleFloorGuards.FindTaxonomyDrift(IReadOnlyCollection<string> shippedRoleKeys, IReadOnlyCollection<string> targetRoles, IReadOnlyCollection<string> emittedKeys, string residualRoleKey)` → `string?`, null when clean, otherwise a message naming every offending key. This is the whole of D-02's decision logic with the reflection and the probing lifted out.
- `RoleFloorGuards.HasNoQualifyingCommanders(int qualifyingCommanderCount)` → `bool`. Trivial by itself; the point is that the CLI calls a named, tested predicate instead of inlining a comparison whose placement nobody can test.

What stays in the CLI is only the untestable glue: the reflection call, the probe `CardFact`s, the
`Console.Error` writes, and the `return` statements. That is the smallest residue this split can
leave, and it is stated here rather than left as an unexamined gap.

Adding a test project for `DeckFlow.CLI` was considered and **rejected for this phase**: CLAUDE.md
forbids adding a test project on the AI's initiative, and the harness's remaining CLI surface is
I/O-bound orchestration that a unit test could not meaningfully cover. The residual risk — that the
exit-2 guard is correct in isolation but mis-placed in `RunAsync` — is closed instead by plan
`02-08`'s deliberate `--min-decks 999999` smoke run against the live corpus, which proves exit 2 AND
that no artifact was written.

### D-07 — the connection string may come from the environment, not only from argv

`Program.cs:79` declares `--connection-string` with `IsRequired = true` and no environment fallback,
so today the only way to supply it is as a **command-line argument**. Command-line arguments are
visible in the process list (`ps`, `/proc/<pid>/cmdline`, Windows Task Manager details) to any other
user on the machine, for the **entire duration** of the run — and this run is measured in hours.
Plan `02-08`'s wrapper already keeps the value out of files, logs and shell history via
`DECKFLOW_ROLE_FLOOR_CONNECTION_STRING`; passing it onward as argv reopens the exposure the wrapper
closed.

Decision: **the harness reads `DECKFLOW_ROLE_FLOOR_CONNECTION_STRING` directly as an alternative to
`--connection-string`.** The requirement becomes "satisfied by either", not "flag mandatory":

- `--connection-string` stays declared, keeps working, and takes precedence when both are present
  (explicit beats ambient) — backward compatibility for any existing invocation.
- Its `IsRequired` becomes `false`, and the "you must supply one of these" validation moves into the
  runner so the error message can name both sources.
- When neither is supplied, write to `Console.Error` a message naming BOTH the flag and the
  environment variable, and `return 1` — the existing bad-arguments code, unchanged in meaning.
- The environment variable's **value is never echoed, logged, or included in any error message**, on
  the same D-03 grounds.

This is the plan that owns `Program.cs`'s `role-floor-research` option block: Task 3 here already
edits that block's defaults and description, it lands in **wave 2** — before `02-06`'s `--edhrec-data`
addition in wave 4 and well before `02-08`'s wrapper in wave 7 — and `02-06` Task 3 explicitly
forbids itself from touching `--connection-string`. Putting the change anywhere else would either
split one option's definition across two plans or land it after the wrapper that depends on it.

### D-03 — derive the host from the connection string, never log the credential

`NpgsqlConnectionStringBuilder` parses the normalized connection string; take `.Host` and, if
present, `.Port` and `.Database`. **Emit host (and optionally port and database) only.** Never emit
`Username`, `Password`, or the raw connection string — not to the artifact, not to the console, not
to the log. CLAUDE.md's Secrets handling section is explicit: connection strings are secrets and must
never reach output, commits, logs or error messages.

Because the findings artifacts are committed to a **public repository** (`luntc1972/DeckFlow`), a
leaked credential here would be a live incident, not a nuisance. If deriving the host proves awkward
for any connection-string shape, emit the literal string `unavailable` rather than falling back to
anything that could contain a credential.

### D-08 — provenance must not fail SOFT: a degraded field is a stated warning, not a silent value

`DescribeDatabaseHost` returns `"unavailable"` on any exception and `DescribeHarnessCommitSha`
returns `"unknown"` on any failure (D-04). Those fallbacks are correct — provenance must never block
a run, and must never leak a credential to avoid a fallback. But they let a run satisfy criterion 2's
**letter** while carrying no usable provenance, and one combination is outright self-contradictory:
**a run that connected to Postgres successfully and then reports host `unavailable`.** The artifact
would assert both "here are figures from the corpus" and "I don't know which corpus".

Rule: when a provenance field holds a fallback value, the artifacts must say so **as a warning, not
as a value**. Specifically:

- The `## Run Provenance` table renders the fallback in the cell as today, AND
- A `> **WARNING — provenance degraded:**` line is emitted immediately beneath the table naming each
  degraded field and what it means. For the connected-but-`unavailable` case the line must state
  explicitly that the run DID connect (the deck counts prove it) and that the host could not be
  derived, so this artifact cannot be traced to a specific database by its own contents.
- The JSON payload carries a `provenanceWarnings` array of the same strings — empty when every field
  resolved.

The warning is computed from the fallback values themselves, so it cannot be forgotten: if
`DatabaseHost == "unavailable"` or `HarnessCommitSha == "unknown"`, the array is non-empty and the
markdown line is emitted. There is no flag to suppress it.

### D-04 — commit SHA is read at runtime, not baked at build time

Read the harness commit SHA by invoking `git rev-parse --short HEAD` from the process working
directory at run start and capturing stdout. On any failure — not a git checkout, git absent,
non-zero exit — record `unknown` and continue. Provenance is a reporting requirement, not a run
blocker.

Also capture whether the working tree is dirty (`git status --porcelain` produces output) and record
the SHA as `<sha>-dirty` when it is. **This matters more than usual here:** the entire harness is
currently untracked, so the first real run will necessarily be from a dirty tree, and an artifact
claiming a clean SHA would be misleading.

`git rev-parse` and `git status --porcelain` are read-only and are the ONLY git commands this plan's
code may invoke. Use `ProcessStartInfo` with `ArgumentList`; do not construct a shell string.

### D-05 — the zero-qualifying-commanders exit is a guard, not an exception

Place the check immediately after `qualifyingCommanders` is populated and **before** `BuildGoNoGo` /
`WriteFindingsFiles` at `:274-275`. Write a diagnostic to `Console.Error` naming the threshold, the
number of commanders enumerated, and the `ThresholdCounts` diagnostic table (`:257-259`) so the
operator can see which lower threshold would have qualified somebody. Then `return 2`.

Use **exit code 2**, not 1: `1` already means "bad arguments or unhandled exception" (`:64-77`,
`:289-293`). A distinct code lets plan `02-08`'s run script distinguish "the harness broke" from
"the harness ran correctly and found nothing" — a legitimate outcome under criterion 10. Document
both codes in the command's `--help` description text.

Do NOT throw. An exception would be swallowed by the `catch` at `:289-293` and reported as a failure
message, losing the diagnostic table.
