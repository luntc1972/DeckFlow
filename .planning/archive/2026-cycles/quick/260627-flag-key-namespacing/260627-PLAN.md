# Quick Task: Flag-key namespacing + admin "feature"→"tool"

## Goal

Every feature-flag key follows a consistent prefix that names what it does:
- `tool.*` — user-facing tool/page visibility kill-switches
- `service.*` — backend/integration service toggles
- `analysis.*` — analysis behavior tuning

Rename 14 keys, add an **idempotent migration** so existing prod DB rows keep
their operator toggle state under the new key, and relabel the admin Flags page
UI copy from "Feature flags" to "Tool flags".

## Migration design (the only non-mechanical part)

In `FeatureFlagStore.EnsureSchemaAsync`, between CREATE TABLE and the existing
DO-NOTHING seed, run a rename migration over a static `(old,new)` pair array.
Per pair, two parameterized statements (identical SQL for Postgres + SQLite):

```sql
-- carry operator value to the new key (only if new not already present)
UPDATE feature_flags SET key = @new, updated_at = @now
 WHERE key = @old AND NOT EXISTS (SELECT 1 FROM feature_flags WHERE key = @new);
-- drop the orphan old row if the new key already exists (idempotent / re-run safe)
DELETE FROM feature_flags
 WHERE key = @old AND EXISTS (SELECT 1 FROM feature_flags WHERE key = @new);
```

Idempotency cases: fresh DB (no-op → seed inserts new), existing prod (rename
carries enabled value, seed DO-NOTHING), re-run (no-op), both-present (delete orphan).
