# Phase 01.1 Plan 01 — Bug 1: "Counters" / counterspell substring collision

## Why This Plan Exists

`PlanRoleClassifier.cs:245-246`:

```csharp
private static bool IsCounterCategory(string category)
    => Has(category, "counter");
```

`Has` is a plain `StringComparison.Ordinal` substring test over the already-lowercased tag. So a
crowd-sourced Archidekt category literally spelled **`Counters`** — the +1/+1-counters synergy
theme — matches the needle `counter` and is treated as a counterspell tag. In
`ManabaseMode.Cedh` that earns `PlanRole.Interaction` (`FromCategories`, `:147-150`).

Real corpus examples of cards carrying a `Counters` tag, none of which counter a spell:
Cordial Vampire, Drana Liberator of Malakir, Blade of the Bloodchief, Rakish Heir,
Knight of the Ebon Legion.

This must land before Phase 2. Phase 2 counts roles per card via `CutLabRoleAssigner`, which routes
`PlanRole.Interaction` into its `interaction-targeted` key through `interactionMeritPreGate`
(`CutLabRoleAssigner.cs:153-158`). Measuring interaction floors while every +1/+1-counters deck
inflates its own interaction count is measuring the defect, not the deck.

## Design Decision — D-01: word-boundary match + explicit compound needles

Three candidate fixes were considered:

| Option | Verdict |
|---|---|
| Drop the `"counter"` needle, keep only `"counterspell"` | **Rejected.** Loses the real tags `Counter`, `Counter Magic`, `Countermagic`, which are common Archidekt spellings. |
| Add a negative guard `&& !Has(category, "counters")` | **Rejected.** A tag reading `"counterspells / counters matter"` would be wrongly stripped, and it does nothing about `Encounter`. |
| Word-boundary match on the singular token, plus explicit needles for the closed compounds | **Chosen.** |

The chosen rule:

```
IsCounterCategory(c) = Has(c, "counterspell", "countermagic") || HasWord(c, "counter")
```

`HasWord` matches `needle` only at an index where the preceding character (if any) and the character
immediately following the match (if any) are both non-alphanumeric ASCII. Everything stays
`StringComparison.Ordinal` over the caller's already-lowercased string, matching the existing `Has`
convention — no regex, no culture dependence, no allocation, because this runs per card in the Cut Lab
role-tally hot path.

`"counterspell"` is a prefix of `"counterspells"`, so the plural is covered by the substring arm and
needs no separate needle.

Truth table this produces (input is the lowercased tag):

| Tag | Result | Path |
|---|---|---|
| `counterspell` | counter tag | `Has("counterspell")` |
| `counterspells` | counter tag | `Has("counterspell")` |
| `countermagic` | counter tag | `Has("countermagic")` |
| `counter magic` | counter tag | `HasWord("counter")` — bounded by space |
| `counter-magic` | counter tag | `HasWord("counter")` — bounded by `-` |
| `counter` | counter tag | `HasWord("counter")` — bounded by both ends |
| `permission / counters, counterspells` | counter tag | `Has("counterspell")` |
| **`counters`** | **not a counter tag** | `s` follows the match; no compound needle |
| **`counters matter`** | **not a counter tag** | same |
| **`+1/+1 counters`** | **not a counter tag** | same |
| **`encounter` / `encounters`** | **not a counter tag** | `n` precedes the match |

The prompt's framing is honored exactly: a tagger who writes bare `Counters` and *means*
counterspells now loses the role. That is the accepted trade — the plural noun sense is
overwhelmingly the +1/+1 sense in the harvested corpus, and `Counterspells` / `Counter Magic` /
`Counter` all still work.

## Known Behavior Change — stranded subthemes (intended, not a regression)

`CutLabStructuralFindings.ComputeStrandedSubthemes` (`:227`) skips any theme where
`PlanRoleClassifier.CategoryMapsToPlanRole(theme.Key)` is true. Today a 3-card `Counters` theme is
skipped, because the collision makes it look like a plan role. After this fix it becomes **eligible**
for a `StrandedSubtheme` finding.

That is the correct outcome — a 3-card +1/+1-counters subtheme genuinely is stranded — but it is a
user-visible change in Cut Lab output and must be stated plainly in the plan SUMMARY so UAT does not
file it as a new bug.
