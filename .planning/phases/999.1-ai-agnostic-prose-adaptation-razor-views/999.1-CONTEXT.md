## Implementation Decisions

### Adaptation strategy

- **D-01:** **Hybrid adaptation — universal phrasing above the Step 2 selector, selected-platform name below.**

  - **Above selector** (H1, page lede, Step 1 prose, intro text, Home.cshtml hub cards): universal phrasing using the **`your AI`** convention (D-05). Examples:
    - "what to paste into your AI and what to paste back into this page" (was: "what to paste into ChatGPT...")
    - "your AI will return..." (was: "ChatGPT will return...")
    - "Ask your AI to return the `deck_profile` JSON..." (was: "Ask ChatGPT to return...")
  - **Below selector** (Step 3 paste instructions, prompt panel headings, "Suggested conversation title" copy, error-banner area): inject the selected platform's `DisplayName` via Razor `@aiPlatform.DisplayName`, where `aiPlatform = AiPlatform.Normalize(Model.TargetAiPlatform)`. Examples:
    - `<h3>Suggested @aiPlatform.DisplayName conversation title</h3>` (was: hardcoded "Suggested ChatGPT conversation title")
    - "Paste this into @aiPlatform.DisplayName for the main deck analysis." (was: hardcoded "Paste this into ChatGPT...")
    - "@aiPlatform.DisplayName should return a `deck_profile` JSON object matching this schema." (was: hardcoded "ChatGPT should return...")

  **Rationale:** Above-selector prose runs before `Model.TargetAiPlatform` has user intent (default is the Phase 10 fallback `"ChatGPT"`), so injecting a platform name there would still say "ChatGPT" on first render — exactly the bug we're fixing, just deferred. Below-selector prose runs after Step 2 submit, so `Model.TargetAiPlatform` reflects the user's pick. The boundary lines up cleanly with the existing step-flow structure of all three pages.

  **Edge case:** the `_AiSelector` partial itself sits at the top of Step 2. Step 2 prose surrounding the selector (e.g., DeckAnalysis.cshtml:359 "Choose which deck builder you will paste the generated lists into. ... ChatGPT should return the decklist in a fenced ```text``` block.") sits AT-selector. Treat AT-selector prose as ABOVE — the user hasn't necessarily committed the selector to a value yet at first render; universal phrasing is safest.

### Scope boundary — what counts as "visible prose"

- **D-02:** **Full scope expansion.** All four candidate surfaces are in scope:

  1. **`.cshtml` visible text** — primary scope (3 multi-AI views + Home.cshtml hub cards excluding JudgeQuestions card per D-03).
  2. **C# exception messages user-facing on bad paste** — `ResponseParsers.cs` (4 hits), `MetaGapService.cs` (2 hits), `DeckComparisonService.cs` (2 hits) all throw `InvalidOperationException` with hardcoded "ChatGPT" prose that renders directly into the form error banner. Same prose surface as the .cshtml; convenience of file extension doesn't change user-visibility. Apply the universal noun convention (D-05) since exceptions render without access to the selector state.
  3. **`data-busy-title` HTML attribute** — `DeckAnalysis.cshtml:72` has `data-busy-title="Building ChatGPT Packets"` and `data-busy-message="Resolving the deck and generating prompt files."` rendered in the loading overlay. Rename title to `"Building Deck Analysis Packet"` (matches Phase 13 class naming + the other two pages' neutral form-busy titles).
  4. **`DeckFlow.Web/Help/*.md`** — Markdig-rendered help pages at `/help/{slug}`. Same user-visible surface. No per-platform dispatch available (`HelpContentService` reads the .md file statically), so universal noun convention throughout. `ask-a-judge.md` follows the D-03 carve-out.
  5. **`_logger.LogInformation` prefixes** — 5 hits in `DeckAnalysisPacketService.cs` reading "ChatGPT packet deck load completed", etc. NOT user-visible (Serilog console + file sinks only), but in scope as a cheap consistency follow-on; matches Phase 13's class rename so log lines align with class names.

  **Out of scope** (kept off the list intentionally):
  - XML `///` doc comments mentioning "ChatGPT" (e.g., `PacketArtifactStore.cs:194` "Rehydrates a saved ChatGPT packet zip..."). Phase 13 D-07 allowed narrative ChatGPT in doc comments. Do not touch.
  - `JsonTextFormatterService.cs:14` `ResultWrapInstruction` raw-string ("Wrap the entire JSON response in `<result>...</result>` tags so DeckFlow's parser can extract it uniformly across ChatGPT/Claude/Gemini.") — already AI-agnostic enumerated form; leave alone.
  - `RequestContextParser.cs:338` comment "Null means absent in zip (legacy zip — caller defaults to 'ChatGPT')" — Phase 10 invariant; the fallback default is the literal Key value, leave the comment intact since it documents the Phase 10 behavior.
  - Service-layer comments like `// legacy artifacts (no wrapper) and ChatGPT-fenced-only responses` (`JsonTextFormatterService.cs:60`) — internal narrative; leave alone.

### JudgeQuestions carve-out

  Reasoning:

  - The page intent is positioned as: "real volunteer judges first; ChatGPT as a fast, fallible fallback." The current copy ("ChatGPT prompt generator", "ChatGPT can be confidently wrong about MTG rules") is genuinely about ChatGPT-the-product, not the generic AI category, because the recommended fallback workflow targets ChatGPT's free web UI specifically.
  - Generalizing would require: adding `_AiSelector`, building a JudgeQuestion PromptVariants family (none exists), routing through new per-AI prompts. Meaningful scope creep — promote to its own backlog phase if user changes mind later.

  **Carve-out tracking:** keep the 6 hits intact:
  - `JudgeQuestions.cshtml:9` lede paragraph
  - `JudgeQuestions.cshtml:39` volunteer-judge fallback line
  - `JudgeQuestions.cshtml:67` `<h2>ChatGPT prompt generator</h2>`
  - `JudgeQuestions.cshtml:68` intro paragraph

  **Help/ask-a-judge.md** follows the same carve-out: no edits in 999.1.

### Per-page prompt-content scope

- **D-04:** **View-side narration only. PromptVariants raw-string literals are Phase 15 territory and stay untouched.**

  Phase 15 already extracted the 5 prompt-builder families (`Analysis`, `SetUpgrade`, `Comparison`, `FollowUp`, `MetaGap`) into `DeckFlow.Web/Services/PromptBuilders/` with one variant class per AI per family (15 variants). Those variants emit the prompt BODY that goes into the AI chat — they are already per-platform-targeted by construction (the `ChatGptAnalysisPromptVariant.Build(...)` returns ChatGPT-specific prompt text, etc.).

  Phase 999.1 only modifies the .cshtml prose that DESCRIBES what the prompt does for the user. Example boundary:
  - **In scope** (view narration): `<p>Paste this into ChatGPT for the main deck analysis. It requests prose analysis plus a structured deck_profile JSON object.</p>` → becomes `<p>Paste this into @aiPlatform.DisplayName for the main deck analysis. It requests prose analysis plus a structured deck_profile JSON object.</p>`
  - **Out of scope** (raw-string prompt body inside `ChatGptAnalysisPromptVariant.cs`): anything in the `"""..."""` raw-string literal. Per CLAUDE.md: never re-indent C# raw-string literals.

  **Verification gate:** at end of phase, run `grep -nE 'ChatGPT|ChatGpt' DeckFlow.Web/Services/PromptBuilders/` — hits inside non-ChatGPT-variant files (i.e., a ChatGPT mention appearing in `ClaudeAnalysisPromptVariant.cs`) are Phase 15 follow-up bugs, not Phase 999.1 scope. Document any findings in the SUMMARY as Phase 15 follow-up backlog items; do NOT fix them in 999.1.

### Universal noun convention

- **D-05:** **Universal noun = `your AI`.**

  Used everywhere above the Step 2 selector and in C# exception messages (which have no selector access). Examples of the transform:
  - "paste into ChatGPT" → "paste into your AI"
  - "Ask ChatGPT to return..." → "Ask your AI to return..."
  - "ChatGPT will return..." → "your AI will return..."
  - "the submitted ChatGPT response did not contain a valid `deck_profile` payload." → "the submitted AI response did not contain a valid `deck_profile` payload." (note: drop "your" when the sentence already has a definite article structure; pick the variant that reads naturally — see Claude's Discretion below)

  **Why `your AI`** (over `the AI`, enumerated form, or `your AI assistant`):
  - Short — important since the noun repeats 5–10× per page.
  - Possessive — implies the user already picked one (they did, in Step 2).
  - Natural-reading — keeps the existing instructional voice ("paste into your AI" reads identically to "paste into ChatGPT" structurally).
  - 4th-platform-safe — stays correct when a 4th AiPlatform lands without view edits.

  **Exception**: page lede lines already use the explicit enumerated form `"ChatGPT, Claude, or Gemini"` (Phase 12 work). Keep those enumerated ledes as-is; they read fine and explicitly enumerate the supported platforms which is useful at page entry. The convention `your AI` applies to sub-prose, NOT the lede.

### Claude's Discretion

- Specific phrasing of each universal-noun substitution per sentence — pick the variant that reads naturally. "Your AI" works in most cases; "the AI" reads better in some C# exception messages already starting with "The submitted X response..."; drop the possessive when the surrounding clause already has one. The plan author makes the call sentence-by-sentence.
- Where in each view file to introduce the `var aiPlatform = AiPlatform.Normalize(Model.TargetAiPlatform);` Razor block — top of the file with the other `@{` block is fine; matches the existing pattern in `_AiSelector.cshtml` (which already does similar normalization).
- Whether to use `@aiPlatform.DisplayName` inline or compute a local string variable for repeated injection — either works; inline is simpler.
- Order of file edits — alphabetical by view filename (CedhMetaGap → DeckAnalysis → DeckComparison → Home) is fine; or page-by-page with help.md sibling next to each .cshtml. Plan author picks.
- Whether the data-busy-title rename ("Building ChatGPT Packets" → "Building Deck Analysis Packet") needs to also adjust the busy-message ("Resolving the deck and generating prompt files." — already brand-neutral). Audit both attributes; only the title needs the rename.

## Specific Ideas

- Hybrid pattern aligns naturally with the step-flow already structured into all 3 multi-AI views: Step 1 universal, Step 2 at-selector universal, Step 3 below-selector dynamic. No new structural pattern is invented — the page architecture already supports the split.
- Universal noun `your AI` is short enough to repeat without bloat (compare to `your AI assistant` which adds 1 word × 10 uses per page). It also implies user agency without committing to a brand the user might not have picked yet.
- `data-busy-title="Building Deck Analysis Packet"` (new value) matches the Phase 13 class rename (`DeckAnalysisPacketService`) and the other two pages' existing busy titles (`"Building Deck Comparison Packet"`, `"Building cEDH Meta Gap Packet"`). Trio becomes consistent post-phase.
- `_logger.LogInformation` prefix rename ("ChatGPT packet" → "Deck Analysis packet") matches Phase 13's `DeckAnalysisPacketService` class name and the busy-title rename — three pieces of the same brand follow-on.
- JudgeQuestions.cshtml carve-out has historical justification: that page is the only one without an `_AiSelector` partial because its core proposition (volunteer judges first, fallback as side-pitch) doesn't depend on AI choice. Generalizing it would scope-creep into adding a 4th workflow surface to the multi-AI design.
