## ⛔ Anti-pattern 5 (NEW, blocking): the dev server locks the build output

## Critical Anti-Patterns (1-7, all still live)

| # | Anti-pattern | severity |
|---|---|---|
| 1 | Trusting a Codex-reported "clean run" instead of the process exit code | blocking |
| 2 | Reading a build warning baseline from a non-rebuild `dotnet build` | blocking |
| 3 | Running the gate spec as one batched invocation instead of `-g` per gate | blocking |
| 4 | Calling `gsd-tools query state.begin-phase` on this STATE.md | blocking |
| 5 | Running e2e/build against a server older than HEAD (see above) | blocking |
| 6 | Running e2e without `--workers=1 --project=<one>` — admin-lock cascade | blocking |
| 7 | A gate test with a silent guard, or a threshold never proven to fail | blocking |

**6 — The admin lockfile turns one hang into a whole-sweep failure.** `e2e/support/admin-lock.ts`
serializes every cut-lab test on the single lockfile `/tmp/deckflow-admin-e2e.lock`. Playwright runs
`chromium-desktop` and `chromium-mobile` **concurrently**, so a default invocation has two projects
fighting for it; worse, a test that hangs holds the lock for its full 120 s timeout, after which
every later spec dies with `Timed out waiting for admin e2e lock` — failures that have nothing to do
with the code under test. **A full 14-process sweep on 2026-08-03 ~23:12 was invalidated exactly
this way and had to be thrown out**; only the isolated re-run was trustworthy. Always
`--workers=1 --project=chromium-desktop`, one spec per process, `rm -f /tmp/deckflow-admin-e2e.lock`
between runs, then repeat for `chromium-mobile`. Related: `followup_admin_e2e_serialize_throttle`.
⚠ **Observed 2026-08-04:** the four gates *did* pass with both projects concurrent (2 workers).
**This does not retire the anti-pattern** — lock contention is a race, so it is intermittent by
construction and a single clean run is not evidence of absence. Keep the isolation discipline for
any run whose result you intend to act on.

**7 — A guard is politeness in a helper and a silent verdict in a gate.** Two of the four gates
shipped defects of exactly this shape and both reported PASS for months: G-3's
`if (!decideTab) return;` measured the wrong element, and G-4's `if (!textarea) return true;`
asserted success on missing markup. **Structural mitigation, not acknowledgement:** a gate gets
*no* early exits — every lookup is an assertion (`await expect(x).toBeVisible()`), and after
writing or touching one you **mutate its threshold to force a failure** and confirm both that it
fails and that the reported number is the quantity you meant. Green alone proves nothing; the four
gates here were green while three were incapable of failing. Second lesson from the same bug:
before asserting on an attribute, **grep the Razor that emits it** — G-2 and G-3 both matched
`[disabled]`, which `_WorkflowStepTabs.cshtml` documents it will never render.

**1 — Exit codes, not footers.** 07-02's Codex reported specs "rerun cleanly"; actual exit was 1.
**2 — MSBuild only prints warnings for projects it RECOMPILES.** Only `-t:Rebuild` shows the true
0-errors/9-CS8629 baseline; a plain incremental build prints `0 Warning(s)` while warnings exist.
**3 — The gate spec is `mode: 'serial'`.** A batched run halts on first failure and reports the
rest as "did not run", which skims as a pass. Run `-g "G-1"` … `-g "G-4"` as four processes.
**4 — `state.begin-phase` corrupts this STATE.md** (wrong counters, orphaned prose fragments; it
still parses so nothing complains). Hand-edit frontmatter.
`percent = ((completed_phases/total_phases) + (completed_plans/total_plans)) / 2`.

## Dispatch model

Codex writes the code; Claude plans, reviews and verifies. Seats: `gpt-5.6-terra` @ medium for
multi-file UI plans; `gpt-5.6-luna` @ low only for a single-file tight-spec edit. A round-2
dispatch after a review finding is terra work. **Never use `codex exec resume`** — it silently
ignores `-m` and downgrades the seat; pay the prefix cost and dispatch fresh. Always `-o <file>`
plus `> <log> 2>&1`; never let a Codex transcript into the parent context.
