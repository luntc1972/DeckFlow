# Phase 37.6: Harvest Video Block + Hard-Delete — Research

**Researched:** 2026-06-10
**Domain:** Content KB harvest/storage internals (DeckFlow.Core/Content + DeckFlow.CLI + DeckFlow.Web admin)
**Confidence:** HIGH (all evidence is file:line from the live codebase; greenfield `blocked_videos` table)

## Summary

This is grep-verified fact-finding for a planner, not a design. The seven research questions are answered below with exact file:line evidence. Three findings dominate planning and the planner MUST reconcile them against locked decisions D1–D4:

1. **Two separate databases, two separate id spaces.** `content_videos` (with the internal `long` PK + the YouTube id string) lives in the **local-only `content-kb.db`** (CLI-only; NOT registered in Web DI). `content_site_index` — the grid the admin actually sees at `/Admin/ContentKb` — lives in the **Postgres-eligible `content-site-index.db`** and is the ONLY content store wired into the Web app. The admin grid row's `KbEntryRow.Id` is the **site-index surrogate id**, and the YouTube id is recoverable via `IContentSiteIndexStore.GetByIdAsync(...).YoutubeVideoId` (= `natural_key_value`).

2. **The stable block key is the YouTube video id string.** Both the harvest dedup (`GetVideoByYoutubeIdAsync`) and the site-index natural key (`natural_key_value` where `natural_key_type='youtube_channel'`) key on it. The internal `content_videos.id` long is reassigned on every re-ingest, so the block row MUST key on the YouTube id string, not the long PK. `DeleteVideoAsync(long videoId)` takes the long — the block flow must resolve the YouTube id separately for the block row.

3. **`DeleteVideoAsync` relies on FK cascade for content-kb child rows but CANNOT reach `content_site_index`** (different DB / different connection, no FK). SC#1's "site-index row gone" requires a **separate, explicit delete on the site-index store** — which today has **no delete method at all** (only Set/Upsert/Get). That method must be added.

**Primary recommendation (for the planner, not a design lock):** Treat the block key as the YouTube id string; add `IContentSiteIndexStore.DeleteByIdAsync`/`DeleteByNaturalKeyAsync`; and explicitly resolve the D1 cross-process tension below before writing tasks — the CLI harvest process does NOT open `feedback.db` today.

## Q1 — Video id space (RESOLVED)

**Internal PK (the `long`):** `content_videos.id`.
- SQLite: `id INTEGER PRIMARY KEY AUTOINCREMENT` (`ContentVideoStore.cs:655`).
- Postgres: `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` (`ContentVideoStore.cs:601`).
- This is the `long videoId` that `IContentVideoStore.DeleteVideoAsync(long videoId, …)` takes (`IContentVideoStore.cs:139`; impl `ContentVideoStore.cs:288`). **Reassigned on every re-ingest** — NOT stable across re-harvest.

**Natural / YouTube id (the stable string):** `content_videos.youtube_video_id TEXT NULL` with table-level `UNIQUE (youtube_video_id)` (`ContentVideoStore.cs:603` Postgres / `:657, :664` SQLite). A `CHECK ((youtube_video_id IS NOT NULL) <> (rss_guid IS NOT NULL))` enforces exactly one of YouTube id / RSS guid per row (`:612` / `:666`).

**The column the ingest dedups on:** `youtube_video_id`, via `GetVideoByYoutubeIdAsync(sourceId, youtubeVideoId)` → `GetVideoByYoutubeIdSql` filtering `WHERE source_id = @sourceId AND youtube_video_id = @youtubeVideoId` (`ContentVideoStore.cs:444-457`).

**Same id reused by the site-index:** `content_site_index.natural_key_value` (TEXT) holds the YouTube id string when `natural_key_type='youtube_channel'` (`ContentSiteIndexStore.cs:473-476`, `GetNaturalKey` `:440-442`, schema `:621-625`).

**Conclusion the planner must lock:** the `blocked_videos` row + the ingest skip-check key on the **YouTube video id string** (`youtube_video_id` / `natural_key_value`), NOT the `long` PK. `[VERIFIED: codebase grep]`

## Q2 — Harvest ingest / persist path (RESOLVED)

**Exact insert point:** `ContentVideoStore.InsertVideoAsync(...)` (`ContentVideoStore.cs:70-107`), SQL at `InsertVideoSql` (`:485-503`, `INSERT INTO content_videos ... RETURNING id`).

**The single caller / skip-check site:** `CommandRunners.ResolveHarvestVideoIdAsync` (`CommandRunners.cs:991-1027`):
- Dedup read: `GetVideoByYoutubeIdAsync(source.Id, video.VideoId, ct)` at `:998`.
- If existing + terminal success → returns `(null, MayMarkFailed:false)` and the caller skips (`:999-1008`). This is the exact "already harvested" model the skip-check should mirror.
- The NEW-video insert: `InsertVideoAsync(source.Id, video.VideoId, rssGuid:null, …)` at `:1017-1025`.

**The skip-check belongs immediately before `:998`/`:1017`**, keyed on `video.VideoId` (the YouTube id string). Returning `(null, MayMarkFailed:false)` from `ResolveHarvestVideoIdAsync` for a blocked id reuses the existing "caller returns, no insert" plumbing (`HarvestVideoAsync` `:973-976`).

**Both harvest entry paths converge here:** the channel-walk path and the explicit `--video-ids` path BOTH call `HarvestVideoAsync` (`:919`, `:941`) → `ResolveHarvestVideoIdAsync`. One skip-check covers both. `[VERIFIED: codebase grep]`

## Q3 — DeleteVideoAsync coverage (RESOLVED — partial cascade)

`ContentVideoStore.DeleteVideoAsync` (`:288-300`) runs ONLY:
```
DELETE FROM content_videos WHERE id = @videoId;
```

**Child rows it relies on FK `ON DELETE CASCADE` to remove (all in `content-kb.db`):**
- `content_distill_status` — FK cascade (`:615` PG / `:669` SQLite)
- `content_transcripts` — FK cascade (`:621` / `:675`)
- `content_summaries` — FK cascade (`:628` / `:682`)
- `content_clips` — FK cascade (`:634` / `:688`)
- `content_tags` — FK cascade (`:641` / `:695`)

**FK enforcement is real for SQLite:** `RelationalDatabaseConnection.OpenConnectionAsync` issues `PRAGMA foreign_keys=ON;` on every SQLite open (`RelationalDatabaseConnection.cs:61-68`), and `ContentVideoStore` opens through it (`:374-375`). So the single-row delete DOES cascade all five child tables. **No orphans within `content-kb.db`.**

**The gap — `content_site_index` is NOT cascaded.** It is a different DB (`content-site-index.db`, prod Postgres) with **no FK to `content_videos`** (schema `:609-647` has only its own `natural_key` unique). `DeleteVideoAsync` cannot touch it. SC#1 ("dependent … site-index rows gone") therefore needs a **separate explicit delete on `IContentSiteIndexStore`**, which currently has **no delete method** (methods: `EnsureSchema`, `UpsertRow*`, `GetByNaturalKey`, `GetPublishedRows`, `GetAllRows`, `GetById`, `SetVisibility`, `SetEvergreen`, `SetVisibilityBySource` — `ContentSiteIndexStore.cs:44-350`). **Plan must add `DeleteByIdAsync` and/or `DeleteByNaturalKeyAsync`.**

**Connection used:** `ContentVideoStore` uses its injected `RelationalDatabaseConnection` (`:374-375`); for harvest it is the local SQLite `content-kb.db` (`CommandRunners.cs:772`). `[VERIFIED: codebase grep]`

## Q4 — feedback.db dual-dialect create pattern (RESOLVED)

**Canonical idempotent create pattern** (`FeatureFlagStore.EnsureSchemaAsync`, `FeatureFlagStore.cs:104-131`): a `_schemaReady` volatile + `SemaphoreSlim` double-checked gate, then `create.CommandText = _connectionInfo.IsPostgres ? PostgresCreateTableSql : SqliteCreateTableSql;` with `CREATE TABLE IF NOT EXISTS`. (`ContentVideoStore.EnsureSchemaAsync` `:43-67` uses the identical gate idiom.)

**Dual-dialect divergence the new `blocked_videos` table must follow** (`FeatureFlagStore.cs:154-170`):
- Postgres: `TEXT PRIMARY KEY`, booleans as `BOOLEAN ... DEFAULT TRUE`, timestamps as `TIMESTAMPTZ NOT NULL DEFAULT now()`.
- SQLite: same `TEXT PRIMARY KEY`, booleans as `INTEGER ... DEFAULT 1/0`, timestamps as `TEXT NOT NULL DEFAULT (datetime('now'))`.
- For a string-keyed table, model on `feature_flags(key TEXT PRIMARY KEY, …, updated_at <dialect ts>)` — `blocked_videos(youtube_video_id TEXT PRIMARY KEY, blocked_utc <dialect ts>)` fits this mold directly.

**Connection factory entry points (both alias the feedback connection):**
- `CreateFeedbackConnection(env)` → `CreateConnection(env, "feedback.db")` (`DeckFlowDatabaseConnectionFactory.cs:19-20`).
- `CreateHarvestStateConnection(env)` → `CreateFeedbackConnection(env)` (`:46-47`) — same logical DB.
- `CreateFeatureFlagConnection(env)` → `CreateFeedbackConnection(env)` (`:37-38`).
- Provider selection: `DECKFLOW_DATABASE_PROVIDER` (Sqlite default) + `DECKFLOW_DATABASE_CONNECTION_STRING` (`:74-111`); prod is Postgres.

**⚠️ D1 cross-process tension (HIGH — planner must resolve):** This factory is `DeckFlow.Web`-only. The **CLI harvest process does not use it** — it builds `ContentVideoStore(dbPath)` against the local SQLite `artifacts/content-kb.db` (`CommandRunners.cs:768-772`; default path `ResolveContentKbDatabasePath` → `cwd/artifacts/content-kb.db`, `:1659-1660`). The CLI never opens `feedback.db`. So a `blocked_videos` table "in feedback.db" is not reachable from harvest as written. Options the planner faces: (a) the harvest skip-check reads `blocked_videos` from a CLI-supplied connection (new `--feedback-db` / reuse `--db` pointing at a shared SQLite holding both, or a Postgres connection string); (b) the block-list lives in `content-kb.db` for the CLI's read while a copy/mirror in feedback.db satisfies "survives 37.5 reset". D1 explicitly wants feedback.db for reset-survival — the planner must thread a feedback/operational connection INTO the CLI harvest path. **This is the single biggest unresolved wiring decision.** `[VERIFIED: codebase grep]`

## Q5 — AdminContentKb action pattern (RESOLVED)

**Exact mutating-action shape** (`AdminContentKbController.SetVisibility`, `:127-145`; identical in `SetEvergreen` `:147-165`, `BulkSetVisibility` `:167-190`, `ReloadSeed` `:192-210`):
```csharp
[HttpPost("SetVisibility")]
[ValidateAntiForgeryToken]
public async Task<IActionResult> SetVisibility(long entryId, bool visible, CancellationToken cancellationToken)
{
    if (!SameOriginRequestValidator.IsValid(Request))
        return StatusCode(StatusCodes.Status403Forbidden, SameOriginRequestValidator.GetForbiddenMessage());
    await _store.SetVisibilityAsync(entryId, visible, cancellationToken).ConfigureAwait(false);
    TempData[BannerKey] = "Visibility updated.";
    return RedirectToAction(nameof(Index));
}
```
- Controller route: `[Route("Admin/ContentKb")]` (`:17`); per-action `[HttpPost("SetVisibility")]` etc. New actions: `[HttpPost("BlockAndDelete")]`, `[HttpPost("Unblock")]`.
- Banner: `TempData[BannerKey]` (`BannerKey = "AdminContentKbBanner"`, `:20`) surfaced via `AdminContentKbViewModel.SuccessBanner` (`:23`, set in `Index` `:106`).
- The exact same double-guard is also in `AdminFlagsController.Toggle` (`AdminFlagsController.cs:71-101`) — D4's named reference pattern.
- BasicAuth on `/Admin/*` is applied at the pipeline level (referenced `AdminFlagsController.cs:27` "Program.cs:330-332" branch); controllers do not re-declare it.

**Grid row → source video id mapping (CRITICAL for the Block button):**
- `KbEntryRow.Id` is the **site-index surrogate `long`** (`AdminContentKbViewModel.cs:60-61`, "the SetVisibility key"). It is NOT the YouTube id.
- To get the YouTube id for the block row, the action must call `IContentSiteIndexStore.GetByIdAsync(entryId)` → `.YoutubeVideoId` (= `natural_key_value`; `ContentSiteIndexStore.cs:256-289`, `ReadRow` `:475`). `KbEntryRow` does NOT currently carry the YouTube id, so either the VM gains a field or the action resolves it server-side via `GetByIdAsync`.

**Controller dependencies today:** only `IContentSiteIndexStore _store`, `IContentKbSeedLoader`, `IFeatureFlagCache`, `ILogger` (`:22-46`). It has **no `IContentVideoStore`** — see Q7 wiring gap. `[VERIFIED: codebase grep]`

## Q7 — Pitfalls (flagged)

1. **Two databases, not one (HIGH).** `content_videos` ⊂ local-only `content-kb.db` (CLI/SQLite, never on Render — `DeckFlowDatabaseConnectionFactory.cs:56-65`, "must never be uploaded to Render"). `content_site_index` ⊂ `content-site-index.db` (Postgres-eligible — `:71-72`). **Only the site-index store is registered in Web DI** (`Program.cs:178-181`); `IContentVideoStore` is NOT. So a Web admin "Block & delete" cannot call `DeleteVideoAsync` against prod content-kb (it doesn't exist in prod). The planner must decide what "delete" means from the Web admin: realistically it deletes the **site-index row** (the only thing the Web app and the public `/content-kb` browse actually read) + writes the `blocked_videos` row; the `content_videos`/child purge is a CLI-local concern (or a no-op in prod). Re-read SC#1 against this split.

2. **`content_site_index` has no delete method (HIGH).** Must add `DeleteByIdAsync(long)` (and/or `DeleteByNaturalKeyAsync(type,value)`) to `IContentSiteIndexStore` + `ContentSiteIndexStore` + `FakeContentSiteIndexStore`. Interface change ⇒ per CLAUDE.md memory "Verify builds test project too" — grep ALL implementers (real store, both fakes in `RunDistillAsyncTests.cs:626`, `TestDoubles/FakeContentSiteIndexStore.cs`) or the build breaks with CS0535.

3. **Postgres vs SQLite SQL divergence (HIGH — CLAUDE.md memory).** New `blocked_videos` table needs BOTH `PostgresCreateTableSql` (TIMESTAMPTZ/now(), BOOLEAN if any flag) and `SqliteCreateTableSql` (TEXT/datetime('now'), INTEGER 0/1). Booleans must round-trip through a `ReadBool` style reader (`FeatureFlagStore.cs:133-145`) — `bool|long|int|short|string`. Don't assume one dialect.

4. **`{ get; init; }` serialization trap (MED — CLAUDE.md).** Any new record/VM field (e.g. adding `YoutubeVideoId` to `KbEntryRow`, or a `BlockedVideoRow` record) must use `{ get; init; }` and NEVER be collapsed to `{ get; }` — System.Text.Json silently drops get-only props in .NET 9+ (has broken deserialization before). Do not let a formatter touch these.

5. **D1 block-list reachability from CLI (HIGH).** See Q4 — the CLI harvest does not open feedback.db. Threading an operational connection into `RunHarvestAsync` is net-new wiring. If skipped, the skip-check has nothing to read and SC#2 fails silently.

6. **Atomic block+delete boundary (MED).** Block (write `blocked_videos` in feedback.db/PG) and delete (site-index row in content-site-index.db/PG, + optional content-kb.db) span up to **three different connections / DBs** — a single SQL transaction cannot wrap them. The planner should define ordering (write block row first so a mid-failure leaves the video blocked-but-present rather than deleted-but-reharvestable) and accept best-effort atomicity, mirroring the harvest "record spend first" conservative-ordering comment (`CommandRunners.cs:1044-1046`).

7. **Unblock does not resurrect (D2 — already locked).** Unblock = delete the `blocked_videos` row only. No data restore. Tests should assert unblock re-permits a subsequent harvest insert (via the skip-check seam), not that rows come back.

8. **No existing `blocked_videos` / 37.5-reset coupling (LOW — good).** Grep found ZERO references to `blocked_videos` anywhere and no 37.5 corpus-reset code that touches it (only the pre-existing `ContentVideoStore.cs` matched `DELETE FROM content_videos`). The table is fully greenfield; placing it in feedback.db keeps it out of any `content_*` reset blast radius as D1 intends — but confirm the actual 37.5 reset implementation (not present in this tree yet) only purges `content_*` tables.
