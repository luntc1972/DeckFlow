Wire the three workflow services so each (a) writes into PacketSessionCache at the bottom of `BuildAsync` (line 467 / 198 / 196), and (b) exposes a PUBLIC ASYNC INSTANCE helper `TryComputeCacheKeyAsync(request, ct)` that the controller calls on the download path. **Architectural pivot from iter 1 (Codex reviews H1-H4):** The iter-1 design used a `public static string ComputeCacheKey(request, normalizedDeckSource, commander)` helper that required the CONTROLLER to supply pre-normalized deck text and pre-extracted commander name. Codex review correctly identified this CANNOT WORK for DeckAnalysisRequest (no `CommanderName` property exists) and DOES NOT enforce parity in the general case (D-02 normalization depends on which importer ran).

The iter-2 fix moved cache-key composition to a per-service async instance helper. Codex pass-2 then identified a remaining parity gap (H1 UNRESOLVED): the iter-2 plan's helper logic did not exactly match `DeckAnalysisPacketService.BuildAsync` — BuildAsync uses `Take(2)` partner inference + third-entry alphabetical guard at lines 226-253, may call `ValidateCommanderAsync` (Scryfall round-trip at line 283), and may oracle-normalize the commander at line 435. The iter-2 helper used `Take(1)` and tolerated the divergence.

**Pass-3 fix (this revision):** Introduce ONE shared private instance method `BuildDeckAnalysisCacheInputs(request, entries, commanderName)` in `DeckAnalysisPacketService`. Both `TryComputeCacheKeyAsync` (read) AND the line-467 write site call this helper with `commanderName` extracted at the **pre-Scryfall stage** (the post-line-271 value — after FirstOrDefault commander board, after Moxfield-ordering Take(2) partner inference, after the third-entry alphabetical guard, BUT BEFORE the ValidateCommanderAsync round-trip and BEFORE the oracle-name remap). The write site captures this pre-Scryfall commander into a separate local at the time of first extraction (around line 271) and reuses it at line 467 for the cache key. The post-validation / post-oracle commander is used in the result itself (correct behavior — the user sees the validated name), but NOT in the cache key.

This is the explicit single-stage decision: **cache key uses commander as extracted from the parsed deck entries BEFORE ValidateCommanderAsync / oracle-normalization.** Both read and write paths call the same `BuildDeckAnalysisCacheInputs` helper with the same pre-Scryfall commander value. Key parity is enforced by code locality.

For DeckComparisonService and MetaGapService: I verified (by reading BuildAsync line-by-line, 2026-05-21) that neither service has analogous pre/post commander mutation stages. DeckComparisonService extracts each deck's commander once inside LoadDeckAsync (`loadedDeck.CommanderName` is set by the loader at lines 140/144 and never mutated downstream — ValidateSameCommander at line 147 is a pure assertion, not a mutation). MetaGapService's commander is deterministic from request + loadedDeck at line 132-134 and unchanged through line 198. So the shared helper for these two services is simpler — no pre/post stage choice needed — but is still added for symmetry and single-source-of-truth.

Per checker B7: services call `PacketSizeEstimator.EstimateSizeBytes(result)` (co-located in PacketSessionCache.cs by Plan 01); service-side code does NOT inline property sums.

Per checker B3 and B6: cache writes attach to the FULL-PIPELINE return only — line 467 (DeckAnalysisPacketService), line 198 (DeckComparisonService), line 196 (MetaGapService). Short-circuit branches at 156 / 188 (deck-analysis) and 122 (meta-gap) DO NOT receive a cache write.

                   .Append(entry.CollectorNumber ?? string.Empty).Append('\n');
        }
