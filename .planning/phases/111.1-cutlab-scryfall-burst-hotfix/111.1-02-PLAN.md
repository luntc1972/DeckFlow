DeckFlow.Web/Services/UpstreamErrorMessageBuilder.cs — the EXACT strings, re-derived from source
(`:44-48` routing, `:67-90` detailed, `:92-107` site-specific). ROUND-1 REVIEW BLOCKER B-3: the
previous plan asserted a string this path never produces.

| Failure origin | Exception message | BuildScryfallMessage output |
|---|---|---|
| Batch `cards/collection`, any status N (`ScryfallReferenceResolver.cs:129-131` -> `"Scryfall card reference lookup (cards/collection) returned HTTP N."`) | contains `cards/collection` | `Scryfall card reference lookup failed while building the analysis packet with HTTP N. Try again shortly.` |
| Per-card fallback search, any status N (`ScryfallCardResolver.cs:153-156` -> `"Scryfall fallback lookup failed while resolving {card} with HTTP N."`) | contains `Scryfall`, not `cards/collection` | `Scryfall returned HTTP N. Try again shortly.` |

The routing reason: `BuildScryfallMessage` tries `BuildDetailedScryfallMessage` FIRST, which matches
on the substring `cards/collection` (`:73-77`) and returns the "analysis packet" wording; only when
that returns null does it fall through to `BuildSiteSpecificMessage`, which produces the
`"Scryfall returned HTTP N. Try again shortly."` shape. So the SC-3 banner literal named in the
ROADMAP arises from the FALLBACK path, and the batch path has its own distinct wording. Both must be
proven unreachable for 429; both must be proven still reachable for 503.

`CutLabController.Process()` renders `View("CutLab", ...)` as a normal 200 OK with `ErrorMessage`
populated — which is why prod logs showed a completed request while the user saw a banner. Asserting
on `CutLabProcessResult.ErrorMessage` is therefore an exact proxy for "the user sees the banner."
