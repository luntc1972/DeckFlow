**Researched:** 2026-06-01

**Confidence:** HIGH (all 3 critical unknowns verified live against real binaries on this machine)

## Summary

Phase 21.2 adds a `CliLlmDistillationService` that implements `ILlmDistillationService` by shelling out
to `claude` or `codex`, selected by `DECKFLOW_LLM_PROVIDER`, and falls back to the existing OpenAI path
by default. All 3 locked design decisions (D-01 through D-04) map cleanly onto existing patterns in the
codebase. The primary risk is the **cross-platform process launch** problem: on this machine `claude` and
`codex` are WSL-only binaries (`/home/clunt/.local/bin/claude`, `/home/clunt/.npm-global/bin/codex`) and
are **not in the Windows PATH**, so a child spawned by the Windows `dotnet.exe` process cannot find them.
The practical answer is that the operator runs `DeckFlow.CLI` from the WSL bash (using the Windows
`dotnet.exe` but setting `PATH` via `DECKFLOW_LLM_CLI_COMMAND` to an absolute path), or pipes through
`wsl.exe` on Windows. The `DECKFLOW_LLM_CLI_COMMAND` env-override escape hatch covers both cases.

The JSON I/O contracts for both CLIs were verified live. Claude Code's `--output-format json` emits a
single JSON object with the model text in `.result`. Codex `exec` emits only the final agent message on
stdout by default (agent chatter goes to stderr), making stdout directly parseable without a JSON layer.
Both CLIs accept the transcript via stdin — one way for Claude (piped stdin, instruction in `-p` arg),
two ways for Codex (instruction-in-arg + piped context, or `-` to read prompt from stdin).

**Primary recommendation:** Implement `CliLlmDistillationService` using `System.Diagnostics.Process`
(mirroring the existing `FfmpegAudioChunker` pattern), write prompt to stdin, read stdout. For `claude`:
parse `.result` from the JSON envelope. For `codex`: read stdout directly. Both paths feed into the same
fence-strip → brace-match → deserialize → shape-validate → retry pipeline.

### Pattern 2: TranscriptProviderFactory — Factory Shape to Copy Exactly

```csharp
// Source: DeckFlow.Core/Integration/TranscriptProviderFactory.cs (verified)
public static class TranscriptProviderFactory
{
    public const string EnvironmentVariableName = "DECKFLOW_YOUTUBE_TRANSCRIPT_PROVIDER";
    private const string DirectProvider = "direct";

    public static IYouTubeTranscriptFetcher Resolve(HttpClient httpClient)
        => Resolve(Environment.GetEnvironmentVariable(EnvironmentVariableName), httpClient);

    public static IYouTubeTranscriptFetcher Resolve(string? providerEnvValue, HttpClient httpClient)
    {
        ArgumentNullException.ThrowIfNull(httpClient);
        var provider = string.IsNullOrWhiteSpace(providerEnvValue)
            ? DirectProvider
            : providerEnvValue.Trim();

        if (string.Equals(provider, DirectProvider, StringComparison.OrdinalIgnoreCase))
            return new YouTubeTranscriptFetcher(httpClient);

        throw new NotSupportedException(
            $"Unsupported {EnvironmentVariableName} '{provider}'. Supported: direct.");
    }
}

// [ASSUMED] — direct copy of shape above, adapted for distillation
public static class LlmDistillationProviderFactory
{
    public const string EnvironmentVariableName = "DECKFLOW_LLM_PROVIDER";
    private const string OpenAiProvider = "openai";
    private const string ClaudeProvider = "claude";
    private const string CodexProvider = "codex";

    public static ILlmDistillationService Resolve(HttpClient httpClient)
        => Resolve(Environment.GetEnvironmentVariable(EnvironmentVariableName), httpClient);

    public static ILlmDistillationService Resolve(string? providerEnvValue, HttpClient httpClient)
    {
        ArgumentNullException.ThrowIfNull(httpClient);
        var provider = string.IsNullOrWhiteSpace(providerEnvValue)
            ? OpenAiProvider
            : providerEnvValue.Trim();

        if (string.Equals(provider, OpenAiProvider, StringComparison.OrdinalIgnoreCase))
            return new LlmDistillationService(httpClient);  // existing OpenAI impl

        if (string.Equals(provider, ClaudeProvider, StringComparison.OrdinalIgnoreCase))
            return new CliLlmDistillationService(ClaudeProvider);

        if (string.Equals(provider, CodexProvider, StringComparison.OrdinalIgnoreCase))
            return new CliLlmDistillationService(CodexProvider);

        throw new NotSupportedException(
            $"Unsupported {EnvironmentVariableName} '{provider}'. Supported: openai, claude, codex.");
    }
}
```

The cap-gate calls are at `CommandRunners.cs:990`, `1019`, `1047`. These must be conditional on the

### Anti-Patterns to Avoid

- **UseShellExecute=true with redirection:** .NET requires `UseShellExecute=false` to redirect
  stdin/stdout. These flags are mutually exclusive at the OS level.
- **Forgetting `process.StandardInput.Close()`:** Without closing stdin, `claude`/`codex` will wait
  forever for more input — the call hangs. Always close stdin after writing the transcript.
- **Reading stdout before process exits without async tasks:** Reading stdout synchronously while waiting
  for exit causes deadlock if the output buffer fills. Use `ReadToEndAsync` concurrently with
  `WaitForExitAsync` — mirror how `FfmpegAudioChunker` does `var stderrTask = process.StandardError.ReadToEndAsync(ct)` before `WaitForExitAsync`.
- **Calling `ComputeProjectedCallCostUsd` for non-openai provider:** Token pricing only applies to the
  OpenAI backend. The dry-run path in `RunDistillAsync` also calls `ComputeProjectedVideoCostUsd` and
  `WouldExceedCapAsync` (~L595-L607) — these must also be bypassed when provider is not openai.
- **Spawning `.cmd` shims via `FileName` alone on Windows:** `UseShellExecute=false` cannot execute
  `.cmd` files. Must use `FileName = "cmd.exe"`, `Arguments = "/c claude.cmd ..."` on Windows. The
  `DECKFLOW_LLM_CLI_COMMAND` env-override is the escape hatch; the auto-detect default uses the Linux
  binary name on Linux/WSL.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JSON schema injection | Custom schema-embedding protocol | Inline schema text in the system-prompt string (D-03) | CLIs have no Structured-Outputs API; prompt engineering is the only channel |
| Process I/O | Custom pipe abstraction | `System.Diagnostics.Process` + `ProcessStartInfo` | Already used by `FfmpegAudioChunker` in the same project; no new pattern needed |
| Token cost computation | New pricing table | Skip entirely for non-openai (D-04); `LlmSpendLedger.ComputeCostUsd` for openai path | Subscription billing = $0 per call; no token pricing for CLI backends |
| Structured output guarantee | Prompt design to make CLIs 100% reliable | Retry ×2 + shape-validate + mark-failed on persistent failure | CLIs give no `strict: true` guarantee; resilient parse pipeline is the right answer |

**Key insight:** The JSON repair pipeline (fence-strip → brace-match → deserialize) is a well-understood
pattern for LLM output. Rolling a custom parser is unnecessary — use `System.Text.Json.JsonSerializer`
with the same `JsonOpts` already in `LlmDistillationService` after extracting the JSON fragment.

`claude -p "<instruction>"` reads piped stdin as the user message context. Transcript goes to stdin;

echo "transcript content" | claude -p "Summarize this. Output JSON: {\"summary\": \"<text>\"}" \

`--model <alias-or-full-name>` selects the model. Confirmed with `--model claude-haiku-4-5`.

### Tool disabling (VERIFIED)

`--allowedTools ""` (empty string) disables all tools — no filesystem or Bash access. This is the
correct flag for a pure text-in/text-out distillation call.

### Auth model (VERIFIED)

Claude Code uses **OAuth credentials from `~/.claude/.credentials.json`** (or macOS Keychain) by

1. `ANTHROPIC_API_KEY` (if set — bills API account, not subscription)
2. `apiKeyHelper` script
3. `CLAUDE_CODE_OAUTH_TOKEN` env var (long-lived token from `claude setup-token`)
4. `/login` OAuth session (subscription — the normal case for this operator)

draws from a new monthly "Agent SDK credit," separate from interactive usage. The operator's subscription
plan must include this credit. [CITED: code.claude.com/docs/en/headless]

**IMPORTANT (`--bare` flag):** `--bare` mode skips OAuth and keychain reads — it requires

### Recommended default command (VERIFIED)

```bash
claude -p "<system-prompt+schema+transcript>" --output-format json --allowedTools ""
```

Where the full prompt (system-prompt + schema instructions + transcript) is written to stdin and the

Writes the final message to a file in addition to stdout. Not needed for DeckFlow since stdout is

## Critical Unknown 3: .NET System.Diagnostics.Process Cross-Platform Spawn

### Verified facts about this machine's setup

- **claude binary:** `/home/clunt/.local/bin/claude` (symlink, WSL Linux only)
- **codex binary:** `/home/clunt/.npm-global/bin/codex` (Node.js script shim, WSL Linux only)
- **Windows PATH:** Neither `claude` nor `codex` found via `where claude` / `where codex` on Windows
- **Windows dotnet.exe:** `/mnt/c/Program Files/dotnet/dotnet.exe` (this is the dotnet the project uses)
- **WSL available:** `wsl.exe` version 2.7.3.0 accessible from Windows

[VERIFIED: live environment probe, 2026-06-01]

### The cross-platform problem (HIGH PRIORITY)

When `DeckFlow.CLI` is launched via Windows `dotnet.exe` (the standard invocation per project memory),
the `CliLlmDistillationService` spawns a child process. That child process inherits the Windows
`dotnet.exe` environment — which does NOT include the WSL `/home/clunt/.local/bin` or
`/home/clunt/.npm-global/bin` directories.

**Net result:** `new ProcessStartInfo("claude")` fails with "The system cannot find the file specified"
on a standard Windows `dotnet.exe` invocation, because `claude` is not in the Windows PATH.

### Recommended launch strategy

**Tier 1 — `DECKFLOW_LLM_CLI_COMMAND` explicit override (always wins):**

```
# Windows operator with claude in WSL:
DECKFLOW_LLM_CLI_COMMAND=wsl.exe claude -p --output-format json --allowedTools ""

# WSL operator with claude on PATH (most common case):
DECKFLOW_LLM_CLI_COMMAND=claude -p --output-format json --allowedTools ""
```

When this env var is set, `CliLlmDistillationService` uses it verbatim as `FileName + Arguments` (first

### Stdin write pattern for CliLlmDistillationService

The `FfmpegAudioChunker` does NOT redirect stdin (ffmpeg reads files). The new pattern:

```csharp
// [ASSUMED] — required addition beyond FfmpegAudioChunker pattern
var startInfo = new ProcessStartInfo(fileName)
{
    Arguments = args,
    RedirectStandardInput = true,
    RedirectStandardOutput = true,
    RedirectStandardError = true,
    UseShellExecute = false,
    CreateNoWindow = true,
};
using var process = Process.Start(startInfo)
    ?? throw new InvalidOperationException($"'{fileName}' process failed to start.");

// Write transcript + close stdin BEFORE reading stdout to avoid deadlock
await process.StandardInput.WriteAsync(prompt, ct).ConfigureAwait(false);
process.StandardInput.Close();

// Read stdout and stderr concurrently to avoid buffer deadlock
var stdoutTask = process.StandardOutput.ReadToEndAsync(ct);
var stderrTask = process.StandardError.ReadToEndAsync(ct);
await process.WaitForExitAsync(ct).ConfigureAwait(false);
var stdout = await stdoutTask.ConfigureAwait(false);
var stderr = await stderrTask.ConfigureAwait(false);

if (process.ExitCode != 0)
{
    throw new InvalidOperationException(
        $"'{fileName}' exited {process.ExitCode}. stderr: {Tail(stderr)}");
}
```

**Deadlock prevention:** Reading stdout concurrently with stderr is critical. If stdout fills its OS
pipe buffer while .NET is waiting for the process to exit, the process blocks on write → deadlock.
Start both read tasks before `WaitForExitAsync`. [VERIFIED: standard .NET Process pattern documented
in Microsoft docs]

## Common Pitfalls

### Pitfall 1: Forgetting to close stdin

**What goes wrong:** Process hangs waiting for more input. `ReadToEndAsync` on stdout never returns.
**Why it happens:** The CLI reads until EOF on stdin. If stdin is never closed, the CLI thinks more
input is coming and blocks.
**How to avoid:** Call `process.StandardInput.Close()` (or `.Dispose()`) before `ReadToEndAsync`.
**Warning signs:** Test hangs rather than failing; process never exits.

### Pitfall 2: stdout/stderr deadlock

**What goes wrong:** `WaitForExitAsync` hangs; process is blocked trying to write to a full pipe buffer.
**Why it happens:** OS stdout/stderr pipe buffers are ~4KB–64KB. A large model response fills the
buffer; the process blocks on write; .NET is blocked on WaitForExitAsync → deadlock.
**How to avoid:** Start `ReadToEndAsync` tasks for BOTH stdout AND stderr BEFORE `WaitForExitAsync`.
The `FfmpegAudioChunker` does this for stderr — extend the same pattern to stdout.
**Warning signs:** Test hangs on long transcripts; works on short transcripts.

### Pitfall 3: `--bare` flag breaks subscription auth

**What goes wrong:** `claude --bare -p` cannot find credentials. Auth fails silently in headless mode.
**Why it happens:** `--bare` skips keychain/OAuth reads. Requires `ANTHROPIC_API_KEY` or `apiKeyHelper`.
**How to avoid:** Do NOT include `--bare` in the default claude command for DeckFlow. The operator's
interactive subscription session in `~/.claude/.credentials.json` is the auth source.
**Warning signs:** `"Not logged in"` in `is_error` result on first run.

### Pitfall 4: Windows `.cmd` shims cannot be spawned with `UseShellExecute=false`

**What goes wrong:** `Process.Start` throws `Win32Exception` ("The system cannot find the file"
or "Access is denied") when `FileName = "claude"` on Windows with `UseShellExecute=false`.
**Why it happens:** `.cmd` files are not executables — they require `cmd.exe` as interpreter.
**How to avoid:** Use `DECKFLOW_LLM_CLI_COMMAND=cmd.exe /c claude.cmd ...` on Windows, or
`DECKFLOW_LLM_CLI_COMMAND=wsl.exe claude ...` to run the WSL binary.
**Warning signs:** Works in WSL bash, fails when launched via `dotnet.exe` from Windows.

### Pitfall 5: Dry-run path also calls WouldExceedCapAsync

**What goes wrong:** Dry-run for a CLI backend incorrectly reports a cap-hit ("WOULD skip over cap")
even though there is no per-token cost.
**Why it happens:** The dry-run block in `RunDistillAsync` (~L595-L607) also calls
`ComputeProjectedVideoCostUsd` + `WouldExceedCapAsync`.
**How to avoid:** Guard the dry-run cap-check with the same `isSubscriptionProvider` flag.
**Warning signs:** Dry-run output says "$0.0000" projected but still "WOULD skip over cap".

### Pitfall 6: claude `-p` + `--output-format json` billing on June 15, 2026

**What goes wrong:** After June 15, 2026, `claude -p` on a subscription plan draws from a monthly
"Agent SDK credit" (separate from interactive usage). If the operator's plan doesn't include this,
calls fail with a new billing error.
**How to avoid:** Document in operator docs. Not a code problem — a subscription plan problem.
**Warning signs:** Auth succeeds but calls return a billing error after June 15.
