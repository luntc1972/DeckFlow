<domain>
## Phase Boundary

Today, when a user pastes a truncated AI response (Claude / ChatGPT / Gemini) into one of the three AI-workflow textareas — Step 3 deck_profile on `/deck-analysis`, Step 5 set_upgrade_report on `/deck-analysis`, the response textarea on `/deck-comparison`, or the response textarea on `/cedh-meta-gap` — the parse path throws `System.Text.Json.JsonReaderException`. None of the controller actions catch `JsonException` shapes (current filters cover only `InvalidOperationException` / `HttpRequestException` / `DeckParseException` / `InvalidDataException`), so the exception bubbles to the global `app.UseExceptionHandler("/Deck")` handler and the user sees the raw stack trace ("Expected end of string, but instead reached end of data. LineNumber: X | BytePositionInLine: Y" or "Expected depth to be zero at the end of the JSON payload. There is an open JSON object or array that should be closed. LineNumber: X | BytePositionInLine: Y").

Both shapes confirmed in `DeckFlow.Web/logs/web-20260520.log:569,598,910,942` during Phase 999.2 UAT on 2026-05-20.

Phase 999.4 closes the gap at the parse-site layer: wrap `JsonDocument.Parse(json)` in `ResponseParsers.ParseAnalysisResponse`, `ResponseParsers.ParseSetUpgradeResponse`, `DeckComparisonService.ParseComparisonResponse`, and `MetaGapService.ParseMetaGapResponse` with a `catch (JsonException)` (which covers `JsonReaderException`, since the latter inherits from the former) that re-throws `InvalidOperationException` with the locked friendly message. The existing controller `catch (InvalidOperationException)` filters then render the message inline via `ErrorMessage` on each page's view model — the same pattern Phase 10 / 999.1 already use for upstream and parse errors.

**What this phase does:**

1. Edit `DeckFlow.Web/Services/ResponseParsers.cs` — wrap `JsonDocument.Parse(json)` at lines 24 and 55 in `try { ... } catch (JsonException) { throw new InvalidOperationException(TruncatedResponseMessage); }`. The constant `TruncatedResponseMessage` lands in this file (or a closely related shared site if cleaner) and reads exactly: `"The pasted response appears truncated — wait for the AI to finish generating before copying, then re-submit."`
2. Edit `DeckFlow.Web/Services/DeckComparisonService.cs:915` — wrap `JsonDocument.Parse(json)` in the same pattern, raise `InvalidOperationException` with the same locked message string.
3. Edit `DeckFlow.Web/Services/MetaGapService.cs:946` — wrap `JsonDocument.Parse(json)` in the same pattern, raise `InvalidOperationException` with the same locked message string.
4. Add a controller-side carve-out on the three upload actions (`DeckAnalysisUpload` at `DeckController.cs:587` → catch at `:631`, `DeckComparisonUpload` at `DeckController.cs:841` → catch at `:912`, `CedhMetaGapUpload` at `DeckController.cs:1094` → catch at `:1163`) so that an `InvalidOperationException` carrying the `TruncatedResponseMessage` (raised when a corrupted zip contains truncated embedded response JSON) is re-mapped to a corrupted-zip-specific message before re-rendering. This preserves D-03 (single locked paste-path message) while not misleading users who uploaded a file. Catch-site is the existing controller `catch (InvalidOperationException)` on the three upload actions — branch on `exception.Message == ResponseParsers.TruncatedResponseMessage` and substitute the corrupted-zip copy. `DeckAnalysisUpload` invokes `DeckAnalysisPacketService.BuildAsync` which parses zip-restored JSON via `ResponseParsers.ParseAnalysisResponse` / `ParseSetUpgradeResponse` at `DeckAnalysisPacketService.cs:343, 366, 369, 490, 495` — same JsonException-to-InvalidOperationException re-throw applies (Codex pass-2 fix; original pass-1 carve-out missed this third site).
5. Add xUnit tests in `DeckFlow.Web.Tests` exercising the truncation branch on each of the 4 parse sites: feed truncated JSON fixtures (sourced from `web-20260520.log:569` and `:910` shapes), assert `InvalidOperationException` is thrown with the locked message string. Pure-helper static parse path → no HTTP, no WSL VSTest flake risk.
6. Manual UAT across the 3 pages (`/deck-analysis` Step 3 + Step 5, `/deck-comparison`, `/cedh-meta-gap`): paste deliberately truncated JSON, confirm the inline `ErrorMessage` renders, no stack trace surfaces, and the textarea content survives the re-render so the user can edit + re-submit.
7. `dotnet build DeckFlow.sln -c Release` exits 0 with zero new warnings vs the post-Phase-999.3 baseline.

**What this phase does NOT do:**

- Touch `JsonTextFormatterService.cs` — the parser chokepoint stays untouched. Phase 999.2 D-12 invariant (parser tolerates both `<result>` and fenced shapes) carries forward unchanged.
- Add controller-level `JsonException` filters — D-01 locks the catch at the parse-site layer; controllers see only `InvalidOperationException`. The upload-action D-06 carve-out (added during Codex pass-1 review convergence) operates on the existing `InvalidOperationException` catch, not on a new `JsonException` filter.
- Introduce a new public `TruncatedResponseException` type — D-01 rejected; `InvalidOperationException` re-throw is the smallest change consistent with existing controller catch boundaries.
- Inject `@aiPlatform.DisplayName` into the message — D-02 locked AI-agnostic universal noun. No new Razor surface; no `AiPlatform.Normalize(...)` call in any of the 4 service catch blocks.
- Classify exception messages (truncation vs malformed) by sniffing exception text — D-03 rejected (fragile across .NET versions, marginal UX gain). All `JsonException` is treated as truncation.
- Add semantic-completeness guards to `DeckComparisonService.ParseComparisonResponse` and `MetaGapService.ParseResponse` mirroring the `HasMeaningfulDeckProfileContent` / `HasMeaningfulSetUpgradeContent` pattern in `ResponseParsers`. D-07 (added during Codex pass-1 review convergence) defers this. Syntactically valid but semantically empty AI output (e.g., `{"deck_comparison":{"deck_a_name":"Atraxa"}}`) currently parses into mostly-empty objects and bypasses the new truncation UX. Out of scope for 999.4; tracked in `.planning/STATE.md` Deferred Items.
- Touch the EDH Top16 override parse at `MetaGapService.cs:407` — already has its own `catch (JsonException)` for admin/dev pasted fetched-entries JSON; not the user-facing AI-response surface.
- Touch `PacketArtifactStore.cs:529` — already has its own `catch (JsonException)` on zip-load; verify the user-visible message is acceptable but no new catch needed (D-03 carve-out).
- Touch the `ScryfallTaggerParsers.cs:66` `catch (JsonException)` — service-layer upstream API surface, not a user-paste path.
- Add a runtime flag (e.g., `DECKFLOW_TRUNCATED_RESPONSE_UX`) — CLAUDE.md prefers structural fixes over flags; behavior change is strictly an improvement on the prior stack-trace UX.
- Add per-AI copy variants, Step-3-vs-Step-5 differentiation, or "copy the entire JSON block from `{` to `}`" actionable hint — locked single-string message under D-02.
- Add a new logging line on the truncation catch — wrap-up gate D-05 path declined; the inline render is itself the user-visible signal, and the catch already swallows the exception, so no `_logger.LogWarning` is added. (If telemetry need arises later, revisit as a new phase.)
- Touch README — wrap-up gate D-05 path declined; the README does not mention parse-failure UX. Plan author confirms with a one-line grep at execution time (`grep -i "truncated\|parse fail" README.md`) and adds a note only if hits exist.
- Touch any non-AI-response JSON parse site (e.g., upstream Scryfall, Archidekt, Moxfield, EDH Top16 deserialize paths).

## Implementation Decisions

### Catch-site layer

- **D-01:** **Wrap `JsonDocument.Parse(json)` at the 4 AI-response parse sites and re-throw `InvalidOperationException` with the locked friendly message.** No new exception type; no controller-filter edits.

  Parse sites in scope (4):
  - `DeckFlow.Web/Services/ResponseParsers.cs:24` — `ParseAnalysisResponse` (Step 3 deck-analysis)
  - `DeckFlow.Web/Services/ResponseParsers.cs:55` — `ParseSetUpgradeResponse` (Step 5 set-upgrade)
  - `DeckFlow.Web/Services/DeckComparisonService.cs:915` — `ParseComparisonResponse` (deck-comparison)
  - `DeckFlow.Web/Services/MetaGapService.cs:946` — `ParseMetaGapResponse` (cedh-meta-gap)

  Catch shape (per site, ~3 lines added):
  ```csharp
  JsonDocument document;
  try
  {
      document = JsonDocument.Parse(json);
  }
  catch (JsonException)
  {
      throw new InvalidOperationException(TruncatedResponseMessage);
  }
  using (document)
  {
      // existing logic
  }
  ```

  (Plan author may equivalently use a local helper or pattern that preserves `using var` semantics — exact local refactor pattern is plan-author judgment, as long as `JsonDocument` is still disposed and the catch shape is symmetric across all 4 sites.)

  Rationale: `JsonReaderException` inherits from `JsonException`, so a single `catch (JsonException)` covers both observed shapes (`web-20260520.log:569,910`) and any sibling shape future .NET versions may add. Re-throwing `InvalidOperationException` is the smallest change consistent with the existing controller catch filters (DeckController action methods at lines 244, 266, 288, 359, 434, 485, 562, 631, 691, 811, 912, 975, 1067, 1163, 1235 etc. already cover `InvalidOperationException`). Per-parse-site locality means each catch sees the user-paste context (Step 3 vs Step 5 vs comparison vs meta-gap) for future per-site message differentiation if ever needed.

  Rejected alternatives:
  - Controller `when (... or JsonException)` filter additions — touches 3+ action methods, loses per-parse-site context, and the controller catch sees only the bottom exception text rather than which textarea was bad.
  - `JsonTextFormatterService.ExtractJsonPayload` chokepoint — that helper does regex + brace-scan, not a real parse; would either duplicate `JsonDocument.Parse` upstream of the existing callers or fire on legacy zip-load (parser is shared with `PacketArtifactStore` round-trip).
  - New public `TruncatedResponseException` type — over-engineered per CLAUDE.md "do not introduce abstractions beyond what task requires." A single use case does not earn a new public exception.

### Message wording + per-AI copy

- **D-02:** **AI-agnostic universal-noun single string, locked verbatim.**

  Verbatim message (binding):
  > `The pasted response appears truncated — wait for the AI to finish generating before copying, then re-submit.`

  Punctuation note: em-dash `—` (U+2014), not hyphen-minus. Match the surrounding codebase convention (Phase 999.1 `.page-lede` strings use em-dash; `JsonTextFormatterService` const wording uses em-dash). Plan author confirms exact bytes via grep at execution time.

  Storage: single `private const string TruncatedResponseMessage = "..."` declared once and reused across all 4 parse sites. Plan author chooses the host file:
  - **Option A (preferred default):** declare on `ResponseParsers` (existing internal static helper); reference via `ResponseParsers.TruncatedResponseMessage` from the two service classes. Keeps the string in the same file as 2 of the 4 catch sites.
  - **Option B:** declare on a small new shared internal static class (e.g., `internal static class ResponseParseMessages { public const string TruncatedResponse = "..."; }`) if Option A causes a circular reference or visibility issue.
  - Both options pass D-04 xUnit gate as long as the same const drives all 4 sites.

  Rationale: One string across 4 call sites means one place to edit if wording is ever refined, and no Razor `@aiPlatform.DisplayName` plumbing into a server-side service catch. Matches Phase 999.1 D-05 universal-noun convention.

  Rejected alternatives:
  - Per-AI `@aiPlatform.DisplayName` injection — needs the request handle in all 4 parse sites, lengthens copy, and produces 3 wording variants for marginal warmth gain. Phase 999.1 Hybrid pattern applies to Razor surfaces, not service-layer exception messages.
  - Actionable hint ("copy the entire JSON block from `{` to `}`") — longer copy; user already sees their truncated paste in the textarea (D-04 textarea preservation), which is the implicit hint.
  - Classification nuance (truncated vs malformed) — fragile string-sniffing on .NET exception messages; rejected under D-03.

### Upload-path carve-out (added by Codex pass-1 review convergence)

- **D-06:** **`DeckAnalysisUpload`, `DeckComparisonUpload`, and `CedhMetaGapUpload` re-map the truncation message to a corrupted-zip message before re-rendering.**

  All three upload actions reuse the same parsers as the paste actions. `DeckAnalysisUpload` invokes `DeckAnalysisPacketService.BuildAsync` which calls `ResponseParsers.ParseAnalysisResponse` / `ParseSetUpgradeResponse` at `DeckAnalysisPacketService.cs:343, 366, 369, 490, 495` to parse zip-restored JSON. `DeckComparisonUpload` calls `DeckComparisonService.ParseComparisonResponse` at `DeckController.cs:891`. `CedhMetaGapUpload` calls `MetaGapService.ParseResponse` at `DeckController.cs:1149`. After D-01 lands, a corrupted zip whose embedded response JSON is truncated would surface the paste-oriented "appears truncated" copy, which mis-leads users who uploaded a file rather than pasted text. The three upload `catch (InvalidOperationException)` blocks also reset `Request` to a new instance, so textarea preservation does not hold on those paths.

  Carve-out shape (per upload action, ~3 lines added to the existing `catch (InvalidOperationException)`):
  ```csharp
  catch (InvalidOperationException exception)
  {
      _logger.LogInformation(exception, "Deck-comparison upload failed validation.");
      var errorMessage = exception.Message == ResponseParsers.TruncatedResponseMessage
          ? "The uploaded zip contains an incomplete response payload. Re-export from the originating session or paste a fresh response."
          : exception.Message;
      return View("DeckComparison", new DeckComparisonViewModel
      {
          ActiveTab = DeckPageTab.DeckComparison,
          Request = new DeckComparisonRequest(),
          ErrorMessage = errorMessage
      });
  }
  ```

  Identical shape for `CedhMetaGapUpload` (`DeckController.cs:1163` catch block; same View / ViewModel substitutions, `DeckPageTab.CedhMetaGap`, `MetaGapRequest`) and for `DeckAnalysisUpload` (`DeckController.cs:631` catch block; `DeckPageTab.DeckAnalysis`, `DeckAnalysisRequest`). Constant string for the corrupted-zip copy is plan-author-chosen wording, but MUST be a single const reused across all three upload actions to keep one editable point of truth (plan author may host it on `PacketArtifactStore`, on a new `UploadMessages` static class, or inline-as-const at the controller — discretion). All three branches still log via `_logger.LogInformation` matching the existing pattern.

  Rationale: Honors D-03 (single locked message for paste path) without lying to upload users. Catch site is the existing `catch (InvalidOperationException)`, not a new `JsonException` filter, so the per-parse-site locality from D-01 is preserved. The message-string comparison is byte-identical and stable because the truncation re-throw uses the same `ResponseParsers.TruncatedResponseMessage` const that the controller now references.

  Rejected alternatives:
  - Add the corrupted-zip message inside the parser catch (sniff the call site somehow) — parser would need to know whether it was invoked from paste or upload; that information is not available at the parser layer without leaking controller context.
  - Skip the carve-out and accept the shared copy — explicitly rejected during Codex pass-1 review; "uploaded" + "paste" mismatch is a measurable UX regression.
  - Introduce a `TruncatedJsonException` subtype to discriminate from generic `InvalidOperationException` — over-engineering per D-01 rejection rationale.

### Semantic-completeness scope carve-out (added by Codex pass-1 review convergence)

- **D-07:** **Semantic-completeness guards (`HasMeaningful*Content` pattern mirror) explicitly OUT OF SCOPE for 999.4; tracked as a deferred backlog item.**

  `DeckComparisonService.ParseComparisonResponse` and `MetaGapService.ParseResponse` only check `result is null` and trust the deserializer otherwise. Inputs like `{"deck_comparison":{"deck_a_name":"Atraxa"}}` or `{"meta_gap":{"commander":"Tymna / Kraum"}}` parse successfully into mostly-empty objects and bypass both the existing wrong-shape guard and the new truncation UX. `ResponseParsers` already has a `HasMeaningfulDeckProfileContent` / `HasMeaningfulSetUpgradeContent` pattern (`ResponseParsers.cs:99-130`) that catches this for the deck-analysis paths.

  Why deferred from 999.4:
  - D-01 scope is "truncated JSON" — i.e., the `JsonException` path catching syntactically broken paste. Adding semantic-completeness mid-review expands the locked CONTEXT.md scope.
  - The semantic-empty case produces a non-truncated `InvalidOperationException` from a different code path; the truncation UX (D-01..D-06) does not regress in its presence — they are orthogonal issues.
  - Mirroring `HasMeaningful*Content` to two more services is real new code-shape work; better captured as its own focused phase than tacked onto 999.4.

  Tracked: `.planning/STATE.md` Deferred Items table receives a new entry: `tech_debt | Semantic-completeness guards for ParseComparisonResponse + ParseResponse (mirror HasMeaningful*Content pattern from ResponseParsers) | deferred — surfaced in Codex pass-1 999.4 review; tracks the "valid JSON but empty AI output" edge case`.

  Rejected alternatives:
  - Add the guards now — mid-review scope expansion violates locked CONTEXT.md scope; phase would balloon beyond the 5-6 commit envelope.
  - Drop without backlog entry — silent gap; future bug report would lose the chain-of-reasoning trail back to this review.

## Existing Code Insights

### Controller catch + render pattern (load-bearing for D-01 and D-06)
- Paste-path DeckController action methods at lines 912 (`DeckComparison` POST), 975, 1067 (cedh-meta-gap POST), and the deck-analysis POSTs around lines 691/811 all follow `catch (InvalidOperationException exception) { return View("ViewName", model with { ErrorMessage = exception.Message }); }`. D-01 piggybacks on this pattern: re-throw `InvalidOperationException` with the locked message from the parse-site catch, controller catches it as if it were a service-thrown business validation error, renders inline. No new controller code; no new view-model fields.
- Upload-path actions `DeckAnalysisUpload` (catch at ~line 631), `DeckComparisonUpload` (catch at ~line 912), and `CedhMetaGapUpload` (catch at ~line 1163) follow the same shape BUT reset `Request = new ...Request()` rather than preserving the user's input. D-06 inserts a message-substitution branch inside these existing catches: when `exception.Message == ResponseParsers.TruncatedResponseMessage`, swap in the corrupted-zip-specific copy; otherwise pass through unchanged. `DeckAnalysisUpload` differs from the other two in that its parse calls live inside `DeckAnalysisPacketService.BuildAsync` (lines 343, 366, 369, 490, 495) rather than a direct controller-level parser call.

### `JsonDocument.Parse` is the exception throw site
- `JsonReaderException` (inheriting from `JsonException`) is what `JsonDocument.Parse(string)` raises on malformed/truncated input. A single `catch (JsonException)` on each parse site covers both subclasses. Confirmed by `System.Text.Json.ThrowHelper.ThrowJsonReaderException` frames in `web-20260520.log:570,599,911,943` — all originate from `JsonDocument.Parse(json)` calls inside the 4 in-scope parse sites.

### `JsonTextFormatterService.ExtractJsonPayload` cannot replace the in-service catch
- `ExtractJsonPayload` does regex match on `<result>...</result>` then falls back to brace-scan on a string. It does NOT invoke `JsonDocument.Parse`. Adding `JsonDocument.Parse` validation inside `ExtractJsonPayload` would either (a) duplicate the parse that downstream callers already do, or (b) fire on `PacketArtifactStore` zip-load (which calls `ExtractJsonPayload` on legacy artifacts — Phase 999.2 D-12). D-01 explicitly rejects this option for those reasons.

### `using var document = JsonDocument.Parse(json);` refactor pattern
- All 4 parse sites use `using var document = JsonDocument.Parse(json);`. The try/catch wrapper requires either: (a) move `JsonDocument` declaration to a non-`using-var` local, parse inside try, then `using (document) { ... }` for the existing body, or (b) factor parse to a private static `TryParseOrThrow(string)` helper that owns the catch and returns `JsonDocument`. Both preserve dispose semantics. Plan-author judgment per D-05 "Claude's Discretion."

### Internal-ctor test seam (informational for D-04)
- `DeckFlow.Web/AssemblyInfo.cs:3` already declares `[assembly: InternalsVisibleTo("DeckFlow.Web.Tests")]`. If `ParseComparisonResponse` or `ParseMetaGapResponse` is currently `private`, plan author can promote to `internal static` to make the parse method directly testable, matching the established `internal` test-seam pattern (CardLookupService, etc.).

### `EDH Top16 override` and `zip-load` carve-outs
- `MetaGapService.cs:405-413` — admin/dev "fetched-entries override" path with its own `catch (JsonException)`. Different surface (developer-pasted JSON, not user AI-response paste); message acceptable as-is.
- `PacketArtifactStore.cs:520-540` (approximate; D-03 cites line 529 as the catch) — zip-load `catch (JsonException)`; failure mode is "uploaded zip contains malformed embedded JSON," which is structurally different from "user pasted half a response into a textarea." Carve-out under D-03.

### Existing `HasMeaningful*Content` pattern (relevant to D-07 deferral)
