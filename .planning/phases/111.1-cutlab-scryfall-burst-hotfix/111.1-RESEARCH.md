# Phase 111.1: Cut Lab Scryfall Burst Hotfix - Research

**Researched:** 2026-07-31
**Domain:** Scryfall REST integration (RestSharp + Polly v8 + custom throttle), C#/ASP.NET Core service-layer control flow
**Confidence:** HIGH (all claims verified against source at file:line, plus two read-only doc-page fetches; no live Scryfall API calls made)

## Summary

The root cause is already fully diagnosed in `.planning/debug/cutlab-import-scryfall-429.md` and is
NOT re-derived here. This document answers the five planning questions the orchestrator posed, plus
one additional verified finding (documented Scryfall per-endpoint rate limits) that materially
affects how the planner should size the fix for success criterion #2.

The single most important new finding: **`CutLabAnalysisContextBuilder.cs:410` is the ONLY caller,
across all five services that use `ScryfallReferenceResolver.ResolveBatchAsync`, that passes
`ResolveSingleAsync` (the two-call redundant path) as the fallback delegate.** The other four
callers (`DeckComparisonService`, `MetaGapService`, `DeckAnalysisPacketService`,
`DeckHistoryPageService`) already pass `SearchFallbackCardAsync`/`SearchPrintingFallbackCardAsync`
directly. This means success criterion #1 can be satisfied with a **one-line change at a single call
site**, touching zero shared code and creating zero blast radius on Manabase or Cut Lab's own
what-if simulator (both of which call `ResolveSingleAsync` directly, in a context where the
"redundant" collection POST is in fact the *only* attempt, not a real redundancy for them).

The second most important new finding: Scryfall's **documented, endpoint-specific hard rate limit
for `/cards/collection`, `/cards/search`, `/cards/named`, and `/cards/random` is 2 requests/second
(500ms)** — not the general "10 req/sec, all other methods" ceiling that `ScryfallThrottle`'s own
code comment cites. `ScryfallThrottle.MinInterval` is 200ms (~5 req/sec), which is **2.5x faster
than Scryfall's documented limit for exactly the endpoints Cut Lab's redundant fallback chain
hammers.** This is independent of and additive to the redundant-call defect, and the planner should
decide explicitly whether to fold a `MinInterval` change into this phase (it is not named in any of
the 6 ROADMAP success criteria, but it is squarely inside "correct handling of HTTP 429" and
leaving it unaddressed means the burst can still trip 429s even after the call-count fix, just at a
higher card-pool size).

**Primary recommendation:** (1) Fix the delegate wiring at `CutLabAnalysisContextBuilder.cs:410`,
not `ResolveSingleAsync` itself. (2) Narrow the `failOpenOnLookupErrors: false` catch in
`CutLabAnalysisContextBuilder.ResolveCardsAsync` to fail-open specifically on HTTP 429 (and
arguably 5xx) while still failing closed on everything else. (3) Surface the `MinInterval` /
documented-limit mismatch to the user as a discretionary in-scope-or-not decision before planning
proceeds — it is cheap to fix (one constant) but changes global Scryfall call pacing for every
service, not just Cut Lab. (4) For the match-key asymmetry (success criteria #4/#5), the evidence
below supports a *specific, narrower* fix than "adopt `CardNormalizer` in the batch matcher" — using
Scryfall's own already-deserialized `not_found` echo array instead of client-side name-equality —
but this still touches the four shared services and their locked "H2 lock" test, so it must be an
explicit decision, not a drive-by.

## Question 1 — Does `/cards/collection` echo `not_found`, and is it already deserialized here?

**Answer: YES to both.** This is the highest-leverage, most surprising finding.

**Evidence (Scryfall docs, fetched read-only 2026-07-31 via `curl` against
`https://scryfall.com/docs/api/cards/collection`):**

> "Each identifier will return up to one card. Identifiers that are not found will be returned in
> the `not_found` array. While cards will be returned in the order that they were requested, cards
> that aren't found will throw off the mapping of request identifiers to results, so you should not
> rely on positional index alone while parsing the data."

Max 75 identifiers per request (already respected — `ScryfallReferenceResolver.ScryfallBatchSize =
75`, `ScryfallReferenceResolver.cs:75`).

**Evidence (this repo already has the DTO and already uses it — just not in Cut Lab's path):**
- `ScryfallDtos.cs:32-34` — `ScryfallCollectionResponse(List<ScryfallCard> Data, [property:
  JsonPropertyName("not_found")] List<ScryfallCollectionIdentifier>? NotFound)`. This is deserialized
  on **every** collection response in the app, including the one `ScryfallReferenceResolver` and
  `ScryfallCardResolver` already receive — the field is just never read by either of them.
- `CardLookupService.cs:139-145` and `:214-216` — a **different, unrelated service** (`cards`
  deck-lookup text tool, not Cut Lab) already consumes `response.Data.NotFound` to build a
  `missingNames` set, using it as the authoritative miss signal instead of name-equality against
  returned `card.Name`. This is a working, tested, in-repo precedent for the pattern.

**Why this matters for the match-key asymmetry (success criteria #4/#5):** Scryfall's own docs
confirm that WITHOUT `not_found`, you cannot rely on positional index alone — but WITH it, you can:
subtract the `not_found`-echoed names from the submitted chunk, and the remainder maps 1:1
positionally, in original order, to `response.Data.Data`. This sidesteps needing ANY string
comparison against the *returned* `card.Name` at all (neither raw `OrdinalIgnoreCase` nor
`CardNormalizer.Normalize`) for determining hit/miss. A card that Scryfall itself resolves — e.g. a
single-slash Archidekt DFC name `"A / B"` that Scryfall's own `name` identifier lookup accepts and
resolves to `"A // B"` — would simply not appear in `not_found`, and the current phantom-miss (caused
by comparing `"A / B"` to the returned `"A // B"` and finding no match) would not occur.

**Caveat, explicitly flagged, not glossed over:** I could NOT verify, without a live API call
(disallowed by the task constraints beyond doc-page fetches), whether Scryfall's `name` identifier
lookup inside `/cards/collection` performs the same forgiving/fuzzy matching as `/cards/named`
(which its docs describe as accepting "fuzzy" input) or whether it requires an exact name match. If
it requires exact match, `"A / B"` would land in `not_found` regardless of the client-side matching
logic, and the not_found-based fix would not by itself resolve the DFC phantom-miss case — it would
only remove one class of client-side matching bugs (e.g. case/whitespace drift in what Scryfall DOES
resolve) while leaving DFC separator drift to the fallback path, same as today. **This is a real
open question for the ADR/decision in success criterion #4, not something to assume either way.**

**Planning implication:**
- This is evidence *for* a possible fix to the match-key asymmetry that is narrower and lower-risk
  than "adopt `CardNormalizer.Normalize` in the batch matcher" (which has its own DFC-collision risk
  — see `CardNormalizer.cs:24-28`, which drops the back face entirely when normalizing, so two
  different DFC cards sharing a front face would collide under that scheme). The not_found approach
  changes *miss detection*, not *name normalization semantics*, and Scryfall's own resolution
  becomes the source of truth.
- It does NOT eliminate the need for a fallback strategy entirely — cards Scryfall genuinely cannot
  resolve by name still land in `not_found` and still need the search/fuzzy fallback.
- It DOES require touching `ScryfallReferenceResolver.ResolveBatchAsync` (`:126-156`), which is
  explicitly marked LOAD-BEARING / "do not fix" and shared by 5 services — still requires an
  explicit decision per success criterion #4, not a drive-by.
- If adopted, the existing "H2 lock" test
  (`ScryfallReferenceResolverTests.ResolveBatchAsync_SingleSlashNameWithNormalizeOn_FallsThroughToFallbackKeyedByOriginalName`,
  `ScryfallReferenceResolverTests.cs:27-52`) asserts the OPPOSITE of what the not_found-driven
  version would do for its own fixture (its fixture supplies `NotFound: []` and a returned card
  `"A // B"` for request `"A / B"`; a not_found-driven matcher would treat that as a **hit**, not a
  fallback). This test would need to be rewritten to supply a fixture where `NotFound` actually
  contains `"A / B"` to keep asserting the fallback path, and a NEW test added asserting the hit
  path when `NotFound` does not contain the identifier. This is a concrete, scoped, single-file test
  edit — not evidence the fix is unsafe, but proof it is not free.

## Question 2 — Correct handling of 429 vs 404, and does the mapping onto `ScryfallThrottle` hold up?

**Answer:** The described three constants exist as claimed, the "does not retry 429" memory claim is
**TRUE for the Polly pipeline but FALSE for `ScryfallThrottle`**, and Scryfall's documented rate
limit is materially stricter than the code's own comment claims for exactly the endpoints in play.

**Evidence — Polly pipeline does not retry 429 (confirmed):**
`ResiliencePipelineFactory.BuildScryfall` (`ResiliencePipelineFactory.cs:123-139`):
```
.AddRetry(new RetryStrategyOptions<RestResponse>
{
    MaxRetryAttempts = 2,
    BackoffType = DelayBackoffType.Exponential,
    UseJitter = true,
    ShouldHandle = new PredicateBuilder<RestResponse>()
        .HandleResult(static r => r.StatusCode >= HttpStatusCode.InternalServerError)   // 5xx ONLY
        .Handle<Exception>(static ex => IsTransientException(ex)),
})
```
Comment at `:120`: "Retry(2 on 5xx ONLY - NOT 429, defer to ScryfallThrottle backoff)." Confirmed by
reading the predicate: `r.StatusCode >= HttpStatusCode.InternalServerError` excludes 429 (`409 <
429 < 500` is false — 429 is below 500, so it is excluded). Correct as documented.

**Evidence — `ScryfallThrottle` DOES retry 429 (this is the actual retry layer):**
`ScryfallThrottle.ExecuteAsync<T>` (`ScryfallThrottle.cs:43-61`) loops up to `MaxRetryAttempts = 2`
additional attempts while `(int)response.StatusCode == 429`, honoring `Retry-After` (delta-seconds
or HTTP-date, `ParseRetryAfter`, `:192-215`) capped at `RetryAfterCap = 30s`
(`ResolveRetryDelay`, `:115-131`), falling back to `FallbackRetryDelay = 2s` when the header is
absent or unparseable. This layer is well-covered by `ScryfallThrottleTests.cs` (retry-once,
fallback-delay, above-cap-gives-up, both generic and non-generic overloads — 9 tests already named
in the file). **No new tests are needed here for success criterion #6** unless `MinInterval` itself
changes (see below).

**Evidence — documented Scryfall rate limits (fetched read-only 2026-07-31, `curl` against
`https://scryfall.com/docs/api/rate-limits`, HTTP 200):**
> "The Scryfall API (api.scryfall.com) has the following hard rate limits: `/cards/search` — 2/second
> (500ms); `/cards/named` — 2/second (500ms); `/cards/random` — 2/second (500ms); `/cards/collection`
> — 2/second (500ms); `/cards/manifest` — 10/minute (10,000ms); All other methods — 10/second
> (100ms)... Receiving an HTTP 429 response will result in your access being limited for 30 seconds.
> Continuing to overload the API after this point may result in a temporary or permanent ban of your
> application... It is not acceptable to ignore HTTP 429 responses."

**The code's own comment is wrong about which ceiling applies.** `ScryfallThrottle.cs:13`: "Scryfall
asks for 50-100ms between requests. We pace at 200ms (~5 req/sec) to leave plenty of headroom for
Cloudflare's burst detection, which is stricter than the published 10 req/sec ceiling." The 10
req/sec figure is real but applies only to "all other methods" — every endpoint Cut Lab's redundant
fallback chain touches (`cards/collection`, `cards/search`, and `cards/named` inside
`SearchPrintingFallbackCardAsync`) is individually capped at **2/sec (500ms)**, 2.5x slower than the
code's 200ms pacing. This is consistent with, and independently explains part of, the observed
burst: even after halving the redundant-call count (success criterion #1), a large-miss-count import
alternating `cards/collection`/`cards/search` at 200ms spacing will still exceed the documented
per-endpoint ceiling and can still draw 429s, just less often.

**Planning implication:**
- Success criterion #2 ("A Scryfall 429 during Cut Lab pool intake no longer aborts the entire
  import") is satisfiable purely by the fail-open policy change described below — the throttle
  already retries automatically before any exception is even raised.
- However, the ROOT cause of *why* 429s happen at all is partially the pacing mismatch, and this
  finding is squarely responsive to the "correct handling of HTTP 429" research question even though
  it's not literally named as a success criterion. **Recommend surfacing to the user as an explicit
  in/out-of-scope call**: raising `MinInterval` to `500ms` (matching the documented per-endpoint
  limit) is a one-line, low-risk change, but it is a **global** change (the static `ScryfallThrottle`
  gate serves every Scryfall caller in the app, not just Cut Lab), so it affects request latency for
  DeckComparison, DeckAnalysis, MetaGap, DeckHistory, Manabase, and CardLookupService too — small
  per-call cost (Ξ+300ms) but a real behavior change outside Cut Lab, worth a deliberate go/no-go
  rather than folding it in silently under "hotfix."
- If NOT changed this phase, the ADR/decision for #4/#5 should explicitly note that the burst-count
  fix (#1) reduces but does not eliminate 429 risk for very-high-miss-count pools, because the
  documented per-endpoint ceiling is still being exceeded by design.

## Question 3 — Blast radius of each candidate change

**Answer:** Confirmed via full-repo grep of every non-test call site of `ResolveSingleAsync`,
`ResolveBatchAsync`, and `IScryfallCardResolver`. This directly changes the recommended shape of
success criterion #1's fix.

**`ResolveSingleAsync` has exactly 3 non-test callers, and they use it in two different roles:**

| Caller | File:line | Role | Is the "redundant" POST actually redundant here? |
|---|---|---|---|
| `CutLabAnalysisContextBuilder` | `:410` | Post-batch-miss fallback delegate passed into `ResolveBatchAsync` | **YES** — the identifier already failed on `cards/collection` in the batch call moments earlier |
| `CutLabSimulationService` | `:328` | Standalone single-card resolve (what-if simulation), NOT preceded by any batch collection call for that name | **NO** — this is the only collection attempt for that card |
| `ManabaseAnalysisService` | `:1094` | Standalone single-card resolve, NOT preceded by any batch collection call for that name | **NO** — this is the only collection attempt for that card |

**Therefore modifying `ResolveSingleAsync` itself (e.g. adding a "skip collection" parameter or
removing the POST unconditionally) would regress `CutLabSimulationService` and
`ManabaseAnalysisService`** — both would lose their only `cards/collection` attempt and go straight
to the slower/less-precise `cards/search` fallback for every card, not just batch-misses.

**The delegate-wiring fix avoids this entirely.** Grep of every `ResolveBatchAsync` call site shows
Cut Lab is the outlier:

| Caller | File:line | Fallback delegate passed |
|---|---|---|
| `DeckComparisonService` | `:378` | `_scryfallCardResolver.SearchFallbackCardAsync` |
| `MetaGapService` | `:564` | `_scryfallCardResolver.SearchFallbackCardAsync` |
| `DeckAnalysisPacketService` | `:1895` | `_scryfallCardResolver.SearchPrintingFallbackCardAsync` |
| `DeckHistoryPageService` | `:271` | `SearchPrintingFallbackCardAsync` (local wrapper) |
| **`CutLabAnalysisContextBuilder`** | **`:410`** | **`_cardResolver.ResolveSingleAsync`** ⚠ the only one that re-POSTs |

`SearchFallbackCardAsync`'s signature — `Task<ScryfallCard?> SearchFallbackCardAsync(string
cardName, CancellationToken cancellationToken)` (`ScryfallCardResolver.cs:24,129`) — already matches
the `Func<string, CancellationToken, Task<ScryfallCard?>>` delegate shape `ResolveBatchAsync`
expects (`ScryfallReferenceResolver.cs:99`), exactly as it's already passed by
`DeckComparisonService`/`MetaGapService`.

**Recommended fix shape for success criterion #1:** change `CutLabAnalysisContextBuilder.cs:410`
from
```csharp
(name, ct) => _cardResolver.ResolveSingleAsync(name, ct),
```
to
```csharp
(name, ct) => _cardResolver.SearchFallbackCardAsync(name, ct),
```
This is a **single line in a single file**. `ResolveSingleAsync` itself is untouched, so
`CutLabSimulationService` and `ManabaseAnalysisService` are provably unaffected (they never call
through `ResolveBatchAsync`). This is a materially smaller and safer change than the debug doc's
originally-suggested "remove the redundant POST inside `ResolveSingleAsync`" — that framing would
have required either a new overload/parameter or accepted a real regression in the two standalone
callers. **This finding should replace, not merely inform, the plan's approach to success criterion
#1.**

**Blast radius of the fail-open fix (success criterion #2):** `ResolveCardsAsync` is shared by BOTH
`BuildAsync` (`:179`, already `failOpenOnLookupErrors: true`, i.e. always fail-open — no behavior
change if the catch clause narrows) and `ResolvePoolCardsAsync` → `CutLabPageService.ResolveEntriesAsync`
(`:500`, `failOpenOnLookupErrors: false`, the only false caller). Narrowing the catch block at
`CutLabAnalysisContextBuilder.cs:432-437` to distinguish 429 from other failures only changes
observable behavior for the `false` caller, i.e. only `CutLabPageService.ResolveEntriesAsync`. No
other consumer of `CutLabAnalysisContextBuilder` is affected. Confirmed no other caller passes
`failOpenOnLookupErrors: false` anywhere in the non-test codebase (grep above found only these two
call sites for the parameter).

**Test seam pattern (confirmed, matches CLAUDE.md's documented convention):** every HTTP-touching
service exposes a public DI ctor plus an `internal` ctor taking `Func<RestRequest,
CancellationToken, Task<RestResponse<T>>>` override delegates, gated by `[assembly:
InternalsVisibleTo("DeckFlow.Web.Tests")]`. `ScryfallCardResolver`'s internal ctor
(`ScryfallCardResolver.cs:63-93`) is the canonical example and is already used by both
`ScryfallCardResolverTests` and `ScryfallReferenceResolverTests`. New regression tests for success
criteria #1/#2/#6 should follow this exact pattern rather than mocking `IScryfallCardResolver`
directly, OR use the existing `CountingResolver`/`ThrowingResolver` doubles in
`CutLabAnalysisContextBuilderTests.cs` when testing at the `CutLabAnalysisContextBuilder` level
(closer to the actual bug, since the delegate-wiring fix lives there).

**What a regression test for success criterion #1 needs to assert:** given a batch with N misses,
the fallback delegate (`SearchFallbackCardAsync`, post-fix) is invoked exactly N times and
`ExecuteCollectionAsync` is invoked exactly once (the initial batch call) — not `N+1` times as today
via the redundant `ResolveSingleAsync` path. The `CountingResolver` double already tracks
`ExecuteCollectionCalls`; it needs the new `SearchFallbackCalls` counter described above.

**What a regression test for success criterion #2 needs to assert:** a 429 raised during
`ResolvePoolCardsAsync`'s fallback dispatch with `failOpenOnLookupErrors: false` does NOT propagate
— the pool resolution completes with that card in the "missing" set instead — while a non-429
failure (e.g. `ScryfallReferenceCollectionException` for the batch call itself, or an unrelated
exception type) still propagates as it does today. This can be built with a resolver double whose
`SearchFallbackCardAsync` throws `new HttpRequestException(msg, null,
HttpStatusCode.TooManyRequests)` for a specific name.

## Question 5 — Caching: is there a cheap win, or does a cold import legitimately re-resolve everything?

**Answer: no bypass found; a cold import legitimately re-resolves everything; no cheap win exists
without scope creep.**

`CutLabResolvedCardCache` (`CutLabResolvedCardCache.cs`) is a dedicated `IMemoryCache` instance
(`SizeLimit = 20,000,000` bytes, separate from the shared app cache — "the 512 MB render cap requires
Cut Lab cache pressure to stay isolated," `:35`), keyed by a SHA-256 hash of the normalized
`(name, quantity)` multiset (`ComputePoolKey`, `:44-67`, delegates to `PacketSessionCache.ComputeKey`),
with a 30-minute absolute TTL (`EntryTtl`, `:16`).

`CutLabPageService.ResolveEntriesAsync` (`:490-502`) already checks
`_analysisContextBuilder.TryGetCachedResolvedCards` FIRST and only calls
`ResolvePoolCardsAsync` (which triggers live Scryfall calls) on a cache miss. This is correctly
wired — there is no bypass to fix.

By construction, the cache is keyed on the exact pool contents. **A genuinely new deck paste (first
time seeing that exact card+quantity combination) is a guaranteed cache miss** — there is nothing to
hit yet. The 21-request burst described in the debug doc is specifically the cold-import case; a
second identical import within 30 minutes would hit the cache and emit zero Scryfall calls. This is
already optimal for the "repeat the same import" case and does not need touching.

**No cheap win surfaced.** Flagging explicitly per the task's "do not scope-creep" instruction: I
looked for (a) a bypass — none found; (b) a shorter TTL or narrower key that's accidentally causing
avoidable misses — the 30-minute TTL and exact-multiset key look intentional and reasonable; (c) any
opportunity to warm the cache from a *related* but not identical pool (e.g. partial overlap) — this
would be a real feature, not a hotfix, and is out of scope here.

```
UpstreamErrorMessageBuilder.BuildScryfallMessage -> "Scryfall returned HTTP 429. Try again shortly."
                  |
                  v
CutLabController.Process() renders View("CutLab", ...) as a normal 200 OK
                  |
                  v
Browser: sees error banner, logs show a completed 200 request
```

### Recommended fix (minimal diff, matches Q3 findings)

```
CutLabAnalysisContextBuilder.cs:410
  fallback delegate: ResolveSingleAsync  -->  SearchFallbackCardAsync
    (removes the redundant second POST /cards/collection; goes straight to
     GET /cards/search on a batch miss, exactly like the other 4 services)

CutLabAnalysisContextBuilder.cs:432-437 (catch block inside ResolveCardsAsync)
  when failOpenOnLookupErrors == false:
    if exception is HttpRequestException { StatusCode: HttpStatusCode.TooManyRequests }
      -> treat as fail-open (log + continue), same as the true-path already does
    else
      -> rethrow (unchanged)
```

### Anti-Patterns to Avoid

- **Editing `ResolveSingleAsync` to "fix" the redundant call.** Confirmed by Q3: this method is
  shared by two standalone (non-batch-fallback) callers where the collection POST is not redundant.
  Editing it would regress `CutLabSimulationService` and `ManabaseAnalysisService`.
- **Editing the match key inside `ScryfallReferenceResolver.ResolveBatchAsync` as a side effect of
  fixing #1 or #2.** It is explicitly LOAD-BEARING for 4 other services and has a dedicated locked
  test. Any change here is success criterion #4's job, gated by an explicit decision, never a
  drive-by inside the #1/#2 fix.
- **Widening `failOpenOnLookupErrors` fail-open logic globally (i.e., making `false` behave like
  `true`).** The debug doc and roadmap both specifically ask for a **429-vs-404 (or 429-vs-everything-else)
  distinction**, not blanket fail-open on the intake path — the intake path's fail-closed default
  on genuine, non-transient failures is presumably intentional (surfacing real problems to the user
  rather than silently importing a partial pool).

## Common Pitfalls

### Pitfall 1: Conflating "redundant call" with "the method that makes the redundant call"
**What goes wrong:** Fixing `ResolveSingleAsync` directly (as the debug doc's suggested direction
implies) regresses two unrelated standalone callers.
**Why it happens:** The debug doc's investigation correctly identified `ResolveSingleAsync` as
*where* the redundant POST executes, but didn't cross-reference all its callers to see it plays two
different roles.
**How to avoid:** Fix the call site (`CutLabAnalysisContextBuilder.cs:410`), not the shared method.
**Warning signs:** Any diff that touches `ScryfallCardResolver.cs` for success criterion #1 should
be treated as suspicious and cross-checked against `CutLabSimulationService.cs:328` and
`ManabaseAnalysisService.cs:1094`.

### Pitfall 2: Assuming `ScryfallThrottle`'s 200ms pacing is correct because "it says 10 req/sec is the ceiling and we're at 5"
**What goes wrong:** The code comment cites the wrong ceiling. The endpoints actually in play
(`cards/collection`, `cards/search`, `cards/named`) are individually capped at 2/sec (500ms), not
10/sec.
**Why it happens:** Scryfall's rate-limit docs distinguish a general "all other methods" ceiling from
per-endpoint hard limits on the four card-lookup endpoints; the original comment appears to have
picked up only the general figure.
**How to avoid:** Treat `MinInterval` as a discretionary in-scope decision for this phase (see Q2),
not settled fact.
**Warning signs:** If success criterion #6's regression run still shows occasional test-environment
429s under a large synthetic miss count, this is why.

### Pitfall 3: Rewriting the "H2 lock" test as collateral damage of an unrelated fix
**What goes wrong:** `ScryfallReferenceResolverTests.cs:27-52` is a deliberately-named regression
lock for the CURRENT (buggy) match-key behavior. If success criterion #1's fix is scoped correctly
(delegate wiring only), this test is untouched. If a planner accidentally touches
`ScryfallReferenceResolver.ResolveBatchAsync`'s matching logic while doing #1 or #2, this test will
fail — and that failure should never be silently "fixed" by weakening the assertion; it should be
recognized as the ADR-gated match-key change from #4, done deliberately and separately.
**How to avoid:** Keep #1/#2's diff confined to `CutLabAnalysisContextBuilder.cs` (single file);
keep #4/#5's diff (if adopted) confined to `ScryfallReferenceResolver.cs` +
`ScryfallReferenceResolverTests.cs`, as its own reviewable unit.
