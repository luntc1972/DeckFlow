## Description

Cut Lab currently builds its pool from `AnalyzedBoards = { "mainboard", "commander" }` (`CutLabPageService.cs:87-88`, applied at `:207`), silently dropping every `sideboard` and `maybeboard` entry the importer already fetched. For most Commander decks the candidate/extra cards live on the maybeboard ("considering") list, so a deck whose mainboard is exactly 100 imports as "≤100 cards — not oversized" and Cut Lab rejects it, even though the user's real oversized pool is mainboard + extras.

Add an intake option **"Include sideboard & maybeboard cards"** (default OFF) that, when checked, expands the analyzed board set to also include `sideboard` and `maybeboard`, so those candidate cards join the pool and the deck becomes an oversized 101–150 pool Cut Lab can trim.

**User decision (2026-07-20):** the option includes BOTH sideboard and maybeboard under one checkbox (Commander "considering"/maybeboard is where extras usually live).

## Context / grounding

- Importers already fetch both boards: `MoxfieldApiDeckImporter` (`AddBoardEntries(root, "maybeboard"...)` + `"sideboard"`), `ArchidektApiDeckImporter` (category→board mapping). Each `DeckEntry` carries `Board`.
- Existing precedent to mirror for naming/UI: `DeckAnalysisRequest.IncludeCandidateReferencesInAnalysis` (`DeckAnalysisRequest.cs:266`) — "includes the deck's sideboard and maybeboard cards … as candidate references".
- The pool filter is the single line `.Where(entry => AnalyzedBoards.Contains(entry.Board))` at `CutLabPageService.cs:207`.
- Commander inference already excludes sideboard/maybeboard from being reflagged as commander (`:490-494`) — KEEP that. Including those boards in the POOL is independent of commander inference; a maybeboard card must never be inferred as the commander.
- The oversized-range validator (101–150) is unchanged: if including extras pushes the pool past 150, the user correctly sees the existing "too large" message. Not in scope to change.
