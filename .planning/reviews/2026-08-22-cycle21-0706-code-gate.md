## Findings

### R2-1 [HIGH] — Arrow navigation activates the reserved, aria-disabled Plan tab · OPEN

`wwwroot/ts/cut-lab.ts:556` and `:571`

F-2's fix removed the native `disabled` attribute from `aria-disabled` step tabs, which was correct.
But the roving-focus list built for arrow navigation still filters on the DOM property:

```ts
const enabledTabs = getStepTabs().filter(tab => !tab.disabled);
```

With native `disabled` gone, `tab.disabled` is `false` for every tab, so the reserved Plan step joins
the list. Arrow-Right onto it then runs `nextTab.focus(); activateStepTab(nextTab, false);` — which
selects the tab and reveals the empty reserved panel that F-3 exists to keep shut.

The capture-phase guard at `site.ts:294-304` blocks *activation by click*. It cannot see a direct
`activateStepTab` call, so it does not fire here.

**Confirmed by reading the source, not only reported.** F-2 and F-3 are therefore incomplete as
landed: keyboard users can open a step the mouse path refuses to open.

*Fix:* filter the roving list on `aria-disabled` rather than the native property, and skip
`activateStepTab` when the destination carries `aria-disabled="true"` — focus may move there
(a roving tablist should not strand a tab), selection must not follow.

*Killing mutation:* remove the new guard; a test asserting Plan receives focus while its
`aria-selected` stays `false` and the previously visible panel stays visible must fail.

### R2-2 [MEDIUM] — The F-1 regression guard is synthetic · OPEN

`DeckFlow.Web/e2e/cut-lab-workflow-ux.spec.ts:183` — **VACUOUS**

The spec injects a fixed-position workflow button into `.cutlab-proposal__body`, markup production
never emits, and then checks its geometry. Making `.cutlab-proposal--pinned` intercept pointer events
can fail this synthetic check, so it is not inert — but passing it certifies nothing about whether a
*real* workflow control stays clickable. F-1 is the finding this guard exists to prevent recurring,
and F-1's original defect was exactly "tests went green against a live defect".

*Fix:* assert against a control the page actually renders — click through the sticky region at a
point the pinned card overlaps and confirm the underlying control receives the event.
