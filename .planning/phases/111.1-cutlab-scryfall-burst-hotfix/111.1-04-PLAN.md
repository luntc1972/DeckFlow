THE LATENCY FORMULA — corrected per round-1 review W-4. The previous plan used
`(calls - 1) x 300ms` and called it "a measurement, not an estimate." It is neither: it silently
assumes zero service time. The gate enforces a MINIMUM SPACING between call starts, so when a call
itself takes `s` milliseconds, only `max(0, interval - s)` of the interval is actually spent waiting.
The production anchor shows 200-300ms of real per-call latency, which is at or above the current
200ms interval — meaning today's pacing may already be contributing little or no added wait.

  added wall-clock = (throttled calls in the flow - 1) x max(0, 500ms - measured per-call service time)

Report `(calls - 1) x 300ms` explicitly as the UPPER BOUND (the zero-service-time case) alongside the
service-time-adjusted figure. State the measured `s` you used and where it came from. If you cannot
measure `s` for a flow, say `s NOT MEASURED` and report only the bound — do not silently assume zero
and call the result a measurement.

CRITICAL MEASUREMENT FACT: the throttle wraps at the PRODUCTION constructor (e.g.
`ScryfallCardResolver.cs:76-88` build the default `_executeCollectionAsync` / `_executeSearchAsync`
delegates by wrapping them in `ScryfallThrottle.ExecuteAsync`). The `internal` test constructors
inject override delegates that BYPASS the throttle entirely. Consequence: you cannot measure this by
timing a test run — a test-seam run has no pacing in it at all. What a test seam CAN give you,
exactly and deterministically, is the **count** of delegate invocations, and each invocation is
exactly one throttle pass in production. Count, then apply the formula. Do not attempt to time it.

(`ResolvePoolCardsAsync_BatchMiss_IssuesExactlyOneLiveCallPerMiss`, real `ScryfallCardResolver` with
