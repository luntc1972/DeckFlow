Wire the flag to the detector across every production read path, and prove TWIN-02: the new kind is
absent from `ExcludedFindingKindsFromTally`, contributes to the discriminating tally, and actually
changes which card Cut Lab proposes next.

proposal order; this is the only change in the cycle that moves a card up the queue. It is also the
highest-blast-radius change, which is why every read path must be gated by the same dedicated flag
and why the ranking change must be proven by a test that fails if the finding is inert.

production so the deploy is dark.

### D-18 — `CutLabSimulationService` is deliberately NOT wired; the 4th `Compute` call site stays inert

`CutLabSimulationService.CurveCongestionValue` (`CutLabSimulationService.cs:524-535`) is a fourth,
standalone `CutLabStructuralFindings.Compute()` call site outside the three page/AJAX/patch paths. It
feeds round-3 delta-magnitude ordering.

**Decision: leave it alone. Do not pass `twinsEnabled` to it, do not inject a flag cache into it.**

Three reasons:
1. It already filters its own output to `.Where(finding => finding.Kind == CutLabFindingKind.CurveCongestion)`,
   so a `FunctionalTwins` finding could not influence it even if computed.
2. Because plan 04-02 made `twinsEnabled` an optional parameter defaulting to `false`, this call site
   is inert **by construction** and needs zero edits. That is provable, not assumed — it passes no
   value, so the detector cannot run there.
3. Wiring it would change **round-3** ordering, which is the bucket for cards with **zero**
   discriminating findings. TWIN-02 is explicitly about the round-1/round-2 tally. Feeding twins into
   round 3 as well would change ordering for cards the finding does not apply to, expanding the blast
   radius beyond TWIN-01..04. It would also put the detector on a per-card simulation hot path.

Recorded so verification does not mistake the unwired 4th site for an oversight.

### D-19 — how the gate is threaded, and why `IFeatureFlagCache` becomes a required dependency on two components

Research established the good news: `CutLabStructuralFindings.Compute()` reaches the page, AJAX and
patch transports through **one** shared `CutLabCutRoundEngine.BuildFindingsAndRoundPlan`. The Phase 3
dual-path hazard (`03-VERIFICATION.md:127`, three independent `BuildFloorMap` rebuilds over a
user-set-only persisted subset) **does not apply here** — `Compute()` always receives the full,
freshly resolved pool on every call. So the gate can be a single parameter rather than three inline
duplications, and that is what this plan does.

But `BuildFindingsAndRoundPlan` is a static method on a static class: it cannot read a flag itself.
The three callers must each supply the boolean, and only one of them currently has a flag cache:

| Call site | Has `IFeatureFlagCache` today? |
|---|---|
| `CutLabPageService.cs:505` | Yes — `_featureFlags` plus the private `IsFlagOn` helper |
| `CutLabApiController.cs:100` | No |
| `CutLabUiPatchBuilder.cs:80` | No |

**Decision:** add `IFeatureFlagCache` to `CutLabUiPatchBuilder` and `CutLabApiController` as a
**required** (non-optional, null-guarded) constructor dependency, and make `twinsEnabled` a
**non-optional** parameter on `BuildFindingsAndRoundPlan`.

Both choices are deliberately fail-loud rather than fail-quiet:
- Required ctor dependency: `AddDeckFlowFeatureFlags()` is registered unconditionally at
  **`Program.cs:113`** (re-verified during planning), so a required dependency resolves today and a
  future accidental removal throws at startup. The optional-parameter alternative is what the
  commander-floors ledger flagged as load-bearing fact #2 — an optional `IFeatureFlagCache?` silently
  binds to `null`, which pins the flag OFF forever with **no compile error and no failing test**.
  For a dark launch, silent-OFF is the safe direction on day one and a silent inability to ever flip
  the flag ON on day two. Fail-loud at startup is strictly better.
- Non-optional `twinsEnabled` on `BuildFindingsAndRoundPlan`: no call site can silently forget it. The
  compiler enumerates all four sites (three production, one test).

Note the two layers use opposite defaults on purpose: `Compute`'s parameter is optional-`false` so the
untouched 4th call site (D-18) stays provably inert, while `BuildFindingsAndRoundPlan`'s is
non-optional so the three real transports must each answer the question explicitly.

### D-20 — every consumer repeats the 3-line fail-safe read rather than calling a shared helper

Research §D.7: there is no cross-service shared `IsFlagOn` utility. `CutLabPageService.IsFlagOn`
(`CutLabPageService.cs:622-626`) and `CutLabFloorResolver.Resolve` (`CutLabFloorResolver.cs:38-46`)
each inline `_featureFlags is { } flags && flags.Snapshot().TryGetValue(key, out bool enabled) && enabled`.
This plan repeats that pattern in the two new consumers rather than introducing a shared helper.

Rationale: the pattern is deliberately **not** `IFeatureFlagCache.IsEnabled`, because `IsEnabled`
returns `true` for a missing key (documented default-ON). Every dark-launch consumer must invert that.
Introducing a shared helper is a worthwhile cleanup but it would touch `CutLabPageService` and
`CutLabFloorResolver` — Phase 3 code, outside TWIN-01..04, in the cycle's highest-blast-radius phase.
Recorded as a follow-up in plan 04-04, not done here.
