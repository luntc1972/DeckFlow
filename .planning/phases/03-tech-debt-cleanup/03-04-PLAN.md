<objective>
Tighten the trusted forwarded-headers surface in `DeckFlow.Web/Program.cs` so a
non-Render upstream cannot spoof `X-Forwarded-For` to dodge the feedback rate
limiter (ROADMAP SC #4). This goal is non-conditional per orchestrator
resolution: a real tightening MUST ship in this phase. Two paths qualify:

- **Path A (CIDR found):** Restrict `ForwardedHeadersOptions.KnownIPNetworks`
  to documented Render proxy CIDR ranges in Production (per D-12 — Dev keeps
  loopback only). Canonical SC #4 satisfaction at the headers-trust layer.
- **Path B (CIDR NOT found):** Switch the feedback rate-limit partition key
  off the `X-Forwarded-For`-derived `RemoteIpAddress` onto a different identity
  source (per D-11). Defends the actual threat (rate-limit dodging) at the
  consumer layer instead of the trust-list layer.

Defer / no-change is NOT an acceptable Task 1 outcome (orchestrator
resolution). The decision is which tightening ships, not whether tightening
ships.

Per D-12, the Path A restriction applies in Production only
(`IWebHostEnvironment.IsProduction()`):
- Production: `KnownIPNetworks = Render CIDR + preserved loopback defaults`
- Development: zero-config — preserve the default `127.0.0.1` and `::1`
  loopback entries; do not clear, do not add.

The orchestrator's threat-model directive REMOVES the existing comment
("Render assigns dynamic proxy IPs we can't enumerate") and the
`options.KnownIPNetworks.Clear()` / `options.KnownProxies.Clear()` calls
regardless of which path ships, because both statements stop being true after
this plan's research and code change.
