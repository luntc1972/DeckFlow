    IOrchestratorProgress? progress = null, CancellationToken ct = default) -> Task<ContentMaintenanceResult>
  BlockVideoAsync owns safe ordering (block-row first, then hard-delete) — never call store delete directly.

ContentMaintenanceResult (DeckFlow.Core/Orchestration/ContentMaintenanceResult.cs) — RESULT-BASED failure contract:
  bool   Success            // false = operation did NOT complete (NO exception thrown)
  string? Message           // optional status/error message for the host — operator-safe; surface this when present
  int    DeletedContentRows / DeletedSiteIndexRows / DeletedVideos / bool DryRun / bool RemovedExistingBlock (unused here)
  => The page MUST branch on result.Success, not only catch exceptions. A false Success returns normally.

VideoStatus badge arms (LOCKED — 56-UI-SPEC.md "VideoStatus Badge"):
  Approved  -> <span class="badge bg-primary">Approved</span>
  Published -> <span class="badge bg-success text-white"><span class="oi oi-check me-1" aria-hidden="true"></span>Published</span>

[Confirm Block] (btn-danger) + [Keep Video] (btn-outline-secondary) + "This will delete KB artifacts."
warning; Confirm runs ConfirmBlockAsync; Keep resets PendingBlock=false. Focus lands on Confirm Block.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-56-04-01 | Tampering | Accidental / unconfirmed Block (hard-delete) | mitigate | Two-step inline confirmation: first click only sets PendingBlock; the destructive BlockVideoAsync runs only on the explicit "Confirm Block" click, with an always-visible "This will delete KB artifacts." warning and focus landing on the destructive button |
| T-56-04-02 | Tampering | Wrong-video Block | mitigate | ConfirmBlockAsync passes the exact `vm.VideoId` of the confirmed row; the bUnit block test asserts the recorded BlockVideoAsync id matches the clicked row; Block disabled when already Blocked (idempotent guard) |
| T-56-04-03 | Tampering | Block re-harvest race / orphaned artifacts | mitigate | Always route through IContentMaintenanceOrchestrator.BlockVideoAsync (block-row-first, delete-second); acceptance criteria forbid direct store delete from the page |
| T-56-04-04 | Tampering | Malicious/odd paste input crashing resolve | mitigate | Pasted text only flows to the existing GetByIdsAsync (which already validates/suppresses unresolved ids per RESEARCH §9); ADD-01 surfaces a safe "0 resolved" message rather than echoing raw input or exceptions |
| T-56-04-05 | Information Disclosure | Block progress / error leaking internal paths | mitigate | Progress + error copy is operator-safe; do not echo exception.Message stack/paths to _logLines (Phase 47 HIGH-2 pattern). The result-false failure path surfaces only result.Message (or a generic fallback), never raw internals |
| T-56-04-06 | Repudiation | Silent block failure (Success==false, no throw) leaving operator believing the block succeeded | mitigate | ConfirmBlockAsync branches on result.Success; on false it shows an operator-safe error, does NOT refresh the badge to Blocked, and clears the confirm state — pinned by HarvestPage_ConfirmBlock_ResultFailure_ShowsErrorAndLeavesBadgeUnchanged |
| T-56-04-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs; bUnit + xUnit already present |
</threat_model>
