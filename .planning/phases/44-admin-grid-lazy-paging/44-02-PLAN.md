## RESOLVED 403 CONTRACT (single source of truth for this phase)

This was the HIGH review concern; it is settled here once, and SC + actions + tests below are all consistent with it. CONTEXT D-04's prose "Direct browser navigation … returns 403 (SC4)" is INCORRECT against the actual validator and is superseded by this block.

Grounded in `DeckFlow.Web/Security/SameOriginRequestValidator.cs` (verified, lines 17-33):
- If an `Origin` header is present → compare to request origin; mismatch → `IsValid` returns FALSE.
- Else if a `Referer` header is present → compare to request origin; mismatch → FALSE.
- If BOTH `Origin` and `Referer` are absent → `IsValid` returns TRUE (explicit comment line 31: "Allow non-browser callers and same-origin requests where the browser omitted both headers").

Therefore the realized, final contract for `GET /Admin/Harvest/commanders` is:

1. **Cross-origin request** (Origin or Referer present and mismatched, e.g. `Origin: https://evil.test`) → **403** with `{ Message = SameOriginRequestValidator.GetForbiddenMessage() }`. THIS is the SC4-relevant security case and the only 403 the tests assert.
2. **Same-origin request** (Origin/Referer present and matching) → **200** PartialView. This is the normal browser AJAX path used by Plan 03.
3. **Bare direct-nav GET** (address-bar navigation; no Origin/Referer) → **allowed (200, returns the partial)** by validator design — NOT a 403. It is still gated by `BasicAuthMiddleware` on `/Admin/*`, so it is not an unauthenticated data leak; it merely renders bare partial HTML to an already-authenticated admin.

Consequences enforced below:
- SC4 wording = "a cross-origin request returns 403", NOT "direct-nav returns 403".
- Tests assert ONLY the cross-origin → 403 case. There is NO no-header → 403 test (it would falsely fail because the validator allows it).
- The guard code is copied verbatim from the `Status` action so behavior matches the established admin pattern (AdminContentKbController precedent).
</endpoint_403_contract>
