<locked_decisions>
**D-5 (precondition shape) — locked: bound the population the assertion actually ran over, using
that quantity's own lower bound as the sole precondition — no separate `twins.Count > 0` guard.**
`twins.Count > 0` alone is not sufficient for the nested-loop test: a nonempty outer list whose
findings all carry empty `Evidence` collections leaves the inner loop — and therefore
`Assert.DoesNotContain` — executing zero times, and the test is vacuous again with a green
precondition above it. The nested-loop test therefore counts the assertions it executed and
asserts that counter is nonzero; the bounded-evidence test asserts its lower bound is nonzero
immediately before the existing upper bound. Neither test also gets a preceding
`Assert.True(twins.Count > 0, ...)` guard: mutation M10 (`ComputeTwins` returns an empty sequence)
already drives the outer `foreach` in the nested-loop test to zero iterations, and
`distinctEvidenceCount` in the bounded-evidence test to zero, so the exact-population lower bound
fails on its own without any prior guard to stop the test early. A guard ahead of it would instead
intercept M10 at `twins.Count > 0` and prevent the test from ever reaching that lower bound — the
sibling test's idiom does not compose with a test that already has its own exact-population lower
bound (Codex plan review, 2026-08-22). Each lower bound is therefore both the nonempty precondition
and the right-population precondition in one assertion.
Reversibility: **reversible** — test-only change, no production code.

**Scope note:** no production file changes in this plan. `CutLabStructuralFindings.cs` is mutated
transiently in Task 2 and restored byte-for-byte; that is a measurement, not a change, and the
acceptance criteria require the fingerprint to prove it.
</locked_decisions>
