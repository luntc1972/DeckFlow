<objective>

<design_notes>
## Deliberate Design Trade-offs

These are conscious choices documented during Codex pass-1 review convergence; not bugs and not regressions.

### Broad `JsonException` catch labels malformed-but-not-truncated paste as "appears truncated" (LOW-3)

Per D-01, every `JsonException` from `JsonDocument.Parse` is treated as a truncation event regardless of root cause (missing closing brace vs unclosed string vs malformed escape sequence vs invalid Unicode literal). A user who pastes a malformed-but-complete JSON blob (e.g., mismatched quotes mid-string) will see the same "appears truncated" copy as a user who pasted half a response.

This is an intentional UX trade-off:
- The locked D-02 message says "**appears** truncated" — qualifier softens the false positive.
- The vast majority of `JsonException` user-paste cases observed in `web-20260520.log` were genuine truncation (output stopped before the AI finished generating).
- Classification-by-message-sniffing was explicitly rejected under D-03 as fragile across .NET versions.
- The fallback assertion ("regardless of root cause, the user pasted something the parser cannot consume") is true and actionable: re-copy the JSON.

Revisit if telemetry surfaces a meaningful rate of malformed-not-truncated pastes confusing users. Currently no logging on the catch (D-05 wrap-up gate declined), so this gauge would require deliberate instrumentation in a future phase.

### Upload-path carve-out chooses controller-layer disambiguation over parser-layer classification (D-06)

The parsers do not know whether they were invoked from paste or upload. Rather than thread paste-vs-upload context into the parser layer (which would violate D-01's per-parse-site locality), D-06 places the disambiguation in the controller's existing `catch (InvalidOperationException)` block on the three upload actions. The catch test is a literal string-equality check against `ResponseParsers.TruncatedResponseMessage`.

Trade-off:
- Tight coupling between controller and parser via the message constant — but the constant already exists for D-01 and is the single point of truth for the locked message, so the coupling does not add a new failure point.
- If the message ever changes, both the parser const declaration AND the controller substitution branch update in lock-step (compiler enforces via const reference).
- Cleaner than a `TruncatedJsonException` subtype (which was rejected under D-01 for over-engineering).

### Semantic-completeness deferred even though `HasMeaningful*Content` already exists for deck-analysis (D-07 / MED-2)

`ResponseParsers` mirrors `HasMeaningfulDeckProfileContent` and `HasMeaningfulSetUpgradeContent` checks for the deck-analysis paths but `DeckComparisonService.ParseComparisonResponse` and `MetaGapService.ParseResponse` do not. Inputs like `{"deck_comparison":{"deck_a_name":"Atraxa"}}` parse into mostly-empty objects and bypass both the existing wrong-shape guard and the new truncation UX.

Mirroring the pattern is straightforward (literally 3 new helpers plus 2 call sites) but it is **scope expansion mid-review**:
- The Codex pass-1 finding (MED-2) was new information surfaced AFTER the locked CONTEXT.md was committed.
- D-01 scope is "truncated JSON" — `JsonException` path; semantic-empty is a different code path (`result is not null` but mostly-empty fields).
- Adding the guards here would balloon the commit envelope from 5-6 commits to 8-9 commits with new test fixtures.

Deferred to backlog (CONTEXT.md `<deferred>` + STATE.md Deferred Items table). Promote in the next AI-response-shape phase.
</design_notes>

| browser file upload -> PacketArtifactStore.Load*FromZip -> service-layer parser | Same parsers consumed on upload-path. D-06 controller-side message substitution acknowledges this is a distinct user-experience surface even though the parser code path is shared. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

Low-severity (no PII; the paste is the user's own input) but is the **defect this phase closes**. | mitigate | Per D-01: wrap `JsonDocument.Parse` at the 4 in-scope sites in `catch (JsonException) { throw new InvalidOperationException(TruncatedResponseMessage); }`.
