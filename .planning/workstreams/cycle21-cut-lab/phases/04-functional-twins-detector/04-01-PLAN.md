### D-14 — the mana-value dimension is EXACT mana-value equality, not a bucket (OPERATOR DECISION)

Twin grouping matches on **exact** `ManaValue` equality. MV 2 cards group only with other MV 2
cards. Sol Ring (MV 1) must never group with a Mox (MV 0). The private
`["0-1","2","3","4","5+"]` boundaries in `CurveCongestion` (`CutLabStructuralFindings.cs:402-436`)
are **not** reused and **not** extracted.

Rationale: the phase goal says "at the same cost". Exact equality also fires far less often than a
5-wide bucket, which protects Success Criterion 5 (finding density on a real 130-card pool stays
reviewable).

**Traceability tension that must be surfaced, not hidden.** `REQUIREMENTS.md` TWIN-01 literally says
"mana-value **bucket**". Exact equality is a degenerate bucket (width 1), so the implementation is a
strict subset of the requirement rather than a contradiction — but the wording drifts from the
implementation and a plan reviewer is right to flag it.

> **Proposed REQUIREMENTS.md amendment — do NOT apply it in this phase's plans.** Plan 04-02 Task 1
> is the only place authorized to edit `REQUIREMENTS.md`, and only TWIN-01/TWIN-03. The proposed
> replacement text is recorded there verbatim so the developer can review it in one place.

**Second-order consequence the planner must state, because it changes what TWIN-03 means.** Under
exact-MV grouping every member of a group shares the same mana value, so TWIN-03's
"evidence ordered highest mana value first" is *degenerate within a group* — a descending-MV sort
over identical values is a no-op. TWIN-03's intent (surface the costlier card first) therefore has to
be honored at a second level: **the emitted findings themselves are ordered highest mana value
first**, so the most expensive twin cluster is presented before cheaper ones. Plan 04-02 specifies
both the literal within-group `OrderByDescending(ManaValue)` (TWIN-03 compliance, and correct if the
dimension ever widens) and the cross-group descending-MV emission order (TWIN-03 intent).
