# Quick Task 260712 — Harvest job survives page navigation

## Problem

DeckFlow.Studio is a **classic Blazor Server** app (`AddServerSideBlazor` +
`MapBlazorHub`, `<Router>` in `App.razor`). When the operator navigates from the
Harvest page to any other Studio page, Blazor **disposes the Harvest component**.

`Harvest.razor.cs` `Dispose()` (≈ line 1262) calls `_cts?.Cancel()`. The
long-running harvest / distill work runs inside `Task.Run(..., _cts.Token)`, so
disposing the component **cancels the in-flight job**. Net effect the user
reported: *"a job stops running if I switch pages."*

## Goal (must-have)

A long-running Harvest job — **Harvest Selected**, **Harvest + Auto-distill**,
and **Live Distill (Stage B)** — must NOT be cancelled by page navigation. It
keeps running to completion (and persists to the content-kb DB) even while the
operator is on another page.

## Should-have (honest page status on return)

- Navigating back to Harvest reconnects: a "harvest/distill is running in the
  background" banner + the live progress log, and the final outcome when done.
- While a job is running (even backgrounded), the Start buttons are disabled so
  the operator cannot launch a second concurrent job (double-start guard).
- The explicit **Cancel** button still cancels the running job.

## Out of scope

- Preserving typed input / browse results / filters across navigation (the user
  explicitly scoped this to "don't stop the job", Harvest only).
- Any other Studio page (DirectPush, Reconcile, Publish, PullFromProd) — Harvest only.
- Surviving a full circuit teardown / app restart (only same-circuit navigation
  is required; the underlying DB work already persists regardless).

## Design

Introduce a **Singleton** `HarvestJobRunner` in `DeckFlow.Studio/ViewModels/`
(matches the existing coordinator pattern — `HarvestQueueCoordinator`,
`SpendCapCoordinator`, etc. are singletons). It owns the long-job lifecycle so
the job outlives the page component:

- `bool IsRunning`
- `HarvestJobKind? CurrentKind` (enum: `Harvest`, `HarvestAndAutoDistill`, `LiveDistill`)
- `IReadOnlyList<string> Log` — the accumulating progress lines for reconnect
- `event Action? Changed` — raised on every log append + on start/finish so a
  subscribed page can `InvokeAsync(StateHasChanged)`
- `Task<T> RunAsync<T>(HarvestJobKind kind, Func<CancellationToken, Task<T>> work)`:
  - if `IsRunning` → throw `InvalidOperationException` (double-start guard; the
    page never calls this while `IsRunning`, but the runner enforces it)
  - creates its own `CancellationTokenSource`, sets `IsRunning`/`CurrentKind`,
    raises `Changed`, runs `work(cts.Token)`, and in `finally` clears
    `IsRunning`/`CurrentKind`, disposes the CTS, raises `Changed`
  - the returned `Task` completing is what the page awaits for its own UI update
    while it is still alive; the runner's own `finally` (not the page's) is what
    authoritatively flips `IsRunning` off, so completion is correct even if the
    page was disposed mid-run
- `void AppendLog(string line)` — appends to `Log`, raises `Changed`
- `void Cancel()` — cancels the active CTS

Because the runner is a singleton, its CTS is not tied to the page; **page
disposal no longer touches it**, so navigation cannot cancel the job.

### Page changes (`Harvest.razor.cs` / `Harvest.razor`)

1. `@inject`/property-inject `HarvestJobRunner Runner`.
2. The **three long-op handlers** (`HarvestSelectedAsync`,
   `HarvestAndAutoDistillAsync`, `RunDistillStageBAsync`) run their work through
   `Runner.RunAsync(kind, ct => ...)` and use the **passed `ct`** instead of
   `_cts!.Token`. Thread that `ct` through the helpers they call
   (`RunHarvestCoreAsync`, `DetermineHarvestReadyIdsAsync`,
   `RunOneClickDistillAndApproveAsync`, the Stage-B `DistillAsync`/auto-approve).
   Progress callbacks append to **both** the page's `_logLines` (live view while
   attached) **and** `Runner.AppendLog(...)` (so a returning page can rebind).
3. Replace the long-op busy gate: introduce `bool IsBusy => Runner.IsRunning ||
   _isBrowsingChannel || _isAddingToQueue || _loadingPending;` and use it where
   `_operationInFlight` currently gates the long ops and the short ops' mutual
   exclusion. Remove the `_operationInFlight` field (or make it a thin alias) —
   the single source of truth for "a long job is running" is `Runner.IsRunning`.
4. `CancelOperation()` → `Runner.Cancel()`.
5. `OnInitializedAsync`: after the existing loads, `Runner.Changed += OnRunnerChanged;`
   and, if `Runner.IsRunning`, seed `_logLines` from `Runner.Log` so the live log
   reappears. `OnRunnerChanged` = `InvokeAsync(StateHasChanged)`.
6. `Dispose()`: **remove `_cts?.Cancel()` / `_cts?.Dispose()`** for the long-job
   CTS (that CTS now lives in the runner). Instead `Runner.Changed -= OnRunnerChanged;`.
   Keep disposing the short-lived local CTSs and the distill ticker CTS
   (`_distillTickerCts`) — the ticker is a UI-only elapsed clock; stopping it on
   nav is fine, and on return the elapsed can be shown from the runner state /
   stopwatch if still running.
7. `Harvest.razor` markup: when `Runner.IsRunning` show a small banner
   ("A harvest/distill job is running in the background…") and keep the Start
   buttons disabled via `IsBusy`. The existing Cancel button stays.

### Registration (`Program.cs`)

Register next to the other coordinators (≈ line 205):
`builder.Services.AddSingleton<DeckFlow.Studio.ViewModels.HarvestJobRunner>();`

## Tests (DeckFlow.Studio.Tests — xUnit + bUnit already present)

- `RunAsync_SetsIsRunning_DuringWork_ClearsAfter`

- `Cancel_CancelsTheRunningWorkToken`
- `RunAsync_CompletesEvenIfCallerStopsAwaiting` — start work, drop the awaiting
  reference (simulating page disposal), assert the runner still transitions
  `IsRunning` false and returns the result (proves the job is not tied to the caller)
- `AppendLog_RaisesChanged_AndAccumulates`

**`HarvestPageTests.cs`** (bUnit, add one focused case):
- Start a harvest via the runner, dispose the rendered component
  (`cut.Dispose()` / provider dispose), and assert the shared `HarvestJobRunner`
  singleton's `IsRunning` is still `true` (i.e. component disposal did NOT cancel
  the job). Re-render Harvest against the same runner and assert the background
  banner appears. Use the existing test-double orchestrators; make the harvest
  work block on a gate the test controls so `IsRunning` is observable mid-flight.
