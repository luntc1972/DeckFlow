# Plan 109-01 — Rename to ICutLabWhatifService and Add Shared CommitSwapAsync + TryValidateSwap

<objective>
Consolidate Cut Lab what-if logic behind a single interface. Rename the existing preview-only `ICutLabWhatifPreviewService` to `ICutLabWhatifService` (CLUP-04 names this interface exactly), rename `ComputeSwapPreviewAsync` to `PreviewSwapAsync` for symmetry, add one non-throwing `TryValidateSwap` (the single validation source that eliminates the three duplicated pair-validators — controllers' `ValidateWhatifPair`/`IsValidWhatifPair` and the preview service's internal check), and add a new non-throwing `CommitSwapAsync` that extracts the swap-commit rules currently duplicated across both controllers and validates via `TryValidateSwap`. Prove the shared rules (commander-lock, quantity legality, floor-state preservation, swap eligibility, atomicity, input-casing preservation) with service-level tests. This plan is purely additive/mechanical for behavior: after it lands the solution builds clean, all tests pass, and both transports behave exactly as before — the controllers still use their own duplicated commit blocks and private validators. Plan 109-02 flips all four call sites (API preview + commit, no-JS preview + keep) onto `TryValidateSwap`/`CommitSwapAsync`.

Purpose: CLUP-04/CLUP-05 — establish the one shared service surface (validate + preview + commit) and lock its rules with shared tests before the controllers adopt it.
Output: Renamed interface/class, new `TryValidateSwap`, new `CommitSwapAsync` + `CutLabWhatifCommitResult`, updated DI + all name references (including the injected field rename to `_whatifService`), and shared service tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → JSON API / no-JS POST | Untrusted `CutLabStateJson`, `cardOut`, `cardIn` cross here; server must re-validate regardless of client claims |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-109-01 | Tampering | `TryValidateSwap` swap-pair validation (reused by `CommitSwapAsync` and, in 109-02, both preview paths) | mitigate | Re-validate server-side in ONE place: reject when the card-out pool card is missing, `IsLocked`, or `IsCommander`, and when the card-in is not an accepted (cut-pile) card. Adopt the stricter explicit `!IsCommander` check (the no-JS path's variant), not the API path's `IsLocked`-only check, so the commander-lock invariant is provable even if the deserialize-time re-assertion is ever weakened. |
| T-109-02 | Tampering | Atomicity / quantity legality of the restore-then-accept swap | mitigate | Keep the existing decision-count overshoot guard inside `CommitSwapAsync`: if `afterSwap.Decisions.Count == afterRestore.Decisions.Count`, return the original `state` unchanged with `Applied=false` — never surface `afterRestore` as a half-applied partial (regression guard, prior atomicity fix commit `7cb68348`). |
| T-109-03 | Tampering / EoP | Validation drift between the two transports and between preview vs commit | mitigate | Route both commit paths AND both preview pre-checks (in 109-02) through the single `TryValidateSwap` so locked/commander/quantity/cut-pile rules cannot diverge across transport OR across preview/commit; this plan makes the single implementation exist and tests it. |

No package-manager installs occur in this phase (pure internal C# refactor, no new dependency) — no supply-chain (`T-109-SC`) checkpoint required.
</threat_model>
