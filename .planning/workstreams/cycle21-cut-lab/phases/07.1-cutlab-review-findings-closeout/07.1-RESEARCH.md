## Evidence per fork, and what it recommends

### D-1 - F-5 panel hiding: client-side on init, or server-rendered `hidden`?

**Evidence.** `attachStepTabHandler` (`cut-lab.ts:531-541`) toggles only the `is-active` class on
load and never calls `activateStepTab`, so no panel is hidden until the first click - all five
`role="tabpanel"` sections (`CutLab.cshtml:337,868,1128,1131,1362`) render visible while
`_WorkflowStepTabs.cshtml:10-12` marks exactly one tab `aria-selected="true"`. The defect is locked
in by assertion at `ts-tests/cut-lab-step-tabs.test.ts:56`, which asserts `toHaveLength(5)` for
`[role="tabpanel"]:not([hidden])`.

**The fork is a JS-off tradeoff, and neither side is free.** Server-rendered `hidden` fixes first
paint but strands the other four steps permanently for a JS-off user. Client-side hiding leaves
JS-off unchanged - all five panels reachable, which is the honest progressive-enhancement fallback -
but the first paint still briefly shows five panels.

**Recommendation: client-side on init.** It is what the run's own feature description already
assumes, it keeps the JS-off path non-lossy, and it makes the fix a one-tier change. The first-paint
flash is the accepted cost and should be stated as accepted rather than discovered later.

### D-2 - F-5's collapse side effect (the trap in the obvious implementation)

**Evidence.** `activateStepTab` calls
`if (readCollapsedSectionIds() === null) applyDefaultSectionCollapseState(step)` at
`cut-lab.ts:506-508`, which force-opens the step's primary `<details>` and closes the rest.
Reaching D-1's panel hiding *by calling `activateStepTab` on load* therefore runs that on **every**
page load for any user with no stored collapse state, moving which sections are open on arrival.
Nothing is persisted - `applyDefaultSectionCollapseState` does not write `localStorage`, and
`CUT_LAB_SECTION_STORAGE_KEY` is read-only on this path - but the visual default moves.

**Recommendation: hide panels on init *without* routing through `activateStepTab`.** Extract the
panel-visibility half, or call it behind a flag that suppresses the collapse default. Then assert
first-load collapsed-section state is unchanged. This is the single most likely way to ship F-5 and
regress something no one was looking at.

### D-3 - F-7 direction: declare nullable, or always emit a marker?

**Evidence.** `CutLabUiPatchDto.cs:28` declares
`public CutLabDecideNextProposalDto NextProposal { get; init; } = new();`, mirrored non-nullable at
`cut-lab.ts:174`. `CutLabUiPatchBuilder.BuildAdjustPatch` (`:160-166`) emits `null!` whenever
`projection.CanBuildExport` is false - any adjust on a list that is not exactly 100 cards. The
at-100 path instead emits a terminal marker (`IsTerminal = true, IsAtTarget = true`). TS call sites
already guard defensively, so the declaration is *looser than reality*, not actively broken.

**Recommendation: declare it nullable.** Always-emit-a-marker is a wire-payload behaviour change on
a live contract for a LOW-severity declaration mismatch - disproportionate, and it would need its
own regression surface. Nullable makes the declaration honest with zero behaviour change.

**Carve-out that must not be lost:** `.editorconfig` forbids converting `{ get; init; }` to
`{ get; }` - System.Text.Json silently skips get-only properties in .NET 9+. Whatever the direction,
the accessor pair survives.

### D-4 - the no-tab-selected fallback

**Evidence.** `attachStepTabHandler` returns early when no tab is `aria-selected="true"`
(`ts-tests/cut-lab-step-tabs.test.ts:83`), leaving all five panels visible.

**Recommendation: keep it, and state it.** Content must never be stranded behind a tablist with no
selection. The risk is not the behaviour, it is changing it *by accident* while implementing F-5 -
so it needs an explicit assertion, not just a decision.

## Known traps

1. **The naive R2-1 fix breaks a passing test on purpose.** `cut-lab-step-tabs.test.ts:70`'s own
   recorded killing mutation is "skip aria-disabled tabs during ArrowRight traversal" - i.e. removing
   Plan from traversal. That is the obvious fix and it is wrong. Filter on `aria-disabled` for
   *selection*, keep the tab in the *focus* ring. Home/End and wrap-around hit the same predicate.
2. **`site.ts:294-310` cannot help here.** The capture-phase guard swallows *clicks* on
   `[role="tab"][aria-disabled="true"]`; it cannot see a direct `activateStepTab` call. Prefer not to
   touch it - it is shared across tools.
3. **F-5 spills into sibling tools and must not be widened here.** `CedhMetaGap`, `DeckComparison`
   and `DeckAnalysis` render tabpanels without `hidden` too, and `DeckPrimer` shares the partial.
   Follow-up only.
4. **An existing todo overlaps.** `2026-08-02-split-workflow-step-tabs-into-tablist-and-jump-nav.md`
   already owns refactoring `_WorkflowStepTabs.cshtml`. Do not collide with it.
5. **`tool.cut-lab.enabled` is OFF in production.** All five `CutLabApiController` actions carry
   `[FeatureFlagGate("tool.cut-lab.enabled")]`. If F-7 touches the patch DTO, re-confirm the gate
   attributes survive the edit. No controller should change; if one must, scope has drifted.
