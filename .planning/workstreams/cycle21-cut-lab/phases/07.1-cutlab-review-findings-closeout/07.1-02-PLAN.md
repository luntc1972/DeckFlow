that the collapse default did not move.

<locked_decisions>
**D-1 (F-5 hiding mechanism) — locked: client-side on initialization. No server-rendered `hidden`.**
`CutLab.cshtml` is not edited. Rationale: server-rendered `hidden` fixes the first paint but
permanently strands the other four steps for a JavaScript-off user, because nothing would ever
un-hide them. Client-side hiding leaves the JS-off path exactly as it is today — all five panels
reachable, which is the honest progressive-enhancement fallback. **The accepted cost is stated,
not discovered later: with JavaScript on, the first paint briefly shows five panels before
initialization hides four.** That flash is accepted for this phase.
Reversibility: **reversible** — adding server-side `hidden` later is an additive change to the
Razor view and does not conflict with anything this plan writes.

**D-2 (collapse side effect) — locked: initialization hides panels WITHOUT the collapse default.**
See `<assumption_delta_decision>` below for the structural form of this.
Reversibility: **reversible**.

**D-4 (no-tab-selected fallback) — locked: KEEP today's behaviour, and assert it.**
`attachStepTabHandler` returns early at `cut-lab.ts:532-534` when no tab carries
`aria-selected="true"`, leaving all five panels visible. Content must never be stranded behind a
tablist that has no selection. The risk is changing this by accident while implementing F-5, so
the existing case at `cut-lab-step-tabs.test.ts:83` keeps its `toHaveLength(5)` assertion and
gains an explicit statement of why in its name.
Reversibility: **reversible**.
</locked_decisions>

<assumption_delta_decision>
**Signal:** `pluralization`. F-5 gives panel-hiding a **second** caller. Until now the only way any
`[role="tabpanel"]` acquired or lost its `hidden` attribute was `activateStepTab`
(`cut-lab.ts:494`), which additionally force-runs `applyDefaultSectionCollapseState`
(`:506-508`), rewrites `aria-selected` / `tabindex` / `is-active` on every tab, and optionally
moves focus. Initialization now needs the panel-visibility behaviour and none of the rest.

**Noun that is now primary:** the **panel-visibility primitive** — "make exactly one step panel
visible" — not "tab activation". Concretely `setVisibleStepPanel(step: number): boolean`.

**Decision: `promote`.** `setVisibleStepPanel` becomes the primary representation of panel
visibility and the single place the `hidden` attribute is written. `activateStepTab` is demoted to
one caller of it: the caller that additionally layers the collapse default, the ARIA/tabindex/class
sweep and optional focus on top. Initialization is the other caller, and it layers nothing.

**Rationale:** adding a second, parallel hiding path while leaving `activateStepTab` the only real
entry point would leave two places that write `hidden`, which is exactly how the current defect
(one path sets `is-active`, the other sets `hidden`, and load reaches only the first) was made.
One writer, two callers.

**Invariant test (accepted, implemented in Task 2):** `every entry path leaves exactly one panel
visible when the server selected a tab`. It parameterises over the initialization path and the
click path and asserts the visible-panel id set has size 1 and matches the selected tab's
`aria-controls`. It goes red the moment a future phase reintroduces a second `hidden` writer that
disagrees. The documented exception — no tab selected — is asserted separately as D-4.
</assumption_delta_decision>
