## Decisions Made

See `key-decisions` in frontmatter for the batch-chunk placement rationale. In addition:

- Task 1's plan text described "resolver double resolves 100 of the 101 cards ... assert the pool contains the 100 cards that DID resolve" for the fallback-429 test. Actual behavior (verified by running the test RED first) is that `ScryfallReferenceResolver.ResolveBatchAsync` discards its ENTIRE chunk's resolutions — not just the one throwing card — because its `resolved`/`oracleNameMap` dictionaries are local to the method call and a mid-loop exception aborts before `return`. This is analogous to Plan 01's own documented `CountingResolver` finding (its `ExecuteCollectionAsync` always echoes the full card list regardless of the request). Fixed by placing the casualty in the LAST Scryfall batch chunk (27 cards) so the FIRST chunk (75 cards, including the commander and `Card 001`) resolves cleanly before the swallow — this both matches the plan's underlying intent (prove the failure did NOT blank out the whole import) and is achievable with the test double's actual mechanics. Documented as a `<remarks>` xmldoc on both affected tests.
