<objective>
Add an instant client-side filter/search box above the Content KB entries table so an admin
can locate a specific entry to publish/unpublish in a list that has grown long, by typing any
fragment of the entry's title, source/creator, or tags.

Purpose: The curation list (all index rows, published + hidden) is rendered in full and has
grown too long to scan by eye. The Phase 32/30 work already surfaces every row; this phase makes
that long list navigable.

Output: A filter input in `Index.cshtml`, a `wireEntryFilter()` behavior in the existing
`content-kb-admin.ts` module, and `.admin-shell`-scoped CSS in `admin-common.css`.

Design choice — CLIENT-SIDE filtering (rationale, MUST follow):
The controller `AdminContentKbController.Index` already calls `_store.GetAllRowsAsync(...)` and
materializes EVERY row into `model.Entries`; the view renders all of them in one `@foreach`. The
list is a single-operator, bounded admin grid (low hundreds of rows). Therefore filtering is done
in the browser against the already-rendered DOM — NO new controller parameter, NO new endpoint,
NO new query string, NO server round-trip. This also means the filter text never reaches the
server, so there is zero injection/parameter surface introduced (see threat model). The existing
server-side `visibilityFilter` toggle (All / Published / Hidden) is UNCHANGED and continues to be
the server-side narrowing; the client filter narrows further within whatever the toggle returned.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /Admin/ContentKb | Admin-authenticated surface behind BasicAuthMiddleware (`/Admin/*` branch). Operator-only. |
| filter input → DOM | Filter text is consumed only in the browser; it never crosses to the server. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-33-01 | Tampering / Injection | Filter query string used in SQL | accept (not applicable) | Filtering is CLIENT-SIDE only; no new controller parameter, no new query string, no DB query touches the filter text. There is no injection surface because the value never reaches the server. |
| T-33-02 | Information Disclosure (XSS) | `data-kb-search` and entry title/source/tags rendered into the attribute/cells | mitigate | Values are emitted with the default Razor `@` expression which HTML-encodes; no `Html.Raw` is used on entry data. The TS reads `dataset.kbSearch` (already-decoded text) and uses `.includes()` + sets the `hidden` property — it never writes user/data text into the DOM via innerHTML, so no reflected/stored XSS is introduced. |
| T-33-03 | Elevation of Privilege | Admin authz on the page | mitigate | No new endpoint is added; the page remains behind the existing `/Admin/*` BasicAuth branch. The client filter cannot be reached unauthenticated because the page itself is gated. |
| T-33-04 | Denial of Service | Large row count filtered on every keystroke | accept | Single-operator admin grid (low hundreds of rows); `.includes()` over precomputed `data-kb-search` strings on `input` is O(rows) and trivially fast at this scale. No debounce required; revisit only if the corpus grows past a few thousand rows. |
| T-33-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs in this plan — pure view/TS/CSS edits using existing tooling. If any install appears necessary, STOP (see allowed_file_set). |
</threat_model>
