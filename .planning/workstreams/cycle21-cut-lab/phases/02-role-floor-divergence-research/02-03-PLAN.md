# Phase 2 Plan 03 — Make the verdict P25-driven (decision D-B)

## Release Posture

**This phase ships NO user-visible change and is NOT a release.** `DeckFlow.Core/Research/` is
consumed only by the CLI research harness; no controller, view or web service references it. No
CalVer bump, no tag.

## Why This Plan Exists

Decision **D-B** requires floors to be **25th percentiles over real per-deck distributions**. The
common assumption is that this needs new percentile machinery. It does not.

**P25 already exists and is already computed.** Verified:

- `RoleFloorDivergenceStats.ComputePercentile` (`:76-102`) implements inclusive linear interpolation
  (spreadsheet `PERCENTILE.INC` / numpy default), including the single-element and exact-index cases.
- It is already called with `0.25` in two places:
  `RoleFloorResearchCommandRunner.cs:236-238` (per commander) and `:560` (corpus baseline).
- Per-deck values are genuinely retained upstream in
  `CommanderDeckSet.RepresentativeRoleCounts` (`:915`) and passed in at `:228-230` as a real
  `List<double>` of one entry per deduped deck.

**The actual defect is that the verdict ignores it.** `ClearsBar` (`:47-69`, called at `:242-250`) is
computed purely from `commanderMean`, `corpusMean`, `corpusStdDev`, `n`, and fixed ratio/z
thresholds. It never reads P25. P25 is emitted as a cosmetic column in both the markdown table
(`:692-700`) and the JSON payload (`:759`) that has **zero influence** on `ClearsBar`, on
`BuildGoNoGo` (`:567-613`, which keys entirely off `ClearsBar`), or on any downstream decision.

The harness's own methodology text already admits this, at `RoleFloorResearchCommandRunner.cs:643`:

> A floor should be derived from the 25th percentile, not the mean: a mean-derived floor puts roughly
> half of the commander's own decks below the floor, which defeats the purpose of calling it a floor.

It says the right thing and then does not do it. **D-B's real work is rewiring the verdict onto P25,
not building percentiles.**

## Design Decisions

### D-01 — P25 governs divergence; the mean still governs significance

A naive reading of D-B is "replace every mean with a P25". That is wrong, and it would produce a
statistically incoherent bar.

`ComputeZScore` divides by `corpusStdDev / sqrt(n)` — the standard error **of a mean**. A sample
percentile has no closed-form standard error; substituting P25 into that formula would produce a
number with no meaning while looking exactly as authoritative as before. Options considered:

| Option | Verdict |
|---|---|
| Replace both the ratio and the z with P25 versions | **Rejected.** `z = (commanderP25 - corpusP25) / (corpusSD / sqrt(n))` is not a z-score of anything. It would give the findings a false precision. |
| Drop the significance gate; judge on P25 ratio alone | **Rejected.** RFLR-02 requires an effect-size **and** a noise-separation criterion. A P25 ratio alone readmits the "big ratio, tiny N" false positive the existing bar was written to reject. |
| Bootstrap a confidence interval for the P25 | **Rejected for this phase.** Defensible, but it is new statistical machinery on a research harness whose first priority is producing an honest first run. Record it as a possible refinement; do not build it now. |
| **P25 ratio for divergence, mean z for significance, both required** | **Chosen.** |

The chosen bar, stated as one sentence for the class xmldoc:

> A commander-role row clears the bar only when its deduped deck count reaches `minDeckCount`, its
> **25th-percentile role count** diverges from the corpus 25th percentile by at least `ratioHigh`x or
> at most `ratioLow`x (or, where the corpus P25 is zero, by at least `absoluteFloorGap` cards), and
> the commander's **mean** differs from the corpus mean with `|z| >= zThreshold`.

Divergence is the finding; the z-gate is only there to reject noise. Keeping the z on the mean is
honest about what each half measures.

### D-02 — the `corpusP25 == 0` fallback

`corpusP25 == 0` is not a corner case here; it is expected. Roles like `wincons` and `protection`
plausibly have a corpus 25th percentile of zero, because a quarter of decks may contain none of them.
`ComputeRatio` already returns `0.0` when the denominator is zero (`:24-25`), which under a
`ratio <= ratioLow` test would make **every** commander look divergent-low. That is a silent
false-positive factory.

Rule: when `corpusP25 == 0`, the multiplicative ratio is undefined. Divergence is instead
`Math.Abs(commanderP25 - corpusP25) >= absoluteFloorGap`, with `absoluteFloorGap` a new explicit
parameter (default `2.0` cards, adopted as a documented constant by the caller in plan `02-05`). Two
cards is the smallest gap that is meaningful as a *floor* recommendation — a floor differing by one
card is not worth a UI column.

This must be a **parameter**, not a hardcoded literal inside the method, so the single written bar
stays fully visible at the one call site.

### D-03 — keep `ClearsBar` alive in this plan

This plan is wave 1 and must leave the build green on its own. `ClearsBar` has a live caller at
`RoleFloorResearchCommandRunner.cs:242-250`. Deleting or re-signaturing it here would break the
build until plan `02-05` lands.

So this plan **adds** `ClearsFloorBar` alongside `ClearsBar` and changes nothing about the latter.
Plan `02-05` switches the call site and deletes `ClearsBar` in the same commit, so the dead method
never survives a wave.

Do **not** mark `ClearsBar` `[Obsolete]` — that would emit a build warning at the existing call site
and violate the "0 new warnings" gate.

### D-04 — Cohen's d stays reporting-only

`ComputeCohensD` is documented as reporting-only in the existing class xmldoc and is not part of the
bar. That does not change. It remains in the output as a scale-uniform effect size alongside the
scale-dependent ratio.
