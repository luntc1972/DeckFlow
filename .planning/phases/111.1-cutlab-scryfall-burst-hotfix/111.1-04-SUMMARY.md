# Phase 111.1 Plan 04: SC-7 Pacing Measurement Summary

**Measured the true per-flow cost of raising `ScryfallThrottle.MinInterval` from 200ms to 500ms using an already-executed test seam plus cited arithmetic (zero live Scryfall calls), reconciled the modeled numbers against the production 429-burst log anchor, and stopped at the blocking SC-7 acceptance checkpoint without touching any code.**

## What Was Built

`111.1-PACING-MEASUREMENT.md` (created, 315 lines) — the sole artifact this plan is scoped to
produce. No `ScryfallThrottle.cs` edit, no test file edit, no production code of any kind.

**STEP 1 (flow enumeration):** 12 call sites traced back to their triggering flow/controller,
distinguishing the 5 flows that share `ScryfallReferenceResolver.ResolveBatchAsync` (Cut Lab, Deck
Comparison, Meta-Gap, Deck Analysis, Deck History) from Manabase's own hand-rolled batch+fallback
shape and from 6 structurally-different flows (Cut Lab what-if, Deck Convert, card lookup, card
search, set lookup, tagger lookup) that cannot produce the same burst shape.

**STEP 2 (call-count census):** Modeled a 100-card pool at 0/10/25 DFC-and-genuinely-unknown
misses (explicitly NOT counting the punctuation class, which plan 111.1-03's additive second pass
now resolves at zero extra Scryfall calls). Re-ran the existing real-`ScryfallCardResolver` test
seam (`CutLabAnalysisContextBuilderTests.cs:548-585`) fresh in this session — `Passed: 2, Failed:
0` — observing `collectionCalls==1`, `searchCalls==3` for 3 forced misses, which is executed proof
of the `ceil(N/75) + missCount` formula used for the single-call-fallback flows. Deck Analysis and
Deck History's `SearchPrintingFallbackCardAsync` fallback carries a separate typical/worst-case
split (1 vs up to 3 calls/miss), shown with its own arithmetic. Deck Convert was shown to have NO
per-miss fallback loop at all — flat call count regardless of miss rate.

**STEP 3 (latency formula):** Derived the delta function algebraically rather than asserting a
single number: `delta(s) = max(0,500-s) - max(0,200-s)`, which resolves to a flat 300ms/gap for
any `s <= 200ms` (making the "upper bound" exact, not just a ceiling) and shrinks linearly above
that. Reported `s` as the bracket `[200ms, 300ms]` sourced from the production log's own stated
inter-request spacing rather than inventing a false-precision point estimate. Reconciled the
production anchor (21 requests) exactly against the PRE-fix 2-calls-per-miss formula at
`missCount=10`, then showed the POST-fix figure for that identical scenario (11-12 calls) beside
it, as the plan's Step 3 required.

**STEP 4 (highest-volume caller):** Split assumption A2 into two independently-evidenced findings
rather than picking one flow and calling it done — Deck Analysis for per-miss cost (evidence:
`SearchPrintingFallbackCardAsync`'s code at `ScryfallCardResolver.cs:160-205`), Manabase for
timeout risk (evidence: the only flow with a hard `CancelAfter` budget, `ManabaseController.cs:339`
+ `DeckToolControllerBase.cs:14`). Explicitly stated the report cannot measure real production
traffic *volume* (hit-count popularity) — only per-request worst-case cost, which is the axis SC-7
and A2 are actually about.

**STEP 5 (concurrency + timeout census):** Documented the process-wide static gate's concurrency
effect at Render's single-Starter-instance scale. Grepped every controller for
`CancellationTokenSource`/`CancelAfter` and every TS file for `TimeoutMs`/`AbortController`,
producing a genuinely surprising finding: **Cut Lab's own pool-import path — the subject of this
entire phase — has no server-side timeout budget and no client-side `AbortController` on its
intake form**, unlike its own adjust/whatif/decide endpoints (20000ms, verified live against the
stale 3000ms figure the 2026-07-24 debug note recorded). Named Manabase as the sole flow flagged
as measurably closer to its timeout ceiling (7.8s worst-case added latency against its 20s budget).

**STEP 6 (recommendation):** Recorded "adopt, with a named-but-unimplemented per-endpoint-interval
mitigation disclosed" — explicitly not implementing that mitigation, since Scryfall's rate limits
are per-endpoint and a keyed-interval throttle is a materially larger design than the one-constant
edit plan 111.1-05 is scoped to make.

## Checkpoint Response — RECORDED VERBATIM

**Status: ANSWERED — 2026-07-31.**

The checkpoint was presented to the user with the full measurement: the algebraic delta
(`delta_per_gap(s) = max(0,500-s) - max(0,200-s)`, exactly 300ms/gap for `s <= 200ms`), the
N-calls-to-(N-1)-gaps correction, the per-flow census (~5.2-7.8s for Cut Lab / Comparison /

risks (Manabase's 20s hard budget being the only ceiling in play; Cut Lab pool import having no
timeout on either side).

The per-endpoint-interval alternative was explicitly offered as a real option, on the grounds that
Scryfall's limits are per-endpoint while this gate is global.

**USER RESPONSE, VERBATIM: `accept` — "Accept 500ms globally".**

**Authorization granted.** Plan 111.1-05 may proceed exactly as scoped: raise `MinInterval` to
500ms, correct both stale rate-limit comments, add the regression test, re-run the final-state gate.
The narrower per-endpoint variant was NOT selected and must NOT be improvised into 111.1-05.

**Rationale recorded at the gate:** we are currently running 2.5x over Scryfall's published
per-endpoint limit, whose documented penalty is a temporary or permanent application ban. The
measured cost lands almost entirely on flows with no timeout budget to exceed, so the practical
effect is "feels slower", not "fails". Manabase is the one flow to watch after this ships.
