# Phase 37.6 — Harvest Video Block + Hard-Delete — CONTEXT

**Source:** User discuss (2026-06-10), AskUserQuestion 3-fork capture. Supersedes the deferred backlog item (requested 2026-06-08 mid-Phase-33).

## Domain

Admin needs to permanently suppress a harvested YouTube video: hard-delete its KB rows AND record its video id so a later `DeckFlow.CLI harvest` run never re-ingests it. Today's unpublish (`IsVisible=false`) only hides the curation row — the next harvest re-ingests the same video. There is no mechanism to stop re-processing. An orphan `IContentVideoStore.DeleteVideoAsync` already exists but is unwired.

## Locked Decisions (do NOT relitigate in planning)

**ARCHITECTURE (revised 2026-06-10 after RESEARCH BLOCKER): LOCAL-FIRST via CLI.** RESEARCH proved the full content (`content_videos`/transcripts/clips) + the harvester live in `content-kb.db` (local-only, never on Render), and the harvest CLI process never opens `feedback.db`; the content-video store (`IContentVideoStore`) is not even registered in Web DI. So the original feedback.db + prod-admin design does not wire up. The feature is therefore a **local CLI operation** where harvest runs. Prod receives the removal through the normal site-index propagation (operator re-deploys/syncs the slim index).

- **D1 (revised) — block-list lives in the LOCAL `content-kb.db`** (alongside `content_videos`), NOT feedback.db. The single harvest process already opens this DB, so the ingest skip-check reads `blocked_videos` with zero new connection wiring. **MUST be carved out of the Phase 37.5 corpus reset:** the 37.5 reset purges `content_*` tables — `blocked_videos` must be named outside that set AND the reset must explicitly NOT drop it (note this cross-phase dependency in the plan; 37.5 is not built yet, so 37.6 owns making the table reset-proof by name/contract).
- **D2 — block is reversible.** An **unblock** action removes the `blocked_videos` row; a later harvest re-ingests the video normally. Hard-delete of existing rows still happens at block time (unblock does NOT resurrect deleted rows — only re-permits future harvest).
- **D3 (revised) — action is a DeckFlow.CLI command, run locally** (e.g. `block-video <youtube-id> [--reason …]`, `unblock-video <youtube-id>`, optional `list-blocked`). It (a) inserts the `blocked_videos` row, (b) hard-deletes the video's content rows via a NEW all-source `IContentVideoStore.DeleteVideoByYoutubeIdAsync(string)` — `DELETE … WHERE youtube_video_id = @id`, keyed on the globally-unique youtube id with NO sourceId (the source-scoped `GetVideoByYoutubeIdAsync(sourceId,…)`/`DeleteVideoAsync(long)` would MISS a disabled-source video — Codex HIGH 2026-06-10), FK-cascading transcripts/summaries/clips/tags/distill_status, (c) deletes the slim site-index entry via a NEW `IContentSiteIndexStore.DeleteByIdAsync` resolved through `GetByNaturalKeyAsync(ContentSourceType.Youtube, id)` (site-index is a separate DB the video delete can't reach). NO Web/prod-admin changes, NO cross-environment wiring. The operator copies the YouTube id from the curation grid (or knows it).
- **D4 — block key is the YouTube id STRING** (`content_videos.youtube_video_id` / site-index `natural_key_value`), never the reassigned `long` PK. The skip-check matches the ingest id at `CommandRunners.ResolveHarvestVideoIdAsync` BEFORE `InsertVideoAsync`.
- **D5 — single atomic unit.** Block-row insert + content delete + site-index delete should be transactional / best-effort-ordered so a partial failure doesn't leave a deleted video that is NOT blocked (it would re-harvest). Insert the block row FIRST (so even if a delete fails, re-harvest is already prevented), then delete.

## Key identifiers / surfaces (verify in research)

- Video id space the harvester keys on (YouTube id string vs internal `videoId` long PK) — the skip-check must match on whatever natural key the ingest path dedups on. `IContentVideoStore.DeleteVideoAsync(long videoId, …)` takes the internal long; the block-list likely keys on the YouTube id string so it survives re-harvest (a new ingest gets a NEW long PK). RESEARCH must pin both ids per video and which the skip-check + block row use.
- Harvest ingest/persist path (`DeckFlow.CLI` + `DeckFlow.Core/Content/*` harvest stores) — exact point a video is persisted, so the skip-check drops a blocked id BEFORE insert.
- `AdminContentKbController` (`/Admin/ContentKb`) — existing curation actions (SetVisibility / SetEvergreen / ReloadSeed) to mirror for the new Block/Delete/Unblock action shape.
- `DeleteVideoAsync` dependent-row coverage — confirm it cascades transcript/summary/clip/site-index rows (or the plan adds the missing deletes).

## Success Criteria (from ROADMAP)

1. Admin "Block & delete" → video's `content_videos` (+ dependent transcript/summary/clip/site-index) rows gone AND a `blocked_videos` row exists for its id.
2. A subsequent harvest re-encountering that video id does NOT re-insert it (skip-check before persist); a non-blocked video in the same run still ingests.
3. Block list survives a corpus reset (lives in feedback.db, not purged by the 37.5 `content_*` reset).
4. Mutating endpoint admin-only (BasicAuth) + rejects cross-origin / missing-antiforgery POSTs. Unblock is reversible.

## Scope fence

- IN: `blocked_videos` table (local `content-kb.db`, idempotent create, reset-proof name) on the content store; ingest skip-check in `CommandRunners` harvest path (before `InsertVideoAsync`); new `DeckFlow.CLI` commands `block-video` / `unblock-video` (+ optional `list-blocked`); NEW `IContentSiteIndexStore.DeleteByIdAsync`; reuse existing `IContentVideoStore.DeleteVideoAsync` (extend cascade only if RESEARCH shows a gap); tests (block→delete→rows gone + block-row exists; re-harvest skip; unblock re-permits).
- OUT: ALL Web/prod-admin changes (`/Admin/ContentKb`, `/Admin/Harvest`, no controller/view/VM edits); feedback.db; corpus rebuild (37.5); controller SRP split (38); unpublish/visibility semantics; `/content-kb` public browse.
- Public repo — no secrets. Codex codes / Claude reviews. Plain commits, LF, no `{get;init;}` collapse, no reflow. No new deps.
