<objective>
Layer cache lookups onto the three download endpoints in `DeckController.cs` between the existing response-json-only short-circuits and the BuildAsync fallthrough. Plan 02 owns the WRITE side and the async cache-key composition; Plan 03 is THIN — controller just calls `TryComputeCacheKeyAsync`, performs `_packetCache.TryGet`, and decides hit/miss path.

**Pass-2 NEW MEDIUM concern — miss-path latency (acknowledged explicitly, by design):**

The architecture established in Plan 02 (Codex pass-1 H1-H4 + pass-2 H1 fix) is that **all cache-key composition lives inside each service** via a shared private `BuildXxxCacheInputs` helper called from BOTH the BuildAsync write site AND the public async `TryComputeCacheKeyAsync` read helper. The controller does not load decks, does not extract commanders, does not normalize DeckSource.

The consequence: every download cache MISS path now pays an extra deck load before BuildAsync's own deck load. Concretely:

1. Controller calls `TryComputeCacheKeyAsync(request, ct)`.
2. Helper calls `LoadDeckEntriesAsync(request.DeckSource, ct)` (DeckAnalysis) or `LoadDeckAsync(...)` (DeckComparison/MetaGap) — this hits the importer (Moxfield/Archidekt URL → HTTP → parse) or parses paste text.
3. Helper extracts commander + builds field bag + computes SHA-256.
4. Helper returns key string.
5. Controller calls `_packetCache.TryGet(key, out result)`.
6. Cache returns false (miss).
7. Controller falls through to BuildAsync (line 512 / 727 / 971).
8. BuildAsync calls its OWN `LoadDeckEntriesAsync` / `LoadDeckAsync` for the same `request.DeckSource` — **second importer round-trip**.

**Mitigations already in place:**
- The Moxfield importer + Archidekt importer have their own internal caches; on a warm cache (preview just ran, deck just imported), step 8 is a cheap re-hydration from the importer cache.
- The CardLookupCache, CommanderSpellbookService, etc., all participate in absorbing repeated work.
- The typical preview→download flow keeps the importer cache warm; in that flow the cache HIT path skips all of this.

**Cold-miss scenarios that pay the full double cost:**
- Process restart between preview and download.
- TTL expiry on the importer cache (the importer's TTL is unrelated to the 5-min packet cache TTL; they may not align).
- Bookmarked download URL (no preview ever ran for this session).
- First-ever submit (no cache anywhere).

**Net latency on cold miss:** roughly 2x importer cost over pre-phase baseline. For a large Commander deck:
- Pre-phase cold download: BuildAsync once = ~120s (one importer + one full Scryfall pipeline).
- Phase 999.3 cold-miss download: TryComputeCacheKeyAsync (one importer, no Scryfall pipeline) + BuildAsync (one importer + one full Scryfall pipeline) ≈ 120s + ~3-5s for the redundant importer call.

**Why this trade-off is acceptable:**
- D-11 explicitly accepts silent fall-through to BuildAsync on cache miss. The cache is pure optimization, not a correctness contract.
- The TARGET WIN — preview→download HIT path on a warm session — is the >100x speedup (2+ min → <2s). Cold-miss being marginally slower than today is not the value prop being optimized.
- The architectural alternative (controller loads decks once, passes the loaded deck into BuildAsync to skip BuildAsync's own load) requires either (a) changing BuildAsync's public signature to accept a pre-loaded deck — a much larger surface change with cascading test/DI implications, or (b) having the controller reproduce service-internal commander extraction — the Codex pass-1 H1 rejected this. Neither is justified by the cold-miss cost.

**Decision: ACCEPT the cold-miss double-load.** Document it in plan must_haves + UAT Workflow A step l acknowledges it explicitly.
