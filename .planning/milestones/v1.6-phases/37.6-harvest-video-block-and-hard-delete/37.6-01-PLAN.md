<objective>
Add a local-CLI harvest block + hard-delete capability to DeckFlow.CLI/DeckFlow.Core. An operator runs `block-video <youtube-id>` to (1) record the YouTube id in a new `blocked_videos` table so future harvests skip it, (2) hard-delete the video's content-kb rows, and (3) delete the matching slim site-index row. `unblock-video` reverses the block (future harvests re-ingest). The harvest ingest path gains a skip-check that drops blocked ids before insert.

Purpose: Today's unpublish only hides a curation row — the next harvest re-ingests the same video. There is no mechanism to permanently suppress re-processing. An orphan `IContentVideoStore.DeleteVideoAsync` exists but is unwired.

Output: New `IBlockedVideoStore`/`BlockedVideoStore`, new `IContentVideoStore.DeleteVideoByYoutubeIdAsync` (all-source delete keyed on the globally-unique youtube id), new `IContentSiteIndexStore.DeleteByIdAsync`, harvest skip-check, three CLI commands, and xUnit regressions.

ARCHITECTURE NOTE (authoritative — CONTEXT D1/D3 revised 2026-06-10, supersedes RESEARCH's feedback.db/Web-admin framing): This is a LOCAL-FIRST CLI feature. The block-list lives in the LOCAL `content-kb.db` (the same DB the harvest process already opens), NOT feedback.db, and NOT prod. There are ZERO Web/prod-admin changes. RESEARCH's file:line facts remain valid; only the placement (CLI + content-kb.db, not Web + feedback.db) changed. The "block-list lives in feedback.db" lines in RESEARCH/SC#3 are obsolete — the reset-survival guarantee is delivered instead by the non-`content_*` table name in the local DB plus the explicit cross-phase note in Task 1.
</objective>
