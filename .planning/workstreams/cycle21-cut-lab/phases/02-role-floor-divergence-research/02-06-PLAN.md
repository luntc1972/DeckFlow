# Phase 2 Plan 06 — Ingest the EDHREC commander x bracket grid

## Release Posture

**This phase ships NO user-visible change and is NOT a release.** No CalVer bump, no tag.

## Why This Plan Exists

The corpus already exists on disk: `scripts/edhrec-brackets/fetch.py` ran to completion on
2026-07-27 and wrote **1,525 cells** (305 commanders x 5 brackets, 0 failed, 0 404) under
`_edhrec-brackets/`. Plan `02-02` commits that tooling and pins the on-disk contract. Plan `02-05`
produces the types and the emitter that can report the cells. Neither connects the two:
`ResearchComputation.EdhrecPointEstimates` is deliberately left empty, and the markdown prints "no
EDHREC cells were supplied".

This plan closes decision **D-A**'s EDHREC half and the ingestion half of ROADMAP criterion 8.

**No task in this plan makes a network call to EDHREC.** The fetch is done. Do not re-run it.

## The on-disk shape is NOT what this plan originally assumed — read this first

The original `02-02` specified a cell schema with `source`, `estimateKind`, `qualifies`, a pre-parsed
`cards` array, a `parseFailures` array and a `status` field, plus a manifest carrying per-cell `file`
entries. **The shipped fetcher writes none of those.** Plan `02-02`'s rewritten "On-disk contract"
section is authoritative; this section restates the four consequences that land on this plan.

### 1. Qualification is derived here, and the manifest's `min_decks` is a trap

`manifest.json` records `"min_decks": 8000`. That is the **commander-selection** floor applied against
`averages.csv`'s `number_decks` when choosing which 305 commanders to sweep. It is **not** a per-cell
floor and must never be used as one.

The per-cell qualifying floor is the 2026-07-16 prior's rule — **>= 400 decks backing the cell** —
and it is applied by this plan against each cell's own `n_decks`. Introduce it as a single named
constant, `EdhrecMinCellDeckCount = 400`, passed into the reader, so the number is visible in one
place rather than retyped.

Measured yield at that floor, from plan `02-02`'s recount of the cells on disk:

| Bracket | cells | >=400 qualifying | median N |
|---|--:|--:|--:|
| exhibition (B1) | 305 | **1** | 36 |
| core (B2) | 305 | 284 | 1,138 |
| upgraded (B3) | 305 | **305** | 1,048 |
| optimized (B4) | 305 | 175 | 458 |
| cedh (B5) | 305 | 40 | 51 |

**805 qualifying cells of 1,525.** So 720 cells are ingested with `Qualifies == false` — nearly half.
Dropping them would make coverage unreportable; keeping them is what lets the artifact state *fetched
versus qualifying* per bracket, which ROADMAP criterion 8 requires.

### 2. The decklist arrives as raw strings; the parse moves into C#

`deck` is a `string[]` of `"<qty> <Card Name>"` entries — measured:
`["1 Adrix and Nev, Twincasters", "1 Arasta of the Endless Web", "1 Arcane Signet", ...]`, 82 entries
for that cell, summing to 100 cards including basics. There is no pre-parsed `cards` array.

So `EdhrecCellReader` owns the quantity-prefix parse and its failure path. Split on the first space,
integer-parse the prefix, trim the remainder. An entry whose prefix does not integer-parse goes into a
per-cell parse-failure list with its raw string and is excluded from `Cards` — **never silently
discarded**, because a silent drop would undercount a role and look like a real measurement.

### 3. The manifest has no per-cell `file` entries

Cell enumeration is the cross-product of `selected_commanders[].slug` (305 entries) x `brackets`
(5 entries), each mapping to `cells/<slug>__<bracket>.json`. Cross-check that against the files
actually present in `cells/` so both directions of drift are visible: a planned cell missing from disk
is a coverage gap, and a file on disk outside the planned set is an unexpected cell worth reporting.

### 4. There is no `source` / `estimateKind` constant to validate

The original reader validated `source == "edhrec"` and `estimateKind == "point"` as proof a cell came
from the fetcher. Those fields do not exist. Validate instead on the fields that do: `slug`,
`bracket`, `bracket_index`, `n_decks` and `deck` must all be present and well-typed, and `bracket`
must be one of the five known slugs with `bracket_index` agreeing with it. The `source` and
`estimateKind` values are supplied by THIS plan when projecting into plan `02-05`'s
`EdhrecRolePointEstimate` (`Source = RoleFloorSource.Edhrec`), which is where criterion 7's guarantee
actually lives.

## The two things that must not be gotten wrong

### 1. Classification must go through the production classifier, for both corpora

RFLR-01 requires per-commander role classification be reproduced "using the real production
classifiers … not a reimplementation". The requirement text names the Postgres corpus because it
predates D-A, but the reasoning applies with more force to EDHREC: if the two corpora were classified
by different code, every cross-source comparison in the findings — including the lands calibration
control in plan `02-07` — would be measuring the difference between two classifiers rather than
between two corpora.

So an EDHREC cell's cards go through `CutLabRoleAssigner.AssignRoles(fact, [], isComboPiece: false,
mode)` — the identical call shape the Postgres path uses at
`RoleFloorResearchCommandRunner.cs:198-201`, including the empty category list, so the oracle-only
discipline documented in the methodology text holds for both.

### 2. Quantity is NOT 1 for EDHREC decks

The Postgres path fixes quantity at 1 (`:198`), with a comment explaining why: Commander is singleton
for every nonland card that can plausibly earn a target role.

**That assumption breaks for EDHREC**, because EDHREC's `deck` array includes basic lands with real
quantities. Measured on `adrix-and-nev-twincasters__core.json`: EDHREC's own `basic` aggregate is
**20** across an 82-entry list summing to 100 cards — so roughly a dozen entries carry a quantity
above 1. Since D-C put `lands` in scope, treating each entry as quantity 1 would undercount an average
deck's lands by that margin and produce a lands figure that is simply wrong.

The EDHREC path must therefore count each card `quantity` times. This is a real behavioral difference
between the two ingestion paths and must be stated in the emitted methodology, not buried.

## Design Decisions

### D-01 — the reader lives in `DeckFlow.Core`, the classification stays in the CLI

`EdhrecCellReader` deserializes, parses quantities and validates. It performs **no classification** —
it does not reference `CutLabRoleAssigner`, which lives in `DeckFlow.Web`. Keeping it in
`DeckFlow.Core` makes it unit-testable from `DeckFlow.Core.Tests` with inline fixtures and no web
dependency, matching the existing split where `DeckFlow.Core` holds pure domain logic.

The classification loop stays in `RoleFloorResearchCommandRunner`, beside the Postgres loop it must
stay identical to.

### D-02 — the manifest is the index; cells are the source of truth

Read `manifest.json` for `selected_commanders` and `brackets` to enumerate which cells were planned,
then read each cell file for its data. **Take `n_decks` and everything else from the cell**, never
from the manifest — the manifest carries no per-cell counts at all, and its `min_decks` means
something else entirely (see above). A planned cell missing from disk is a coverage gap, not a run
failure: `manifest.json`'s own `missing_cells` and `failed_cells` arrays are empty for the recorded
run, but a future partial fetch is exactly what this branch exists for.

If `manifest.json` itself is absent or unparseable, that IS fatal — there is no way to know what was
supposed to be there. Fail with a clear message and a non-zero exit.

### D-03 — the land self-check is a report, not a gate

Each cell carries EDHREC's own `land` aggregate (measured: 35 for Adrix/core, alongside `basic` 20 and
`nonbasic` 15). After classification, compare it against the harness's own `lands` role count for the
same decklist.

**Report the comparison; do not abort on mismatch.** A mismatch is informative rather than fatal:
EDHREC's land count and `CutLabLockRules.IsLand(typeLine) || fact.HasLandFace` may legitimately
disagree on modal double-faced cards whose front face is a spell. Aborting would throw away the whole
run over a definitional difference.

Emit per-cell `EdhrecLandSelfCheck { CellId, EdhrecLandCount, HarnessLandCount, Delta }` and a summary
line stating how many cells matched exactly, how many were within 1, and how many diverged by more.
If the "diverged by more than 1" count is large, that is a finding about the methodology and plan
`02-07`'s lands verdict must weigh it — which is precisely why lands is the calibration control.

### D-04 — cards are resolved through the existing Scryfall cache

Building a `CardFact` needs a type line and oracle text. The harness already has the machinery:
`ResolveCardsAsync` (`:360-472`) with its resumable `_role-floor-research/cards_full.json` cache and
its 429 retry. The cache currently holds **14,167 entries**.

Feed EDHREC's distinct card names into the **same** resolution pass as the Postgres distinct names,
before either classification loop runs. This reuses the cache, keeps a single Scryfall rate-limit
budget, and means EDHREC ingestion adds close to zero API calls for cards already seen.

A card that fails to resolve is skipped, exactly as the Postgres loop does at `:191-194`, and counts
toward the existing unresolved tallies.

### D-05 — `--edhrec-data` is optional; its absence is stated, never silent

Omitting it runs the Postgres half alone. That is legitimate — the Postgres half is what feeds the
go/no-go. But the artifacts must say so, using the explicit "no EDHREC cells were supplied" line plan
`02-05` already added, so a reader never mistakes an absent corpus for an empty one.

Supplying a path that does not exist, or that has no readable `manifest.json`, is an **error**, not an
absence. Fail with exit code 1.

### D-06 — the coverage block DECLARES its bracket support; B1 is never presented as supported

**New, and binding.** The corpus is not uniformly deep. B3 qualifies at 305/305; B1 qualifies at
**1/305**. A per-bracket figure computed over one cell is a single deck's number wearing the costume
of an average, and printing it in the same table shape as B3's 305-cell figure asserts a support it
does not have.

So the EDHREC coverage block must, per bracket, report **cells fetched, cells qualifying, and the
median backing deck count**, and must carry an explicit support statement derived from the qualifying
count rather than hand-written:

- A bracket with **zero or one** qualifying cell is labelled `NOT REPORTED — insufficient cells`, and
  its figures are omitted from the per-bracket EDHREC lands means that plan `02-07` reads.
- A bracket with fewer than a stated `EdhrecThinBracketThreshold` qualifying cells (adopt **50**, one
  order of magnitude above the 1-or-fewer floor and below B4's 175) is labelled `THIN — n qualifying
  cells`, reported, but flagged wherever its figures appear.
- Everything else is reported without qualification.

On the corpus as it stands this yields: B1 `NOT REPORTED` (1), B5 `THIN` (40), B2/B3/B4 reported.
**Compute the labels; do not hardcode them** — a future re-fetch at a different `--min-decks` would
change which brackets qualify, and a hardcoded label would then lie.

Note the independent corroboration, reached without reference to this run:
`DeckFlow.Web/Services/Manabase/ManabaseAnalysisService.cs:603-605` already restricts EDHREC-derived
land use to brackets 2-3 on the grounds that "the EDHREC population is casual-dominated", and the
committed `DeckFlow.Web/Data/manabase-baseline/latest.json` carries bracket rows for 2, 3, 4 and 5
only — **no B1 row at all**.

### D-07 — record each cell's own recency window

Each cell carries `savedate_summary` — measured for Adrix/core:
`{"min_date": "2024-07-28", "max_date": "2026-07-27", "total": 1055, "distinct_days": 560}`. That is
free provenance about how old the decks behind a cell are, and it is the EDHREC-side counterpart to
the Postgres corpus's *absence* of any recency window (a limitation plan `02-07` must disclose).

Capture `min_date` and `max_date` on the cell and report the overall range in the EDHREC coverage
block. One line; it costs nothing and it is the only currency signal either corpus supplies.
