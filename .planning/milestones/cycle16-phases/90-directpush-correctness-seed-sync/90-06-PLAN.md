<objective>
Rework the DirectPush Blazor page's stage sequencing so it enforces expand→verify→contract at the UI level (SYNC-09 / D-06): the content-only write + git commit/push + redeploy (expand) happen first, then the bounded hash-match poll of the Plan 90-07 deployed-body-hash endpoint (verify), and only a successful confirm (200 && bodySha256==expected) triggers the stamp + visibility flip (contract). Surface the durable awaiting-confirm marker (Plan 90-03/90-05) so a push left mid-flight across a page reload is resumable rather than lost (D-10).

Purpose: RESEARCH's anti-pattern warning is that just reordering coordinator methods is insufficient — today the page's Stage-4 (git) is gated by "row is already published" (`_dbSuccess`), and it treats git failure as non-fatal because content is "already live." This plan re-gates the UI so the contract stage depends on the verify stage, making a git/deploy failure leave the row hidden+awaiting-confirm instead of visible.
Output: the reworked razor stages, a resume-from-marker action, bUnit/xUnit page tests, and explicit manual-verification notes for the live deploy round-trip.
</objective>
