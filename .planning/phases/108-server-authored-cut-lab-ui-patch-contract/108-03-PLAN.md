# Plan 108-03 — TypeScript Patch Rendering

<objective>
Update Cut Lab browser code to render server-authored patch fields after live JSON mutations and stop re-deriving domain state in success paths.
</objective>

<threat_model>
T-108-05: Client-side patch rendering could trust malformed responses and leave hidden state out of sync. Mitigation: success handlers require `patch.cutLabStateJson`; if missing, render the existing Cut Lab error copy and do not partially update the DOM.

T-108-06: Removing client re-derivation could break scenario/local hidden-state behavior. Mitigation: keep serialization helpers for local state construction and scenario storage, but do not use them for live mutation display fields when patch values exist.
</threat_model>

<must_haves>
- Live decision success uses server patch fields for counts, export eligibility, proposal, cuts made, structural findings, and what-if options.
- Live adjust success uses server patch fields for current count, cards remaining, export eligibility, proposal, cuts made, structural findings, and what-if options.
- Live what-if commit success uses server patch fields for cuts made, current count, export eligibility, and what-if options.
- `currentCountFromSerializedState`, `cardsRemainingFromSerializedState`, `buildCutsMadeFromSerializedState`, and `rebuildWhatifSelectOptionsFromState` are not used as source-of-truth in live mutation success paths.
</must_haves>
