# Phase 111.1 Plan 01: Cut Lab Scryfall Burst Hotfix Summary

**Cut Lab's post-batch-miss fallback now dispatches SearchFallbackCardAsync instead of the redundant ResolveSingleAsync POST, a Scryfall 429 during pool intake fails open instead of aborting the import, and a swallowed transient failure is never memoized as a permanent cache miss.**

## Performance

- **Duration:** ~85 min (context/research load ~55 min; execution 12:02–12:11 local for the three task commits)
- **Started:** 2026-07-31T18:02:46Z (first task commit)
- **Completed:** 2026-07-31T18:11:09Z (last task commit)
- **Tasks:** 3 (RED test / GREEN builder / GREEN page service)
- **Files modified:** 3

## Accomplishments

- **SC-1 closed:** the one-line delegate swap at `CutLabAnalysisContextBuilder.cs:410` (`_cardResolver.ResolveSingleAsync` → `_cardResolver.SearchFallbackCardAsync`) removes the redundant second `cards/collection` POST on every batch miss, halving worst-case live-call volume per miss. Proven both via the `CountingResolver` double (`ResolveSingleCalls == 0`) and end-to-end through a REAL `ScryfallCardResolver` with counting collection/search delegate overrides (`collectionCalls == 1`, not 4).
- **SC-2 closed:** `IsTransientRateLimit` narrows the `failOpenOnLookupErrors: false` rethrow to skip ONLY an `HttpRequestException { StatusCode: HttpStatusCode.TooManyRequests }`, covering both a per-card fallback 429 and a batch-collection 429 (`ScryfallReferenceCollectionException` derives from `HttpRequestException` with the upstream status preserved). A non-429 failure still throws — locked by a permanent regression test.
- **B-1 closed (round-1 review blocker):** a per-scoped-instance `_unattemptedNamesByPoolKey` dictionary keeps a swallowed transient casualty out of `knownMissingNamesSet`, and `PrimeResolvedCardsCache` subtracts it from the caller-supplied unresolved-names list before it reaches the 30-minute cache. `CutLabPageService.ResolveEntriesAsync`'s blind `TryGetCachedResolvedCards` short-circuit was removed so a second import of the same pool re-attempts the casualty instead of serving the degraded pool for 30 minutes.
- **W-1 closed (round-1 review):** a degraded import (one or more cards with no facts) now renders a plain, user-facing warning naming up to 5 affected cards via the same warnings channel the banlist failure already uses — no HTTP status codes, no mention of Scryfall or rate limiting.
- **W-8 addressed (round-1 review):** the chunk loop now `break`s once a transient failure is swallowed, instead of continuing to POST into an actively rate-limiting upstream.
- Zero blast radius outside Cut Lab: `ScryfallCardResolver.cs` and `ScryfallReferenceResolver.cs` are unmodified — confirmed by `git diff --name-only -- DeckFlow.Web/Services/Scryfall DeckFlow.Web/Services/Packets` printing nothing across all three commits.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug/spec inconsistency] B-1 regression test mechanism redesigned from the plan's literal description**
- **Found during:** Task 1
- **Issue:** The plan's Task 1 behavior spec says to construct `ResolvePoolCardsAsync_AfterSwallowedRateLimit_SecondResolveReattemptsTheCasualty` with "one CountingResolver whose `cards` DOES contain the target card" and to trigger the swallowed failure via `FallbackException`. But `CountingResolver.ExecuteCollectionAsync` (existing code, not touched by this plan) always echoes its full `cards` list regardless of the request. If `cards` contains a card whose name matches the pool entry, the batch `cards/collection` call resolves it as a direct HIT on every pass, and the per-card fallback delegate (where `FallbackException` lives) is never even dispatched — making the described scenario unreachable with this double.
- **Fix:** Used the `CollectionStatusCode` knob (already needed for the `BatchCollectionRateLimit` test) to force a genuine batch-collection 429 on pass 1 instead. This preserves the test's actual intent (a swallowed transient failure must be re-attempted, not permanently cached) while working within the double's real behavior. Documented in the test's xmldoc `<summary>`.
- **Files modified:** `DeckFlow.Web.Tests/CutLabAnalysisContextBuilderTests.cs`
- **Verification:** Test is RED before Task 2's fix (throws, matching the plan's stated "RED today"), GREEN after Task 2, and the pass-2 re-attempt assertion (`ExecuteCollectionCalls` increases; casualty present) only passes once Task 2's B-1 fix is fully correct.
- **Commit:** `9fe471ef` (RED), verified GREEN in `d56b5918`.

**2. [Rule 1 - Bug] Two pre-existing tests asserted the exact defect SC-1 removes**

- **Issue:** `BuildAsync_PreResolvedCardsMissingOneCard_OnlyResolvesTheMissingCard` and `BuildAsync_SamePoolWithOneUnresolvableCard_FallsBackOnceAndCachesKnownMissing` both asserted `resolver.ResolveSingleCalls == 1` for a genuine miss (`"Typo Card"`). Once the SC-1 delegate swap lands, that miss correctly dispatches `SearchFallbackCardAsync` instead, making `ResolveSingleCalls == 0` and breaking both tests.
- **Fix:** Updated both tests' assertions to check `SearchFallbackCalls`/`SearchFallbackCallsByName` instead of `ResolveSingleCalls`/`ResolveSingleCallsByName`, preserving the same "called exactly once, for the missing card only" shape.
