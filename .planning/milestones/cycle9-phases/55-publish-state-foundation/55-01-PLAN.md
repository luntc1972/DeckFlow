<objective>
Record when each content-KB entry was pushed to production, via a NEW nullable column on `content_site_index`, stamped by BOTH publish paths through a single dedicated writer method and an idempotent dialect-guarded migration (SQLite + Postgres). Implements PUB-01.

Purpose: Phase 55's status engine (Plan 02) and downstream consumers (Phase 56 PUB-03/BROWSE-02, Phase 57 SITE-01) need a reliable "pushed to prod" timestamp on the LOCAL index to distinguish `Published` from `Never published` and `Local-newer`. Without this column, every entry reads `Never published` forever.

Output: A new `pushed_to_prod_utc` column on `content_site_index`, a self-healing migration, a single dedicated batch writer (`StampPushedToProdAsync`), and stamping wired into both the git Publish path (after commit) and the DirectPush path (after prod upsert).
</objective>

<critical_context>
LOCKED DESIGN DECISION (operator) — `pushed_to_prod_utc` is a LOCAL fact:
"the operator published this version to prod," recorded on the LOCAL `content_site_index`. Plan 02's deriver reads the LOCAL row. Git-path deploy lag is ACCEPTED: the git stamp is the commit time ("I published it" intent), even though Render redeploys a few minutes later. `Local-newer` = the operator edited locally since the last publish (local IndexedUtc strictly after pushed_to_prod_utc). Admin/prod-side surfacing is DEFERRED to Phase 57 — Phase 55 must NOT add the field to the byte-stable seed JSON.

DECISION — column naming (deviation from literal ROADMAP/STATE wording, honoring intent):
The existing `published_utc` column already exists and holds the **video's YouTube publish date** (`video.PublishedUtc` — e.g. `2023-07-28T23:50:51+00:00` in the seed). It is serialized as `publishedUtc` in `content-kb/seed/index-seed.json`, which `ContentIndexExportRow` documents as a **byte-stable public contract**. It is NOT the production-push timestamp.

Therefore PUB-01's "when each entry was pushed to production" MUST be a DISTINCT NEW column named `pushed_to_prod_utc`. Do NOT overload `published_utc`. The new C# property is `ContentSiteIndexRow.PushedToProdUtc` (nullable `DateTimeOffset?`). The seed export shape (`ContentIndexExportRow`) MUST remain unchanged — do NOT add the new field to the exported seed (Phase 57 owns prod-side surfacing).

DECISION — exactly ONE writer of the column (HIGH-1, Codex):
`pushed_to_prod_utc` must be written by EXACTLY ONE dedicated method, `StampPushedToProdAsync`, and NEVER by the shared upserts. It must NOT appear in `UpsertSql`, `UpsertPreservingVisibilitySql`, or `UpsertContentColumnsOnlySql`, and must NOT be bound in any of their anonymous param objects. Reason: `UpsertContentColumnsOnlySql` is the DISTILL write path (ContentKbOrchestrator.cs:1317); distill rows carry a null stamp, so if the column were in that upsert, every re-distill would reset a published row's `pushed_to_prod_utc` to NULL. Leaving the column out of ALL upserts means `ON CONFLICT` never touches it → the existing value is preserved across re-distill. The column STILL appears in both CREATE TABLE constants (fresh DBs have it) and ALL SELECT lists (reads round-trip it).

DECISION — UTC + dialect typing (F-51-PG-01 precedent):
Store as `TIMESTAMPTZ NULL` on Postgres and `TEXT NULL` on SQLite (mirror the existing `published_utc` typing on lines ~848 + ~870 of ContentSiteIndexStore.cs). When binding this column, bind the same CLR `DateTimeOffset` type the store already uses for `published_utc` round-trips (so a TEXT-vs-`timestamptz` mismatch — Npgsql `42883`, F-51-PG-01 — cannot occur). Plan 02 owns comparison; this plan only needs the column to round-trip a `DateTimeOffset?` via Dapper exactly as `published_utc` does. Always stamp with `DateTimeOffset.UtcNow`.

DECISION — stamp at the PUBLISH boundary, not the file-write boundary (HIGH-2/HIGH-3):
- git Publish: `ExportIndexAsync` / `CopyApprovedArtifactsToRepoAsync` only read+write FILES; they do NOT prove a publish. The publish is proven only when `Git.StageAndCommitAsync` returns success in `Publish.razor` (~line 504, inside `CommitAsync`). Stamp the local index there, after commit success, for the approved key set captured during Stage-1 export.
- DirectPush: Stage 3 (`DirectPush.razor` `WriteRowsAsync`, ~line 695) currently writes only `prodStore`, leaving the LOCAL row NeverPublished. After the prod upsert batch succeeds, stamp the LOCAL index (required so the deriver-against-local is correct) AND `prodStore` with the SAME captured instant (so Phase 57 admin-on-prod is consistent for DirectPush'd rows).

Deploy-lag note (MEDIUM, Codex): the git-path stamp is COMMIT time, recording operator-published intent; Render deploy happens a few minutes later and that lag is accepted. `Local-newer` means local edits since the last publish — it does NOT track deploy completion.
</critical_context>
