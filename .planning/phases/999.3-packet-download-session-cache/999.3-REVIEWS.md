## Codex Review

## Overall
The packet is strong on scope control, D-10 ordering intent, and verification discipline, but Plans `999.3-02` and `999.3-03` have a correctness gap around cache-key parity. The write side can compute keys inside `BuildAsync`, but the read side as planned cannot reproduce the same key for deck-analysis and some meta-gap requests without new shared normalization/extraction helpers that do not currently exist. That is the main risk to preview→download hits actually firing.

## `999.3-01-PLAN.md`
**Summary**  
Good infrastructure plan. It cleanly isolates the dedicated cache, captures the warning baseline up front, and centralizes D-07 sizing logic. The main issues are small contract drifts in the cache wrapper API/logging details, not major architecture mistakes.

**Strengths**
- Uses a dedicated `MemoryCache` with `SizeLimit = 10_000_000`, matching D-06 and existing `CardLookupCache` precedent.
- Captures `_baseline-warnings.txt` before code changes, which makes later “no new warnings” gates defensible.
- Centralizes size estimation in one place, which reduces drift across the three services.
- Explicitly rejects stampede locking, matching D-12 and current cache patterns.

**Concerns**
- `MEDIUM` — D-13 template drift. Task 1 step 11 adds an eviction log with `reason={Reason}` instead of the exact contract template `_logger.LogInformation("Packet cache {Outcome} for {KeyPrefix} ({SizeBytes} bytes)", ...)`. That weakens grep consistency.
- `MEDIUM` — Hit logs use `0` bytes by design in `TryGet`, while D-13 describes logging `sizeEstimate`. That is probably acceptable operationally, but it is a contract deviation worth calling out.
- `LOW` — The helper-shape guidance is internally inconsistent: “three public static methods immediately after the class” vs “recommended `internal static class PacketSizeEstimator`”. Executors can resolve it, but it should be one shape.

**Suggestions**
- Lock the eviction log to the exact D-13 template and move eviction reason to a second structured property only if truly needed.
- Specify one helper shape only: `internal static class PacketSizeEstimator` with three overloads.
- State explicitly whether `TryGet` hit logging may report `0` bytes or must report stored size.

**Risk Assessment**  
`LOW`. Plan 01 is implementable and mostly correct; the issues are contract/consistency details.

## `999.3-02-PLAN.md`
**Summary**  
This is the most important plan and also the one with the biggest flaw. The write-site placement is well thought through, but the proposed `ComputeCacheKey(...)` helpers do not actually solve parity with the controller read side because the controller cannot reliably supply the same normalized inputs the service uses.

**Strengths**
- Correctly targets the full-pipeline returns only: `DeckAnalysisPacketService.cs:467`, `DeckComparisonService.cs:198`, `MetaGapService.cs:196`.
- Correctly excludes the short-circuit returns at `DeckAnalysisPacketService.cs:156`, `:188` and `MetaGapService.cs:122`.
- Keeps D-09 simple by putting writes inside `BuildAsync`, so `/deck-analysis/upload` participates automatically.
- Uses `PacketSizeEstimator.EstimateSizeBytes(...)` rather than inlining property sums.

**Concerns**
- `HIGH` — Deck-analysis key parity is not actually solved. `DeckAnalysisRequest` has no `CommanderName` property, but Task 1’s helper signature requires `string commander`. The commander is derived inside `DeckAnalysisPacketService.BuildAsync` from parsed/imported entries at `DeckAnalysisPacketService.cs:208-300`, then finalized again near `:435-437`. The controller cannot reproduce that from request state alone.
- `HIGH` — Meta-gap has the same parity risk when `request.CommanderName` is blank. `MetaGapService.BuildAsync` resolves commander from the loaded deck at `MetaGapService.cs:131-134`. A controller that passes only `request.CommanderName` can compute a different key than the write path.
- `HIGH` — D-02 normalization is under-specified for read/write parity. The services use private `LoadDeckEntriesAsync` / `LoadDeckAsync` methods (`DeckAnalysisPacketService.cs:496+`, `DeckComparisonService.cs:315+`, `MetaGapService.cs:401+`). Plan 02 does not expose a shared normalization helper that Plan 03 can call, so the “single source of truth” claim is incomplete.
- `MEDIUM` — The plan treats key composition parity as solved by static helpers, but those helpers still depend on external normalized inputs. That is only partial centralization.

**Suggestions**
- Move from `ComputeCacheKey(request, normalizedDeckSource, commander)` to a shared per-service async helper that resolves the exact cache inputs from the request using the same private load path as `BuildAsync`.
- Better: introduce `TryComputeCacheKeyAsync(request, cancellationToken)` on each service or on the cache wrapper itself, so the read and write paths both use identical normalization and commander extraction.
- For deck-analysis specifically, avoid any plan that requires the controller to infer commander from raw request data.

**Risk Assessment**  
`HIGH`. The write side itself is fine, but the plan does not yet provide a reliable way for the read side to hit the same keys.

## `999.3-03-PLAN.md`
**Summary**  
The intended D-10 ordering is right, and the dependency on Plan 02 is correct. But as written, this plan is not executable: it assumes a loader API that does not exist, references a nonexistent `DeckAnalysisRequest.CommanderName`, and still depends on controller-side reconstruction of service-internal normalization.

**Strengths**
- Correctly puts cache lookup below the existing response-json-only short-circuits in `DeckController.cs:705-725` and `:956-969`, and above `BuildAsync` at `:727` / `:971`.
- Correctly leaves preview endpoints and `/deck-analysis/upload` out of the read path.
- Correctly depends on `999.3-02`, which is necessary if helpers are shared.

**Concerns**
- `HIGH` — The plan assumes `_deckEntryLoader.ResolveCanonicalTextAsync(...)`, but `IDeckEntryLoader` only exposes `LoadAsync(...)` and `ValidateCommanderDeckSize(...)` in `DeckFlow.Core/Loading/DeckEntryLoader.cs:11-25`. The cited method does not exist.
- `HIGH` — Task 2 tells the controller to use `request.CommanderName` for deck-analysis, but `DeckAnalysisRequest` has no such property (`DeckFlow.Web/Models/DeckAnalysisRequest.cs`). This is a compile-time failure.
- `HIGH` — The plan says it modifies exactly one file, but its own fallback allows adding service-side helper logic if controller normalization is too complex. That conflicts with the must-have “one file only” rule.
- `MEDIUM` — Even if a loader were injected, controller-side `LoadAsync(...)` plus ad hoc commander extraction would still duplicate service logic and risks key skew versus the write path.
- `MEDIUM` — The claimed <2s cache-hit path may be optimistic for URL inputs if the controller has to re-import/re-parse before `TryGet`. It still avoids Scryfall, but the plan should acknowledge that importer cost remains on read.

**Suggestions**
- Rewrite Plan 03 around a service-owned key resolver, not controller-owned normalization.
- If controller lookup must stay, Plan 02 needs to add shared helpers that return the final normalized cache inputs, not just `ComputeKey(...)` over caller-supplied strings.
- Remove the nonexistent `ResolveCanonicalTextAsync` reference and replace it with an actual codebase API or a concrete new helper introduced in Plan 02.

**Risk Assessment**  
`HIGH`. As written, Plan 03 will not compile and does not reliably satisfy D-01/D-02 parity.

## `999.3-04-PLAN.md`
**Summary**  
Good closure plan overall. The grep/build gates are solid, and README/STATE/ROADMAP updates follow project rules. The weak point is the manual UAT design: a few checks are too brittle to prove specific behaviors cleanly, especially D-09 upload participation and D-10 precedence preservation.

**Strengths**
- Uses the same MSBuild-summary warning-count extraction consistently across all gates.
- Requires explicit log evidence for hit/miss/write, which is appropriate for this optimization phase.
- Updates README, STATE, and ROADMAP, which matches `CLAUDE.md`.
- Keeps human UAT as the primary gate, consistent with the project’s WSL/VSTest constraints.

**Concerns**
- `MEDIUM` — D-09 verification is weak. “Upload a zip, then download, should hit cache” does not prove `/deck-analysis/upload` was the writer; the cache entry may already exist from preview unless the test isolates state.
- `MEDIUM` — The D-10 precedence UAT is brittle. Asking a human to clear `DeckASource`/`DeckBSource` and manipulate `ComparisonResponseJson` through the UI is cumbersome and may not reflect the actual posted form state reliably.
- `LOW` — STATE counter instructions are safer than line-number edits, but `total_plans` guidance could still miscount if the totals already include planned-but-unfinished 999.3 entries.

**Suggestions**
- Make the upload-write UAT isolated: restart process, upload zip first, then download, then confirm `miss/write/hit` sequence.
- For D-10 precedence, prefer a reproducible POST recipe or saved request payload over manual UI field surgery.
- In STATE updates, prefer “recompute from current roadmap totals” over incremental guidance if the template supports it.

**Risk Assessment**  
`MEDIUM`. The closure mechanics are good; the UAT needs a tighter script to prove the subtle branches.

## Final Assessment
The plan set is close, but not ready as-is. `999.3-01` is solid; `999.3-04` is mostly solid. The blocking issue is the `999.3-02` / `999.3-03` boundary: the plans currently do not provide a real, shared way to derive identical cache keys on both write and read paths for deck-analysis and some meta-gap cases. Until that is fixed, the highest-risk outcome is “cache compiles, logs writes, but preview→download misses most of the time.” Overall risk: `HIGH` until key-resolution ownership is redesigned.

- `H3` `RESOLVED` — Normalization ownership is now correctly moved into per-service async helpers instead of controller-side reconstruction.

- `M4` `PARTIAL` — The cURL-based precedence UAT is better than UI surgery, but the evidence target is wrong: there is no generic “Packet cache lookup” log line in D-13, so the test as written cannot prove the short-circuit bypassed cache logging.

## New Concerns (this pass)
- `HIGH` — `999.3-02`, Task 1, `DeckAnalysisPacketService.TryComputeCacheKeyAsync`: the proposed commander extraction still diverges from the real write path. `BuildAsync` uses `Take(2)` partner inference plus the third-entry alphabetical guard, may call `ValidateCommanderAsync`, and may later oracle-normalize the commander name before return; the planned helper uses `Take(1)` and explicitly skips those later mutations. That can silently skew keys and kill preview→download hits. Fix: extract one private `BuildDeckAnalysisCacheInputs(...)` used by both helper and write site, and choose a single commander stage for the key before any Scryfall-dependent mutations.
- `MEDIUM` — `999.3-03`, Task 2: every download cache miss now pays an extra preflight deck load before `BuildAsync`, so the miss path gets slower than today. Correctness is preserved, but the optimization adds latency on cold/restarted/expired downloads. Fix: either accept and document this explicitly, or redesign around a service method that computes the key and reuses the loaded deck on miss.
- `MEDIUM` — `999.3-04`, Task 2 / Workflow E: “no `Packet cache lookup` line” is not testable because D-13 logs only `hit|miss|write|evicted`. Fix: make the UAT assert no `Packet cache ` lines at all within an isolated log window, or add temporary request-correlated markers if you want stronger proof.
- `LOW` — `999.3-01`, Task 1: hit/evicted logs still use `0` bytes placeholders, which weakens D-13 observability. Fix: store size with the cached value or recompute it on typed hits.
