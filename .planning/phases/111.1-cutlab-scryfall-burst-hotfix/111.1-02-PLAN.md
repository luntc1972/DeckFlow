<objective>
Lock SC-3 at the boundary the user actually sees, and close SC-6.

Plan 01 fixed the two defects at the `CutLabAnalysisContextBuilder` level. That is necessary but not
sufficient evidence for SC-3, which is stated in terms of the rendered banner: *"the banner text
'Scryfall returned HTTP 429. Try again shortly.' is no longer reachable from a pool import whose
cards all exist."* The banner is produced two layers up, at `CutLabPageService.ProcessAsync:231-233`,
by catching `HttpRequestException` and converting it via
`UpstreamErrorMessageBuilder.BuildScryfallMessage` into `CutLabProcessResult.ErrorMessage`. Only a
test at that boundary proves the path is actually severed.

Purpose: the whole reported bug is "user sees a banner." A green unit test one layer down is not
proof the banner is gone. This plan asserts on `CutLabProcessResult.ErrorMessage` directly, and also
proves the inverse — that a real upstream failure still reaches the banner — so the fix cannot be
mistaken for blanket error suppression.

Output: end-to-end regression tests in `CutLabPageServiceTests.cs`, plus `111.1-GATES.md` recording
the phase's runnable verification sequence and its observed results.
</objective>

`CutLabController.Process()` then renders `View("CutLab", ...)` as a normal 200 OK with

`"Scryfall returned HTTP 429. Try again shortly."` for a 429.

`HttpRequestException` and preserves the upstream status code, so a 429 on the batch
`cards/collection` call also arrives at the `ProcessAsync` catch as an `HttpRequestException`.
