<objective>
Extend the existing `ContentSiteIndexStore` (Phase 19, Render-bound slim index) with the curation primitives every other Phase 22 plan depends on: an additive `is_visible` column (default hidden, both SQLite + Postgres), a visibility-preserving upsert for the commit-then-deploy seed path, published-only / all-rows / by-id reads, per-entry and per-source visibility setters, and the `content.kb.enabled` feature-flag seed row (default OFF). Purpose: This is the data-layer foundation. The CLI export (Plan 02), public browse + seed loader (Plan 03), and admin curation grid (Plan 04) all bind to these contracts. Getting the visibility-preserving upsert exactly right is the single highest-risk item in the phase (Pitfall 1: a naive upsert re-hides everything on every deploy). Expanding the interface WITHOUT updating the existing fake is the second-highest risk (it breaks the whole Core.Tests build with CS0535 — review HIGH-7).

Output: Extended store + interface + row record + flag seed + the updated existing fake + a focused Core.Tests fixture proving the migration, the visibility-preserving upsert, the new queries, and the cross-dialect DDL.
</objective>

`content_site_index.artifact_path` is stored as **`content-kb/{source-slug}/{id}.md`** — the `content-kb/` prefix is PART OF the stored value. Do NOT change the writer. Every other plan resolves artifacts as `Path.Combine(contentBase, artifact_path)` where `contentBase` is the directory that CONTAINS `content-kb/` (NOT the `content-kb/` dir itself) — see Plan 02 (delivery) and Plan 03 (runtime resolver) which both bind to this exact convention. This plan does not change `artifact_path`; it only carries it through the new queries unchanged. Recorded here so all four plans agree (review HIGH-3).
