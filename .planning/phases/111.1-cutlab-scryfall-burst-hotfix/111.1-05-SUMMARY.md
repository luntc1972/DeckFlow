# Phase 111.1 Plan 05: SC-7 Implementation + SC-6 Final Gate Summary

**Raised `ScryfallThrottle.MinInterval` from 200ms to 500ms to match Scryfall's documented 2/sec per-endpoint hard limit, corrected both stale "10 req/sec" comments, locked the new floor with a regression test, corrected a related comment defect found by blind verification, and re-ran the phase's full gate sequence against the final branch state with a complete, gap-free criterion map.**

## What Was Built

**Task 1 (RED):** Added `ExecuteAsync_SpacesConsecutiveCallsByAtLeastTheDocumentedPerEndpointLimit`
to `ScryfallThrottleTests.cs` — issues two sequential `ScryfallThrottle.ExecuteAsync<int>` calls and
asserts the elapsed time between them is at least 450ms (a 50ms tolerance below the 500ms target).
Asserts a lower bound only, per the plan's explicit instruction, since `ScryfallThrottle` holds
process-wide static state shared with every other test in the assembly. **Observed RED elapsed time:
200ms** (confirmed by running the test before any production edit — see Test Evidence). All 10
pre-existing `ScryfallThrottleTests` stayed green.

**Task 2 (GREEN):** Edited `ScryfallThrottle.cs`:
- `MinInterval` changed from `TimeSpan.FromMilliseconds(200)` to `TimeSpan.FromMilliseconds(500)`.
- The inline comment above it replaced: states as fact, with a citation
  (`https://scryfall.com/docs/api/rate-limits`), that Scryfall publishes a hard 2/sec (500ms) limit
  for `/cards/collection`, `/cards/search`, `/cards/named`, and `/cards/random`; the previous
  200ms/10-req/sec figure belonged to the doc's "all other methods" row and did not apply. Notes the
  gate is process-wide (global floor, not per-flow) and points at
  `111.1-PACING-MEASUREMENT.md` for the measured latency cost. The now-false "< 3 seconds of pacing
  total" claim was deleted rather than restated with an unverified number.
- The class `<summary>` corrected from "Keeps all Scryfall calls under the 10 req/sec soft cap" to
  reference the 2/sec per-endpoint limit — the same wrong ceiling appeared in two places; both fixed.
- `RetryAfterCap`, `FallbackRetryDelay`, and `MaxRetryAttempts` untouched, as instructed.
- `MinInterval` stayed `private static readonly` — not made public/internal/configurable.

**Comment-only fix (blind verification of wave 1):** In `CutLabAnalysisContextBuilder.cs`'s
batch-resolution catch block, the `// Why (round-1 review W-8)` comment above the `break` claimed
"the upstream is actively rate-limiting" as the universal reason for breaking out. That's true only
when `failOpenOnLookupErrors: false` (only `IsTransientRateLimit` exceptions survive the throw guard
above), but under `failOpenOnLookupErrors: true` — the `BuildAsync` default — ANY swallowed exception
reaches the `break`, including a 503 or a timeout with no rate-limit involved at all. Corrected the
comment to state both paths accurately. `git diff` on this file shows comment lines only; the
`break;` statement and every surrounding line of logic is byte-for-byte unchanged.

**Task 3 (final-state gate re-run):** Re-ran the full command sequence in `111.1-GATES.md` against
HEAD (after plans 03 and 05 both landed) and appended a new "Section 3b" results block — the original
Section 3 (plan 02's baseline, predating plans 03/05) was not overwritten. Updated Section 2's
criterion map: SC-4 and SC-5 flipped to `COVERED` (naming ADR 0004 and the two `ScryfallReferenceResolverTests`
plan 03 added), SC-7 flipped to `COVERED` (naming the new pacing test plus the measurement artifact),
a new row added for the blind-verification break-comment fix, and three new rows added confirming
the H2 lock test and both `submitted_name:` golden tests survive UNMODIFIED against the final state —
these were the three assertions plan 03 most risked, and the phase record now states plainly that
they held.
