# Phase 07.1 Plan 02: SameOriginRequestValidator Honors X-Forwarded-Proto Summary

**Validator-scoped fix (Branch A1): in `UriMatchesRequestOrigin`, promote `requestScheme` to `"https"` when origin is https, request.Scheme is not, AND `X-Forwarded-Proto: https` is asserted by the upstream proxy. Recompute `requestPort` from the promoted scheme so the port-leg comparison stays consistent. Cross-origin attackers cannot forge X-Forwarded-Proto without compromising the network path between client and server, so honoring it does not weaken the CSRF gate. Program.cs middleware ordering not modified (Phase 4/5 invariant preserved). Diagnostic logging from Task 1 fully removed in Task 2 — controller's net diff vs. pre-plan main is zero.**

## Captured Diagnostic (Task 1 Evidence)

Verbatim Render log line from a failing legitimate POST against deckflow.gg at 2026-05-03T18:14:47Z:

```
[18:14:47 WRN] SameOrigin diagnostic:
  path=/api/suggestions/card
  scheme=http
  host=www.deckflow.gg
  origin=https://www.deckflow.gg
  referer=https://www.deckflow.gg/suggest-categories
  xfproto=https
  xfhost=
  xfport=
  xfor=24.10.192.114, 172.71.146.215
```

**Named root cause: SCHEME MISMATCH** (with collateral PORT MISMATCH falling out of it).

Mechanism: Render's reverse proxy correctly sets `X-Forwarded-Proto: https`, but ASP.NET Core's default `ForwardedHeadersOptions` only honors forwarded headers from `KnownNetworks` / `KnownProxies` — by default localhost-range only. Render's proxy IPs are outside that range, so `UseForwardedHeaders` ignores the header, `request.Scheme` stays `http`, and the validator's three-leg comparison fails on both scheme (https vs http) and port (443 vs 80, since the port default derives from the scheme).

## Lesson Captured (per plan output instruction)

Saving project memory entry: **`feedback_csrf_validator_under_proxy.md`** — When a reverse-proxy PaaS (Render here; potentially Fly, Railway, K8s ingress later) terminates TLS in front of an ASP.NET Core app, the default `ForwardedHeadersOptions` only trusts localhost-range proxies. Same-origin/CSRF validators that compare `request.Scheme` against an `Origin` header MUST also honor `X-Forwarded-Proto` — and when promoting the scheme, also recompute the scheme-derived port default. Future PaaS migrations should re-check this code path before merge.

## Deviations from Plan

### Out-of-band emergency fix (no plan-level impact)

**1. [Emergency] Phase 7 circular-DI fix — `dc66a38 fix(harvest): break HarvestRunStore ↔ HarvestStatsAggregator DI cycle`**

- **Found during:** Render redeploy of `f3e2fc7` (Plan 02 Task 1 cherry-pick).
- **Issue:** Render container crashed at startup with `InvalidOperationException: A circular dependency was detected for the service of type 'DeckFlow.Web.Services.Harvest.IHarvestRunStore'`. Phase 7 plan 06 had `HarvestRunStore` take optional `IHarvestStatsAggregator?` and `HarvestStatsAggregator` take `IHarvestRunStore` directly — MS DI traces ctor types regardless of registration order, so the optional-with-default never broke the cycle. Pre-existing Phase 7 bug; previous deploys must have used a cached image, masking it. Surfaced now because Plan 02 Task 1's push forced an actual rebuild.
- **Fix:** Replaced the optional `IHarvestStatsAggregator?` parameter on all three `HarvestRunStore` ctors with optional `IServiceProvider?`. Added a private `InvalidateStats()` helper that resolves `IHarvestStatsAggregator` lazily from `_services` inside a `try { ... } catch { /* swallow */ }` so cache invalidation is best-effort and never fails a write. DI factory updated to pass `sp` itself: `services.AddSingleton<IHarvestRunStore>(sp => new HarvestRunStore(sp.GetRequiredService<IWebHostEnvironment>(), sp))`. `HarvestStatsAggregator` not modified.
- **Functional impact:** None on Plan 02 scope. The fix unblocked the Plan 02 deploy; Render then deployed cleanly. Phase 7's harvest stats invalidation behavior is preserved (still fires after every run-store write, just resolved lazily).
- **Captured for cross-phase tracking:** This is a correction to Phase 7 plan 06 / 07's DI registration. Phase 7 verification (`docs(07): phase 7 verification`) said "all SCs + D-IDs + reqs trace to code"; that pass was based on local build, which apparently doesn't surface the circular-DI startup error the same way Render's container does. Worth a Phase 7 errata note if `gsd-verify-work` style audits are run later.
