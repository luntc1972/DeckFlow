<objective>
Ship SYNC-12: the gated, re-validated destructive apply. Register the `sync.reconcile` web-DB feature
flag (seeded OFF, both dialects), and add `ReconcileCoordinator.ApplyRemovalsAsync` - a two-step,
flag-gated soft-hide that re-runs the seed-drift diff fresh at apply time and hides ONLY the
`seed_managed=true` rows still absent from the current seed (never a prod-owned row, never a stale set).
Add the Apply UI stage to the Reconcile page.

DECISION (per planner confirmation of RESEARCH Open Question 1 / A1): the destructive write lives in
this operator-gated Studio Apply action. Do NOT wire any automatic soft-hide/delete into
`ContentKbSeedLoader.LoadIfPresentAsync` (web boot) - that path only stamps `seed_managed=true`
(shipped in 91-02). An auto-delete at boot would reintroduce the Codex-HIGH "bad seed mass-deletes live
rows" risk the entire D-04/D-08/D-09 design exists to prevent.

SCOPE (Codex-MED fix): only REMOVAL discrepancies (the seed-drift class) are eligible for Apply. The
reviewed set handed to Apply is `reviewedRemovalDiscrepancyIds` (seed-drift IDs only), and the Apply-time
re-validation compares FRESH seed-drift removal IDs against exactly that set. The other three classes
(published-orphan, file-orphan, body-hash-mismatch) are detection-only and MUST NEVER enter the Apply
stale-check - otherwise a dry-run surfacing all four classes would false-reject every Apply as stale.

Purpose: Let a git seed finally REMOVE content from prod - safely, reversibly (soft-hide), gated behind
the marker + flag + re-validation - even when the dry-run also surfaced non-removal discrepancies.
Output: `sync.reconcile` flag + `ApplyRemovalsAsync` (removal-scoped) + Apply UI + tests + README.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator -> destructive Apply | The only destructive write in the phase; must be flag + re-validation + marker gated |
| Studio -> web-DB flag (read) | Cross-store authenticated flag read; indeterminate must fail-safe to refuse |
| Apply -> prod DB (write) | Soft-hide visibility write against prod; must never touch prod-owned rows or timestamps |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-91-19 | Elevation of Privilege | Apply running while the flag is OFF/unset | mitigate | TryReadFlagAsync gate; only confirmed `true` proceeds; false AND null refuse (V4) |
| T-91-20 | Tampering | A bad/regressed seed mass-hiding live prod-owned content | mitigate | seed_managed=true-only filter (SYNC-17 invariant) + fresh re-validation + stale-set rejection (D-08); tests assert prod-owned rows never hidden |
| T-91-21 | Tampering | Indeterminate flag read treated as license to proceed | mitigate | Explicit fail-safe-to-REFUSE for TryReadFlagAsync == null (Anti-Patterns) |
| T-91-22 | Denial of Service / data-loss | Hard-delete or timestamp corruption on the removal write | mitigate | Soft-hide only (is_visible=false), reuse SetVisibilityAsync, touch no timestamp (D-03 / Pitfall 5 / F-51-PG-01) |
| T-91-23 | Information Disclosure | Prod conn-string leak via Apply logging | mitigate | Reuse ProdContentReader/DirectPush conn-string discipline; log natural keys only |
| T-91-24 | Denial of Service (availability) | Non-removal discrepancy classes false-rejecting every Apply as stale | mitigate | Reviewed set + stale-check scoped to seed-drift removals only; mixed-class test asserts Apply still proceeds |
</threat_model>
