### D-16 — a multi-role card contributes to every role's twin group, and the tally consequence is accepted

Research left this open (open question 4): no existing Cut Lab detector groups by role AND type AND
mana value jointly, so there is no precedent. Multi-role membership is explicit and by design —
`CutLabRoleAssigner`'s doc comment says "Multi-role membership is allowed; cutting a card reduces
every role count it currently fills", and `CardsInRole` tests `Roles.Contains(key)` per role
independently, so every existing role-iterating detector already counts a multi-role card once per
matching role.

**Decision:** iterate roles independently. A card that is both `engines` and `wincons` can appear in
an `engines` twin group and a `wincons` twin group, producing **two** `FunctionalTwins` findings that
both name it.

**The consequence, stated rather than hidden:** `BuildFindingTallies` increments a card's tally once
per finding, so such a card gains +2 from twins alone and reaches round 1 on twins alone. That is
accepted, and it is defensible: a card that fills two roles which are *both* over-saturated at its
exact cost and its exact type is genuinely twice as redundant, and rounds 1/2/3 only distinguish
`>= 2` from `== 1` from `== 0`, so the practical effect is "doubly-redundant cards get proposed
first" — the correct call. Plan 04-03 Task 2 pins this with an explicit test rather than letting it
be an accident.

This decision is the one in Phase 4 the developer is most likely to want to override. The alternative
is a single "primary role" per card, which would need a new priority order that does not exist
anywhere in the codebase today. Flagged for review; not treated as settled by fiat.

### D-17 — role and card eligibility, and why the count is distinct cards

Four eligibility rules, each with a reason:

1. **The `lands` role is excluded**, and `IsLand` cards are excluded outright. Thirty-plus lands all
   at mana value 0 with primary type `Land` would form one enormous group that swamps every other
   finding and destroys Success Criterion 5. Land redundancy is the manabase tool's job.
   `ComputeCurveCongestion` already sets the precedent of filtering `!card.IsLand`.
2. **The `other` role is excluded.** `other` is `CutLabRoleAssigner`'s fallback when nothing else
   matched — it means "unclassified", not "functionally equivalent". Three unclassified cards at the
   same cost are not twins; they are three cards the classifier could not read. Note `other` is not
   in `CutLabFloorRules.RoleKeys` at all, so iterating that list excludes it by construction; the
   rule is stated so nobody adds it later.
3. **A blank `TypeLine` makes a card ineligible.** `CardTypeLine.PrimaryType("")` returns `"Other"`,
   so admitting blank type lines would collect every unresolved card into a shared `"Other"` bucket
   and manufacture false twins. Fail closed: no type data means no type claim.
4. **The threshold counts distinct pool entries, not `Sum(Quantity)`.** Three copies of one card
   present no choice to the user; twins is about choosing among *different* cards.
   `ComputeCurveCongestion` uses `Sum(Quantity)` because curve share is about slots — a different
   question. In singleton Commander this distinction only bites for basics, which rule 1 already
   excludes, but the semantically correct rule is cheap to state and prevents a future regression.
