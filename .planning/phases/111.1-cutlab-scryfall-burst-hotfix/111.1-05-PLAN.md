<objective>
Apply the pacing change SC-7 asks for — but only in the form the user authorized at plan 111.1-04's
checkpoint.

`ScryfallThrottle.MinInterval` is 200ms (~5 req/s). Scryfall documents a **hard 2/second (500ms)
limit** for `/cards/collection`, `/cards/search`, `/cards/named`, and `/cards/random` — exactly the
endpoints every flow in this phase touches. DeckFlow has been pacing 2.5x faster than the published
ceiling for those endpoints. The comment at `ScryfallThrottle.cs:13` cites the "all other methods"
10 req/sec figure as though it applied, which is how the mistake survived: the number was real, it
just belonged to a different row of Scryfall's table.

This is the second, independent half of the 429 story. Plan 111.1-01 cut the per-miss call count;
this cuts the rate at which the remaining calls go out. Neither alone is sufficient for a
high-miss-count pool.

Purpose: stop over-driving a documented limit whose stated penalty is "temporary or permanent ban of
your application."

Output: one constant, corrected documentation, one regression test, and a final-state gate run.
</objective>

`DeckFlow.Web/Services/Scryfall/ScryfallThrottle.cs` — the two doc blocks that are wrong, and the
constant, verbatim as they stand today:
```csharp
/// <summary>
/// Process-wide Scryfall pacing and Retry-After retry helper.
/// Keeps all Scryfall calls under the 10 req/sec soft cap and recovers from brief 429s.
/// </summary>
internal static class ScryfallThrottle
{
    // Scryfall asks for 50-100ms between requests. We pace at 200ms (~5 req/sec) to leave
    // plenty of headroom for Cloudflare's burst detection, which is stricter than the published
    // 10 req/sec ceiling. Packet build still completes fast: for a 100-card deck the collection
    // batch + a handful of fallback searches is < 3 seconds of pacing total.
    private static readonly TimeSpan MinInterval = TimeSpan.FromMilliseconds(200);
```
The wrong "10 req/sec" ceiling appears TWICE — in the class summary (line 9) and in the inline
comment (lines 13-16). Both must be corrected; fixing one leaves the next reader misled.

`MinInterval` is `private`, so a test cannot read it. It CAN be observed behaviorally: `Gate` is a
process-wide `SemaphoreSlim(1,1)` (line 35) and `_lastCallUtc` (line 36) spaces consecutive calls, so
two back-to-back `ExecuteAsync` calls in one test are separated by at least `MinInterval`. Assert a
LOWER bound only — never an upper bound, which would be flaky under CI load.

`DeckFlow.Web.Tests/ScryfallThrottleTests.cs` already has the harness needed: it imports
`System.Diagnostics`, defines a `CreateResponse<T>(HttpStatusCode, params (string,string)[])` helper,
and calls `ScryfallThrottle.ExecuteAsync<int>(...)` directly (lines 33-45 are the simplest example).
`ScryfallThrottle` is `internal` and `DeckFlow.Web.Tests` has `InternalsVisibleTo`, so no new seam is
required. Nothing in that file hard-codes 200 as a duration — the only `200` occurrences are in the
test names `ExecuteAsync_Generic_Returns200ResponseAsIs` and `ExecuteAsync_NonGeneric_Returns200ResponseAsIs`,
which are HTTP status codes. So no existing test needs rewriting for the constant change.

Scryfall's documented limits (fetched read-only 2026-07-31, cited in `111.1-RESEARCH.md`):
`/cards/search` 2/second (500ms); `/cards/named` 2/second; `/cards/random` 2/second;
`/cards/collection` 2/second; `/cards/manifest` 10/minute; all other methods 10/second (100ms).
Plus: "Receiving an HTTP 429 response will result in your access being limited for 30 seconds.
Continuing to overload the API after this point may result in a temporary or permanent ban of your
application... It is not acceptable to ignore HTTP 429 responses."
