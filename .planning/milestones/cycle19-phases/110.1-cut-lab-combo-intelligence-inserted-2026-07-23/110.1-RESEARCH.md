# Phase 110.1: Cut Lab Combo Intelligence - Research

**Researched:** 2026-07-24
**Domain:** ASP.NET 10 / C# data-layer feature — Commander Spellbook API parsing, Cut Lab structural-finding
computation, server-authored view/patch DTOs, Razor disclosure rendering.
**Confidence:** HIGH (all code citations read directly; Spellbook API shape confirmed via live requests
against `backend.commanderspellbook.com`, not training-data guesses)

## Summary

Phase 110.1 is a pure data-layer/view-model change on top of a well-established, layered Cut Lab
codebase. Every relevant seam already exists and is exercised by tests: `CommanderSpellbookService`
parses combos into `SpellbookCombo`/`SpellbookAlmostCombo`; `CutLabAnalysisContextBuilder` folds
those into `CutLabClassificationContext`; `CutLabStructuralFindings.Compute` turns classification data
into `CutLabFinding` records; `CutLabFindingPresenter` + `CutLabViewModel` project findings for Razor;
`CutLabUiPatchBuilder` projects the same findings for the JSON live-patch (`CutLabDecideFindingGroupDto`).
The chip lock/unlock wiring in `CutLab.cshtml`/`cut-lab.ts` is attribute-driven
(`data-cut-lab-chip-card` + `aria-pressed`) and is agnostic to what markup lives *inside* the chip
`<button>`, so a badge can be added as nested markup without touching the lock logic.

The single largest gap today is that `CutLabClassificationContext` **only carries card names**
(`ComboNames: IReadOnlySet<string>`) for complete combos — the full `SpellbookCombo` records
(`CardNames`, `Results`, `Instructions`, `Popularity`) are computed in
`CutLabAnalysisContextBuilder.LoadSpellbookFailOpenAsync` and then **thrown away**, keeping only the
extracted names (`CutLabAnalysisContextBuilder.cs:529-535`). This is exactly what LOCKED decision #3
requires fixing: thread the full `IncludedCombos` (and existing `AlmostIncludedCombos`) into a new
card→combo lookup.

The Commander Spellbook `requires` (template slot) and `of`/`includes` (variant grouping) shapes were
**not present in any repo fixture or test** — `CommanderSpellbookServiceTests.cs` only covers
`uses`/`produces`/`description`/`popularity`/`manaValueNeeded`. I fetched the live API directly
(`backend.commanderspellbook.com/variants/`) to record the real JSON shape for the SC-4 research
deliverable — see "Spellbook `requires`/variant shape reference" below. This is HIGH confidence
because it is a live, current API response, not a recollection.

**Primary recommendation:** Extend `CommanderSpellbookService` to keep the already-fetched
`IncludedCombos` reachable from Cut Lab (thread full `SpellbookCombo` objects, not just names, into
`CutLabClassificationContext`), build a new pure card→combo lookup type consumed by
`CutLabStructuralFindings`, add one new `CutLabFindingKind.ComboProtected` value, extend the existing
`CutLabFindingEvidence`/`CutLabFindingView`/`CutLabDecideFindingDto` shapes with a small badge-state
field (not a parallel structure), and reuse the Phase 110 `RenderCardTextDisclosure` partial rather than
building a second disclosure. Add the new finding kind to `CutLabCutRoundEngine`'s
`ExcludedFindingKindsFromTally` set so it does not silently start discriminating cards toward cutting —
this is a one-line addition to an existing exclusion list, not a new engine rule, but the planner must
make this call explicitly (see Pitfall 1).

## 1. Spellbook API shapes (SC-4)

### 1a. What `CommanderSpellbookService` parses today — verified from source

`DeckFlow.Web/Services/CommanderSpellbookService.cs`:

- `SpellbookCombo` record (`:16-21`): `CardNames`, `Results`, `Instructions`, `Popularity?`,
  `ManaValueNeeded?`.
- `SpellbookAlmostCombo` record (`:26-30`): `MissingCard`, `CardsInDeck`, `Results`, `Instructions`.
- `ExtractCardNames` (`:251-265`) reads only `variant.uses[].card.name` — **drops `requires` entirely**.
- `ExtractResults` (`:267-282`) reads `variant.produces[].feature.name`.
- `ExtractInstructions` (`:284-294`) reads `variant.description`, truncated to 300 chars.
- `ParseVariants` (`:182-218`) also reads top-level `popularity` and `manaValueNeeded` scalars via
  `TryGetInt32` guards (not `GetInt32`, deliberately, per the inline `// Why:` comment — malformed
  values degrade to `null` instead of throwing).
- Nothing in the service reads `variant.id`, `variant.of`, `variant.includes`, or `variant.requires`.
  `ParseAlmostVariants` (`:220-249`) only diffs `uses` card names against the deck's card-name set to
  find "exactly one card missing" — it has no concept of variant grouping either.
- `CommanderSpellbookServiceTests.cs` (331 lines, 9 tests) confirms by omission: every test JSON fixture
  omits `requires`, `id`, `of`, and `includes` — there is no existing fixture to crib from for the new
  shape. `[VERIFIED: repo test file]`.

| Field | Shape | Meaning | Confidence |
|-------|-------|---------|------------|
| `requires` | `[{ quantity: int, template: { id, name, scryfallQuery, scryfallApi }, zoneLocations, mustBeCommander, ...cardState fields }]` | Each entry is one **template slot** the variant needs, structurally parallel to a `uses[]` entry but with `template` instead of `card`. `template.name` is the human label shown in the UI screenshot ("Noncreature permanent castable for {0}" style — `{0}` etc. is a mana-value placeholder baked into the template name/scryfallQuery, not a separate field). `template.scryfallApi` is a ready-to-call Scryfall search URL that returns the actual candidate cards (the "View 37 Cards" the user's screenshot showed) — this is the future implementation's enumeration source, no separate "candidate list" field exists on the variant itself. | HIGH — live response |
| `of` | `[{ id: int }]` | The **parent/grouping combo id** this variant belongs to. | `id` (variant id) | string, format `"{cardId1}-{cardId2}[-...]--{templateId}"` (double-dash before any template ids) | Stable per-variant identifier. | `variantCount` | int | Total number of variants under the same `of` parent — this is the number the deferred variant browser would use for "4 variants" type copy. | HIGH — live response |
| `popularity` | int | **This already answers the "EDHREC deck counts" question from the deferred variant-browser scope note** — `[CITED: commanderspellbook.com/syntax-guide "Popularity" section]`: "the number of decks containing the combo, and is updated regularly" (EDHREC-sourced). **No confirmed, documented query-param filter exists (in this session) for "give me all variants sharing
one `of.id`."** I probed `?of=1710` and it silently ignored the filter (returned the default
popularity-sorted list rather than an error or a filtered set) — DRF list endpoints commonly ignore
unrecognized query params rather than erroring, so this is inconclusive, not a negative proof. The
documented, working mechanism (per `[CITED: commanderspellbook.com/syntax-guide]`) is the free-text
`q=` search DSL (e.g. `q=template>0` for "requires at least one template", verified working) —
a future implementation task should budget time to find the correct grouping filter (likely a `q=`
term, not a bare query param) before attempting candidate matching. **This is the one part of the SC-4
research that remains genuinely open — flagged in Open Questions below.**

## 2. Card→combo lookup design

### 2a. Current flow — verified from source

`CutLabAnalysisContextBuilder.LoadSpellbookFailOpenAsync` (`:506-548`):

```csharp
// :528-535 — IncludedCombos is walked ONLY to build a flat name set, then discarded.
if (combos is not null)
{
    almostIncludedCombos = combos.AlmostIncludedCombos;              // full objects kept
    foreach (SpellbookCombo combo in combos.IncludedCombos)          // full objects walked...
    {
        foreach (string cardName in combo.CardNames)
        {
            comboNames.Add(CutLabCardNames.Normalize(cardName));     // ...but only names survive
        }
    }
}
```

`CutLabClassificationContext` (`:78-83`) currently exposes:

```csharp
public sealed record CutLabClassificationContext(
    IReadOnlyList<SpellbookAlmostCombo> AlmostIncludedCombos,   // full objects, unchanged
    bool ComboDataAvailable,
    bool CategoryDataAvailable,
    IReadOnlyDictionary<string, IReadOnlyList<string>> CategoriesByName,
    IReadOnlySet<string> ComboNames);                            // <- name-only HashSet, the target of LOCKED decision #3
```

`ComboNames` is consumed exactly once downstream, in `CutLabAnalysisContextBuilder.BuildAsync` (`:173`)
as a single boolean passed into `CutLabRoleAssigner.AssignRoles(...)` — i.e. today combo membership only
ever answers "is this card in *some* combo, yes/no" for role assignment. It never answers "which combo,
what does it do, who's the missing partner."

Confirmed elsewhere in the codebase: `IncludedCombos` (full `SpellbookCombo` objects with
`Results`/`Instructions`/`Popularity`) is already threaded and used richly by **other** Cut-Lab-adjacent
services — `DeckAnalysisPacketService.cs:1073-1088`, `MetaGapService.cs:737-751`,
`DeckPrimerPacketService.cs:492-538`, `DeckComparisonService.cs:441-512`,
`ManabaseAnalysisService.cs:845` all already consume `combos.IncludedCombos` for their own prompt/analysis
output — so this phase's proposed change (thread the same already-fetched data one layer further into
Cut Lab) has a direct precedent elsewhere in the codebase; it is not a novel pattern.

### 2b. Proposed lookup shape (Claude's Discretion — exact names)

Replace `IReadOnlySet<string> ComboNames` on `CutLabClassificationContext` with a richer lookup, e.g.:

```csharp
/// <summary>Per-card combo membership resolved from Commander Spellbook data.</summary>
/// <param name="CardName">Normalized card name this entry is keyed by (lookup key, not display name).</param>
/// <param name="CompleteCombos">Complete combos this card participates in (badge state: "Combo piece").</param>
/// <param name="NearCombos">Near-combos this card participates in (badge state: "Needs {MissingCard}").</param>
public sealed record CutLabCardComboMembership(
    IReadOnlyList<SpellbookCombo> CompleteCombos,
    IReadOnlyList<SpellbookAlmostCombo> NearCombos);
```

...keyed by normalized card name in a
`IReadOnlyDictionary<string, CutLabCardComboMembership>` (reuse `CutLabCardNames.Comparer`, the existing
`OrdinalIgnoreCase`-family comparer used everywhere else in this file, e.g. `:337`, `:417`, `:440`) on
`CutLabClassificationContext`, replacing `ComboNames`. Build it once in
`LoadSpellbookFailOpenAsync`/a new private helper, from the *same* `combos.IncludedCombos` /
`combos.AlmostIncludedCombos` walk that already runs — no new Spellbook call, no new caching concern
(the existing 30-minute `IMemoryCache` entry in `CommanderSpellbookService` already covers this; the
lookup is a pure re-projection of data already in memory per request).

**Call-site ripple to budget:** `CutLabRoleAssigner.AssignRoles`'s combo-membership boolean parameter
(`CutLabAnalysisContextBuilder.cs:173`) currently reads `classification.ComboNames.Contains(...)`.
Renaming/replacing `ComboNames` means this call site must be updated to
`classification.CardComboMembership.ContainsKey(normalizedEntryName)` (or equivalent) — a mechanical
one-line change, but a required one, and the kind of thing a plan reviewer should specifically check
for since it's easy to leave a dangling reference to the old field name.

## 3. New combo-protected finding kind

### 3a. Existing finding-kind pattern — verified from source

`CutLabStructuralFindings.cs` defines `CutLabFindingKind` as a plain `enum` (`:6-22`) with five members
today (`CurveCongestion`, `StrandedSubtheme`, `RedundantFinishers`, `WeakFloorCase`, `EnablerStarved`).
Each detector is a private static method returning `IEnumerable<CutLabFinding>`, called from the single
public `Compute` entry point (`:127-156`), gated by `comboDataAvailable`/`categoryDataAvailable` flags
where relevant (near-combo detector `ComputeEnablerStarved` is already gated behind
`comboDataAvailable`, `:150-153` — the new detector should follow the identical gate).

`CutLabFinding` (`:34-38`) is a flat record: `Kind`, `Heading` (fixed string per kind), `Lead` (one
generated sentence), `Evidence` (list of `CutLabFindingEvidence { CardName, ManaValue? }`). There is
**no per-evidence "extra badge/state" field today** — `CutLabFindingEvidence` only carries `CardName` and
an optional `ManaValue`. Concretely, LOCKED decision #1 ("Combo piece" vs "Needs {MissingCard}") requires
either:
- (a) extending `CutLabFindingEvidence` with a nullable badge-state field (e.g.
  `ComboBadgeState? BadgeState`, an enum `{ CompletePiece, NeedsPartner }`), consumed by the presenter
  to render the badge text next to the chip, or
- (b) deriving the badge purely at presentation time from the new card→combo lookup (§2b), keeping
  `CutLabFindingEvidence` untouched and doing the badge lookup where chips are rendered
  (`CutLabFindingPresenter`/`CutLab.cshtml`) by re-consulting the lookup per evidence card name.

**(b) is lower-ripple** — it avoids touching the `CutLabFindingEvidence`/`CutLabFindingView`/
`CutLabDecideFindingDto` chain (three parallel record shapes across Razor and JSON paths, see §4) for a
concern (badge state) that is really "what combo(s) is this specific card in," which the lookup already
answers on its own. Recommend (b): keep `CutLabFinding`/`CutLabFindingEvidence` shape stable, and have
the presenter/view resolve badge state per evidence card name against
`CutLabClassificationContext`'s new lookup (threaded onto `CutLabViewModel` similarly to how
`RoleListByCardName`/`CardTextByCardName` are already threaded, `CutLabViewModel.cs:154-163`).

### 3b. `CutLabFindingPresenter` grouping precedent — verified from source

`BuildFindingGroups` (`CutLabFindingPresenter.cs:29-68`) already special-cases one kind
(`WeakFloorCase`) to merge multiple findings of that kind into a single group with one heading and
multiple `Items` — this is the **exact mechanism** LOCKED decision #2 ("new finding kind with its own
heading and grouping") and decision #4 (variant grouping, one finding listing alternatives) should
reuse. Two options, both following this precedent:
- Add a second special-cased merge branch for `ComboProtected` findings (mirrors the `WeakFloorCase`
  branch structurally) if "own heading and grouping" means "one heading, all combo-protected findings
  as `Items` under it" — likely correct reading given decision #2's wording.
- For within-kind **variant grouping** (decision #4 — near-combos differing by one card collapse into
  one finding listing alternatives), that grouping must happen **inside the detector** (in
  `CutLabStructuralFindings.cs`, where the near-combo data first gets shaped into `CutLabFinding`
  objects), not in the presenter's group-merge step — the presenter only groups whole `CutLabFinding`
  objects by kind; it has no visibility into "these two near-combos differ by one card." The detector
  needs to bucket `SpellbookAlmostCombo` entries by their "same cards except one" signature before
  emitting `CutLabFinding`s. `SpellbookAlmostCombo.CardsInDeck` (the shared, in-deck cards) is the
  natural grouping key: two `SpellbookAlmostCombo` records with the same `CardsInDeck` set (order-
  insensitive) but different `MissingCard` are the "differ only by one interchangeable card" case
  decision #4 describes.

### 3c. Advisory copy attachment (decision #5)

`CutLabFinding.Lead` is a plain generated sentence per finding (e.g. `ComputeRedundantFinishers`,
`:231-236`, builds `Lead` via string interpolation). The advisory "cutting this in round 1 is
inadvisable" sentence is naturally a conditional clause appended to (or a second sentence within) the
new `ComboProtected` finding's `Lead`, generated in the same detector method — no new field needed,
consistent with how every other finding's copy is just string-built inline. This satisfies "presenter-
level" attachment loosely (the string is fully formed before it reaches the presenter either way; the
presenter never re-derives finding text) while staying inside the established one-`Lead`-string pattern.

`CutLabFindingPresenter.BuildFindings`/`BuildFindingGroups` (`CutLabFindingPresenter.cs:9-68`) is the
**single shared** projection from domain → the `*View` shape, and `CutLabUiPatchBuilder.BuildStructuralFindings`
(`CutLabUiPatchBuilder.cs:265-281`) calls the **same two presenter methods** and re-maps `*View` →
`*Dto` field-for-field. This means: as long as the badge/combo-context data is resolved from the
card→combo lookup **at render/patch-build time** (option 3a-b, not baked into `CutLabFinding` itself),
both the Razor path and the JSON patch path automatically stay in sync **for free**, because they both
call through `CutLabFindingPresenter` and both have access to (or can be given) the same
`CutLabAnalysisContext`/`CutLabClassificationContext` that produced the findings.

**Where this could still drift, and what to check:** `CutLabUiPatchBuilder.BuildAsync` (`:63-126`)
builds a **fresh** `CutLabAnalysisContext` (`:81-87`, calling `_analysisContextBuilder.BuildAsync`)
independently of the Razor page's own `CutLabAnalysisContext` — they are two separate calls in two
separate request paths (no shared analysis-context instance), but they run the **same builder** against
the **same working list** for the same session, so they will independently compute the **same**
card→combo lookup content (same Spellbook cache key, `CommanderSpellbookService.cs:109`, means both
calls likely hit the 30-minute in-memory cache and get byte-identical data back). This is the existing
pattern for every other piece of state in this DTO (findings, role labels, etc.) — not a new risk
introduced by this phase, but worth calling out because it's the literal "ripple" LOCKED decision #3's
canonical-refs section warns about (`110.1-CONTEXT.md:121-124`).

**`CutLabUiPatchBuilder.BuildAdjustPatch`** (`:132-164`) is the **light** patch path used for quantity
nudges — it explicitly sets `StructuralFindings = []`, `ComboDataAvailable = false` (`:156-157`) and
never calls the analysis-context builder at all. **This means the light-adjust patch path never
computes findings, and therefore never resolves combo badges either** — badges shown after a quantity
nudge round-trip will not update via this path (they'll be stale until the next full patch). Confirm
with the planner whether this is acceptable (it matches today's behavior for the *existing* finding
kinds too — `EnablerStarved` findings also go empty on an adjust-only patch) or whether it's a gap CLUP-18's
"preserve lock/unlock behavior for matched evidence chips" implicitly also expects fixed. Recommend
treating it as **out of scope** (pre-existing behavior, not a regression introduced by this phase) unless
the plan reviewer disagrees.

## 5. Chip lock/unlock invariant

### 5a. Confirmed markup and JS wiring — verified from source

`CutLab.cshtml:608-616` (inside the Structural findings loop):

```cshtml
var chipClasses = $"kb-chip cutlab-role-chip{(evidenceCard.IsLocked ? " cutlab-role-chip--locked" : string.Empty)}";
<button type="button"
        class="@chipClasses"
```

`cut-lab.ts` lock wiring, both confirmed by read:
- Delegated click handler (`:3196-3207`): `target.closest<HTMLButtonElement>('button[data-cut-lab-chip-card]')`
  — resolves to the nearest **ancestor** `<button>` with the attribute, so a click on any nested child
  element (e.g. a `<span class="cutlab-combo-badge">` placed *inside* the button) still bubbles and
  resolves to the same button and toggles the lock exactly as today. This is standard DOM event bubbling
  and requires no new code.
- `syncRoleGroupLockState` (`:1015-1029`): re-queries `getRoleGroupChips(cardName)` (which is
  `document.querySelectorAll('[data-cut-lab-chip-card="${cardName}"]')`, confirmed at `:733`) and only
  ever mutates `classList`/`aria-pressed` on the **matched element itself** (the button) — it never
  touches `innerHTML` or child nodes, so adding a badge `<span>` inside the button is invisible to this
  sync function; it will not be stripped or duplicated on re-sync.

**What must NOT change:** the `data-cut-lab-chip-card` attribute must stay on the outermost interactive
`<button>` element (not move to a wrapping `<div>` or the inner badge `<span>`), and `aria-pressed` must
stay on that same `<button>`. As long as the badge is rendered as a child node inside the existing
`<button>@evidence</button>` (or immediately adjacent within the same clickable region, if the UI-SPEC
wants the badge outside the button — but Phase 110's spec is reused, not redesigned, so default to
"inside"), both invariants hold with zero JS changes. This confirms LOCKED decision #1/#2's implicit
assumption and CLUP-18's explicit "preserve lock/unlock behavior" requirement are compatible with
badge-in-chip markup.

`RenderCardTextDisclosure(evidenceCard.Name)` (`CutLab.cshtml:100-153`) is called immediately after the
chip, once per evidence card, and already reads from `Model.CardTextByCardName` (a

## Common Pitfalls

### Pitfall 1: Adding the new finding kind silently changes cut-round proposal behavior

**What goes wrong:** `CutLabCutRoundEngine.BuildFindingTallies` (`CutLabCutRoundEngine.cs:308-320+`)
folds **every** `CutLabFinding` into per-card "discriminating finding" tallies **except** kinds listed in
`ExcludedFindingKindsFromTally` (currently `{ WeakFloorCase, RedundantFinishers }`,
`CutLabCutRoundEngine.cs:93-97`). If the new `ComboProtected` kind is added without also adding it to
this exclusion set, cards flagged "Combo piece" will start counting as a "discriminating finding" that
nudges the round engine to *propose cutting* them sooner — the exact opposite of "don't cut a complete
combo in round 1."

**Why it happens:** the exclusion set is opt-out, not opt-in — any new `CutLabFindingKind` participates
in tallying by default unless someone remembers to add it here.

**How to avoid:** the plan must explicitly decide whether `ComboProtected` goes into
`ExcludedFindingKindsFromTally`. Recommend yes — this is consistent with LOCKED decision #5's spirit
("no round-1 recommendation to cut a complete combo") without writing a *new rule*; it is one line added
to an *existing* exclusion mechanism the engine already has for exactly this purpose ("findings that
shouldn't discriminate cards toward cutting"). Flag this decision explicitly to the LOCKED-decision
reviewer/Codex reviewer since the CONTEXT text says "do NOT add any rule to `CutLabCutRoundEngine`" and
a one-line set addition could be read either way — safest to call it out rather than silently include or
silently omit it.

**Warning signs:** if a plan task touches `CutLabCutRoundEngine.cs` at all beyond this one-line set
addition (e.g. adds a new `if` branch, a new sort key, a new proposal-ordering rule), that is the
LOCKED-decision violation the CONTEXT explicitly warns against.

### Pitfall 2: Weak-floor + combo-protected overlap needs an explicit precedence decision

**What goes wrong:** `ComputeWeakFloorCases` (`CutLabStructuralFindings.cs:238-261`) and the new
combo-protected detector can both fire for the same card (CLUP-17 explicitly calls out this overlap:
"weak-floor cases where combo context explains why cards are protected"). Today `WeakFloorCase` findings
are merged into one group by the presenter (`CutLabFindingPresenter.cs:37-46`); the new detector must not
accidentally duplicate the same card's evidence into two separate, uncoordinated findings without any
cross-reference, which would read as contradictory/confusing rather than explanatory.

**Why it happens:** the two detectors are independent methods with no shared context about each other's
output today (`Compute`, `:140-153`, calls them in sequence with no shared accumulator).

**How to avoid:** the plan should decide (and the researcher's Claude's-Discretion leaves this open)
whether the weak-floor lead sentence gets a combo cross-reference appended when the card is also a combo
piece, or whether the two findings simply coexist as separate evidence with the reader expected to
connect them via the shared card name in both chip rows. Either is defensible; the plan must pick one and
say so, since it directly affects whether `ComputeWeakFloorCases` needs the new card→combo lookup passed
in as a parameter (a signature change) or stays untouched.

### Pitfall 3: `CutLabClassificationContext.ComboNames` rename is a breaking change to one call site, not zero

**What goes wrong:** it is tempting to think replacing a field with a similarly-shaped richer type is
additive. It is not — `CutLabAnalysisContextBuilder.cs:173` reads `classification.ComboNames.Contains(...)`
directly, and this is the **only** other read site in the whole repo (confirmed via `grep -rn "ComboNames"`
during this research — appears only in `CutLabAnalysisContextBuilder.cs` and its own test file's fake).
Small blast radius, but a real compile break if missed.

**How to avoid:** grep for `ComboNames` (case-sensitive) as a final check before considering this task
done; it should return zero hits outside the new lookup's own definition/tests once complete, or the
rename was skipped somewhere.
